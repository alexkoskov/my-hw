# Task 11: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Финальная QA-стадия фичи `publish-idempotency-fix`: проверка на живом проде после того, как Task 10 выкатил `news_bot.py` + `pending_articles_repo.py` на `news_bot.service` и оператор применил одноразовую SQL-очистку `failed_articles`. Это **операторская** проверка — Claude готовит playbook и сверяет вывод, оператор выполняет SSH/SQL-команды и визуально просматривает канал. Никаких MCP-инструментов и кодовых правок: только `bash`, `ssh`, `sqlite3`, `journalctl` плюс глаза подписчика на `@myhwchannel123`.

Цель — закрыть петлю обратной связи по инциденту 2026-05-07 (два одинаковых поста про Hot Wheels Team Transport «K» CASE REPORT в 10:00 и 11:30 МСК) и подтвердить, что:
1. На проде после деплоя нет крашей `UNIQUE constraint failed` / `IntegrityError` (то есть либо guard сработал штатно, либо зомби-строк просто нет).
2. Одноразовый SQL-cleanup `failed_articles` от Task 10 действительно применился (user-spec «Как проверить» шаг 6).
3. Ближайший 10:00 МСК cron-tick прошёл без `UNIQUE`-ошибок; если в логах видны `[idempotency-guard]`-строки, они кросс-проверяются с визуальной проверкой канала и подтверждают штатное поведение guard'а (срабатывает → пишет marker → не публикует дубль).
4. Подписчики на `@myhwchannel123` не видят дублей Telegraph-URL за 1–2 ближайших дня (subscriber-visible баг ловится только глазами — это последняя инстанция per user-spec).

Если в течение наблюдения приходит admin-ping `Skipped re-publish of <link>` — фича продолжает работать корректно (guard защищает подписчиков), но это сигнал, что корневая причина появления зомби-строк не закрыта; оператор открывает отдельный диагностический task на `crontab` / `backup_db.sh` / `journalctl`.

## What to do

Подготовить и провести четырёхшаговую проверку прода. По каждому шагу: зафиксировать момент времени деплоя (нужен для `--since`), выполнить команду, сравнить вывод с ожиданием, отметить acceptance criterion. Шаги 1, 2 — сразу после Task 10. Шаг 3 — на следующий день после первого 10:00 МСК cron-tick. Шаг 4 — визуальный просмотр канала растягивается на 1–2 дня.

1. **Step 1 — UNIQUE/IntegrityError absence check.** Получить от оператора timestamp окончания Task 10 (момент рестарта `news_bot.service` после деплоя prod). Запросить у оператора запуск:
   ```
   ssh hwbot@148.135.207.54 "journalctl -u news_bot.service --since '<deploy timestamp>' --no-pager | grep -E 'UNIQUE constraint failed|IntegrityError'"
   ```
   Ожидаемый вывод: пусто (нет строк). Любой match — провал шага → собрать полный контекст (journalctl без grep вокруг этого момента) и эскалировать как регрессию фикса.

2. **Step 2 — failed_articles cleanup verification.** Запросить у оператора:
   ```
   ssh hwbot@148.135.207.54 "sqlite3 /home/hwbot/bot/news.db \"SELECT COUNT(*) FROM failed_articles WHERE link LIKE '%team-transport-k%';\""
   ```
   Ожидаемый вывод: `0`. Это закрывает шаг 6 «Агент проверяет» из user-spec и подтверждает, что Decision 6 (одноразовый SQL вместо миграции) выполнен оператором в Task 10. Если `>0` — оператор пропустил cleanup; вернуться к Task 10 и применить SQL.

3. **Step 3 — next 10:00 МСК cron-tick observation.** Дождаться следующего утра (пока на VPS пройдёт 10:00 МСК `daily_morning_post` slot). Запросить у оператора:
   ```
   ssh hwbot@148.135.207.54 "journalctl -u news_bot.service --since today --no-pager | grep -E 'idempotency-guard|UNIQUE'"
   ```
   Ожидание:
   - `UNIQUE constraint failed` — **никаких** match'ей.
   - `[idempotency-guard]` — допустимо несколько строк, если на проде остались зомби-строки. Каждый match означает: guard сработал штатно → подписчики дубль не увидели. Каждую такую строку кросс-чекнуть Step 4 (визуальный канал), что соответствующий Telegraph-URL не запостился повторно.
   - Если есть `[idempotency-guard]` строки — собрать список ссылок и зафиксировать в `decisions.md` как сигнал, что Risk 2 (рекуррентный stale row, см. user-spec) активен → оператор открывает отдельный диагностический task.

4. **Step 4 — visual channel scan.** Оператор открывает `@myhwchannel123` и в течение 1–2 дней после деплоя визуально просматривает все новые посты. Цель: убедиться, что нет двух подряд (или с разницей в 1–2 cron-тика) постов с одинаковым Telegraph-URL. Это subscriber-visible проверка — ловится только глазами; никакой автоматики у проекта нет (нет E2E-инструментов кроме pytest, MCP не используется per tech-spec). Если оператор замечает дубль — это регрессия фикса, эскалировать с конкретным URL и timestamp.

5. **Финал.** Свести результаты Steps 1–4 в краткий отчёт в `decisions.md` (Summary 1–3 предложения, ссылки на journalctl-выдержки, факт прохождения каждого AC). Если все 4 шага зелёные — фича закрыта; если приходил admin-ping `Skipped re-publish` или Step 3 показал `[idempotency-guard]` строки — отметить, что фикс работает, но корневая причина не закрыта, и предложить оператору открыть отдельный task.

- `ssh hwbot@148.135.207.54 "journalctl -u news_bot.service --since '<deploy timestamp>' --no-pager | grep -E 'UNIQUE constraint failed|IntegrityError'"` → пустой вывод.

### User

- Оператор сообщает, приходил ли admin-ping `Skipped re-publish of <link>`. Если приходил — открывается отдельный task на корневую причину (вне scope этой фичи; user-spec Risk 2 / Risk 5).

## Details

**Files:** код не трогаем. Все артефакты — это:
- `decisions.md` (фичи) — куда оператор/Claude пишет финальный отчёт по результатам 4 шагов.
- `news.db` на VPS (`/home/hwbot/bot/news.db`) — только READ через `sqlite3` для Step 2.
- `journalctl -u news_bot.service` на VPS — только READ для Steps 1, 3.

**Dependencies:**
- Task 10 (Deploy) должен быть **успешно завершён** до старта Task 11. Нужен timestamp деплоя для `--since` в Step 1.
- Доступ оператора по SSH к `hwbot@148.135.207.54`.
- Между Step 2 и Step 3 нужно **дождаться следующего 10:00 МСК cron-tick** — это естественная задержка от нескольких часов до суток. Step 4 (визуальный канал) растягивается на 1–2 дня. Это не блокирует Steps 1, 2 от выполнения сразу после деплоя.

**Edge cases:**
- Деплой произошёл уже после 10:00 МСК → ближайший cron-tick для Step 3 будет завтра. Это норма; Step 1 + 2 закрываются сразу, Step 3 + 4 — отложенно.
- В период наблюдения приходит admin-ping `Skipped re-publish` → фикс работает корректно (subscribers не видят дубля), но это сигнал Risk 2 (зомби-строки появляются повторно). Не считается провалом Task 11, но требует открытия отдельного task на корневую причину (см. AC последний пункт).
- Step 1 показал match на `UNIQUE constraint failed` → регрессия фикса; собрать полный journalctl-контекст вокруг match и эскалировать. Возможные причины: guard не задеплоился (откатить + перезапустить Task 10), `move_to_published` `INSERT OR IGNORE` не применился (проверить deployed `pending_articles_repo.py`).
- Step 2 вернул `>0` для team-transport-k link → оператор пропустил одноразовый SQL в Task 10; вернуться к Task 10 и применить.
- Step 4 показал визуальный дубль в канале → критическая регрессия; эскалировать немедленно, собрать оба URL + timestamp + journalctl за этот промежуток.
- VPS недоступен по SSH → дождаться восстановления; альтернативного пути нет — на VPS живёт production runtime, без него верификация невозможна.

**Implementation hints:**
- Все команды выполняет оператор; Claude не пытается ходить по SSH сам (см. memory: «Operator handles production ops»).
- Перед запросом команд оператору сформулировать deploy timestamp как ISO-строку, которую `journalctl --since` понимает (например, `'2026-05-07 14:32:00'`).
- При выводе из `journalctl` не светить токены/ключи в отчётах — копируем только `[idempotency-guard]` маркеры и общий счётчик match'ей `UNIQUE`.
- В отчёт в `decisions.md` включить: конкретный deploy timestamp, дата next-day cron-тика для Step 3, дата окончания визуального наблюдения для Step 4, факт получения/неполучения admin-ping'ов.
- Никаких новых тестов и кода — это pure operational verification stage.
