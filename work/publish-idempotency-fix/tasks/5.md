# Task 5: Add 1 integration test for slot-loop with mixed zombie + fresh rows

## Description

Добавить ОДИН интеграционный тест T7 (`test_slot_loop_does_not_repost_already_published`) в `tests/test_distributed_schedule_integration.py` — расширить существующий класс `TestDistributedSchedule` (строка 128 файла; **не** `_BaseDistributedScheduleCase` — такого класса нет).

Тест проверяет primary guard из Task 1 + `INSERT OR IGNORE` из Task 2 в реальном слот-лупе `news_bot.job()` end-to-end (с замоканными внешними сервисами Telegram / Anthropic / Telegraph). Сценарий — основной production-кейс бага: в БД одновременно лежат
1. строка zombie в `pending_articles` для уже опубликованной ссылки (carry-over tier — `fetched_at` 2 дня назад, есть кешированный `telegraph_url`),
2. соответствующая строка в `published_articles` для той же ссылки (доказательство что публикация уже была),
3. свежая строка в `pending_articles` для новой ссылки (fresh tier — `fetched_at` сегодня).

Цель — литмус-тест AC6: zombie-строка имеет `attempt_count=2`. Без guard'а текущий `job()` упал бы в UNIQUE-конфликт на `INSERT INTO published_articles` → strike #3 → `move_to_failed` → `failed_articles` получит запись. С guard'ом из Task 1 zombie-строка перехватывается ДО любого side-effect, чистится через `skip_pending`, попадает в `processed_news`, а строка из `published_articles` остаётся нетронутой. Свежая строка публикуется ровно один раз. Пустой `failed_articles` после прогона — формальное доказательство того, что guard сработал ДО strike-машинерии (ровно AC6 user-spec).

Этот тест — единственная end-to-end интеграционная проверка фичи; T1–T6 (unit / repository) проверяют куски, T7 проверяет, что куски складываются в работающий слот-луп.

**Edge cases (явно обработать в тесте или зафиксировать формулировкой):**
- **`fetched_at` carry-over**: SQLite `datetime('now', '-2 days')` в raw `UPDATE` — простейший способ. Альтернатива — `dt.datetime.utcnow() - dt.timedelta(days=2)` через параметризованный execute. Оба варианта работают; выбрать один и придерживаться.
- **`attempt_count=2` обязателен**: если тест выставит `attempt_count=0` или `1`, литмус AC6 деградирует до невнятного — без guard'а тест ВСЁ РАВНО прошёл бы (просто потому что после strike #1 / strike #2 строка ещё не уезжает в `failed_articles`). Только `attempt_count=2` гарантирует, что отсутствие guard'а ⇒ `failed_articles` стал бы непуст. Не сокращать.
- **Кешированный `telegraph_url` в zombie-pending**: должен присутствовать (имитирует реальный production scenario, где телеграф был создан в предыдущем слот-цикле). Это также проверяет, что guard срабатывает ДО reuse-ветки телеграфа.
- **`via_review=0`** для published-row pre-stage: подтверждает что зомби-сценарий — это автобот (не оператор через `hw_review`); guard срабатывает на cron-пути (Decision 1 tech-spec).
- **Empty RSS / SOURCES**: настроить так, чтобы `news_bot.job()` НЕ нашёл новых RSS entries во время прогона — иначе `insert_pending` добавит лишние строки и слот-луп пойдёт по 3+ строкам вместо 2. Используй `self._set_rss_entries([])` (helper из строки 252).
- **Содержимое admin-ping**: assert на substring (`link_zombie` И литерал маркера, например `Skipped re-publish` — но точная формулировка определяется реализацией Task 1; согласовать с тем, что делает guard в `news_bot._fallback_publish` после Task 1). Не assert'ить на полный текст ping'а (хрупко при будущей переформулировке).
- **`call_args` API**: `send_telegraph_teaser(telegraph_url, source_url)` (news_bot.py:793) вызывается positional из `_fallback_publish` (news_bot.py:1237: `send_telegraph_teaser(telegraph_url, link)`). Поэтому assert: `self.mock_teaser.call_args.args[1] == link_fresh`. `.kwargs` — пустой dict (positional call), `.kwargs.get('link')` вернёт `None`.

**Implementation hints (без псевдокода):**
- Шаблон для нового теста — `test_full_happy_path_three_articles_three_slots_three_publishes` (строка 282 файла). Скопировать структуру: `_set_rss_entries(...)` → pre-stage → `with freeze_time(...): with patch('news_bot.transcreate_via_claude') as mock_claude: ...` → `news_bot.job()` → asserts.
- Для raw INSERT в `published_articles` — взять template из `code-research.md §H.7.1` (там верифицированный SQL с правильным набором колонок).
- Для `_pending_links()`, `_published_links()`, `_admin_messages()` — использовать готовые helpers из родительского класса (строки 258, 270, 274). Они уже работают корректно с tempfile DB.
- Для litmus-комментария — оформить как docstring теста (multi-line) или как `# AC6 litmus:` блок прямо перед asserts о `failed_articles=0`. Это часть деливерабла теста (читатель должен понять, ПОЧЕМУ пустой `failed_articles` доказывает работу guard'а).
