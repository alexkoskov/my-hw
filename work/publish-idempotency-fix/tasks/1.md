# Task 1: Add idempotency guard to `_fallback_publish`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Бот публикует одну и ту же новость в Telegram-канал дважды, когда в `pending_articles` остаётся «зомби-строка» по ссылке, для которой уже есть запись в `published_articles`. Каждый слот daily-cron-а пробегает по этой зомби-строке, делает Telegraph + Telegram side-effects, упирается в `IntegrityError` на `move_to_published`, и следующий слот повторяет всё заново — пока строка не упадёт в `failed_articles` после 3 страйков. Фикс: вставить идемпотентный guard в самой верхней точке `_fallback_publish` (сразу после `link = row['link']` на строке 984), которая доминирует все 4 пути входа в публикацию (Claude success at 1056, per-article fallback at 1065, ClaudeOutageError at 1079, `is_fallback_active()` shortcut at 1045). **Важно про импорт:** `news_bot.py` импортирует репозиторий как `import pending_articles_repo as pending_repo` (строка 48); в guard-коде используем алиас `pending_repo.get_published(...)` / `pending_repo.skip_pending(...)`, а НЕ полное имя модуля. Тесты Task 3 будут патчить через `news_bot.pending_repo.<func>`. Guard проверяет `pending_repo.get_published(link)`; на не-`None` логирует INFO с маркером `[idempotency-guard]`, шлёт admin-ping (best-effort, по return value), чистит pending через `skip_pending` (try/except: на ошибке — ERROR + второй admin-ping + всё равно `return True`), возвращает `True`. На miss — поток без изменений идёт дальше.

Эта задача — Wave 1 фичи `publish-idempotency-fix`. Реализует Decisions 1, 2, 3, 4, 8 техспека (полные обоснования см. в [tech-spec.md](../tech-spec.md)). Тесты на guard пишутся в Wave 2 (Task 3) — до тех пор verify-smoke ограничен компиляцией модуля.

## Details

**Files:**
- `news_bot.py` — целевой файл. Текущее состояние: `_fallback_publish(row, via_review=False)` определена на строке 960; docstring заканчивается на строке 983; `link = row['link']` на строке 984; пустая строка на 985; `# Step 1: EN → RU` на 986. После правки: между строками 984 и 985 (включительно ПОСЛЕ `link = row['link']` и ДО существующей пустой 985) появляется guard-блок ~20 строк. Существующая пустая строка 985 остаётся как разделитель после guard-а. Импорт `pending_articles_repo` уже есть в файле (используется в `job()` и других местах) — никакого нового импорта добавлять не надо. Логгер `logger` уже есть. Функция `send_admin_notification` определена в том же файле на строке 357 — вызывать без квалификатора модуля.

**Dependencies:**
- Никакие новые пакеты не нужны.
- Используется существующий API через alias: `pending_repo.get_published(link)`, `pending_repo.skip_pending(link)` (alias `pending_repo` объявлен в строке 48 `news_bot.py`), локальная `send_admin_notification(message)`.
- Эта задача не зависит от других задач (`depends_on: []`). Параллельно с ней в Wave 1 идёт Task 2 (правка `move_to_published` в другом файле).

**Edge cases:**
- `get_published(link)` возвращает `None` на miss → guard ничего не делает, функция продолжается (никакого `return`, никаких side-effects).
- `send_admin_notification` возвращает `False`: credentials missing OR `TelegramError` пойман внутри (см. code-research §H.5). Не блокирует cleanup. Логируем WARNING и идём дальше к `skip_pending`.
- `send_admin_notification` НЕ raise-ит — подтверждено в code-research §H.5. НЕ оборачиваем в try/except — это была бы dead defensive code (Decision 4).
- `skip_pending(link)` на missing pending row делает silent early return (см. code-research §H.6) — безопасно даже если конкурентный слот / оператор уже почистил строку.
- `skip_pending(link)` raise-ит на DB-уровне ошибке (`sqlite3.OperationalError` etc.) — Decision 8: ловим, логируем ERROR с маркером `[idempotency-guard]`, шлём ВТОРОЙ admin-ping про cleanup-failure, ВСЁ РАВНО `return True`. Subscriber-visible duplicate prevention важнее, чем strike-count для slot loop.
- На outage-пути (`is_fallback_active() == True`, строка 1046) guard всё равно срабатывает первым, потому что стоит на 985 — ДО shortcut-а на 1046.
- Расположение guard-а строго между 984 и 985: ПЕРЕД любыми чтениями `row.get('title')`/etc. Это даёт «zero-side-effect entry point» — единственная точка, откуда можно безопасно short-circuit'нуть всю функцию.

**Implementation hints:**
- Маркер `[idempotency-guard]` должен быть в обоих лог-сообщениях (INFO на hit + ERROR на cleanup-failure), чтобы оператор мог `journalctl | grep idempotency-guard`. WARNING на admin-ping-failure — по существующему паттерну в `news_bot.py` маркер не строго обязателен, но желательно для консистентности.
- Логи писать через существующий `logger` (он уже есть в модуле); НЕ через `logging.info` напрямую.
- F-строки/.format() — по существующему стилю в `_fallback_publish` (см. строку 1047 `f"[fallback] is_fallback_active=True — routing {link} via Google"` как ориентир формата).
- Текст admin-ping должен начинаться буквально с `⚠️ Skipped re-publish of ` и содержать `link` — это assertable из тестов T4. Для cleanup-failure ping — отдельный текст про cleanup-failure (формат свободный, главное — содержит `link` и упоминание cleanup/idempotency).
- НЕ менять никаких существующих строк ниже 984. Всё, что вставляем, — это новый блок на ~20 строк, после которого идёт текущая пустая 985 + текущий комментарий 986.
