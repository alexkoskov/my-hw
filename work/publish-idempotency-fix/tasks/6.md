# Task 6: Code Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-reviewing` — [skills/code-reviewing/SKILL.md](~/.claude/skills/code-reviewing/SKILL.md)

## Description

Holistic code-quality audit фичи `publish-idempotency-fix` после завершения Wave 1 (правки кода) и Wave 2 (тесты). Аудит — read-only ревью двух точечных правок (idempotency guard в `news_bot._fallback_publish` и `INSERT OR IGNORE` в `pending_articles_repo.move_to_published`) на соответствие техспеку (Decisions 1–4, 8) и проектным паттернам.

Это не пер-задачное ревью отдельных Wave-1 коммитов — те уже проходят через `code-reviewer` внутри своих task'ов. Это **финальный сквозной аудит** всей фичи целиком: проверка, что guard и `INSERT OR IGNORE` хорошо стыкуются друг с другом, что лог-формат и admin-ping консистентны с проектными паттернами (`logger.info`/`logger.warning`/`logger.error` уровни, секрет-редакция в admin-ping payload, отсутствие дублей логики между двумя файлами), что нет shared-resource багов или незакрытых хвостов между двумя правками.

Аудитор сам по себе — review (поэтому `reviewers: []`). Выход: отчёт `logs/working/wave-3-code-audit.md`. Замечания (если есть) формулируются как пост-фактум findings для `decisions.md`; критичные блокеры могут запросить fix-циклы у Wave-1 task'ов до Pre-deploy QA (Task 9).

## What to do

1. Прочитать guard-блок в `news_bot.py` (после Task 1 — ~lines 985–1003) и `INSERT OR IGNORE`-правку в `pending_articles_repo.py` (после Task 2 — line 582).
2. Свериться с tech-spec разделом «Decisions» — проверить каждое из Decisions 1, 2, 3, 4, 8 пункт за пунктом против фактического кода.
3. Свериться с проектными паттернами (`patterns.md`): уровни логирования, формат admin-ping сообщений, использование `_redact_text`, отсутствие дублей логики, отсутствие shared-resource (concurrent access, mutable globals) issues.
4. Кросс-проверить взаимодействие двух правок: что `INSERT OR IGNORE` в `move_to_published` действительно покрывает второй callsite (`hw_review.cmd_publish`) и что guard в `_fallback_publish` не дублирует ту же проверку без необходимости.
5. Записать отчёт в `logs/working/wave-3-code-audit.md` со структурой:
   - **Summary** (1–3 предложения: общий вердикт OK / OK with findings / blockers).
   - **Decision-by-decision check** (Decisions 1, 2, 3, 4, 8 — для каждого: цитата из tech-spec, цитата из кода, вердикт PASS/FAIL).
   - **Project-patterns check** (логи, admin-ping, redaction, дубли, shared resources — по пункту).
   - **Findings** (если есть — список с severity: critical/major/minor + fix suggestion; если нет — явная фраза «No findings»).
   - **Verdict** (Ready for security/test audit / Needs Wave-1 fix-cycle).

- [ ] `INSERT OR IGNORE` правка проверена в `pending_articles_repo.py` line ~582: только keyword изменён (`INSERT INTO` → `INSERT OR IGNORE INTO`); шаги `INSERT OR IGNORE INTO processed_news` (line 593) и `DELETE FROM pending_articles` остались нетронутыми; транзакция в одном `with` блоке.
- [ ] Отсутствие дубликатов логики между guard и `move_to_published`: guard проверяет `get_published()` ДО side-effect'ов, `INSERT OR IGNORE` — defense-in-depth для второго callsite (`hw_review.cmd_publish`); это не дубль, это два слоя.
- [ ] Отсутствие shared-resource issues: guard-блок не использует module-level mutable state, не вводит новые синглтоны (ср. tech-spec «Shared resources: None»).
- [ ] В отчёте явно указан вердикт: либо «PASS — ready for Pre-deploy QA», либо «FAIL — fix-cycle requested for Task N» с конкретными findings.

Что проверить: единственное изменение `INSERT INTO published_articles` → `INSERT OR IGNORE INTO published_articles`; line 593 (`INSERT OR IGNORE INTO processed_news`) не тронута; `DELETE FROM pending_articles` не тронут; транзакция целостная.
- `news_bot.py` `send_admin_notification` lines 357–392 — подтверждение для Decision 4: внутренний try/except ловит `TelegramError`, функция возвращает True/False, никогда не raise'ит.
- `pending_articles_repo.py` `skip_pending` на ~line 656 — подтверждение Decision 2: внутри одной транзакции `INSERT OR IGNORE INTO processed_news` + `DELETE FROM pending_articles`.

**Output file:** `logs/working/wave-3-code-audit.md` (относительно feature-папки `work/publish-idempotency-fix/`). Создать директорию если не существует.

**Dependencies:** Tasks 3, 4, 5 (нужно дождаться Wave 2 — фича целиком готова, тесты зелёные; иначе аудит может быть на промежуточном состоянии).

**Edge cases при аудите:**
- Если guard расположен ПОСЛЕ line 1045 (`is_fallback_active()` shortcut) — это критичный блокер (нарушает AC2: outage path всё ещё может постить дубли).
- Если уровень лога WARNING/ERROR вместо INFO — minor finding (Decision 1: INFO matches existing pattern).
- Если admin-ping вызывается без проверки return value — major finding (Decision 4: return-value check заменяет dead try/except).
- Если try/except оборачивает `send_admin_notification` — minor finding (Decision 4: dead defensive code).
- Если `INSERT OR REPLACE` вместо `INSERT OR IGNORE` — критичный блокер (Decision 5: оригинальные значения первой публикации должны сохраняться).
- Если guard вернул `True` без cleanup и без admin-ping — критичный блокер (нарушает Decisions 2, 3).

**Implementation hints:**
- Аудитор не правит код. Если найдены критичные findings — сформировать fix-request в отчёте: «Task N: исправить X, причина Y» (parent-агент решает, инициировать fix-cycle или нет).
- Цитировать конкретные строки кода в отчёте (с номерами строк), чтобы findings были проверяемы.
- Уровень детализации отчёта: достаточный для того, чтобы security-auditor и test-master в параллельных Task 7 / Task 8 могли использовать его как контекст.
- Не дублировать работу Task 7 (security: SQL injection, secret leak) и Task 8 (тесты).
