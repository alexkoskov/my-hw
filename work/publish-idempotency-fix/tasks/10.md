# Task 10: Deploy

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](~/.claude/skills/deploy-pipeline/SKILL.md)

## Description

Стандартный двухэтапный деплой фичи `publish-idempotency-fix` на VPS `148.135.207.54` через GitHub Actions: сначала на тестовый инстанс (`bot_test/` + `news_bot_test.service` + канал `@myhwchannel123`), потом на прод (`bot/` + `news_bot.service` + прод-канал `-1004027529994`). После прод-деплоя — одноразовая SQL-чистка строки в `failed_articles` (Decision 6: код-миграции нет, операторский SQL дешевле).

Согласно правилу «оператор управляет прод-операциями, Claude готовит — оператор применяет»: Claude готовит коммит и пушит ветки, GitHub Actions автоматически деплоит, оператор выполняет SSH-наблюдение тест-канала + одноразовый SQL DELETE на прод-БД. Claude НЕ запускает SSH-команды и НЕ трогает прод-БД напрямую.

После Task 9 (Pre-deploy QA) ветка `dev` уже содержит все изменения и зелёные тесты — задача сводится к оркестрации пуша + ожидания CI + слияния в `main`.

## What to do

1. **Stage 1 — деплой на тест:**
   - Убедиться, что текущая ветка — `dev`, рабочее дерево чистое (`git status`), последний коммит содержит изменения фичи (`git log -1 --stat`).
   - `git push origin dev` (если ещё не запушено после Task 9).
   - Дождаться зелёного `ci.yml` на `dev` через `gh run watch` или `gh run list --branch dev --workflow ci.yml --limit 1`.
   - После зелёного `ci.yml` GitHub Actions автоматически запускает `deploy_test.yml` через `workflow_run` — дождаться его завершения (`gh run list --workflow deploy_test.yml --limit 1`).
   - Передать оператору: «деплой на test готов, наблюдай `@myhwchannel123` ~30 минут на регрессии; опционально вставь синтетическую zombie-строку в `bot_test/news.db`, чтобы убедиться, что guard срабатывает».
   - Дождаться от оператора «ОК, тест чистый» прежде чем переходить к Stage 2.

2. **Stage 2 — мерж в main и деплой на прод:**
   - `git checkout main && git pull origin main` — синхронизироваться с remote.
   - `git merge dev` (fast-forward или merge commit — нормально оба варианта; для мелкой фичи S-size обычно ff).
   - `git push origin main`.
   - Дождаться зелёного `ci.yml` на `main`, затем автоматически триггернувшегося `deploy.yml`. Проверить через `gh run list --workflow deploy.yml --limit 1`.
   - Зафиксировать timestamp начала деплоя — он понадобится Task 11 для команды `journalctl --since '<deploy time>'`.

3. **Stage 3 — одноразовая SQL-чистка `failed_articles` (Decision 6):**
   - Передать оператору точную команду:
     ```
     ssh hwbot@148.135.207.54 "sqlite3 /home/hwbot/bot/news.db \"DELETE FROM failed_articles WHERE link='https://orangetrackdiecast.com/2026/05/02/hot-wheels-2026-car-culture-team-transport-k-case-report/';\""
     ```
   - Попросить оператора подтвердить выполнение и проверить:
     ```
     ssh hwbot@148.135.207.54 "sqlite3 /home/hwbot/bot/news.db \"SELECT COUNT(*) FROM failed_articles WHERE link LIKE '%team-transport-k%';\""
     ```
     → ожидается `0`.
   - Зафиксировать факт выполнения SQL и timestamp прод-деплоя — Task 11 (Post-deploy verification) будет использовать оба значения.

4. **Передача в Task 11:** уведомить, что прод-деплой завершён, SQL применён, timestamp деплоя зафиксирован — Task 11 готов запускаться.

- `gh run list --workflow deploy_test.yml --limit 1` → `completed success` (триггерится автоматически через `workflow_run`).
- `gh run list --branch main --workflow ci.yml --limit 1` → `completed success` после `git push origin main`.
- `gh run list --workflow deploy.yml --limit 1` → `completed success`.

- Опционально: оператор пред-стейджит синтетическую zombie-строку в `bot_test/news.db` и подтверждает срабатывание guard (admin-ping приходит, дублирующий пост не публикуется).
- После Stage 3: оператор выполнил DELETE и подтвердил, что `SELECT COUNT(*) FROM failed_articles WHERE link LIKE '%team-transport-k%'` возвращает `0`.

## Details

**Files:** новых файлов в репозитории не создаётся; никаких изменений в `deploy.yml`/`deploy.sh` — `news_bot.py` и `pending_articles_repo.py` уже в `FILES` списке (deployment.md → "Core cron-path"). Invariant deployment.md: «any new first-party import added to news_bot.py MUST be mirrored into both FILES arrays» — в этой фиче новых импортов нет, проверка пройдена.

**Dependencies:**
- Task 9 (Pre-deploy QA) — обязательно зелёный pytest локально перед пушем.
- GitHub Secrets уже настроены: `SSH_HOST`, `SSH_USER=hwbot`, `DEPLOY_PATH=/home/hwbot/bot/`, `DEPLOY_PATH_TEST=/home/hwbot/bot_test/`, `SSH_PRIVATE_KEY`, `ANTHROPIC_API_KEY`. Если деплой упал на ssh-шаге — проверить наличие сикретов в `gh secret list`.
- Серверный sudoers (`/etc/sudoers.d/news_bot`, mode 0440) уже установлен для обоих сервисов — `news_bot.service` и `news_bot_test.service` могут перезапускаться без пароля.

**Edge cases:**
- `ci.yml` упал на `dev`: НЕ пушить в `main`. Чинить в `dev`, пока тесты не зелёные.
- `deploy_test.yml` упал на `scp`/`pip install`: проверить `gh run view <id> --log-failed`. Частые причины — отсутствие `DEPLOY_PATH_TEST` сикрета, отозванный SSH-ключ, переполненный диск VPS. Эскалировать оператору.
- Оператор обнаружил регрессию на тест-канале: остановиться на Stage 1, не мержить в `main`. Откат — `git revert HEAD && git push origin dev` (test-инстанс редеплоится автоматически).
- Прод-деплой прошёл, но SQL DELETE упал (например, `database is locked`): попросить оператора повторить через 30 секунд (cron-тик может держать БД). Не критично для самой фичи — guard уже активен и предотвратит дубль; оставшаяся в `failed_articles` строка просто помечает уже опубликованную ссылку и не вредит логике.
- Конфликт при `git merge dev` в `main`: разруливать в `dev` (rebase на `main` если нужно), затем повторить мерж. НЕ форсить пуш в `main`.

**Implementation hints:**
- `gh run watch` блокирует терминал и удобен для последовательного ожидания CI → deploy. Альтернатива: `gh run list --limit 5 --json status,conclusion,workflowName` в цикле.
- Timestamp прод-деплоя проще всего взять из `gh run view <deploy.yml-run-id> --json updatedAt` — пригодится для Task 11 `journalctl --since '...'`.
- Согласно памяти оператора («ask before commit+push, then do both»): если на момент Task 10 в `dev` ещё не закоммичены/не запушены изменения от предыдущих задач — спросить оператора перед `git push origin dev`. Если всё уже запушено в Task 9 — просто проверить и идти дальше.
- НЕ использовать `--no-verify` или флаги отключения GPG; pre-commit hooks (gitleaks) — часть quality gate.
- НЕ echo-ить секреты ни в логи, ни в чат с оператором (правило из памяти: «never echo secrets»).
- Single concurrent prod deploy at a time — если предыдущий `deploy.yml` ещё крутится, новый встанет в очередь; не паниковать.
