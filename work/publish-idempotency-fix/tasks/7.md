# Task 7: Security Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Полный security audit фичи `publish-idempotency-fix` против OWASP Top 10. Это аудит после Wave 1 (правки кода в `news_bot.py` и `pending_articles_repo.py`) и Wave 2 (тесты), перед pre-deploy QA. Проверяем, что guard-блок и переход `INSERT` → `INSERT OR IGNORE` не вносят новых уязвимостей и не обходят существующие защитные механизмы (token redaction, INSTANCE_LABEL prefix, parse_mode=None в admin-ping).

Ключевые точки внимания:
1. **Admin-ping payload** — содержит URL зомби-строки. Подтвердить, что `_redact_text` (`news_bot.py:249`) корректно пропускает URL без ложных совпадений и не утекает посторонних секретов через embedded text. Текст ping'а формируется в guard-блоке (Task 1) и попадает в `send_admin_notification` (`news_bot.py:357`), которая прогоняет его через `_redact_text` и затем через Telegram bot API с `parse_mode=None`.
2. **Источник входных данных guard'а** — guard читает только `link = row['link']`, где `row` приходит из `pending_articles_repo.list_pending()` (внутренняя БД, заполняется RSS-fetch'ем самим ботом). Никакого untrusted input от внешнего пользователя в guard не попадает. Подтвердить это явно.
3. **Параметризация SQL в `INSERT OR IGNORE`** — изменение в `pending_articles_repo.move_to_published` (line 582) — это keyword-only правка, плейсхолдеры `?` и tuple-параметры остаются. Проверить, что параметризация сохранена и SQL-инъекция невозможна.
4. **Не вводится bypass существующих security-инвариантов** — token redaction, INSTANCE_LABEL prefix, parse_mode=None в admin-ping должны применяться ко всем новым admin-ping'ам guard'а (включая ping о cleanup failure из Decision 8) автоматически — потому что guard вызывает `send_admin_notification`, а не строит payload Telegram'а напрямую.

Аудит — read-only. Кода не пишем. Результат — отчёт на ~1-3 страницы в `logs/working/wave-3-security-audit.md` с findings (если есть) и явным "no issues found" по тем зонам, где нет проблем.

**Dependencies:**

- Task 4 (repository test for `move_to_published` idempotency) — даёт контекст по поведению INSERT OR IGNORE.
- Task 5 (integration test for slot-loop) — даёт контекст end-to-end поведения.
- Все три зависимости — для того, чтобы аудит шёл по уже стабилизированному коду + тестам, а не по в-процессе-меняющемуся drafт'у.

**Edge cases (что проверить специально):**
- URL в admin-ping содержит подстроку `Aiza` или `sk-` (маловероятно для news-URL, но проверить regex'ы на ложное срабатывание — это не security issue, но affects audit-quality reporting).
- Cleanup-failure ping (Decision 8) — текст этого ping'а строится с включением `type(exc).__name__`. Подтвердить, что это не leak'нет sensitive поля из exception args (Decision 12 invariant: `type(exc).__name__` only, не `str(exc)`).
- Logger emits с f-string'ом `f"[idempotency-guard] {link} ..."` — `_TokenRedactingFilter` (`news_bot.py:290`) применяется на root-уровне, так что любой случайно попавший в log token будет заскраблен. Verify это явно.

**Implementation hints:**
- Guard читает `link` из `row['link']`. `row` — sqlite3.Row из `list_pending()` (`pending_articles_repo.py`). Field `link` populated `pending_articles_repo.add_pending()` при RSS-fetch'е. Источник — RSS feed, контролируемый владельцем сайта (autoevolution.com и т.п.). Это semi-trusted: уже было проанализировано в исходной фиче `feed-ingestion`. Здесь нового surface'а не добавляется — guard работает с теми же `link`'ами, что уже шли в Telegraph и Telegram до фикса. Если был бы XSS в link'е, он бы уже эксплуатировался публикацией на канал — guard этого surface'а не расширяет.
- `INSERT OR IGNORE` SQLite-семантика: на duplicate-key (UNIQUE constraint на `link`) — silent no-op, не raise. Это известная семантика, документированная в SQLite. Не открывает covert channels или race conditions, потому что транзакция и так single-writer (cron `news_bot.service`, см. tech-spec Risk «concurrent writers»).
- Если find findings — severity `low/medium` достаточно для pass-with-recommendations (record в decisions.md и продолжать). `high/critical` — fail, blocking deploy.
