## Description

Холистический аудит качества всех 7 новых тестов фичи publish-idempotency-fix, добавленных в Wave 2 (задачи 3, 4, 5). Цель — проверить, что тесты действительно ловят баги, на которые рассчитаны (а не проходят вакуумно), что моки соответствуют реальному поведению зависимостей, и что критические assertions (litmus-checks) на месте.

Аудит покрывает три тестовых файла:
- `tests/test_fallback_publish_paths.py` — 5 unit-тестов (T1–T5) на guard в `_fallback_publish`.
- `tests/test_pending_articles_repo.py` — 1 repository-тест (T6) на идемпотентность `move_to_published`.
- `tests/test_distributed_schedule_integration.py` — 1 integration-тест (T7) на slot-loop с зомби+свежими строками.

Это аудит — задача read-only. Никаких правок в код или тесты в рамках этой задачи не вносим. Если найдены проблемы — фиксируем в отчёте и эскалируем оркестратору фичи (он создаст fix-задачу либо вернёт работу автору теста). TDD-якоря нет — задача не пишет код.

Задача выполняется параллельно с Task 6 (Code Audit) и Task 7 (Security Audit), все три аудита формируют Wave 3.

## What to do

1. Прочитать новые тесты во всех трёх файлах (T1–T5 в `test_fallback_publish_paths.py`, T6 в `test_pending_articles_repo.py`, T7 в `test_distributed_schedule_integration.py`). Понять структуру setup/act/assert каждого.

2. Сверить тесты с tech-spec разделом «Testing Strategy» — соответствие имён, состава assertions, mock-стратегии и tier-данных (carry-over vs fresh).

3. Прогнать целевые litmus/quality проверки по каждому тесту (см. Acceptance Criteria ниже). Для каждой проверки — зафиксировать в отчёте: PASS / FAIL / N/A с цитатой строки теста.

4. Дополнительно осмотреть на типовые анти-паттерны:
   - вакуумные assertions (assert True, assertions без семантики, моки, проверяющие сами себя);
   - моки, которые скрывают реальный путь кода (например, мок поверх guard и тут же assert на guard);
   - дублирование setup-логики, которую стоило бы вынести в helper (информативно, не блокер);
   - отсутствие `assertLogs` там, где требование AC10 явно его требует (T1).

5. Оценить баланс пирамиды тестов для S-фичи: 5 unit + 1 repo + 1 integration. Сверить с `patterns.md` (Testing section), не перекошено ли в сторону интеграционных.

6. Написать audit-отчёт в `logs/working/wave-3-test-audit.md` (путь относительно `work/publish-idempotency-fix/`). Структура отчёта:
   - **Summary** — вердикт по каждому тесту (PASS / NEEDS-FIX / FAIL) и общая оценка пирамиды.
   - **Per-test findings** — секция на каждый из T1–T7 с цитатами строк и оценкой каждой litmus-проверки из Acceptance Criteria.
   - **Anti-pattern findings** — список замеченных проблем (если есть).
   - **Pyramid balance** — комментарий по балансу unit/repo/integration для S-фичи.
   - **Recommendations** — что нужно поправить (если что-то найдено), либо «no action required» если всё чисто.

## Verification Steps

### Automated

Аудит — read-only задача, она сама не запускает тесты с целью проверки кода. Опционально, если в отчёте появляется сомнение по конкретному mock-поведению или assertion, можно прогнать целевой тест точечно для подтверждения:

- `pytest tests/test_fallback_publish_paths.py -q -k "skip_if_link_already_published or admin_ping" -v` → 5 тестов passed.
- `pytest tests/test_pending_articles_repo.py -q -k "test_move_to_published_idempotent_on_duplicate_link" -v` → 1 тест passed.
- `pytest tests/test_distributed_schedule_integration.py -q -k "test_slot_loop_does_not_repost_already_published" -v` → 1 тест passed.

Итог запуска не является самостоятельным критерием — аудит проверяет КАЧЕСТВО assertions, а не green-status.

## Details

**Read-only nature:** задача не вносит изменений в тесты. Если что-то нужно поправить — это решает оркестратор фичи (создаёт fix-задачу на автора Task 3/4/5 либо self-fix).

**Files to read (audit targets):**
- `tests/test_fallback_publish_paths.py` — особое внимание на T1 (assertLogs для AC10), T2 (мок `outage_state.is_fallback_active`), T5 (мок `send_admin_notification` с `return_value=False`, не `side_effect`).
- `tests/test_pending_articles_repo.py` — T6: после второго `move_to_published` проверить, что строка в `published_articles` имеет ОРИГИНАЛЬНЫЕ значения. `INSERT OR REPLACE` бы тихо обновил — тест должен это поймать.
- `tests/test_distributed_schedule_integration.py` — T7: `send_telegraph_teaser.call_args` (или `mock_teaser.call_args`) должен включать `link_fresh`, не просто `call_count == 1`. Дополнительно: zombie row подготовлена с `attempt_count=2` ДО job(), `failed_articles` после job() — пусто.

**Where the report goes:** `work/publish-idempotency-fix/logs/working/wave-3-test-audit.md`. Если папка `logs/working/` отсутствует — создать.

**What constitutes a finding:**
- **FAIL** — assertion отсутствует или явно не проверяет требуемую семантику (например, T7 проверяет только count, не call_args).
- **NEEDS-FIX** — assertion есть, но слабая (например, проверяется только тип, не значения; мок настроен не на ту семантику).
- **PASS** — assertion на месте, семантика покрыта, мок соответствует реальному поведению.

**Edge cases для аудита:**
- T1 может использовать `caplog` (pytest-style) вместо `assertLogs` (unittest-style) — оба валидны, проверка должна это учесть.
- T6 может проверять значения через `SELECT * FROM published_articles` raw SQL или через `get_published(link)` — оба валидны.
- T7 может ассертить call_args через `call_args.kwargs['link']` или `call_args[0][N]` — оба валидны, важно что link сравнивается с `link_fresh`.

**Implementation hints (для аудитора):**
- Сначала прочитай все 7 тестов целиком — получишь общее впечатление перед litmus-проходом.
- На каждый ATR-критерий цитируй конкретные строки теста (имя теста + номер строки или фрагмент).
- Если найдена проблема — формулируй её как actionable: «T7: assert на line N проверяет только `call_count == 1`. Нужно добавить `assert mock.call_args.kwargs['link'] == link_fresh`» — это сразу разворачивается в fix-задачу.
