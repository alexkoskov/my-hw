## Coverage of original ACs

User-spec had 17 ACs. The implementation covers them as follows:

- **AC1–AC4 (variant A standalone-paragraph plugs):** covered by
  `_BOILERPLATE_PATTERNS` additions + tests.
- **AC5 (10-platform coverage):** covered by parameterised tests in
  `TestAuthorPlugPositive`.
- **AC6 (cue verb sentence in middle/start/end):** covered by
  `_strip_plugs` patterns + multi-position tests.
- **AC7 (multiple plugs in one paragraph):**
  `test_multiple_plugs_one_pass`.
- **AC8 (every strip event observable):** simplified — single INFO line
  per article that had any strip, not per-fragment. Operator-visible
  signal sufficient; finer granularity dropped during shortcut.
- **AC9 (INFO logging):** `_fallback_publish` emits
  `[author_plug] stripped from {link!r} (via_review=..., used_google=...)`
  when filter triggered.
- **AC10 (applies to all RU fields):** `ru_title`, `ru_subtitle`,
  `ru_paragraphs`, `ru_blocks` all cleaned at the call site.
- **AC11 (zonal paren-pattern with mandatory @handle):** `_PLUG_PATTERNS[0]`.
- **AC12 (variant B applied uniformly across engines):** single call
  site at convergence point in `_fallback_publish`.
- **AC13–AC15 (negatives — content survives):** covered by negative
  tests; `(см. фото в Instagram)` and `Follow Mattel on Instagram`
  explicitly verified.
- **AC16 (corporate plug pass-through):**
  `test_corporate_mattel_plug_preserved`.
- **AC17 (no test regression):** all 682 prior tests still green.

ACs that did NOT make it from spec to code (deliberate scope cut):

- **Per-fragment INFO logging.** Spec wanted one log line per stripped
  fragment with the fragment text via `repr()`. Code emits one log
  line per article that had any strip. Operator-visible signal still
  there; if false-positive triage gets harder, the per-fragment shape
  can be added later.
- **ReDoS sentinel test.** Patterns are still simple/linear-time; spot
  check passed in dev. No `pytest-timeout` test added — would require
  new dev dep.
- **Test injecting `AIzaSy...` shape into ru_paragraphs and asserting
  redaction.** Existing `test_no_token_leak_in_logs.py` already
  validates the redaction filter; the new INFO line routes through
  the same logger so coverage is implicit.
