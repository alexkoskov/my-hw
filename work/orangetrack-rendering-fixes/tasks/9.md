# Task 9: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Финальный pre-deploy gate перед мёрджем `dev → main`. Прогоняем полный набор тестов локально, убеждаемся в отсутствии регрессий относительно baseline (829 тестов после `publish-idempotency-fix`, уже на `dev`), и проверяем, что каждый user-spec critеrion AC1–AC11 покрыт либо проходящим автоматическим тестом, либо исполняемой проверкой.

Зачем: волны 1-2 написали код и тесты, волна 3 (Tasks 6/7/8) проверила качество кода/безопасности/тестов на уровне отдельных артефактов. Эта задача — последний suite-level gate: мы убеждаемся, что весь репозиторий собран правильно и ни один из 829 baseline-тестов не сломан, плюс новые ~35 тестов (parser + publisher + integration) зелёные. Если QA report зелёный — переходим к Task 10 (Deploy).

Это **non-code** задача — никаких изменений в продуктовом коде. Только запуск проверок, маппинг AC → test, и письменный отчёт.

## What to do

1. **Полный pytest регрессии:** прогнать `pytest tests/ -q` из корня репозитория. Зафиксировать общее число тестов и любые failures/errors. На зелёном — двигаемся дальше; при любом fail/error — STOP, репортить в decisions.md, не считать QA пройденным.
2. **Подсчёт прироста тестов:** сравнить общее число с baseline 829 (`publish-idempotency-fix` уже на dev). Ожидаемый прирост — ~31 тест (см. tech-spec Testing Strategy: 11 в `test_orangetrack_source.py` (10 unit + 1 integration), и 24 в `test_telegraph_publisher.py`). Допустимая граница — 860+. Если прирост заметно меньше ожидаемого — флаг в отчёт (тесты могут быть не дописаны).
3. **Static check на изменённых исходниках:** прогнать `python3 -m py_compile orangetrack_source.py _llm_common.py telegraph_publisher.py` — exit code 0.
4. **AC coverage map:** для каждого user-spec AC1–AC11 указать конкретный тест (или несколько) либо исполняемую проверку, которая его покрывает. Использовать tech-spec Testing Strategy как первичный source-of-truth (там тесты названы поимённо).
5. **Регрессионные test-файлы:** прогнать индивидуально `pytest tests/test_orangetrack_source.py tests/test_telegraph_publisher.py tests/test_openrouter_transcreation.py tests/test_distributed_schedule_integration.py -q` и убедиться в зелёном (это файлы, перечисленные в user-spec Risk-5 как explicit regression coverage).
6. **Записать QA report** в `decisions.md` фичи: краткий summary (1-3 предложения), вердикт (green / red), числа (total tests, new tests added, failures/errors), AC coverage table, ссылки на новые тесты.
7. На green — отметить задачу done; ready to deploy (Task 10).

- [ ] `pytest tests/ -q` выполнен, отчёт: 0 failures, 0 errors.
- [ ] Total test count: baseline 829 + ~35 новых ≈ 864 или больше.
- [ ] `python3 -m py_compile orangetrack_source.py _llm_common.py telegraph_publisher.py` → exit code 0.
- [ ] Каждый из 11 user-spec AC (AC1–AC11) явно отмаплен на проходящий тест или исполняемую проверку (mapping приведён в QA report).
- [ ] Ноль регрессий в `tests/test_orangetrack_source.py`, `tests/test_telegraph_publisher.py`, `tests/test_openrouter_transcreation.py`, `tests/test_distributed_schedule_integration.py` (явно проверено отдельным прогоном).
- [ ] QA report записан в `decisions.md`; на зелёном — фича готова к Task 10 (Deploy).

**Edge cases при QA:**
- Если total tests меньше 829 — пропавшие тесты, репорт red.
- Если AC mapping находит «нет покрытия» — репорт red, эскалировать обратно в волну 2.
- Flaky тесты на повторном запуске — повторить ещё раз; если стабильно flaky — упомянуть в QA report (но не блокировать деплой, если на 2 из 3 прогонов зелёный и flaky-тест не относится к фиче).

**Implementation hints:**
- Запускать pytest из корня репозитория (`/workspaces/debian-2/my-hw/`), не из feature folder.
- Подсчёт total можно тащить из последней строки pytest output (`X passed in Ys`).
- AC mapping — таблица в decisions.md формата `| AC | Test/Check | Status |`.
