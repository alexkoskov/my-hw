# Task 1: Parser changes — `<li>`/`<ol>` + heading dispatch + `paragraphs_flat`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Это первая (и единственная парсерная) задача фичи `orangetrack-rendering-fixes`. Меняем `orangetrack_source.py` сразу под две из трёх багов фичи:

- **Bug 1 — `<li>` parsing.** Сейчас `_walk` не имеет ветки для `<li>` — попадая в `<ul>`/`<ol>`, walker рекурсивно идёт в детей через fallback `if name not in handled_tags: _walk(child)`, но тэги `<li>` оказываются в неизвестной ветке (тоже `not in handled_tags`) и их текст никуда не эмитится как блок. Нужна явная ветка для `<li>` (детей `<ul>` или `<ol>` обрабатываем одинаково — Decision 8): эмитим новый блок-тип `{type: "list_item", text, runs}` с runs из существующего `_runs_from_tag`. Bullet `"• "` НЕ вставляется на этом уровне — это сделает publisher после LLM-перевода (AC2, Decision 1).
- **Bug 2 — heading levels.** Сейчас `_emit_heading` для всех h2/h3/h4/h5 эмитит `type: "paragraph"` (это поведение зафиксировал коммит `babc67c` через сессию SESSION-2026-05-06.md break 3). Меняем: для h2/h3/h4 эмитим `type: "heading", level: 3`. Для h5 поведение остаётся прежним — `type: "paragraph"` (карв-аут сохраняет `babc67c`, потому что на orangetrack `<h5>` используется как внутри-параграфные section-маркеры с длинным текстом). Соответственно меняется и dispatch в `_walk`.
- **`paragraphs_flat`.** Расширяем существующее извлечение `[b["text"] for b in blocks if b["type"] in ("paragraph", "heading")]` так, чтобы оно включало `"list_item"`. Это критично для `_llm_common._patch_text_with_ru_paragraphs`: количество элементов `paragraphs_flat`, отдаваемых LLM, должно совпадать с количеством блоков, чьи тексты мы хотим обновить (lead/paragraph/heading/list_item). Без этого расширения trailing list_item-блоки останутся на английском.

Все три изменения локализованы в одном файле — один атомарный коммит.

## What to do

1. В `orangetrack_source.py`, внутри функции `_parse_content_encoded`, в локальной функции `_walk`:
   - Добавить ветку для `name == "li"`: извлечь runs через `_runs_from_tag(child)`, собрать `text` тем же способом, что в `_emit_paragraph`/`_emit_heading` (`" ".join(r["text"] for r in runs).strip()`); если `runs` пуст или `text` пустой — ничего не эмитить (empty `<li>` dropped, AC); иначе добавить блок `{"type": "list_item", "text": text, "runs": runs}` в `blocks`. Делаем inline в `_walk` (tech-spec Solution прямо говорит: «inline in `_walk`, no separate helper function»).
   - Расширить `handled_tags`, добавив в него `"li"` (и можно `"ul"`, `"ol"` — для явности, чтобы walker по-прежнему рекурсивно заходил в children через свой fallback). Цель — гарантировать, что `<li>` явно ловится новой веткой.
2. Изменить `_emit_heading` так, чтобы для `level in (2, 3, 4)` эмитился блок `{"type": "heading", "level": 3, "text": text, "runs": runs}` (все три уровня → level=3, Decision 3). Для `level == 5` — оставить эмит `{"type": "paragraph", ...}` (Decision 2 — preserves `babc67c`). Обновить комментарий в `_emit_heading` так, чтобы он отражал новое поведение и упоминал карв-аут h5.
3. Обновить dispatch в `_walk`:
   - Ветка `name in ("h2", "h3", "h4")` — оставить `_emit_heading(child, int(name[1]))`, поведение внутри `_emit_heading` теперь различается по `level`.
   - Ветка `name == "h5"` — оставить `_emit_heading(child, 5)`.
   - Ветки `name in ("h1", "h6")` — оставить `continue` (ignored, AC5).
4. Расширить `paragraphs_flat` extraction (после `blocks = filter_blocks(blocks)`):
   - Было: `[b["text"] for b in blocks if b["type"] in ("paragraph", "heading")]`
   - Стало: `[b["text"] for b in blocks if b["type"] in ("paragraph", "heading", "list_item")]`
   - Обновить комментарий выше, чтобы отразить, что `list_item` теперь тоже патчится через `_patch_text_with_ru_paragraphs` (см. Task 2 — расширение `_PATCHED_TEXT_BLOCK_TYPES`).
5. Прогнать `python3 -m py_compile orangetrack_source.py` — должен пройти без ошибок.

## Details

**Files:**
- `orangetrack_source.py` — единственный файл, который меняется в этой задаче.
  - Текущее состояние:
    - `_walk` (строки ~484–556) handlет `p`/`h2-h6`/`figure`/`img`/`iframe` — нет явной ветки для `<li>`. Теги `<ul>`/`<ol>`/`<li>` попадают в fallback-рекурсию через `if name not in handled_tags: _walk(child)`, и `<li>` эмитится никак.
    - `_emit_heading` (строки ~415–434) принимает аргумент `level` (уже передаётся call-sites), но игнорирует его — эмитит ВСЕ headings (h2/h3/h4/h5) как `type: "paragraph"`. Комментарий явно ссылается на SESSION-2026-05-06.md.
    - Извлечение `paragraphs_flat` (строки ~575–577) включает только `("paragraph", "heading")`.
  - Что меняем:
    - Добавить явную ветку `name == "li"` в `_walk` с inline-эмитом блока `{type: "list_item", text, runs}`. Опционально: добавить `"li"` (и `"ul"`, `"ol"` для явности) в `handled_tags`.
    - Обновить `_emit_heading`: для level∈{2,3,4} эмитить `type: "heading", level: 3`; для level==5 — оставить текущий `type: "paragraph"`.
    - Расширить фильтр `paragraphs_flat` на `"list_item"` и обновить комментарий выше списка.

**Dependencies:**
- Этой задачи: нет (`depends_on: []`).
- Семантически в одной волне с Task 2 (`_llm_common._PATCHED_TEXT_BLOCK_TYPES` расширение) и Task 3 (publisher); Wave 2 (тесты) ждёт всю Wave 1.

**Edge cases:**
- `<li>` без текста (например `<li><img></li>`) — `_runs_from_tag` вернёт пустой список → блок не эмитится.
- `<li>` со вложенным `<a>` — `_runs_from_tag` уже умеет вытаскивать href в run; `block.runs` будет содержать href-runs, которые позже использует publisher (Task 3) для same-site линковки.
- `<li>` с вложенным `<strong>`/`<em>` — `_runs_from_tag` flatten'ит форматирование (см. docstring `_runs_from_tag`), `block.text` содержит plain текст.
- Вложенный `<ul>` внутри `<li>` (вложенный список) — текущий walker рекурсивно зайдёт во внутренний `<ul>` через fallback, так как наш handler для `<li>` обрабатывает только text-runs верхнего уровня. Вложенные `<li>` потенциально попадут отдельным блоком — приемлемо для MVP (orangetrack делает плоские списки).
- `<h5>` с inline `<a>` — `_emit_heading(child, 5)` идёт в paragraph-ветку, runs сохраняются — link rendering включится в publisher через тот же путь, что и для обычных параграфов.
- `<h2>`/`<h3>`/`<h4>` пустой/только-whitespace — после `_runs_from_tag` пустой список → блок не эмитится (поведение `_emit_heading` уже это покрывает).

**Implementation hints:**
- НЕ создавать новую helper-функцию для `<li>` — tech-spec Solution прямо говорит «inline in `_walk`, no separate helper function». Логика идентична `_emit_paragraph` за исключением `type: "list_item"`.
- `handled_tags` — это set, он пер-функционный (определён внутри `_parse_content_encoded` рядом с `_walk`). Добавление `"li"` в него — минимальная семантическая чистка; без неё fallback `_walk(child)` всё равно зайдёт внутрь, но явная ветка читается лучше.
- В `_emit_heading` сейчас параметр называется `level` — оставляем имя, добавляем условную ветку: `if level in (2, 3, 4): blocks.append({"type": "heading", "level": 3, ...})` иначе текущий paragraph-emit. НЕ менять сигнатуру — call-sites в `_walk` уже передают `level`.
- При обновлении комментария `_emit_heading` — упомянуть оба полюса карв-аута (h2/h3/h4 → heading level=3; h5 → paragraph для in-paragraph section markers, ссылка на SESSION-2026-05-06.md break 3 сохраняется).
- Перед коммитом: `git diff orangetrack_source.py` должен показать изменения только в `_walk` (новая ветка `<li>`, опционально расширение `handled_tags`), `_emit_heading` (условный type/level) и фильтре `paragraphs_flat`. Никакие другие функции не трогаем.
