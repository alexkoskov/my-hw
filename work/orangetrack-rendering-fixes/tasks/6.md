# Task 6: Code Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-reviewing` — [skills/code-reviewing/SKILL.md](~/.claude/skills/code-reviewing/SKILL.md)

## Description

Полнофичевый аудит качества кода после Wave 1 (изменения в трёх исходниках) и Wave 2 (тесты), перед pre-deploy QA. Это read-only задача: аудитор НЕ редактирует код, только читает три модифицированных файла (`orangetrack_source.py`, `_llm_common.py`, `telegraph_publisher.py`) на фоне tech-spec и decisions, и пишет отчёт-вердикт в `logs/working/wave-3-code-audit.md`.

Цель — поймать классы дефектов, которые проходят сквозь per-task code-reviewer'ов, потому что у них нет цельной картины фичи: дублирующаяся логика между файлами, расхождения между задекларированными в tech-spec Decisions 1-10 и фактической реализацией, неравномерное применение helper'а `_render_paragraph_with_runs` (Decision 7 требует, чтобы он вызывался единообразно для paragraph / heading / list_item), стилистическая рассогласованность с существующей кодовой базой проекта, бедные/вводящие в заблуждение комментарии.

Вердикт аудита открывает или блокирует Wave 4 (Pre-deploy QA): PASS / PASS WITH ISSUES → можно продолжать; FAIL → именованная задача (1, 2 или 3) уходит на fix-cycle.

## What to do

1. Прочитать все три исходника целиком в их текущем состоянии после Wave 1: `orangetrack_source.py`, `_llm_common.py`, `telegraph_publisher.py`.
2. Прочитать tech-spec и decisions фичи, держать перед глазами список Decisions 1-10 и их трассировку на ACs.
3. Прогнать каждое из десяти Decision-утверждений по фактическому коду — есть ли реализация, соответствует ли тексту решения.
4. Сделать кросс-файл-проверку Decision 7: `_render_paragraph_with_runs` должен вызываться внутри `_build_content_from_blocks` единообразно для трёх типов блоков (paragraph, heading, list_item); для list_item — после `lstrip` ведущего буллета и DoS-bound'а. Любое расхождение (например, helper вызван только для paragraph, а heading рендерится напрямую) — это finding.
5. Поискать дублирующуюся логику: одинаковые по сути куски в разных функциях/файлах, которые должны были быть вынесены (например, два места проверки same-site, два места обхода `runs`, два места strip'а буллета).
6. Проверить, что границы новых helper'ов чистые: `_is_same_site` принимает только то, что декларирует (href, source_netloc), не лезет в `block.text`; `_render_paragraph_with_runs` не делает ничего, что должно делать вызывающее место (например, не дописывает буллет — это работа list_item-ветки в `_build_content_from_blocks`).
7. Сравнить стиль новых функций с существующим кодом проекта — naming, типизация, docstrings, log-уровни, импорты, exception handling. Любые отклонения от установленной в проекте практики.
8. Оценить качество комментариев и docstrings: ссылается ли код на номера Decisions/AC там, где это критично; нет ли вводящих в заблуждение или устаревших комментариев; описана ли семантика first-wrap-wins, www-prefix-via-removeprefix, DoS-bound — тех мест, где «как» неочевидно из имён.
9. Сформировать отчёт в `logs/working/wave-3-code-audit.md` со структурой:
   - Вердикт первой строкой: `Verdict: PASS` | `Verdict: PASS WITH ISSUES` | `Verdict: FAIL`.
   - Сводка (2-4 предложения): что проверили, ключевые наблюдения.
   - Раздел «Decision 1-10 traceability»: чек-лист по каждому Decision — pass/issue + одна строка обоснования.
   - Раздел «Decision 7 uniform helper application»: явный вердикт с указанием строк/функций, где helper вызывается.
   - Раздел «Duplicated logic»: список найденного дублирования или явно "none found".
   - Раздел «Helper boundaries»: чистые / есть протечки.
   - Раздел «Code style consistency»: соответствие проектной практике.
   - Раздел «Comment quality»: оценка комментариев и docstrings.
   - Раздел «Findings» (если есть): список с severity (critical/major/minor) и конкретной локацией (file:line или функция).
   - Если вердикт FAIL — обязательный раздел «Fix-cycle target»: какая именно задача (Task 1, Task 2 или Task 3) уходит на fix-cycle и какие findings должны быть закрыты.

## Details

**Files (read-only):**
- `orangetrack_source.py` — после Task 1: новая ветка `<li>` в `_walk` через `_runs_from_tag`, изменённый `_emit_heading` с `level`-аргументом и диспетчеризацией h2/h3/h4 → heading level=3, h5 → paragraph, расширение `paragraphs_flat` на `"list_item"`.
- `_llm_common.py` — после Task 2: добавлен `"list_item"` в кортеж `_PATCHED_TEXT_BLOCK_TYPES`.
- `telegraph_publisher.py` — после Task 3: новые функции `_render_paragraph_with_runs(text, runs, source_url)` и `_is_same_site(href, source_netloc)`; модификация `_build_content_from_blocks` (НЕ `preview_nodes` — это диспетчер) — вызов helper'а для paragraph / heading / list_item; для list_item — `lstrip` ведущего буллета и префикс `"• "` после helper'а; DoS-bound на `len(text) > 100000` или `len(runs) > 100` со skip helper'а и WARNING-логом.

**Output report:** `work/orangetrack-rendering-fixes/logs/working/wave-3-code-audit.md` — создать каталог при необходимости (`mkdir -p`).

**Dependencies:** Task 4 (тесты парсера) и Task 5 (тесты publisher'а) — depends_on. Аудит запускается после того, как код Wave 1 уже зелёный по своим тестам Wave 2; иначе нечего аудитить целостно.

**Edge cases / на что особенно смотреть:**
- Decision 4: проверить, что используется именно `removeprefix("www.")`, а не `lstrip("www.")` — в коде и в обе стороны (для href и для source_url). Это security-критично (lookalike-bypass).
- Decision 5: убедиться, что при перекрытии run-спанов второй (overlapping) run не «исчезает» из текста, а остаётся plain-text-сегментом — не должно быть `continue`/skip, который выкидывает substring из вывода.
- Decision 7: ключевая интегральная проверка — `_render_paragraph_with_runs` вызывается во всех трёх ветках. Empty/None `runs` должны идти через helper тоже (helper возвращает `[block.text]`), а не быть отдельной shortcut-веткой в caller'е.
- Decision 9: гард на пустой `run.text` ДО `str.find` — без него `"".find("")` вернёт 0 и обернёт zero-width `<a>` в начале параграфа.
- Decision 10: `block.text.lstrip(" ••\t")` для list_item ДО prepend `"• "` — bullet-doubling guard. И DoS-bound с WARNING-логом, не silent fallthrough.
- Negative: парсер НЕ должен прицеплять `"• "` к `block.text` для list_item. Если этот символ всё-таки попал в парсер — это критический отход от Decision 1 / AC2.
- Стиль: новые функции должны соответствовать существующему стилю модуля (typing, docstrings, naming) — особенно в `telegraph_publisher.py`, где уже сформирована проектная конвенция.

**Implementation hints:**
- Это аудиторская задача — никаких правок кода. Все находки идут только в отчёт.
- Для каждой находки указывать severity (critical / major / minor), файл и строку или сигнатуру функции, конкретное расхождение, ссылку на Decision/AC если применимо.
- Differentiate: critical = блокирует деплой (нарушение Decision-инварианта, реальный баг, security-регрессия); major = надо чинить, но фича работает; minor = улучшение/полировка.
- При FAIL — называть задачу по номеру (Task 1 / Task 2 / Task 3) и группировать findings под этой задачей; orchestrator поднимет именно её на fix-round.
- При PASS WITH ISSUES — minor findings можно оставить как technical debt; описать в отчёте, что не блокируют Wave 4.
