# User Spec: Добавление Facebook Hot Wheels в качестве источника новостей

## Что делаем
Добавляем страницу Facebook https://www.facebook.com/hotwheels/ в список источников новостей для автоматической публикации в Telegram-канале Hot Wheels News. Используем RSS-ленту Facebook, если доступна; в противном случае — парсинг HTML с ограничением частоты запросов. Посты фильтруются по ключевым словам (event, announcement, coming soon, glow-n-fire), чтобы отсеивать анонсы ивентов.

## Зачем
Решаем проблему недостатка официальных анонсов Hot Wheels в текущих источниках новостей (только autoevolution.com). Добавление Facebook позволяет подписчикам получать прямые анонсы от производителя, увеличивает оперативность и полноту новостей. Конкретная выгода: подписчики канала будут видеть новости о новых коллекциях, ограниченных выпусках и мероприятиях раньше, чем на сторонних сайтах. Подписчики получают анонсы на 24 часа раньше, чем через сторонние агрегаторы.

## Как должно работать
1. Бот каждые 24 часа проверяет страницу Facebook на новые посты.
2. Если есть RSS-лента, использует её; если нет — загружает HTML и извлекает посты через парсинг.
3. Для каждого нового поста извлекает текст и изображения.
4. Фильтрует посты по ключевым словам: если пост содержит слова “event”, “announcement”, “coming soon”, “glow-n-fire”, он пропускается (не публикуется).
5. Оставшиеся посты проходят через стандартный пайплайн бота: перевод с английского на русский, суммаризация (при необходимости), форматирование.
6. Пост публикуется в Telegram-канал с ссылкой на оригинал.
7. Ссылка на пост сохраняется в базу SQLite, чтобы избежать дубликатов.

## Критерии приёмки
- [ ] Бот каждые 24 часа проверяет страницу Facebook на новые посты.
- [ ] Извлекает основной текст поста (без служебных полей) и изображения (первые 1-2).
- [ ] Фильтрует посты с ключевыми словами event, announcement, coming soon, glow-n-fire (не публикует их).
- [ ] Переводит текст с английского на русский (если исходный язык английский).
- [ ] Публикует пост в Telegram-канал с корректным форматированием: заголовок (переведённый), текст (переведённый и суммаризированный, если длинный), изображения (первые 1-2), ссылка на оригинальный пост, хэштег #hotwheels #facebook.
- [ ] Сохраняет обработанные посты в базу данных для предотвращения повторной публикации.
- [ ] При ошибке парсинга (RSS недоступен, HTML изменился) отправляет уведомление администратору и продолжает работу с другими источниками.

## Ограничения
Facebook может блокировать парсинг, требуется соблюдение лимитов запросов (не более 200 запросов/час). Возможно потребуется использование официального Graph API (требуется токен). Также нужно учитывать изменение структуры HTML, что может сломать парсинг. Разработка должна быть выполнена в рамках существующей архитектуры бота, без переписывания ядра.

## Риски
- **Риск 1:** Facebook изменит структуру HTML или отключит RSS, что сломает парсинг. **Митигация:** добавить мониторинг ошибок и уведомления администратору; провести исследование Graph API как основной метод; предусмотреть fallback на парсинг HTML только как крайнюю меру.
- **Риск 2:** Facebook заблокирует IP из-за слишком частых запросов. **Митигация:** соблюдать лимиты (не более 200 запросов/час), использовать задержки между запросами, возможно прокси.
- **Риск 3:** Фильтрация по ключевым словам может пропустить ивентные посты или наоборот отфильтровать нормальные новости. **Митигация:** использовать более точный список ключевых слов и регулярные выражения; предусмотреть возможность ручной настройки через конфиг.
- **Риск 4:** Ошибки при парсинге Facebook могут остановить обработку остальных RSS-источников. **Митигация:** реализовать изоляцию ошибок (каждый источник обрабатывается в отдельном try-catch), использовать rate limiting, настроить прокси при необходимости.

## Граничные случаи

- **RSS недоступен:** Facebook может не предоставлять RSS-ленту. В этом случае мы переходим к Graph API, а если он недоступен — к парсингу HTML.
- **Ограничение частоты запросов Graph API:** Graph API имеет лимит 200 запросов в час. Бот должен соблюдать этот лимит и делать паузы между запросами.
- **Изменение структуры HTML:** Facebook может изменить вёрстку, что сломает парсинг. В этом случае бот отправляет уведомление администратору и продолжает работу с другими источниками.
- **Пустые посты:** Пост может не содержать текста или изображений. Бот должен корректно обрабатывать такие случаи, публикуя только доступный контент.
- **Неанглийский контент:** Пост может быть на другом языке. Бот должен определять язык и переводить только если это английский (или другие поддерживаемые языки).
- **Ошибки парсинга:** Любая ошибка при обработке Facebook-источника не должна влиять на обработку других RSS-лент (изоляция ошибок).

## Технические решения
- Мы решили сначала проверить доступность RSS-ленты Facebook и, если она работает, использовать её как основной источник.
- Если RSS недоступен, мы исследуем Facebook Graph API (официальный метод) как приоритетный вариант, а парсинг HTML оставляем как крайний fallback из-за его хрупкости.
- Мы решили фильтровать посты по ключевым словам с использованием регулярных выражений и конфигурируемого списка, чтобы снизить количество ложных срабатываний.
- Мы решили обеспечить изоляцию ошибок и ограничение частоты запросов для минимизации влияния на другие источники.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.

**Интеграционные тесты:** делаем — для проверки парсинга Facebook поста и публикации в Telegram. Используем мок страницы Facebook (статический HTML) и мок Telegram API.

**E2E тесты:** не делаем — из-за зависимости от внешних сервисов (Facebook, Telegram) и ограничений по времени. Проверку работоспособности в production будем выполнять через мониторинг и ручное тестирование после деплоя.

### Пользователь проверяет
- После деплоя проверить, что в Telegram‑канале появились посты из Facebook (не ивентные) с переводом и изображениями.
- Убедиться, что ивентные посты (содержащие ключевые слова) не публикуются.
- Проверить лог на наличие ошибок парсинга и уведомлений администратору.
