# Task 2: Make `move_to_published` idempotent on duplicate link

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Defense-in-depth изменение в `pending_articles_repo.move_to_published`: меняем `INSERT INTO published_articles` на `INSERT OR IGNORE INTO published_articles` (одно ключевое слово, line 582). Это вторая половина фикса дубликатов в Telegram-канале (первая половина — guard в `_fallback_publish`, Task 1).

Зачем нужна именно defense-in-depth, а не один guard:
- `_fallback_publish` (cron-путь) уже защищён guard'ом из Task 1.
- Но `move_to_published` имеет ВТОРОГО живого вызывающего — `hw_review.cmd_publish` (`hw_review.py:569`, диспатч `hw_review.py:815`). Этот путь НЕ проходит через guard в `_fallback_publish`. Без `INSERT OR IGNORE` оператор-driven retry через `hw_review` всё ещё может упасть с `IntegrityError`.
- `INSERT OR IGNORE` — нативный SQLite-паттерн идемпотентности, уже используется этой же функцией для `processed_news` (line 593). Замена сохраняет первую запись (first publish wins), что семантически правильно: первая публикация — каноничная, дубликат — симптом, который мы подавляем.

Шаги 2 (`INSERT OR IGNORE INTO processed_news`) и 3 (`DELETE FROM pending_articles`) исполняются безусловно в той же транзакции — это и есть желаемое поведение: stale pending row будет удалён даже при повторной попытке публикации уже-опубликованной ссылки.

Соответствует Decision 5 tech-spec'а.

  - Текущее состояние (line 582): `"INSERT INTO published_articles "`
  - Целевое состояние: `"INSERT OR IGNORE INTO published_articles "`

Завершающий пробел в строковом литерале на line 582 ОБЯЗАТЕЛЕН — без него получится `published_articles(link,...` без пробела между именем таблицы и колонками (синтаксис sqlite не упадёт, но diff станет шумнее, чем нужно).

- Прямых зависимостей от других tasks в Wave 1 нет (Task 1 правит `news_bot.py`, эта таска — `pending_articles_repo.py`; параллельно).
- Task 4 (Wave 2) зависит от этой таски — добавляет T6 в `tests/test_pending_articles_repo.py` против пост-Task-2 кода.

**Edge cases:**
- **Первый вызов (link не в `published_articles`):** поведение прежнее — insert проходит, rowcount = 1. `INSERT OR IGNORE` не меняет успешный insert.
- **Второй вызов с тем же link (наш bug-сценарий):** insert тихо пропускается (rowcount = 0), `published_articles` сохраняет ОРИГИНАЛЬНЫЕ `telegraph_url`/`telegraph_path`/`via_review`/`published_at`. Steps 2 и 3 исполняются → `processed_news` уже содержит link (IGNORE), `pending_articles` row удалён. Транзакция коммитится без ошибки.
- **Pending row отсутствует (early return на line 574):** код не доходит до line 582; правка не активируется. Поведение прежнее.
- **`OperationalError` на любом из 3-х execute:** ловится `except Exception` на line 603, rollback + re-raise. Поведение прежнее (см. регрессионный тест `test_move_to_published_rollback_on_error`).
- **Параллельные writers с разными metadata:** архитектурно невозможно в проде (single-writer cron, code-research §E.1). Defense-in-depth.
- **Caller, ожидающий `IntegrityError` как сигнал «уже опубликовано»:** таких НЕТ (verified в code-research §B.3, grep по tests/ news_bot.py hw_review.py — ни одного матча на ожидание `IntegrityError` от `move_to_published`).

**Implementation hints:**
- Это однотокенная правка. Не ищите архитектурных доработок: добавлять новый параметр, читать `cur.rowcount`, возвращать булево из функции — всё это OUT OF SCOPE и поломает существующих вызывающих.
- НЕ заменять на `INSERT OR REPLACE`. Различие: `OR REPLACE` затрёт оригинальные `telegraph_url`, `telegraph_path`, `published_at`, `via_review` второй версией values — это ИСКАЖЕНИЕ исторических данных. `OR IGNORE` сохраняет первую запись (first publish wins), что правильно (первый publish — каноничный; повторный — симптом, который подавляем).
- Не добавлять log-statements в эту функцию: операционная видимость идёт через `[idempotency-guard]` лог в `_fallback_publish` (Task 1). Здесь — silent defense-in-depth.
- Если линтер/форматтер захочет переформатировать соседние строки — отвергнуть, оставить только однотокенный diff. `git diff pending_articles_repo.py` должен показывать ровно одну изменённую строку.
- Параметризация SQL (`?`-placeholders + bind tuple) уже корректная — не трогать. SQL-injection невозможна, потому что `link`, `title`, etc. передаются через bind tuple, а не через f-string.
