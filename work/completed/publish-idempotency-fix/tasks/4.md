# Task 4: Add 1 repository test for `move_to_published` idempotency

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Тест-страховка для изменения, сделанного в Task 2 (одна замена ключевого слова в `pending_articles_repo.move_to_published`: `INSERT INTO published_articles ...` → `INSERT OR IGNORE INTO published_articles ...`, строка 582).

Цель теста — формально зафиксировать новый контракт уровня репозитория:

1. Повторный вызов `move_to_published(link, ...)` с уже опубликованным `link` НЕ должен поднимать `IntegrityError` (UNIQUE на `published_articles.link`). Сейчас, до Task 2, такой вызов и есть тот самый прод-сбой, ради которого фича вообще запущена.
2. При повторе значения в `published_articles` остаются от ПЕРВОЙ публикации (`telegraph_url`, `telegraph_path`, `via_review`). Это критично: используется `INSERT OR IGNORE`, а НЕ `INSERT OR REPLACE` — иначе оператор-driven retry молча перетирал бы исторический Telegraph URL у подписчиков.
3. Шаги 2–3 транзакции (`INSERT OR IGNORE INTO processed_news`, `DELETE FROM pending_articles`) выполняются всегда — то есть таблица `pending_articles` после второго вызова пуста.

Тест соответствует **T6** из tech-spec → "Testing Strategy → Unit tests → 1 new test in `tests/test_pending_articles_repo.py`" и закрывает defense-in-depth слой Decision 5 (страховка для второго реального вызывающего — `hw_review.cmd_publish`, см. Risks в tech-spec).

Test-only задача: код продакшена не меняем, новые тесты только в `tests/test_pending_articles_repo.py`. Зависит от Task 2 (без изменения `INSERT OR IGNORE` тест в чистом виде упадёт на втором `move_to_published` — это нормально на TDD-этапе, но финальный CI-зелёный возможен только после Task 2).

## What to do

1. Открой `tests/test_pending_articles_repo.py`. Найди класс `TestMoves(_TmpDbCase)` (строка 566) — рядом с существующим `test_move_to_published_atomic` (577) и `test_move_to_published_rollback_on_error` (623). Новый тест добавляется в этот же класс — он наследует `_TmpDbCase`, который поднимает временный sqlite-файл и патчит `news_bot.DB_FILE` (строки 99–128).
2. Имя нового метода — ровно `test_move_to_published_idempotent_on_duplicate_link`. Регрессивная команда фичи:
   `pytest tests/test_pending_articles_repo.py -q -k "test_move_to_published_idempotent_on_duplicate_link"`.
3. В теле теста подними две последовательные публикации одного и того же `link` через `move_to_published`:
   - **Setup A.** Создай pending-строку `_sample_entry(link='http://m/idem')`, прогони `repo.insert_pending(entry)` + `self._stage(entry)` (helper класса `TestMoves`, строка 568, выставляет `ru_title='РуТ'` чтобы пройти `NOT NULL` на published-уровне).
   - **First call.** `repo.move_to_published(link, telegraph_url='https://telegra.ph/first', telegraph_path='first', via_review=False)`. После него pending пуст, published содержит одну строку с `via_review=0` и URL/path из first-вызова — это пред-условие шага 4.
   - **Re-stage.** Pending PK на `link` был удалён шагом DELETE первого вызова. Чтобы вызвать `move_to_published` второй раз, надо вернуть pending-строку с тем же `link`. Делай это **сырым SQL** через `self._conn()` — `INSERT INTO pending_articles (link, source_name, title, ru_title, paragraphs, telegraph_url, telegraph_path, fetched_at, attempt_count) VALUES (...)` со значениями второй публикации (`title2`, `ru_title2` и т. п.), commit, close. Помни: `published_articles.ru_title` имеет `NOT NULL` — pending-источник через шаг 0 (`SELECT title, ru_title, source_name, pub_date`) поставит ru_title в новую вставку, поэтому ru_title в re-staged строке должен быть строкой (любой непустой), даже если ты её не проверяешь.
   - **Second call.** `repo.move_to_published(link, telegraph_url='https://telegra.ph/second', telegraph_path='second', via_review=True)`. По контракту Task 2 — НЕ должно поднимать `sqlite3.IntegrityError`.
4. Asserts (строго все, в порядке логики):
   - Второй вызов завершился без исключения (нет `with self.assertRaises` — просто прямой вызов).
   - `repo.get_published(link)` вернул не-None словарь.
   - В `published_articles` ровно одна строка по этому `link`: `SELECT COUNT(*) FROM published_articles WHERE link=?` → `1`.
   - Сохранены **первичные** значения: `telegraph_url == 'https://telegra.ph/first'`, `telegraph_path == 'first'`, `via_review == 0`. Это тот самый litmus, который ловит регрессию `INSERT OR REPLACE` — она бы перезаписала на `second/second/1`.
   - `repo.get_pending(link)` вернул `None` (pending очищен вторым DELETE).
   - Опционально, для надёжности: `SELECT COUNT(*) FROM pending_articles` → `0` (общая чистота, не только по link).
5. Запусти smoke-команду из секции Verification Steps → Smoke. Должна сообщить о 1 пройденном новом тесте. Если она падает на этапе TDD до выполнения Task 2 — это ожидаемо; финальная зелёная проверка возможна только после landing Task 2 (Wave 1).

- `pending_articles_repo.py` — НЕ модифицируем (это test-only задача); читаем только пост-Task-2 версию для понимания пред-условия (строка 582 должна содержать `INSERT OR IGNORE INTO published_articles`). Если Task 2 ещё не применена — координируйся через wave-зависимость, но не правь репозиторный код в этой задаче.

**Dependencies:**
- Task 2 (Wave 1) — изменение `INSERT INTO published_articles` → `INSERT OR IGNORE INTO published_articles` в `pending_articles_repo.move_to_published`. Без него тест по определению будет падать на втором вызове с `sqlite3.IntegrityError` (UNIQUE на `link`). Wave-зависимость уже зафиксирована в frontmatter `depends_on: [2]`.
- pytest, sqlite3 (stdlib), unittest (stdlib) — всё уже есть в проекте.

**Edge cases:**
- `published_articles.ru_title` имеет `NOT NULL`. На re-stage pending-строки сырым SQL ОБЯЗАТЕЛЬНО клади непустой `ru_title`, иначе шаг 0 `move_to_published` (`SELECT title, ru_title, source_name, pub_date FROM pending_articles`) вернёт `None` для ru_title и шаг 1 при отсутствии `INSERT OR IGNORE` упал бы на NOT NULL вместо UNIQUE — а с `INSERT OR IGNORE` шаг 1 «потерян» (rowcount=0), но шаг 2 (`processed_news`) и шаг 3 (DELETE pending) пройдут штатно. Поведение остаётся корректным; просто следи, чтобы pending-строка не была вырожденной.
- Транзакция в `move_to_published` единая (`commit` в конце try-блока, `rollback` в except). `INSERT OR IGNORE` НЕ поднимает `IntegrityError` на UNIQUE — это документированное поведение SQLite. Не путать с `INSERT OR ABORT` (дефолт для `INSERT INTO`).
- Изоляция: каждый тест из `_TmpDbCase` стартует с tempfile-БД и удаляет её в `tearDown` (строки 102–125). Не трогай `news_bot.DB_FILE` напрямую — патч уже стоит.
- Параметры `move_to_published`: `link, telegraph_url, telegraph_path, via_review` — три последних именованные. `title/ru_title/source_name/pub_date` НЕ передаются — они читаются шагом 0 из pending-строки. Поэтому второй вызов «увидит» именно те `title/ru_title`, которые ты положил в re-staged pending-строку (но в published они не попадут из-за `INSERT OR IGNORE`).
- НЕ дублируй паттерны из `test_move_to_published_rollback_on_error` (WrappingConn-mocking) — для этого теста коннект-патч не нужен; sqlite-коннект нативно сделает то, что нужно.

**Implementation hints:**
- За образцом базовой структуры теста — смотри `test_move_to_published_atomic` (l. 577): то же `_sample_entry` + `insert_pending` + `_stage` + `move_to_published`.
- Для проверки `COUNT(*)` используй паттерн из самого файла (строки 177, 600–606): `with self._conn() as c: c.execute("SELECT COUNT(*) FROM published_articles WHERE link=?", (link,)).fetchone()[0]`.
- Имя ключа dict `pub` совпадает с колонками: `pub['telegraph_url']`, `pub['telegraph_path']`, `pub['via_review']` (см. `test_move_to_published_atomic`, l. 594–596).
- При re-stage используй ровно те же ключевые колонки, что и реальный insert_pending (см. `pending_articles_repo.py:insert_pending` для имён). Минимально достаточный набор — `link, source_name, title, ru_title, paragraphs`. `paragraphs` — JSON-строка (например `'[]'`); pending-схема хранит paragraphs как TEXT (JSON-строка), это видно в тесте `test_init_schema_is_idempotent` (l. 156–158): `('http://x/1', 'mattel', 't', '[]')`.
- Для контраста значений между первым и вторым вызовом используй явно разные строки (`'first'` vs `'second'`) — так фейл по `INSERT OR REPLACE` будет очевиден в diff ассерта.
