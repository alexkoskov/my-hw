# Task 3: Add 5 unit tests for the `_fallback_publish` guard

## Required Skills

Перед выполнением задачи загрузи:

## Description

Тесты на guard, добавленный в `_fallback_publish` в Task 1. Покрываем все четыре сценария входа в функцию через dominator-position семантику guard'а: Claude-path (default), outage-shortcut (line 1045), no-telegraph_url variant, плюс две проверки на admin-ping (что он действительно отправляется и что guard не падает, если ping вернул False).

Все 5 тестов расширяют существующий `_FallbackPublishPathsCase` базовый класс из `tests/test_fallback_publish_paths.py:90`, который уже даёт tempfile DB с инициализированной схемой, замоканные env-переменные (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID`, `TELEGRAM_ADMIN_ID`), и helper `_insert(...)` для добавления pending-строки.

Pre-staging уже опубликованной строки в `published_articles` делается raw SQL через `sqlite3.connect(self.db_path)` — паттерн скопирован из `tests/test_hw_review_publish_flow.py:271`. Это нужно потому, что у `pending_articles_repo` нет публичного helper'а для прямой записи в `published_articles` (move_to_published удаляет pending-строку — нам это не подходит, мы хотим именно «zombie» состояние: link есть и там, и там).

T1 включает `assertLogs` на `[idempotency-guard]` маркер — это литмус-тест по AC10 user-spec'а (operator должен иметь возможность грепать journalctl по этой строке).

T1 также включает позитивную проверку, что `transcreate_via_claude` НЕ был вызван — это доказывает dominator-position семантику guard'а (он стоит до любого из 4 branching points в `_fallback_publish`).

T2 критически важен: ловит регрессию, при которой guard поставлен ПОСЛЕ shortcut'а на line 1045 (`if outage_state.is_fallback_active(): ...`). Без guard'а перед этой веткой outage-day'и продолжали бы плодить дубликаты.

T3 проверяет, что guard срабатывает и для случая, когда у zombie-строки `telegraph_url=NULL` (то есть Telegraph ещё не был создан). Тут специфично проверяем, что `publish_article` (Telegraph CREATE branch) НЕ вызван — guard стоит до Telegraph-create, а не только до Telegraph-reuse.

T4 фиксирует, что admin ping действительно отправляется при срабатывании guard'а. Текст должен содержать "⚠️ Skipped re-publish of " и сам link.

T5 проверяет degraded-mode: `send_admin_notification` вернул False (Telegram down). Guard всё равно должен вызвать `skip_pending`, вернуть True и записать WARNING в лог. Это критично — никогда не возвращаем False из-за проблем с админ-каналом, т.к. это привело бы к strike-counting и в конечном итоге к ложному `move_to_failed`.

### T1 `test_skip_if_link_already_published_claude_path`

- Setup: pre-stage `published_articles` row + zombie pending row для одного и того же link; default Claude-OK мок.
- Call: `_fallback_publish(row, via_review=False)`.
- Negative side-effect asserts: `send_telegraph_teaser` NOT called; `publish_article` NOT called; `mark_telegraph_published` NOT called; `update_staged` NOT called; `move_to_published` NOT called; `transcreate_via_claude` NOT called.
- Cleanup asserts: pending row удалена (`repo.get_pending(link)` returns None); link присутствует в `processed_news` (raw SQL SELECT).
- Return: `assertTrue(result)`.
- Log marker (AC10): `with self.assertLogs('news_bot', level='INFO') as logs:` capture; assert один INFO-entry содержит `[idempotency-guard]` И сам link.

### T2 `test_skip_if_link_already_published_outage_shortcut_path`

### T3 `test_skip_if_link_already_published_no_telegraph_url`

- Specifically asserts: `publish_article` (Telegraph CREATE branch) NOT called — это доказывает, что guard стоит до Telegraph-create, не только до Telegraph-reuse.

### T4 `test_admin_ping_fires_when_guard_skips`

- Claude-path setup как в T1.
- Мокаем `news_bot.send_admin_notification` (default return True).
- Assert: `send_admin_notification.assert_called_once()`; вызван с текстом, содержащим `"⚠️ Skipped re-publish of "` И сам link (через `assertIn` на первом позиционном аргументе или через `call_args`).

### T5 `test_guard_continues_when_admin_ping_returns_false`

- Claude-path setup.
- Мокаем `news_bot.send_admin_notification` чтобы возвращал `False` (semantically соответствует реальной функции — она никогда не raises, возвращает bool).
- Assert: `skip_pending` всё равно вызван (через side-effect — pending row удалена, link в `processed_news`); функция вернула `True`; в логах есть WARNING-запись (например через `with self.assertLogs(level='WARNING')`).

**Edge cases:**
- В T1/T2/T3: убедиться, что мок `transcreate_via_claude` сделан с `side_effect=AssertionError(...)` — это сделает падение более понятным, если guard вдруг не сработает (вместо тихого продолжения flow).

- В T4: текст admin-ping'а проверять через `assertIn`, не через `assertEqual` — точная формулировка может содержать дополнительные символы (instance prefix, эмодзи), и тест не должен ломаться при незначительных изменениях формата.

- Изоляция между тестами: `setUp`/`tearDown` базового класса уже создаёт свежий tempfile DB на каждый тест — ничего дополнительно делать не нужно.
