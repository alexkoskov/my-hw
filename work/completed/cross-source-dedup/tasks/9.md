# Task 9: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Приёмочное тестирование фичи cross-source-dedup перед деплоем. Финальная контрольная точка после Waves 1-3 (реализация Tasks 1-5 + аудиты Tasks 6-8). Подтверждаем, что вся фича готова к выкладке: тестовый набор полностью зелёный без регрессий относительно baseline (1012 тестов на HEAD до начала фичи), все 12 пользовательских AC из `user-spec.md` и все 11 технических AC из `tech-spec.md` выполнены, бэкфилл-скрипт исполняется на свежей БД и выдаёт корректную сводку, контракт формы фингерпринта (`{"strict": [...], "brands": [...]}` — dict с двумя list-ключами) явно зафиксирован в отчёте как одобренное отклонение от первоначального user-spec AC1 (`list[str]`).

QA не пишет код — только запускает тесты, читает источники (тесты + код), сопоставляет с AC и формирует структурированный JSON-отчёт. Скрипт `backfill_fingerprints.py` запускается в режиме `--dry-run` против временной in-memory или fixture-БД (никаких записей в боевую БД). Никаких ревьюеров — отчёт сам по себе является результатом верификации, который читает оркестратор фичи перед запуском Task 10 (Deploy).

## What to do

1. **Прогнать полный тест-сьют.** Запустить `pytest -q` из корня репо. Зафиксировать суммарные числа: passed / failed / skipped / errors. Все тесты должны быть зелёными. Сверить с baseline на HEAD до начала фичи (≥1012 тестов проходило) — суммарное число тестов должно вырасти (за счёт новых файлов из Tasks 1-5), но число `failed` должно остаться 0. Если что-то падает — это критический финдинг, фича не готова к деплою.
2. **Проверить каждый пользовательский AC** (AC1-AC12 из `user-spec.md`). Для каждого: указать конкретный тест (имя файла + имя теста) или путь в коде, который реализует/доказывает критерий. Статус — `passed | failed | not_verifiable`. `not_verifiable` оставить для тех AC, которые требуют живого окружения, оператора в Telegram или 2-недельного мониторинга (это домен Task 11, post-deploy-qa).
3. **Проверить каждый технический AC** из секции `## Acceptance Criteria` техспека (11 критериев): идемпотентность ALTER TABLE при двойном `init_schema()`, schema-pin тесты (`EXPECTED_PENDING`, `EXPECTED_PENDING_COLUMNS`, `EXPECTED_PUBLISHED_COLUMNS`), общий зелёный `pytest -q`, отсутствие регрессий, performance budget (<10ms на 10KB body, <100ms на полный dedup-этап), отсутствие новых пакетов в `requirements.txt`, идемпотентность бэкфилла, рейт-лимит E016, миграция переживает двойной `init_db()` без шума в логах, `deploy.sh` FILES list содержит `model_extractor.py` и `backfill_fingerprints.py`, `backfill_fingerprints.py` импортирует `news_bot` ДО `logging.basicConfig()`.
4. **Запустить бэкфилл в dry-run против тестовой БД.** Команда: `python3 backfill_fingerprints.py --dry-run --days 1`. Проверить: exit code 0, в stdout присутствует summary-блок (Window / Processed / Skipped / Empty fp / Errors / Duration), никаких UPDATE-запросов не выполнено (dry-run контракт). Если в репозитории нет тестовой БД для запуска — создать временную пустую SQLite через скрипт init и прогнать на ней. Зафиксировать stdout-фрагмент summary в отчёте как evidence.
5. **Зафиксировать отклонение по форме фингерпринта.** Прочитать `decisions.md` и секцию `## User-Spec Deviations` техспека. Подтвердить, что переход с `list[str]` (user-spec AC1) на `dict[str, list[str]]` (`{"strict": [...], "brands": [...]}`) задокументирован, обоснован (нужна двухуровневая гранулярность для AC8/AC10) и явно одобрен оператором. В QA-отчёт включить это как note рядом с AC1 — `passed (deviation approved)`, evidence = ссылка на запись в `decisions.md` + параграф в техспеке.
6. **Coverage check.** Для каждого нового или модифицированного файла из `files_to_modify` Tasks 1-5 (`model_extractor.py`, `backfill_fingerprints.py`, `pending_articles_repo.py`, `admin_alerts.py`, `news_bot.py`, `deploy.sh`) подтвердить наличие соответствующего тестового файла. Для каждого AC со статусом `passed` — убедиться, что связанный тест реально упражняет поведение, а не просто импорт-чек.
7. **Сохранить отчёт.** Записать JSON-отчёт по форме из pre-deploy-qa skill в `work/cross-source-dedup/logs/working/task-9/qa-report.json`. Status `passed` если все AC зелёные и тесты зелёные; `failed` если есть хотя бы один critical-финдинг.
8. **Финальный вердикт.** В summary к decisions.md записать 1-3 предложения: общий статус (`passed | failed`), число AC по статусам, ссылка на JSON-отчёт, флаги для оператора (если есть). Если status=failed — фича НЕ идёт в Task 10 (Deploy), оркестратор должен открыть corrective wave.

## Verification Steps

### Automated
- `pytest -q` → 0 failed, 0 errors; число passed ≥ 1012 + новые тесты из Tasks 1-5
- `pytest tests/test_model_extractor.py -v` → TestExtractFingerprint + TestSimilarity + test_calibration_accuracy (≥7/8) + test_calibration_real_pair_must_pass — все зелёные

### Smoke
- `python3 backfill_fingerprints.py --dry-run --days 1` против свежей тестовой БД → exit code 0; stdout содержит summary-блок (Window / Processed / Skipped / Empty fp / Errors / Duration); ни одного UPDATE в БД (dry-run)
- `python3 -c "import sqlite3, pending_articles_repo; conn=sqlite3.connect(':memory:'); pending_articles_repo.init_schema(conn); pending_articles_repo.init_schema(conn); cols=[r[1] for r in conn.execute('PRAGMA table_info(pending_articles)')]; print('model_fingerprint' in cols)"` → `True`, без эксепшенов (двойная миграция идемпотентна, AC10)
- `python3 -c "from model_extractor import extract_fingerprint; print(extract_fingerprint({'title':'2018 Toyota 4Runner gold chase', 'subtitle':'', 'paragraphs':['Subaru Legacy GT (BP).']}))"` → strict содержит `toyota 4runner` и `subaru legacy gt`, brands содержит `toyota` и `subaru`
- `grep -E "model_extractor.py|backfill_fingerprints.py" deploy.sh` → обе строки найдены в FILES list
- `python3 -c "import ast; src=open('backfill_fingerprints.py').read(); tree=ast.parse(src); ...` или визуальная проверка верха `backfill_fingerprints.py` → `import news_bot` ВЫШЕ `logging.basicConfig(...)`
- `python3 -c "import pkg_resources; ..." ` или `diff` `requirements.txt` против `git show HEAD:requirements.txt` (предфичевого baseline) → различий нет (AC: без новых пакетов)

**Edge cases / на что обратить внимание:**
- Несколько AC из user-spec требуют живого окружения / Telegram / мониторинга (AC оператора в секции «Как проверить → Пользователь проверяет»). Они должны иметь статус `not_verifiable` с указанием «scope of Task 11 post-deploy-qa», а не `failed`.
- AC1 («`list[str]`») формально не совпадает с реализацией — это известное одобренное отклонение. Статус: `passed (deviation approved)` с ссылкой на запись в `decisions.md`/`tech-spec.md ## User-Spec Deviations`.
- AC11 backfill: user-spec предполагал чтение `paragraphs` из `published_articles`, реализация — re-fetch через `fetch_full_article` (Decision 10). Тоже одобренное отклонение, та же пометка.
- Performance budget (<10 ms на 10 KB body, <100 ms на полный dedup-этап на статью) в tech-spec заявлен качественно (Decision 3 объясняет, что нет жёстких wall-clock assertions в CI чтобы избежать flakiness). QA-отчёт фиксирует это как `not_verifiable` через прямые wall-clock (структурная гарантия через bounded quantifiers + Decision 3 review) — критерий считается выполненным конструктивно, а не измерением.
- Если в `pytest -q` есть `skipped` тесты — каждый должен иметь явный `@pytest.mark.skip(reason=...)` или conditional skip; немотивированные skip — major finding.
- Если число тестов выросло слишком слабо (<+20) — возможно Task 4/Task 5 пропустили часть сценариев; major finding к coverage.

**Implementation hints:**
- Для быстрой проверки baseline: `git log --oneline | head -20` чтобы найти HEAD до начала фичи, потом `git show <sha>:requirements.txt > /tmp/req-baseline.txt && diff /tmp/req-baseline.txt requirements.txt` — должен быть пустой diff (AC: без новых пакетов).
- При записи JSON-отчёта использовать абсолютные пути в evidence (например, `tests/test_model_extractor.py::TestSimilarity::test_empty_fingerprint_returns_zero` для AC6).
- Если `qa-report.json` уже существует от предыдущей попытки — перезаписать.
- Команды запускать из корня репо (`/workspaces/debian-2/my-hw/`), не из `work/cross-source-dedup/`.
- Категории severity для финдингов: `critical` (AC failed, тесты упали), `major` (AC works но с edge-case проблемами), `minor` (косметика). Любой `critical` → итоговый status=failed → НЕ переходим к Task 10.
