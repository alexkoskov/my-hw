## Description

Полнофункциональный security-аудит фичи cross-source-dedup. Аудитор сам по себе является ревью этой задачи — отдельных reviewers нет (см. фронтматтер `reviewers: []`). Цель — найти и зафиксировать все уязвимости в коде, написанном/изменённом в Wave 1-2 (Tasks 1-5), прежде чем фича пойдёт в pre-deploy QA (Task 9). Аудит охватывает:

- **SSRF-поверхность backfill-скрипта** — `backfill_fingerprints.py` собирает `entry_stub` и передаёт его в `news_bot.fetch_full_article`. Нужно убедиться, что stub-форма (минимальный набор полей, link-формат) совпадает с ожиданиями `fetch_full_article` и не открывает дополнительный канал для SSRF (подмена схемы, internal-host, `file://`).
- **ReDoS-верификация regex** — Decision 3 заявляет «bounded quantifiers, anchored, ReDoS-safe». Аудитор валидирует каждый паттерн в `model_extractor.py` против реальных правил (нет вложенных безграничных жадных квантификаторов, граничные кейсы `{0,24}`/`{0,2}`/`{1,2}` корректны, нет catastrophic backtracking на 10KB body).
- **SQL injection в новых helper-ах** — все 7 новых функций в `pending_articles_repo.py` (`list_recent_pending_fingerprints`, `list_recent_published_fingerprints`, `update_published_fingerprint`, `is_pair_rate_limited`, `mark_pair_pinged`, `is_dedup_degraded_rate_limited`, `mark_dedup_degraded_pinged`) должны использовать только параметризованные запросы (`?` placeholders), без f-string/`%`/конкатенации.
- **Секреты в admin-ping шаблонах E014/E015/E016** — ни в одном из трёх builder-ов не должно протекать ничего из секретов (API-токены, ENV-имена, URL с credentials). Проверить, что `_TokenRedactingFilter` всё ещё работает после изменений в `news_bot.py` и `backfill_fingerprints.py`.
- **Rendering injection через link content в пингах** — `new_link`/`existing_link` приходят из источников (autoevolution, t-hunted, и т. д.). Operator-trusted — но проверить, что они не ломают Telegram parse mode (HTML/MarkdownV2 escaping), не позволяют инъекцию управляющих символов.

Выход — отчёт `work/cross-source-dedup/logs/audits/security-audit.md` с разделами по каждому фокусу, перечнем находок (severity: HIGH/MED/LOW), и явным сигналом PASS/FAIL по фиче в целом.

## Details

**Files (read-only):**
- `model_extractor.py` — проверить bounded quantifiers (`{1,2}`, `{0,24}`, `{0,2}`), case-sensitivity split (BMW/AMC/Lotus — case-sensitive по Decision 3 §14.A.3), anchored single-pass alternation regex.
- `backfill_fingerprints.py` — `entry_stub` shape (какие поля в stub, валидируется ли link перед передачей в `fetch_full_article`); import order (`import news_bot` ДО `logging.basicConfig()` — security-review caveat 5).
- `pending_articles_repo.py` — все 7 новых helper-ов: убедиться что используется `?` parametrization для `link`/`days`/`window_days`/`new_link`/`existing_link`. Особое внимание: bot_state key `softflag_pair:{new_link}\n{existing_link}` — newline-separator, но это VALUE-shape, не SQL — не injection-vector, но проверить экранирование в parse-back.
- `admin_alerts.py` — три builder-а E014/E015/E016: проверить что не форматируют через `str(exc)` (только `type(exc).__name__` для E016), что link-текст не ломает Telegram parse_mode (HTML escape или plain mode).
- `news_bot.py` — `_check_cross_source_dedup` обёрнут в broad `except Exception` (Decision 12). Проверить что в except не утекает `str(exc)` в ping (security pattern из существующего кода). `mark_processed` вызывается до E015 — проверить порядок.

**Dependencies:**
- Зависит от Task 4 (news_bot.py wiring) и Task 5 (backfill_fingerprints.py) — финальный код этих задач должен быть в дереве к моменту запуска аудита (wave 3, после wave 2).
- НЕ зависит от Task 6 (Code Audit) и Task 8 (Test Audit) — все три аудита запускаются параллельно в wave 3.

**Edge cases для проверки:**
- ReDoS: synthetic body 10KB с adversarial pattern (`A` * 10000 + `Toyota X` * 1000) — не должен висеть >100ms.
- SSRF: `entry_stub['link'] = 'file:///etc/passwd'` или `'http://169.254.169.254/...'` — должен отклоняться `fetch_full_article` (унаследованная защита) ИЛИ источник stub не позволяет такой формат.
- SQL: `link = "'; DROP TABLE pending_articles; --"` — параметризация должна полностью защитить.
- Secret leak: API-токен в `os.environ` — `_TokenRedactingFilter` должен срезать его из любого log-сообщения, включая backfill stdout summary.
- Rendering: link с `<script>` или `*bold*` — Telegram parse_mode plain → текст экранируется; если parse_mode HTML — должен пройти HTML-escape.

**Implementation hints (для аудитора):**
- Используй `grep -n "execute" pending_articles_repo.py | grep -v "?"` для быстрого поиска не-параметризованных SQL.
- Используй `python3 -c "import re, time; rx=re.compile(...); t=time.time(); rx.search('A'*10000); print(time.time()-t)"` для эмпирической ReDoS-проверки (на новых regex'ах из `model_extractor.py`).
- Сравни E014/E015/E016 builder pattern с уже-существующим E006 (`alert_mattel_publish_failure` — последний раз ревьюился ~2026-04). Если форма дрейфует — это сигнал.
- Token redaction: `grep -n "_TokenRedactingFilter\|_SECRET_ENV_NAMES" news_bot.py admin_alerts.py` — убедиться, что filter не обходится новыми ping-путями.
