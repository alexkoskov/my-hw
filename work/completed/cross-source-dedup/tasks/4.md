# Task 4: Wire dedup gate in news_bot.job() + integration tests

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Подключаем готовый cross-source dedup в основной пайплайн бота. Wave 1 уже дала чистые модули — `model_extractor.extract_fingerprint/similarity` (Task 1), новые helpers в `pending_articles_repo` (Task 2) и три алёрт-билдера `E014/E015/E016` (Task 3). Эта задача — последний интеграционный шов: внутри `news_bot.job()` появляется приватный helper `_check_cross_source_dedup(article, fp, conn) -> tuple[str, dict | None]`, который вызывается между `_is_text_only_checklist` и сборкой `row` (позиция определена Decision 14). Вся логика обёрнута в `try/except Exception` (Decision 12, AC9) — любой сбой extract/similarity/repo не блокирует публикацию, статья проходит дальше с `model_fingerprint=None`, а оператор получает rate-limited E016.

Три ветки решения:
- **hard-block** (`('block', match)`): вызвать `mark_processed(link, title, pub_date)` (Decision 8 — линк попадает в `processed_news` навсегда, чтобы не пересчитывать дубль на каждый тик), отправить короткий `[E015]` ping, `continue`.
- **soft-flag** (`('flag', match)`): проверить `is_pair_rate_limited(conn, new_link, existing_link)`, если нет — отправить полный `[E014]` и `mark_pair_pinged`. Статья при этом проходит дальше — fingerprint попадает в `row['model_fingerprint']`.
- **degraded** (исключение): `logger.exception("dedup gate failed, degraded mode active")`, если `is_dedup_degraded_rate_limited(conn)` False — отправить `[E016]` и `mark_dedup_degraded_pinged`, выставить `fp = None`, пройти дальше.

Параллельно пишем интеграционные тесты: 7 сценариев в `TestCrossSourceDedup` (на базе `_PrepPhaseBase` — он уже мокает `_fallback_publish` и `time.sleep`, изолируя prep-фазу) плюс отдельный `TestFingerprintCarryThrough`, который проверяет AC2 — fingerprint, записанный в `pending_articles`, не теряется при `move_to_published` и доступен в `published_articles`.

## What to do

1. Добавить приватный helper `_check_cross_source_dedup(article, fingerprint, conn) -> tuple[str, dict | None]` в `news_bot.py`. Helper читает `pending_articles_repo.list_recent_pending_fingerprints(conn, 7)` и `list_recent_published_fingerprints(conn, 7)`, итерирует по всем кандидатам, вычисляет `model_extractor.similarity(fingerprint, candidate_fp)`, отдаёт лучший match по порогам: `≥0.50` → `('block', match_dict)`, `0.30-0.49` → `('flag', match_dict)`, иначе `('pass', None)`. `match_dict` содержит как минимум `link`, `source_name`, `models` (для рендеринга в E014), `overlap_pct` (целое, округлённое), `n_matches`, `n_total`. Пустой fingerprint (`strict=[]`) сразу возвращает `('pass', None)` — никаких запросов в БД.
2. Найти позицию вставки в `news_bot.job()` — между `if _is_text_only_checklist(...)` (около строки 1810-1815) и `row = {...}` (около строки 1817). Вставить туда блок dedup gate.
3. Реализовать ветки решения:
   - В блоке `try`: открыть собственное соединение через `conn = pending_articles_repo._connect()` (приватный helper в `pending_articles_repo.py:155`; в `job()` нет ambient `conn` — каждый существующий вызов репо открывает своё соединение per-call, мы следуем тому же стилю). Имя источника НОВОЙ статьи (для E014 `new_source`) вычисляется как `entry.get('source_name') or _resolve_source_name(link)` — это та же формула, что в сборке `row` на строке 1819 (`row_source` ещё не существует, dedup-гейт стоит ДО сборки `row`). Имя источника СУЩЕСТВУЮЩЕЙ статьи берётся из matched fingerprint row — `match['source_name']` (там колонка `source_name` уже лежит). Отправить, вызвать `pending_articles_repo.mark_pair_pinged(conn, link, match['link'])`. Статья проходит дальше — fingerprint сохраняется.
   - На `'pass'`: ничего не делать, fingerprint попадёт в `row`.
4. Обернуть весь блок в `try/except Exception as exc` (Decision 12 — широкий handler намеренный). В `except`: `logger.exception("dedup gate failed, degraded mode active")`, проверить `is_dedup_degraded_rate_limited(conn)` — если False, собрать `alert_dedup_degraded(type(exc).__name__)`, отправить, вызвать `mark_dedup_degraded_pinged(conn)`. Использовать паттерн мокинга из `TestIntegration::test_full_pipeline_with_multiple_feeds` (мокать `load_feeds`, `fetch_rss`, `fetch_full_article`, `send_admin_notification`).

**Dependencies:**
- Task 1: `model_extractor.extract_fingerprint`, `model_extractor.similarity` — модуль и сигнатуры готовы.
- Task 2: новые helpers в `pending_articles_repo` (`list_recent_*_fingerprints`, `update_published_fingerprint`, `is_pair_rate_limited`, `mark_pair_pinged`, `is_dedup_degraded_rate_limited`, `mark_dedup_degraded_pinged`), `insert_pending` принимает `model_fingerprint`, schema migration применена.
- Task 3: `admin_alerts.alert_cross_source_dupe` (E014), `alert_cross_source_blocked` (E015), `alert_dedup_degraded` (E016).

**Edge cases:**
- Пустой fingerprint (`{'strict':[],'brands':[]}`): `_check_cross_source_dedup` должен сразу вернуть `('pass', None)` без обращения к БД — оптимизация и защита от ложных совпадений на пустых наборах (similarity на пустых → 0.0 по Decision 4, но лишний SQL-запрос не нужен).
- Одна и та же пара (new_link, existing_link) — порядок аргументов в `is_pair_rate_limited`/`mark_pair_pinged` сохранять стабильно: new_link первым, existing_link вторым. Tech-spec Decision 6 key: `softflag_pair:{new_link}\n{existing_link}`.
- Hard-block в том же тике, когда статья уже была в `pending_articles` (race с другим тиком): после `mark_processed` следующий `pending_repo.insert_pending` всё равно не вызывается (мы делаем `continue`), но если бы вызвался — UNIQUE conflict бы отловился существующим `try/except`. Race safe.
- Within-source dedup (Decision 9): тест должен явно проверить, что фильтрации по `source_name` НЕТ. Это защищает от будущей "оптимизации" "не сравнивать с собственным источником".
- `logger.exception` в degraded ветке выводит полный traceback — это требование Decision 12 для диагностики.
- E016 rate-limit окно — 1 час; тест на degraded mode должен проверить, что повторный вызов `job()` в том же часе НЕ шлёт второй E016 (через `mock_admin_notification.call_count`).

**Implementation hints:**
- `conn` в `job()` — в `pending_articles_repo.py` ВСЕ публичные функции открывают своё соединение per-call через приватный `_connect()` (строка 155 — `def _connect() -> sqlite3.Connection`). Никакого `_get_conn()` в кодовой базе НЕТ. В `job()` тоже нет ambient `conn`. Для dedup-гейта открыть собственное соединение: `conn = pending_articles_repo._connect()` в начале try-блока, передавать его явно во все новые helpers (Task 2 уже принял такую сигнатуру: `is_pair_rate_limited(conn, ...)`). Соединение закрывать в `finally` блоке (или через `with` — sqlite3.Connection — context manager только для транзакций, лучше явный `conn.close()` в finally).
- Source-name на позиции гейта: переменной `row_source` ещё НЕ существует (она появляется только при сборке `row` на ~строке 1817, dedup-гейт стоит ВЫШЕ). Для E014 `new_source` использовать ту же формулу, что строка 1819 уже использует для `row['source_name']`: `entry.get('source_name') or _resolve_source_name(link)`. Это source НОВОЙ (текущей) статьи. Source EXISTING (matched) статьи — берётся из колонки `source_name` matched fingerprint row, т.е. `match['source_name']`, которое `_check_cross_source_dedup` обязан положить в match_dict.
- При сборке `match_dict` для E014: `models` — список строк для отображения; можно собрать как объединение `match_fp['strict']` или пересечение с `fp['strict']` (последнее точнее показывает "что именно совпало"). Tech-spec Decision 7 не фиксирует строго; следовать примерам из code-research §14.K.
- `overlap_pct` — целое число 0-100, округлённое от `similarity() * 100`. Используется в E014 и E015 для рендеринга.
- В тесте `test_empty_fingerprint` мокать `model_extractor.extract_fingerprint` через `patch('news_bot.model_extractor.extract_fingerprint', return_value={'strict':[],'brands':[]})` чтобы избежать зависимости от точной работы extractor — это интеграционный тест gate-ветки, а не extractor.
- В `test_degraded_mode` пропатчить `extract_fingerprint` на `side_effect=RuntimeError("boom")`. Проверить вызов `mock_admin_notification` с аргументом, содержащим `[E016]` и `RuntimeError`.
- Для `TestFingerprintCarryThrough` использовать `_IntegrationBase` (не `_PrepPhaseBase`), потому что тест не запускает `job()` — он напрямую дёргает `insert_pending` → `move_to_published` → SELECT.
