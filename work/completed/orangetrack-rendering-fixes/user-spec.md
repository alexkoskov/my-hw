# User Spec: Orangetrack Rendering Fixes

## Что делаем

Чиним три visual-бага в публикации статей с `orangetrackdiecast.com`, обнаруженных оператором при пост-деплой наблюдении канала:

1. Пункты bullet-списков (`<ul><li>`) не появляются в публикации — теряются при парсинге.
2. Секционные подзаголовки (`<h2>`/`<h3>`/`<h4>`) сливаются с обычным текстом — визуально неотличимы.
3. Внутритекстовые ссылки на каноничные страницы того же сайта стираются — становятся plain text.

## Зачем

7 мая 2026 года оператор открыл `@myhwchannel123` и увидел свежую orangetrack-статью «Modern Classics S CASE REPORT» — но без главного: списка моделей в кейсе («'94 NISMO 270R (S14)», «Ferrari Testarossa», «Toyota Soarer», «Porsche 993 GT2», «Mazda 323 GTR», «Mercedes-Benz 190 E 2.5-16 EVO II»). Это буквально суть статьи; без списка читатель не понимает, о чём она. Аналогично — подзаголовки секций в обзорной статье «Airwolf Helicopter», «'66 Porsche 906 Carrera 6», «Cobra H.I.S.S.» идут плоским текстом, без визуального выделения. И ссылки на каноничные страницы моделей (например, «Mercedes-Benz 190E 2.5-16 EVO II» в текстe ведёт на orangetrackdiecast.com/.../mercedes-evo) превращаются в plain text — пропадает связность с источником.

Все три бага — на каждой orangetrack-публикации. Канал теряет в качестве как curated news source.

**Контекст ранее принятых решений (SESSION-2026-05-06.md, фикс `babc67c`):** на orangetrack встречаются `<h5>`-маркеры внутри параграфов как in-paragraph section dividers. При прежней логике их рендер с `<h3>`-стайлингом выглядел визуально неровным. Поэтому ВСЕ h-теги стали эмититься как paragraph. Этот фикс остаётся в силе для `<h5>` — мы исправляем только over-application к `<h2>/<h3>/<h4>`, которые на orangetrack играют роль настоящих section headers, не in-paragraph markers.

## Как должно работать

**Сценарий A — статья со списком моделей (Bug 1):**
1. Источник содержит `<ul><li>'94 NISMO 270R (S14)</li><li>Ferrari Testarossa</li>…</ul>` (или `<ol>` — упорядоченный список).
2. После пайплайна каждый пункт списка появляется в Telegraph-публикации как отдельный абзац с маркером **«• »** в начале (буллит-префикс — потому что Telegraph API не поддерживает `<ul>/<li>`, только `<p>`/`<h3>`/`<h4>`).
3. Маркер вставляется на этапе **рендера в Telegraph** (после LLM-перевода), чтобы LLM не имел возможности стереть/перевести его. RU-перевод текста пункта остаётся как есть; буллит-префикс добавляется поверх.

**Сценарий B — статья с секционными подзаголовками h2/h3/h4 (Bug 2):**
1. Источник содержит `<h3>Airwolf Helicopter (Airwolf)</h3>` (или `<h2>` / `<h4>`).
2. После пайплайна подзаголовок появляется в Telegraph-публикации как **визуально выделенный блок** (крупный/жирный шрифт). Все уровни h2/h3/h4 получают одинаковое визуальное выделение — единая иерархия секций.
3. **Особый случай — `<h5>`** (in-paragraph markers): продолжают идти обычным текстом, как сейчас. Это сохраняет фикс `babc67c` от 2026-05-06 для статей с `<h5>`-маркерами внутри тела (см. SESSION-2026-05-06.md).

**Сценарий C — статья с внутритекстовыми ссылками (Bug 3):**
1. Источник содержит абзац вида: «The [Mercedes-Benz 190E 2.5-16 EVO II](orangetrack-link) debuted in the very first [Modern Classics](external-link) series for [Car Culture](orangetrack-link).»
2. Парсер сохраняет ссылки как metadata к блоку (как сейчас).
3. После LLM-перевода текст абзаца — на русском, ссылки остаются на английском (metadata).
4. На этапе рендера в Telegraph, для каждой ссылки в metadata:
   - Если домен ссылки = `orangetrackdiecast.com` (с любым из `www.`-префиксов или без), И ровный английский текст ссылки точно встречается в RU-тексте абзаца — оборачиваем **первое** вхождение в кликабельную `<a href>`-ноду; остальные совпадения (если есть) остаются plain text.
   - Если домен другой — ссылку не рендерим (текущее поведение).
   - Если EN-текст ссылки не находится в RU-тексте (LLM перевёл фразу) — ссылку не рендерим, plain text.

**Сценарий D — нормальные публикации других источников (не должны регрессить):**
Парсеры autoevolution, lamley, mattel и архивный hw_review не наполняют ссылочные metadata — для них фикс ничего не меняет; их рендер блоков работает как раньше.

## Критерии приёмки

- [ ] **AC1.** В Telegraph-публикации orangetrack-статьи каждый `<li>`-пункт из исходной `<ul>` или `<ol>` отображается как отдельный абзац, начинающийся с буллит-маркера «• ». Пустые `<li>` пропускаются. Вложенные внутри `<li>` теги (`<a>`, `<strong>` и т.п.) сохраняются как часть текста пункта (то же поведение, что для `<p>`).
- [ ] **AC2.** Буллит-маркер «• » для пунктов списков **гарантированно присутствует в финальной публикации** — он добавляется в публикатор Telegraph после LLM-перевода, а не в парсере до перевода (защита от того, что LLM в RU мог бы потерять/перевести буллит).
- [ ] **AC3.** В Telegraph-публикации orangetrack-статьи подзаголовки уровней `<h2>`, `<h3>`, `<h4>` отображаются как **визуально выделенные блоки** (крупный/жирный шрифт). Все три уровня получают одинаковое визуальное выделение — единая иерархия (нет «h2 крупнее, h4 мельче»).
- [ ] **AC4.** Подзаголовки уровня `<h5>` продолжают рендериться как обычный текст (paragraph) — поведение из фикса `babc67c` сохраняется для совместимости с in-paragraph markers (см. SESSION-2026-05-06.md).
- [ ] **AC5.** Подзаголовки уровней `<h1>` и `<h6>` — игнорируются (как сейчас): h1 уже использован для title, h6 редкий/декоративный.
- [ ] **AC6.** Ссылки на домен `orangetrackdiecast.com` в текстe абзацев orangetrack-статей становятся **кликабельными в Telegraph-публикации**, при условии что точный английский текст ссылки сохранился в русском переводе. Match — case-sensitive, точное вхождение, оборачивается **первое** вхождение в абзаце.
- [ ] **AC7.** Ссылки с другим доменом (не `orangetrackdiecast.com`) **не рендерятся** в публикации — продолжают становиться plain text (текущее поведение, не меняется).
- [ ] **AC8.** Если английский текст ссылки **не находится** в русском тексте абзаца (LLM перевёл фразу, например «Modern Classics» → «Современная классика»), ссылка **не рендерится** (silently drop) — НИ как клик, НИ как ошибка. Plain text.
- [ ] **AC9.** Edge-cases ссылок не падают: пустой/отсутствующий href, malformed URL, regex/специальные символы в тексте ссылки, две ссылки с одинаковым href, runs с пустым текстом, перекрывающиеся substring-ы — всё обрабатывается без exceptions; в худшем случае ссылка просто не рендерится.
- [ ] **AC10.** Все существующие тесты в `tests/test_orangetrack_source.py`, `tests/test_telegraph_publisher.py` и других файлах остаются зелёными — никаких регрессий ни для других источников (autoevolution, lamley, mattel, hw_review), ни для базовых orangetrack-сценариев без `<li>`/headings/links.
- [ ] **AC11.** End-to-end проверка: синтетическая orangetrack-статья с `<ul><li>`, `<h3>`, и `<a href>`-ссылками — пройдя полный пайплайн (парсинг → симуляция LLM-перевода → Telegraph-рендер), производит ноды, в которых: каждый пункт списка — `<p>` с буллитом, каждый `<h3>` — `<h3>`-нода, абзацы со ссылками к orangetrackdiecast.com содержат inline `<a>`-ноды для найденных substring-ов.

## Ограничения

- **Без изменений схемы БД** — все существующие таблицы сохраняют структуру.
- **Без новых внешних зависимостей** — используем только stdlib (`urllib.parse` для domain comparison, уже импортирован).
- **Минимально-инвазивно** — меняем только: `orangetrack_source.py` (парсинг `<li>`/headings), `telegraph_publisher.py` (рендер runs + буллит-вставка для list-items), и возможно `_llm_common.py` (добавить новый block-type в список «patchable», если решим разделять list_item от paragraph). Точные файлы — в tech-spec.
- **Архивный `hw_review.py` не трогаем** — он не вызывает этот код в cron-пути.
- **Other parsers (autoevolution/lamley/mattel) не трогаем** — фикс target'ит orangetrack-специфичную обработку.
- **Деплой комбинированный** с уже-залипшим `publish-idempotency-fix` на `dev`. Один merge `dev → main` → один prod-релиз с обоими фиксами.

## Риски

- **Риск 1 — Bug 2 reversal затрагивает прежнее решение `babc67c`.** **Митигация:** AC4 явно сохраняет old behavior для `<h5>` (h5 остаётся paragraph); AC3 ограничивает фикс уровнями h2/h3/h4 (которые на orangetrack играют роль section headers, а не in-paragraph markers). Перед коммитом — ручная проверка существующих тестов и сценариев из SESSION-2026-05-06.md.
- **Риск 2 — Bug 3 fuzzy match может дать false positives** в редких случаях (две модели с одинаковыми названиями в одном абзаце). **Митигация:** AC6 — точное (case-sensitive) substring, оборачиваем только первое вхождение; LLM-перевод не меняет позицию модели в RU-тексте; brand names обычно уникальны в одном абзаце.
- **Риск 3 — Bug 3 теряем external ссылки.** **Митигация:** сознательное решение MVP (AC7): рендерить external ссылки — это отдельная Phase-2 задача (cross-article linking). Subscriber видит обогащённый same-site experience.
- **Риск 4 — Bug 3 fragile: при смене LLM или сильно агрессивном переводе some Latin proper nouns могут не сохраниться.** **Митигация:** AC8 — silently drop, never crash. Альтернативный архитектурный подход (sentinel-token: заменять run.text на маркер ДО LLM, восстанавливать ПОСЛЕ) рассмотрен и отложен — требует изменений в `_llm_common`-инфраструктуре, расширяет scope из M в L. Может стать отдельной Phase-2 фичей если substring-подход окажется недостаточным.
- **Риск 5 — регрессия существующих тестов.** **Митигация:** AC10 явно требует green; перед коммитом — полный pytest на `tests/test_orangetrack_source.py`, `tests/test_telegraph_publisher.py`, `tests/test_distributed_schedule_integration.py`.

## Технические решения

- **Буллит-маркер «• » добавляется в Telegraph-публикаторе после LLM-перевода**, не в парсере до перевода. Reason: это гарантирует, что маркер точно попадёт в финальный артикль; LLM в любых обстоятельствах не имеет возможности его удалить или перевести.
- **Все heading-уровни h2/h3/h4 → единое визуальное выделение** (один уровень, не двухуровневая иерархия). Reason: на orangetrack обычно один уровень секционирования (модель = секция); двухуровневая визуальная иерархия избыточна.
- **`<h5>` остаётся paragraph** — фикс `babc67c` от 2026-05-06 сохраняется. Reason: h5 на orangetrack используется как in-paragraph markers, не section headers; их рендер с big-bold typography делает статью неровной.
- **Same-site domain check — только `orangetrackdiecast.com`** (с/без `www.`-префикса). Reason: парсеры autoevolution/lamley/mattel не наполняют runs metadata — universal-проверка добавит мёртвой логики.
- **Substring approach (не sentinel-token).** Reason: MVP, минимально инвазивно; меняет только парсер и публикатор, не задевает `_llm_common` инфраструктуру. Sentinel-token может быть Phase-2 если потребуется.
- **При повторе run.text — оборачиваем первое вхождение.** Reason: original run был в первой позиции в EN; first-match — наиболее предсказуемое поведение.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.

- В `tests/test_orangetrack_source.py`: `<li>` парсинг (нормальный пункт, пустой пункт, пункт с вложенными тегами, `<ol>`); `<h2>`/`<h3>`/`<h4>` → выделенный block-type; `<h5>` остаётся paragraph (regression).
- В `tests/test_telegraph_publisher.py`: рендер блоков с runs (same-site → `<a>`, external → drop, run.text не в block.text → drop, повторы → first only, edge cases — пустой href, malformed URL, спецсимволы); рендер list-items с буллитом; рендер headings.

**Интеграционные тесты:** делаем минимум 1 — синтетический orangetrack HTML с `<ul><li>`, `<h3>`, `<a href>` → парсинг → симуляция LLM-перевода → Telegraph-рендер → asserts на финальные ноды.

**E2E тесты:** не делаем — у нас нет E2E-инструментов кроме pytest. Integration test покрывает всю цепочку с моками.

Конкретные имена тест-функций, файлы, и assertion-структура — в tech-spec.
