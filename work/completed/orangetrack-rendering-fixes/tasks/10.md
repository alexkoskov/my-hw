## Description

Двухстадийный деплой фичи `orangetrack-rendering-fixes` через существующий CI/CD pipeline (`ci.yml` → `deploy_test.yml` → `deploy.yml`). Фича стэкается поверх `publish-idempotency-fix`, которая уже на `dev` — значит коммиты этой фичи уже в дереве `dev`, и push на `origin dev` запустит тестовый деплой; merge `dev → main` запустит prod-деплой.

**Stage 1 (test):** `git push origin dev` → `ci.yml` (pytest на 829+ тестов) → `deploy_test.yml` (SCP в `/home/hwbot/bot_test/`, restart `news_bot_test.service`) → оператор наблюдает тестовый канал `@myhwchannel123` ~30 минут на ближайшем тике 10:00 МСК или вручную рестартит сервис, чтобы триггернуть `job()` сразу. Цель — глазами увидеть на свежем orangetrack-посте, что три бага действительно исправлены: маркеры списков, h3-заголовки, кликабельные same-site ссылки.

**Stage 2 (prod):** только после визуального подтверждения оператором — `git checkout main && git merge dev && git push origin main` → `deploy.yml` → SCP в `/home/hwbot/bot/`, restart `news_bot.service`.

Per memory rule: Claude готовит инструкции и проверяет CI, оператор сам выполняет git push / SSH. Никакого кода в этой задаче нет — только координация двухстадийного деплоя.

**Важно:** одноразовая SQL-операция `DELETE FROM failed_articles` (для строки `team-transport-k`) — это deploy-задача фичи `publish-idempotency-fix`, отдельная сущность; в эту задачу НЕ включается.

## Details

**Files:** изменений в репо нет. Этой задаче нужны только git-операции и наблюдение за workflow.

**Dependencies:**
- Task 9 (pre-deploy QA) должна быть `done` — все тесты локально зелёные.
- `publish-idempotency-fix` уже на `dev` (предыдущая фича-стэк); коммиты `orangetrack-rendering-fixes` стэкаются поверх.
- GitHub Actions secrets уже настроены (`SSH_HOST`, `SSH_USER`, `DEPLOY_PATH`, `DEPLOY_PATH_TEST`, `SSH_PRIVATE_KEY`, `ANTHROPIC_API_KEY`) — менять не нужно.
- Server-side sudoers `/etc/sudoers.d/news_bot` уже разрешает hwbot рестартовать оба сервиса без пароля — менять не нужно.

**Edge cases:**
- **CI failure on dev:** если `ci.yml` падает — `deploy_test.yml` не запустится. Изучить логи `gh run view <id> --log-failed`, поправить, повторить.
- **deploy_test.yml restart fails:** обычно из-за отсутствия sudoers NOPASSWD-правила. В нашей инфре оно стоит — но если внезапно отвалилось, в логах будет hint про `/etc/sudoers.d/news_bot` (см. `deployment.md`).
- **`news_bot_test.service` не стартует после deploy:** оператор смотрит `journalctl -u news_bot_test.service --since '<deploy time>' -n 100`. Самый частый случай — отсутствующий env var (но в этой фиче новых env vars нет, поэтому маловероятно).
- **На тестовом канале не появляются свежие orangetrack-посты в окне 30 мин:** это нормально, если orangetrack RSS не отдаёт ничего нового. Тогда оператор может либо подождать ещё, либо рестартовать сервис ещё раз (триггер немедленного `job()`). Если совсем не приходит ничего — проверить визуально на старой статье после ручной правки `news.db` (рискованно — лучше дождаться нового тика).
- **Merge conflicts на `dev → main`:** не ожидаются (фича стекалась на `dev` чисто), но если возникнут — оператор разрешает локально и пушит.

**Per-stage rollback:**
- Stage 1 откат: `git revert HEAD && git push origin dev` → `deploy_test.yml` пере-деплоит родительский коммит, `news_bot_test.service` рестартует на старой версии. ~2-3 мин.
- Stage 2 откат: `git revert HEAD && git push origin main` → `deploy.yml` пере-деплоит prod на родительский коммит. ~2-3 мин.

**Implementation hints:**
- Per memory rule: Claude готовит команды и проверяет статус CI, оператор сам выполняет git push / SSH. Не пытаться SSH из своих рук.
- Проверять статусы через `gh run list` / `gh run view` — никаких сторонних UI.
- Никогда не эховать секреты в чате (`ANTHROPIC_API_KEY`, `SSH_PRIVATE_KEY` и т.п.).
- `INSTANCE_LABEL=test` / `prod` в админ-пингах помогает оператору отличить test от prod в Telegram-уведомлениях.
- На случай долгого CI — `gh run watch <id>` следит за прогрессом; не лупить в `sleep`.
- Запросить у оператора подтверждение перед Stage 2 (merge в main) — это product gate, не технический.
