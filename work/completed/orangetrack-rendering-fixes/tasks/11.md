# Task 11: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Финальный gate фичи orangetrack-rendering-fixes — верификация на живом prod-окружении после того, как Task 10 (deploy) завершился merge'ем `dev → main` и автоматическим деплоем через `deploy.yml` на VPS `148.135.207.54` (`/home/hwbot/bot/`, systemd unit `news_bot.service`).

Проверяем две вещи:
1. **Технический срез** — `journalctl` логи `news_bot.service` с момента деплоя не содержат регрессионных индикаторов (UNIQUE / IntegrityError / idempotency-guard / TypeError / AttributeError). Эти паттерны покрывают как ошибки самой фичи (новые ветки рендеринга `list_item` / `_render_paragraph_with_runs` / heading-dispatch — TypeError/AttributeError при разломе типов), так и потенциальные взаимодействия с уже задеплоенной фичей `publish-idempotency-fix` (UNIQUE/IntegrityError/idempotency-guard).
2. **Визуальный срез** — оператор в течение 1–2 суток после деплоя следит за свежими orangetrack-постами в канале `@myhwchannel123` и подтверждает, что три бага user-spec'а реально исправлены глазами читателя: маркированные списки в case-report статьях, отдельная h3-типографика для секционных заголовков, кликабельные `orangetrackdiecast.com`-ссылки прямо внутри абзацев.

Задача оператор-ориентированная (это указано в tech-spec, Wave 6): код не пишется, тесты не запускаются, ревью нет. Агент только готовит команды и инструкции — оператор сам подключается к VPS и сам визуально сканирует канал. Это согласуется с MEMORY: «Operator handles production ops; Claude prepares, operator applies — don't attempt SSH».

Особый случай: фича едет стэком поверх `publish-idempotency-fix` (тоже Wave 6 в её собственном плане). Если в окне наблюдения прилетит admin-ping `Skipped re-publish` — это сигнал той фичи, и его НЕ надо чинить здесь; вместо этого оператор открывает отдельную задачу на root-cause investigation, чтобы не смешивать срезы.

## What to do

1. Дождаться зелёного `deploy.yml` на main после Task 10 и зафиксировать **точный timestamp деплоя** (UTC и МСК) — момент, когда `news_bot.service` был перезапущен на prod. Источник timestamp'а: либо вкладка GitHub Actions (run завершён), либо `systemctl show news_bot.service -p ActiveEnterTimestamp` на VPS.
2. Подготовить и передать оператору команду `journalctl`-проверки (см. секцию Verification Steps → Smoke). Команда — однострочник, который оператор копирует в свой ssh-сеанс. Подставить в `--since` зафиксированный timestamp.
3. Оператор выполняет команду на VPS. Ожидаемый результат: пустой вывод `grep` (нет совпадений). Если что-то нашлось — зафиксировать строки и завести diagnostic-task с конкретным URL/контекстом.
4. Договориться об окне визуального наблюдения: 1–2 суток (минимум один cron-tick на 10:00 МСК + один на следующий день). Цель — поймать минимум 1–2 свежие orangetrack-публикации в `@myhwchannel123`.
5. По каждой свежей orangetrack-публикации (определяется по источнику в подписи поста / по характерным `orangetrackdiecast.com`-ссылкам в Telegraph) визуально проверить три точки:
   - случай-репорт пост → есть `<p>• …</p>` блоки в Telegraph-статье (визуально — список с буллетами);
   - заголовки секций (h2/h3/h4 в исходнике) → видны как явная h3-типографика (крупнее основного текста), а не как обычный абзац;
   - встречаются `orangetrackdiecast.com`-ссылки внутри абзацев → они кликабельны (синий цвет / подчёркивание), при тапе ведут на orangetrack.
6. Если визуально что-то не сходится — оператор открывает diagnostic-task с конкретным URL поста / Telegraph-статьи и описанием расхождения.
7. Параллельно мониторить admin-чат на admin-ping `Skipped re-publish`. Если такой пинг прилетит в окне наблюдения — НЕ обрабатывать в рамках этой задачи; завести отдельную задачу на root-cause investigation (это сигнал фичи `publish-idempotency-fix`, наблюдаемая там же по Wave 6).
8. По завершении окна наблюдения отчитаться в `decisions.md` фичи: сводка `journalctl` (clean / нашлось такое-то), сводка визуальной проверки (сколько свежих orangetrack-постов посмотрели, по каждому — три галочки или описание расхождения), статус — закрыта или эскалирована.

## Acceptance Criteria

- [ ] `journalctl`-проверка проходит чисто: нет совпадений по `UNIQUE`, `IntegrityError`, `idempotency-guard`, `TypeError`, `AttributeError` в логах `news_bot.service` с момента деплоя.
- [ ] За 1–2 суток наблюдения за `@myhwchannel123` визуально подтверждено для свежих orangetrack-статей: маркированные списки в case-report постах, отдельная h3-типографика секционных заголовков, кликабельные orangetrack-ссылки внутри абзацев.
- [ ] Если визуально или в логах что-то рендерится неожиданно — оператор открыл diagnostic-task с конкретным URL поста / Telegraph-статьи.
- [ ] Если в окно наблюдения (пересекается с Wave 6 фичи `publish-idempotency-fix`) прилетел admin-ping `Skipped re-publish` — заведена отдельная задача на root-cause investigation (НЕ закрывается тихо в этой задаче).

## Verification Steps

### Smoke

Команда оператору (после фиксации timestamp'а деплоя; подставить вместо `<deploy timestamp>` в формате, понятном `journalctl --since`, например `2026-05-07 18:42:00`):

```
ssh hwbot@148.135.207.54 "journalctl -u news_bot.service --since '<deploy timestamp>' --no-pager | grep -E 'UNIQUE|IntegrityError|idempotency-guard|TypeError|AttributeError'"
```

Ожидание: пустой вывод (exit code 1 у `grep`, что норма для «ничего не найдено»). Любая выведенная строка — повод эскалировать в diagnostic-task.

### User

Оператор в течение 1–2 суток после деплоя визуально просматривает свежие orangetrack-публикации в канале `@myhwchannel123` и для каждой подтверждает три пункта:
1. **Маркированные списки** — в case-report статьях (если в исходнике на orangetrackdiecast.com был `<ul>`/`<ol>`) Telegraph-статья содержит блоки вида `• <текст>`.
2. **Заголовки h3** — секционные заголовки (исходные `<h2>`/`<h3>`/`<h4>` orangetrack) визуально отличаются от обычных абзацев (более крупная/жирная h3-типографика Telegraph). При этом мелкие in-paragraph маркеры (исходные `<h5>`) НЕ должны выглядеть как заголовки — они остаются абзацами (регрессия `babc67c`).
3. **Кликабельные ссылки** — внутри абзацев встречаются текстовые фрагменты, кликабельные как ссылки на `orangetrackdiecast.com`-страницы (подчёркивание/синий цвет, тап ведёт на orangetrack).

Если хотя бы один пункт не сходится — оператор фиксирует URL Telegram-поста и URL Telegraph-статьи и заводит diagnostic-task.

## Details

**Files:** код не модифицируется. Эта задача — operator-driven QA на живом prod-окружении.

**Dependencies:**
- Task 10 (Deploy) должен быть закрыт: `deploy.yml` зелёный, `news_bot.service` на `148.135.207.54` перезапущен и `active (running)`.
- Стэк деплоя: фича `orangetrack-rendering-fixes` едет поверх уже задеплоенной `publish-idempotency-fix` — это создаёт пересечение Wave 6 двух фич, см. Edge cases.

**Edge cases:**
- **Нет свежих orangetrack-постов в окне наблюдения.** orangetrackdiecast.com публикует не каждый день; cron-тик в 10:00 МСК может не подобрать ни одной orangetrack-статьи за 1–2 суток. В этом случае `journalctl`-проверка остаётся валидной (логи по другим источникам не должны давать TypeError/AttributeError), а визуальное окно продлевается до появления первой свежей orangetrack-публикации либо закрывается с пометкой «no fresh orangetrack content in window — visual gate carried forward».
- **Пересечение Wave 6 с фичей `publish-idempotency-fix`.** Обе фичи финализируются на проде в одном окне. Admin-ping `Skipped re-publish` — это сигнал второй фичи; его обработка вынесена в отдельную задачу. Не закрывать его тихо в рамках этой задачи.
- **Timestamp деплоя.** Если оператор не зафиксировал точный момент рестарта, безопаснее взять чуть более раннее время (на 5–10 минут раньше) — это лишь чуть расширит окно `journalctl --since`, ничего не сломает.
- **`grep` exit code.** При отсутствии совпадений `grep` возвращает 1 (не 0). Это нормально и означает «чисто». Не интерпретировать как ошибку команды.
- **Sensitive-data в логах.** В журнале `news_bot.service` могут попадаться bot-token / api-key фрагменты в случае нештатных traceback'ов. Оператор знает не пересылать сырые строки логов в открытые каналы — фиксировать только сам факт совпадения и редактированный контекст (см. MEMORY: «never echo secrets»).

**Implementation hints:**
- Точный timestamp деплоя удобно брать командой `ssh hwbot@148.135.207.54 "systemctl show news_bot.service -p ActiveEnterTimestamp"` — она выводит момент последнего рестарта unit'а.
- Если в `journalctl` найдётся `idempotency-guard` — это **ожидаемый ping** фичи `publish-idempotency-fix`, но в КОНТЕКСТЕ нашей фичи он индикатор только если коррелирует с orangetrack-статьёй. Решение по эскалации принимает оператор после просмотра соседних строк (URL источника).
- Для визуальной проверки по Telegraph-статье удобно: открыть пост в Telegram → перейти по «source» / preview-карточке Telegraph → инспектировать DOM не нужно, всё видно глазами (буллеты, типографика заголовков, синие кликабельные ссылки).
- Если оператор хочет ускорить появление orangetrack-поста для проверки, он может на VPS сделать `systemctl restart news_bot.service` (триггерит немедленный `job()`) — но это опционально и не требуется по acceptance.
