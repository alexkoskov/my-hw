# User Spec: orangetrack-source

## Что делаем

Добавляем четвёртый источник новостей — блог [orangetrackdiecast.com](https://orangetrackdiecast.com/) (single-author Hot Wheels-блог Брэда Бэннаха). Бот будет ежедневно фетчить его RSS-ленту наравне с тремя существующими (autoevolution / lamley / mattel), переводить статьи на русский через LLM и публиковать в канал `@myhwchannel123` с хэштегом `#orangetrackdiecast #news`.

## Зачем

Канал в режиме observation mode даёт ~7 публикаций/день максимум, и оператор замечает, что **бэклог часто пустеет до конца окна публикаций** — три источника не дают достаточно контента. Orangetrackdiecast — Hot Wheels-only блог по дизайну (тэглайн «A PLACE FOR ALL HOT WHEELS FANATICS»), Брэд публикует Case Reports и Pop Culture coverage примерно раз в день. Добавление этого источника увеличивает поток статей без риска засорить канал смежными брендами.

## Как должно работать

1. Cron на сервере просыпается в 10:00 МСК → фетчит четыре RSS-ленты, включая `https://orangetrackdiecast.com/feed/`.
2. Парсер orangetrack читает поле `<content:encoded>` каждой статьи (там полный HTML-текст), извлекает заголовок, лид, абзацы, картинки и YouTube-видео в исходном порядке.
3. Если у конкретной статьи `<content:encoded>` пустой — парсер делает дополнительный HTTP-запрос к самой странице статьи и парсит её HTML (защитный fallback, срабатывает редко).
4. Дедуп против таблиц `processed_news` и `pending_articles` отсекает уже виденные ссылки. Новые статьи становятся в очередь со `source_name='orangetrack'`.
5. В окне публикации (10:00–20:00 МСК, ≥90 мин между постами) очередная orangetrack-статья переводится через LLM по существующему промпту `ux-guidelines.md`, заливается на Telegra.ph и шлётся в канал.
6. Пост в канале — однострочный `#orangetrackdiecast #news` + IV-карточка превью с большой картинкой и кнопкой ⚡ INSTANT VIEW.
7. На странице Telegra.ph рендерится полная статья: заголовок, лид-абзац, текст с картинками и встроенным YouTube-плеером в исходном порядке, футер «Источник:» со ссылкой на оригинал.

## Критерии приёмки

- [ ] Cron в 10:00 МСК фетчит `https://orangetrackdiecast.com/feed/` параллельно трём существующим лентам через `_fetch_rss_entries`. HTTP-ошибки одного источника не блокируют остальные.
- [ ] Новые записи проходят дедуп и попадают в `pending_articles` со `source_name='orangetrack'`, `feed_url='https://orangetrackdiecast.com/feed/'`.
- [ ] Парсер извлекает поля `{title, subtitle, paragraphs, images, blocks}`. Список `blocks` сохраняет исходный порядок параграфов, картинок и YouTube-видео в виде типизированных элементов (`paragraph` / `image` / `video` / опционально `heading`).
- [ ] LLM переводит EN → RU: заголовок с emoji-префиксом, лид, абзацы и `ru_blocks` с переведёнными текстовыми полями (медиа-блоки нетронуты).
- [ ] Telegra.ph рендерит страницу через blocks-путь: hero-картинка, лид с `💬 «…»`, далее в порядке оригинала параграфы / картинки / видео, в конце футер «Источник:».
- [ ] Видео на Telegra.ph встраивается через прокси-обёртку `https://telegra.ph/embed/youtube?url=<urlencoded>` (как у autoevolution) — кликабельный YouTube-плеер прямо на странице.
- [ ] Канал-пост: одна строка `#orangetrackdiecast #news` + IV-превью со сборной карточкой и кнопкой INSTANT VIEW.
- [ ] **Admin-ping (агрегированный, один за cron-tick).** Если за tick зафиксированы проблемы с этим источником — оператор получает одно сообщение в Telegram с заголовком `[<INSTANCE_LABEL>] orangetrack: N issues this tick` и буллет-списком вида `• <CODE> (<count>×) — <link>` сгруппированно по кодам. Если проблем нет — никакого пинга.
- [ ] Набор кодов ошибок:
  - `FEED_HTTP_<status>` (например `FEED_HTTP_503`) — RSS-лента ответила HTTP-ошибкой.
  - `FEED_TIMEOUT` — таймаут сетевого запроса к ленте.
  - `FEED_XML_PARSE` — лента вернула некорректный XML.
  - `ART_FALLBACK_HTTP_<status>` — у статьи пуст `content:encoded`, fallback-HTTP к странице упал с HTTP-ошибкой.
  - `ART_FALLBACK_TIMEOUT` — то же, но таймаут.
  - `ART_FALLBACK_PARSE_EMPTY` — fallback-HTTP сработал, но парсер не смог извлечь контент.
  - `ART_PARSE_EXCEPTION` — неожиданная ошибка в парсере (defensive catch-all).
- [ ] Успешный fallback (content:encoded пуст → HTTP-парсинг страницы сработал) — **silent**, никаких пингов.
- [ ] Boilerplate-фильтр расширен короткими паттернами для рекламных строк типа «*QUICK LINK!* Buy from 1 Stop Diecast now.» — фильтр режет stand-alone параграф, если он короткий (≤ 120 символов) и совпадает с шаблоном. Inline-рекламные предложения внутри обычных абзацев — out of scope этой фичи (см. Технические решения).
- [ ] Negative: содержательные предложения, упоминающие «buy» вне рекламного шаблона (например «I'd buy that for $1»), проходят фильтр.
- [ ] Negative: пост, тело которого целиком — рекламная строка, фильтр режет → `paragraphs=[]` → существующий downstream-фильтр дропает статью; такой пост в канал не попадает.
- [ ] Все существующие тесты продолжают проходить. Добавлены unit-тесты на парсер orangetrack (~30-40 штук) + 3-5 тестов на новые рекламные паттерны в `tests/test_boilerplate_filter.py`.
- [ ] Тест `tests/test_sources_registry.py` обновлён: множество ожидаемых источников включает `'orangetrack'`.
- [ ] Новый модуль `orangetrack_source.py` добавлен в **оба** списка деплоя — `deploy.sh` и `.github/workflows/deploy.yml`. Без этого сервер падёт с ошибкой при следующем рестарте.
- [ ] Парсер устойчив к мелким изменениям WordPress-вёрстки: подтверждается unit-тестом, который скармливает парсеру минимальную HTML и проверяет, что он всё равно корректно достаёт абзацы и картинки (детали реализации — в техспеке).
- [ ] RSS recovery: если сайт лежал в день N — на день N+1 cron возьмёт пропущенные посты автоматически, потому что лента содержит окно из 10-20 свежих записей и дедуп против `processed_news` отфильтрует только уже опубликованные. Детекция «сайт лежал и потерянные посты выпали из окна» **не делается** by design — вероятность близка к нулю (см. R5).

## Ограничения

- **Observation mode.** Изменения исключительно аддитивные. Существующие парсеры (autoevolution / lamley / mattel) не трогаются — нулевой риск регрессии для них.
- **WordPress.com hosting** — нет Cloudflare, нет анти-бота, обычные `requests` работают и для ленты, и для fallback-страницы. `curl_cffi` не нужен.
- **Парсер контракт.** Возвращает `{title, subtitle, paragraphs, images, blocks}` — тот же двойной формат, что у autoevolution. Telegra.ph-рендерер автоматически выбирает blocks-путь, когда поле непустое.
- **Один HTTP-запрос за обычную статью** (только лента). Дополнительный fallback-запрос — только при пустом `content:encoded`, что бывает редко (≤1 раз в неделю по оценкам).
- **Лимиты на размер** аналогично lamley: ответ ленты и fallback-страницы — не больше 5 MB; не больше 10 картинок на статью (Telegraph всё равно ограничивает).
- **Нет новых зависимостей** — только существующие `requests`, `feedparser`, `beautifulsoup4`. Никаких новых env-переменных, API-ключей, схемы БД, миграций.
- **INVARIANT (из patterns.md):** новый модуль `orangetrack_source.py` обязан попасть в FILES-list **обоих** файлов деплоя (`deploy.sh` и `.github/workflows/deploy.yml`), иначе следующий cron-tick на сервере крашнется с `ImportError`. Проверка — ручной diff обоих файлов в PR.
- **Per-source style notes block в `ux-guidelines.md` НЕ добавляется** в этой фиче. Сначала запускаем общий промпт, наблюдаем; если будет дрейф тона — отдельная маленькая фича.
- **Lamley video preservation НЕ в скоупе** этой фичи. Делается отдельно потом.

## Риски

- **R1: WordPress block-class drift.** Брэд может в любой момент сменить редактор (Gutenberg → classic) или WordPress.com обновит тему — Gutenberg-классы вроде `wp-block-paragraph` исчезнут, парсер начнёт возвращать пустой контент. **Митигация:** ходим по HTML-тегам, не по классам — теги стабильны во всех вариантах WP. Юнит-тест на минимальной HTML без `wp-block-*` классов проверяет это явно. Если что-то всё равно сломается — admin-ping `ART_PARSE_EXCEPTION` срабатывает, оператор инвестигирует.
- **R2: Inline affiliate sentences leak.** Брэд часто вставляет «*QUICK LINK!* Buy from 1 Stop Diecast now» **внутри** реальных абзацев. Variant A boilerplate-фильтр (длина ≤120, standalone) их не цепляет; они утекут в канал в переводе. **Митигация:** out of scope этой фичи (см. Технические решения). Если регулярно будут полыхать — отдельная маленькая фича с `_strip_plugs`-style postprocessor.
- **R3: Один из двух FILES-list забыт при деплое.** Если в `deploy.sh` модуль есть, а в `.github/workflows/deploy.yml` нет (или наоборот) — сервер при следующем рестарте упадёт с `ImportError`. **Митигация:** явный checklist-пункт в тех-спеке; ручной diff обоих файлов при review PR; pytest этого не ловит автоматически.
- **R4: orangetrackdiecast.com rate-limit.** Теоретически WordPress.com может ограничить частоту запросов. **Митигация:** наш профиль нагрузки — один запрос ленты в день + редкий fallback к странице статьи. Это далеко от любого нормального лимита, риск практически нулевой. Специальные защиты (как у Lamley с throttle и 429-retry) **не делаем** — у Lamley они появились после реальных 429 в проде, у нас нет основания их предрассчитывать.
- **R5: Сайт лежит >5-7 дней подряд И Брэд за это время публикует >10 постов** — старые записи выпадут из окна RSS-ленты, мы их безвозвратно потеряем. **Митигация:** в этой фиче не адресуется. Вероятность близка к нулю (uptime WP.com 99.9%+, Брэд ~1 пост/день). Если случится — оператор может вручную скачать пропущенные через архивный hw_review путь (код жив).
- **R6: Брэд меняет URL ленты или плагин фида.** Detection: `FEED_*` коды в admin-ping. Operator investigates manually и обновляет `feeds.json`.
- **R7: test_sources_registry.py set assertion ломается** при добавлении нового источника. **Митигация:** обновляем тест в том же коммите.

## Технические решения

- Мы решили **сделать парсер по гибридной схеме** (основной путь — `<content:encoded>` из RSS-ленты; запасной — HTTP-запрос к странице статьи), потому что `content:encoded` орангетрэка содержит полный HTML-текст в 99% случаев — это бесплатный способ читать статью без отдельного HTTP-запроса. Но при пустом `content:encoded` мы всё равно умеем дотянуться до страницы — defensive fallback.
- Мы решили **выдавать blocks-путь** (а не плоский), потому что у Брэда часто YouTube-видео в середине статьи, и в плоском формате `{paragraphs, images}` нет места для видео — оно бы тихо терялось. С blocks-путём Telegra.ph рендерит видео в том же месте, где оно стоит в оригинале.
- Мы решили **парсер делать устойчивым к мелким изменениям WordPress-вёрстки** (не привязываться к конкретным CSS-классам типа `wp-block-paragraph`, а ходить по самим HTML-тегам), потому что Брэд может в любой момент сменить редактор или тему сайта. Конкретные технические приёмы — в техспеке.
- Мы решили **не делать per-source style notes в `ux-guidelines.md`** для orangetrack в этой фиче, потому что общий промпт уже покрывает блог-стайл (как у autoevolution и lamley). Сначала наблюдаем результат, при заметном тоновом дрейфе делаем отдельную маленькую правку промпта.
- Мы решили **не править Lamley для поддержки видео** в этой фиче, потому что (а) это правка существующего боевого кода с риском регрессии, (б) задача orangetrack — аддитивная и низкорисковая. Lamley video — отдельная фича.
- Мы решили **out of scope для inline-рекламных предложений** внутри обычных абзацев (Брэдовы «*QUICK LINK!* Buy from <store>» в конце нормального параграфа), потому что наш текущий boilerplate-фильтр не умеет резать половину абзаца, а делать новый отдельный пост-фильтр на русском тексте — это уже другая задача. Если регулярно будут утекать в канал, добавим отдельной маленькой фичей.
- Мы решили **внутреннее имя источника = `orangetrack`, эмодзи в admin-уведомлениях = 🔵, хэштег в канале = `#orangetrackdiecast`**, потому что: короткое имя совпадает с существующим стилем (`lamley`, `mattel`); синий — четвёртый свободный цвет в наборе; хэштег формируется автоматически по адресу сайта, его не настраиваем вручную.
- Мы решили **полагаться на естественное окно RSS-ленты для recovery**, потому что лента содержит 10-20 свежих постов, дедуп против `processed_news` отрабатывает автоматически, нет нужды в специальном retry-state. Простота надёжнее.
- Мы решили **агрегировать admin-ping по одному за cron-tick** с кодами ошибок и ссылками, потому что оператор не хочет флуда уведомлений при единичной проблеме (3 проблемные статьи = 1 пинг с тремя пунктами, не 3 отдельных). Коды стабильные строки — оператор может грепать journalctl.
- Мы решили **успешный fallback не пинговать**, потому что fallback — рутинный механизм, его срабатывание не требует внимания оператора, только провал требует.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.

**Интеграционные тесты:** не делаем — orangetrack проходит через тот же pipeline `_fetch_rss_entries` → `fetch_full_article` → `pending_articles_repo.insert_pending` → `_fallback_publish` → Telegraph + Telegram, что и существующие 3 источника. Этот путь уже покрыт `test_distributed_schedule_integration.py` без хардкода идентичности источника. Дополнительный integration test ничего не добавит сверх unit-покрытия парсера и fetch_full_article-диспетчера.

**E2E тесты:** не делаем — pre-deploy QA на dev-инстансе через test channel `@myhwchannel123` (визуальная проверка после первой публикации) даёт практический e2e-покрытие без необходимости в автоматизированном tooling. Перевод оценивается оператором глазами.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|---|---|---|
| 1. `pytest tests/` локально / в CI | bash + GitHub Actions | Все существующие тесты + ~35-45 новых проходят зелёным |
| 2. Pre-commit хук перед коммитом | gitleaks + whitespace + EOF + merge-conflict checkers | Все проверки зелёные |
| 3. Smoke-fetch ленты в Python REPL до коммита | bash + python | `orangetrack_source.fetch_orangetrack_article(<entry from live feed>)` возвращает корректный dict с непустыми `paragraphs`, `images`, `blocks` |
| 4. После push на `dev` — деплой в test-инстанс | GitHub Actions (ci.yml + deploy_test.yml) | Workflow зелёный, `news_bot_test.service` рестартует без ошибок |
| 5. После рестарта — log-проверка | `journalctl -u news_bot_test.service -n 50` | Бот стартовал без `ImportError`, никакого admin-ping flood, orangetrack feed успешно фетчится на следующем cron-tick |
| 6. Manual diff обоих FILES-list перед PR-merge | bash + GitHub PR diff | `deploy.sh` и `.github/workflows/deploy.yml` оба содержат `orangetrack_source.py` в FILES |

### Пользователь проверяет

- **Первая публикация orangetrack на test channel.** В рабочем окне 10:00-20:00 МСК после deploy в test (если в очереди есть orangetrack-статья) — открыть `@myhwchannel123` в Telegram и:
  - убедиться, что под IV-карточкой превью стоит хэштег `#orangetrackdiecast #news` (одна строка)
  - тапнуть IV-карточку → открывается Telegra.ph страница с заголовком на русском (с emoji-префиксом), лидом, абзацами текста, картинками в порядке оригинала и встроенным YouTube-плеером (если в исходном посте было видео)
  - русский перевод читается как живой текст, не как калька с английского, нет канцелярита, нет фразы «*QUICK LINK!* Buy ...» отдельным абзацем (inline-вариант может проскочить — это known leak per Q5)
- **Если что-то выглядит сломанным на test channel — НЕ мержим в `main`.** Откатываем коммит, диагностируем, чиним.
- **После merge в `main`** — посмотреть `journalctl -u news_bot.service` за первые 24 часа: бот фетчит orangetrack-ленту ежедневно, статьи попадают в очередь, проблемных admin-пингов нет (или они объяснимы и не требуют экстренного вмешательства).
- **Через неделю** — окинуть взглядом канал. Если тон orangetrack-постов резко отличается от Lamley/Autoevolution в нежелательную сторону — открыть отдельную фичу для per-source-блока в `ux-guidelines.md`. Это не блокер для приёмки этой фичи.
