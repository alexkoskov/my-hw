# User-spec self-validation — dedup-review-buttons

**Дата:** 2026-07-22
**Причина ручного ревью:** оба валидатора (userspec-quality-validator,
userspec-adequacy-validator) упали на инфраструктурных ошибках API
(stalled mid-stream, 401, 403 ×2) — не по содержанию спека. Ревью выполнено
основной моделью по тем же критериям.

## Качество документа

- Структура шаблона — все секции присутствуют. PASS.
- Критерии приёмки — проверяемые (наличие/отсутствие кнопок, удаление строки из
  `pending_articles`, замена кнопок на статус, ответ «уже опубликовано», проверка
  админа, гейт «только прод»). PASS.
- Противоречий не найдено. PASS.
- Правки по итогам ревью:
  - Добавлен критерий на идемпотентность повторного/устаревшего нажатия
    (не падать, понятный статус).
  - Добавлено техническое решение: логировать решение оператора (в духе
    диагностики проекта).

## Адекватность решения

- Right-sizing: фича переиспользует готовый `skip_pending(link)`, поверхность
  минимальна, размер M корректен. PASS.
- Приём нажатий: user-spec НЕ фиксирует механику (поток getUpdates vs отдельный
  процесс vs webhook) — правильно оставлено на тех-задание. Webhook отмёл бы как
  оверинжиниринг (нет веб-сервера, бот за VPN). PASS.
- Concurrency/lock и shared-token 409 — не решены (это тех-задание), но
  ЗАФИКСИРОВАНЫ как ограничения/риски. PASS.
- Честное ограничение: сквозной E2E на тест-канале невозможен (слушает только
  прод) → первый живой прогон проверяет оператор вручную. Задокументировано.

## Открытые вопросы для тех-задания (не блокируют user-spec)

1. Короткий id/токен для callback_data (PK = URL не влезает в 64 байта).
2. busy_timeout на путь отмены (защита от «database is locked»).
3. Числовой `TELEGRAM_ADMIN_ID` для проверки `callback.from_user.id`.
4. Механизм фонового приёма нажатий (поток vs процесс) + гейт «только прод».

**Вердикт:** user-spec готов к утверждению.
