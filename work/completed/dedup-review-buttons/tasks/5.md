# Task 5: Background review listener + main() wiring

## Required Skills

## Description

Это финальный кусок входящего пути: бот впервые начинает **принимать** нажатия из
Telegram. Сегодня всё общение с Telegram — только исходящее (`Bot(...).send_message`
внутри `asyncio.run`). Задача — добавить фоновый **демон-поток** `_run_review_listener()`,
который в цикле длинно-опрашивает `bot.get_updates(...)`, разбирает callback-нажатия под
E014-кнопками (`dd:<c|k>:<token>`), передаёт их в чистую логику `resolve_dedup_callback`
(Task 4), и даёт оператору обратную связь: правит текст исходного алерта (добавляет строку
статуса, убирает клавиатуру) и отвечает на нажатие.

Ключевые ограничения из тех-спека:
- **Изоляция от публикаций (Risk «Listener thread crashes», Decision 1).** Поток — `daemon`,
  со своим `Bot` и своим `asyncio`-циклом (`asyncio.run` на вызов, как в существующем стиле).
  Любая ошибка внутри цикла должна логироваться (и опционально пинговать админа с backoff),
  но **никогда** не ронять процесс публикации. Основной поток (`schedule` + `while True`)
  продолжает работать, даже если listener падает раз за разом.
- **Fail-closed гейт (Decision 5 + 6).** Поток стартует из `main()` **только** когда
  `REVIEW_BUTTONS_ENABLED` истинно **И** `TELEGRAM_ADMIN_ID` числовой. Общий бот-токен на
  прод+тест: два потребителя `getUpdates` дают 409, поэтому слушает ровно один инстанс
  (флаг по умолчанию выключен — Task 3). Нечисловой admin id (дефолт `@sunny413x`) не может
  совпасть с числовым `from_user.id`, поэтому такой конфиг **отключает** слушание, а не
  «тихо всех отвергает».
- **Наблюдаемость (Decision 6 Risk, user-spec «записывать в лог решение оператора»).** При
  старте — лог/пинг «review listener active» (или warning, если выключено из-за нечислового
  id). На каждое терминальное нажатие — лог решения оператора (cancel/keep + ссылка + статус)
  на уровне INFO, в диагностическом стиле проекта.

Задача НЕ трогает исходящий путь E014 (Task 3), чистую логику решения (Task 4), token-store
и busy_timeout (Task 1) — они уже готовы к Wave 3.

## What to do

1. **Добавить `_run_review_listener()` в `news_bot.py`** — функцию-тело фонового потока:
   - Создаёт собственный `Bot(token=TELEGRAM_BOT_TOKEN)` (свой экземпляр, не переиспользует
     чужой) и держит собственный `offset`.
   - В бесконечном цикле вызывает `bot.get_updates(offset=offset, timeout=30,
     allowed_updates=['callback_query'])` через `asyncio.run(...)` (свой event loop на вызов —
     как `send_admin_notification` делает `asyncio.run(_send())`).
   - Для каждого полученного `update` с `callback_query`:
     - Продвигает `offset = update.update_id + 1`.
     - Разбирает `callback_query.data` по грамматике `dd:<c|k>:<token>`; всё, что не подходит
       под шаблон, — молча игнорирует (только продвигает offset).
     - Мапит букву callback в полное слово: `c → 'cancel'`, `k → 'keep'` (это согласованный
       контракт с Task 4 — `resolve_dedup_callback` принимает именно полные слова `'cancel'`/`'keep'`,
       а НЕ односимвольные `c`/`k`). Извлекает `from_user.id` (числовой int).
     - Вызывает `resolve_dedup_callback(action, token, from_user_id)` (Task 4), где `action` —
       уже смапленное полное слово `'cancel'` или `'keep'` → получает `(status_text, answer_text)`.
     - Если результат не «ignored» (нажатие админа, терминальный исход): `edit_message_text`
       на исходном сообщении — дописывает строку статуса к оригинальному тексту и убирает
       клавиатуру (`reply_markup=None`); затем `answer_callback_query(callback_query.id,
       text=answer_text)`. Не-админ → только `answer_callback_query` (или тихо), без правки.
     - Логирует решение оператора на INFO: действие (cancel/keep), ссылку на статью и
       итоговый статус.
   - **Весь цикл (или тело итерации) обёрнут в try/except**, который логирует ошибку, при
     необходимости пингует админа с backoff, и **продолжает цикл** — ни одно исключение не
     выходит наружу из потока. `getUpdates`-timeout / сетевые ошибки не должны приводить к
     busy-loop: короткая пауза (backoff) перед повторной попыткой при ошибке.
2. **Завести seam для тестируемости бесконечного цикла.** Цикл должен уметь завершаться в
   тесте (например, инъекция `stop_event: threading.Event | None = None`, проверяемого в
   начале итерации, ИЛИ иной механизм одной итерации). Это WHAT: тесту нужен способ прогнать
   1–2 итерации и выйти без вечного блока. Конкретный механизм — на усмотрение реализатора.
3. **Проводка в `main()`** (`news_bot.py` ~L2818, ПЕРЕД `schedule.every()...` и немедленным
   `job()`, чтобы listener жил всю жизнь процесса, включая долгий блокирующий publish-window):
   - Вычислить гейт: `REVIEW_BUTTONS_ENABLED` истинно **И** `TELEGRAM_ADMIN_ID` числовой.
   - Если гейт открыт → запустить `threading.Thread(target=_run_review_listener, daemon=True)`,
     стартовать, и эмитировать startup-лог/пинг «review listener active».
   - Если `REVIEW_BUTTONS_ENABLED` включён, но admin id нечисловой → лог WARNING (fail-closed:
     «review listener disabled — TELEGRAM_ADMIN_ID is not numeric»), поток НЕ стартует.
   - Если `REVIEW_BUTTONS_ENABLED` выключен → ничего (тест-инстанс, дефолт off), поток НЕ
     стартует.
   - Вынести решение гейта в маленький чистый предикат (например `_review_listener_enabled()`
     → bool), чтобы юнит-тест проверял on/off/нечисловой id без запуска `main()`.
4. **Добавить `import threading`** в шапку `news_bot.py` (сейчас его нет).
5. **Тесты в `tests/test_integration.py`** — см. TDD Anchor. Написать ДО реализации.

  Что сделать: (1) `import threading`; (2) `_run_review_listener()` — фоновый цикл get_updates
  → parse → `resolve_dedup_callback` → edit/answer; (3) чистый предикат гейта
  (`_review_listener_enabled()` или аналог); (4) в `main()` перед L2820 запустить daemon-поток
  при открытом гейте + startup-лог/пинг «review listener active» (или WARNING при нечисловом id).
- `tests/test_integration.py` — добавить тесты из TDD Anchor. Файл уже импортирует `news_bot`,
  использует tempfile-SQLite, `patch`, монипатч module-констант.

**Dependencies:**
- Задачи: Task 3 (`REVIEW_BUTTONS_ENABLED` — константа-флаг, гейт исходящих кнопок) и Task 4
  (`resolve_dedup_callback(action, token, from_user_id) -> (status_text, answer_text)`) — обе
  ДОЛЖНЫ быть готовы (depends_on: [3,4], wave 3). Task 1 дал token-store + busy_timeout, Task 2
  — клавиатуру/`reply_markup`.
- Пакеты: новых нет. `python-telegram-bot==21.10` уже даёт `Bot.get_updates`,
  `Bot.edit_message_text`, `Bot.answer_callback_query`. `threading`, `asyncio` — stdlib.

**Edge cases:**
- **Нечисловой `TELEGRAM_ADMIN_ID`** (дефолт `@sunny413x`): гейт закрыт (fail-closed), поток не
  стартует, WARNING. Проверять число надёжно (например `int()`-guard, учитывая возможный знак/
  пробелы), не через наивный `.isdigit()` на значении со знаком.
- **`callback_query.data` не по грамматике** (`None`, `'garbage'`, чужой префикс) → игнор, только
  offset++. Не падать на отсутствии `data` / `from_user`.
- **Не-админ нажал** → `resolve_dedup_callback` вернёт «ignored» (Task 4): без правки сообщения,
  без изменения очереди; ответить пустым `answer_callback_query` (или тихо) — состояние не менять.
- **Устаревший/повторный токен, статья уже опубликована/недоступна** → `resolve_dedup_callback`
  вернёт безопасный статус; listener всё равно правит сообщение и отвечает, не падает.
- **`getUpdates` timeout / сетевой сбой / TelegramError** → поймать, залогировать, backoff, продолжить.
  Не busy-loop-ить на повторяющейся ошибке.
- **409 Conflict** (если по ошибке слушают два инстанса) — попадёт в общий except: логируется,
  процесс публикации выживает; операторский runbook (Task 6) требует включать флаг ровно на одном.
- **Изоляция offset:** сохранять `offset` между итерациями, чтобы не переобрабатывать/не терять
  апдейты; при рестарте бота старые апдейты Telegram отдаст один раз — обрабатываются идемпотентно
  (устаревший токен → безопасный статус).

**Implementation hints (НЕ псевдокод):**
- Повторяй существующий стиль: `Bot(token=TELEGRAM_BOT_TOKEN)` + `asyncio.run(coro)` на вызов
  (см. `send_admin_notification` L492-509). Не тащить `telegram.ext.Application`/`Updater`
  (Decision 1: конфликт с сигналами вне main-thread, чужеродно кодовой базе).
- Для лога ссылки на статью: `resolve_dedup_callback` удаляет токен на терминальном исходе —
  если нужен `link` в лог-строке, получить его до вызова resolve (`get_review_token_link(token)`)
  либо согласовать, чтобы resolve вернул его. Не изобретать второй источник истины.
- Гейт-флаг читать как MODULE-атрибут (`news_bot.REVIEW_BUTTONS_ENABLED`), чтобы тесты монипатчили
  его, как `DEDUP_SERIES_ENABLED` (L128-132).
- Startup-пинг «review listener active» — через `send_admin_notification` (уже редактирует
  секреты, добавляет `[INSTANCE_LABEL]`), обёрнутый в try/except как прочие startup-пинги (см.
  L2773-2781).
- Тестируемость бесконечного цикла: заложи stop-seam (например `threading.Event`) — тест
  прогоняет 1 итерацию и выходит без вечного блока и без реальной сети.
- Не логируй `callback_data`/токен в открытом виде сверх нужного; редакция логов уже есть
  (`_redact_text`), но токен — не секрет-ключ, важнее не спамить и не ломать `test_no_token_leak_in_logs`.
