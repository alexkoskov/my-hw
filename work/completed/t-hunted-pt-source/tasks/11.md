# Task 11: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [skills/test-master/SKILL.md](~/.claude/skills/test-master/SKILL.md)

## Description

Full-feature test quality audit for the `t-hunted-pt-source` feature. Read every test file created or extended across Waves 1-3 (Tasks 1-8) and assess them holistically against the test-master methodology: meaningful assertions, coverage of error paths, no inter-test ordering dependence, ReDoS safety bounded by timeout, fixture freshness, and that the integration test genuinely proves cross-language non-interference (not just "no crash"). The deliverable is a JSON audit report at `work/t-hunted-pt-source/logs/audits/test-audit.json` summarising per-test-file findings and overall verdict. This is an analysis-only task — no test code is modified here. Findings that warrant fixes are routed back by the feature lead to a fixer agent in a follow-up step; this task's job is to surface them.

The audit covers ~16 new test methods spread across 8+ test files, plus the integration smoke. Because the parser is the most security/quality-critical artefact (SSRF allowlist + Blogger HTML scrape + PT boilerplate stripping), `tests/test_t_hunted_source.py` and `tests/test_boilerplate_filter.py` (PT-pattern additions) receive deepest scrutiny.

## What to do

1. Read the tech-spec Testing Strategy section to anchor expectations (what each test file is supposed to assert).
2. Read each test file in the scope list (see Details → Files). For each file, evaluate:
   - **Assertion quality** — every test should assert observable behaviour, not just `is not None` or "did not raise". Identify any test whose only assertion is existence/non-emptiness.
   - **Error-path coverage** — for the parser, the three failure modes (host rejected, fetch error, no body) must each have a dedicated test that asserts `None` return AND the corresponding admin alert ping. For admin alerts E031-E033, each builder needs a positive test asserting the code prefix and link inclusion.
   - **Edge cases** — SSRF allowlist must test userinfo-attack, suffix-host-attack, subdomain variants, non-HTTP scheme (all from tech-spec). Blogger image dedup must test the `=s\d+(-c)?` size-suffix strip with a real-shaped fixture URL.
   - **Test interdependence** — scan for shared module-level state, ordering assumptions, or cross-test fixtures that aren't reset. Each test must be runnable in isolation (`pytest tests/test_x.py::TestY::test_z`).
   - **Integration test cross-language proof** — `test_integration_t_hunted_smoke_en_pt_mixed_tick` must assert both EN and PT rows land with correct `source_name`, both publish, no dedup over-eagerness, slot ordering preserved. Verify the assertions actually prove non-interference, not just that the tick completes.
   - **ReDoS safety** — `test_pt_patterns_no_redos_under_120_char_input` must use a bounded timeout (`pytest-timeout` or `signal.alarm`) under which each PT regex executes against adversarial 120-char inputs. Verify the timeout value is sane (≤100ms per pattern) and adversarial inputs target known ReDoS shapes.
   - **Fixture freshness** — any HTML fixtures used by `test_t_hunted_source.py` should be realistic Blogger output, not lamley-shaped HTML rebadged. Verify fixtures match the tech-spec's expected `.post-body`/`.entry-content` flat structure.
   - **Structural tests** — `test_ux_guidelines_structure.py` should anchor by content, not line number. Verify each of the 4 assertions is content-anchored.
   - **Deploy invariant tests** — `test_deploy_files_invariant.py` should assert `"t_hunted_source.py"` literal presence in all three FILES arrays.
3. Produce the audit report as a single JSON file with per-file findings, overall verdict (pass / pass-with-issues / fail), severity-graded issues (critical / major / minor), and concrete remediation suggestions for each issue.
4. Surface any cross-file concerns (e.g. coverage gap that no individual file owns, duplication between dispatcher unit test and integration smoke).

## Details

**Files:**
- `work/t-hunted-pt-source/logs/audits/test-audit.json` (new, the deliverable) — JSON structure described in Acceptance Criteria. Create parent dir if absent (`mkdir -p work/t-hunted-pt-source/logs/audits`).

**Inputs to read (test files):**
- Aggregated above in Context Files → Test files in audit scope. Read each test file in full — partial reads risk missing fixture definitions or skipped tests.

**Dependencies:**
- Tasks 1-8 must be complete (status: done) before this task runs. Wave 4 = Audit Wave per tech-spec.
- No new packages.

**What "meaningful assertion" means in this codebase:**
- Bad: `assert result is not None`
- Acceptable: `assert result['title'] == 'Caça à Mainline Brasil'`
- Best: a structured assert on the full dict shape that catches both missing fields AND wrong-value drift.

**What "error-path coverage" means here:**
- Parser must have one test per failure mode that asserts (a) returns `None`, (b) calls the matching admin-alert builder via the injected notifier, (c) does not raise.

**What "no test interdependence" means:**
- Module-level state in the source file (e.g. caches, counters) must be reset in fixtures.
- Tests must not rely on alphabetical ordering or `sys.modules` side-effects from earlier tests.
- Run a mental `pytest --randomly` pass — would any test fail under random ordering?

**Edge cases the audit must flag if missing:**
- SSRF: userinfo-attack URL (`http://t-hunted.blogspot.com@evil.com/x`)
- SSRF: suffix-host-attack (`http://t-hunted.blogspot.com.attacker.example/x`)
- SSRF: subdomain variant (`evil.t-hunted.blogspot.com`)
- SSRF: non-HTTP scheme
- Image dedup: two URLs differing only by `=s1600` vs `=s640` size suffix must dedupe to one
- Boilerplate: PT pattern false-positive on real PT prose (e.g. an article that legitimately starts with «Postagem sobre Caça...» — must NOT be stripped due to the `^postagem` pattern matching without length bound; verify length bound `_MAX_BOILERPLATE_LEN = 120` is respected)
- ReDoS: each PT regex must be tested with at least one adversarial 120-char input under a bounded timeout

**Implementation hints (NOT pseudocode):**
- Write the JSON report with `json.dump(..., indent=2, ensure_ascii=False)` — Portuguese strings appear in findings, keep them readable.
- Group findings under `files[].findings[]` rather than a flat top-level list — easier to triage per-file.
- Severity guide: `critical` = blocks merge (e.g. missing SSRF userinfo-attack test); `major` = likely-to-leak-bug (e.g. weak assertion on parser happy path); `minor` = style/maintainability (e.g. fixture could be shared).
- Cross-reference each finding to the relevant tech-spec line or user-spec AC where applicable — evidence-backed findings carry more weight than opinions.
- If a test file from the scope list doesn't exist after Wave 1-3, note it as a `critical` finding with `path: missing` rather than skipping silently.

**Edge cases:**
- If two tests cover the same edge case (e.g. dispatcher routing tested both in unit and integration), flag as `minor` redundancy, not a defect.
- If the integration smoke test mocks both RSS feeds and `_fallback_publish`, the assertion strength of "both publish" is weaker than a real publish — verify the mock setup still genuinely exercises the cross-language dispatch path.
- If `_MAX_BOILERPLATE_LEN = 120` is changed by Task 4 (it shouldn't be), flag as breaking change to the RU defence-in-depth precedent.
