## Description

Финальный шаг фичи `llm-transcreation-and-distributed-publishing` — выкатка новой версии бота на продакшн VPS. После того как Task 13 расширил deploy-bundle (добавлены `ux-guidelines.md`, `claude_transcreation.py`, `compute_publish_slots.py`, `outage_state.py` в FILES, проброс `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` / `TZ` в `.env` на сервере), Task 17 прогнал pre-deploy QA (все тесты зелёные, AC пройдены, smoke-вызов Claude API дал валидный RU-словарь), — теперь задача оператора фактически развернуть код на сервере и убедиться, что все артефакты доехали корректно. Сама выкатка может произойти двумя путями:

1. **Через GitHub Actions (предпочтительно)** — после мержа в `main` workflow `CI` отрабатывает зелёным, дальше автоматически триггерится `deploy.yml` (concurrency-group `deploy-prod`). Оператор наблюдает Run в Actions UI.
2. **Вручную через `bash deploy.sh`** — fallback по решению из `project_post_mrw_pending` (CI ещё не катали ни разу с main, оператор может предпочесть ручной первый прогон). В этом случае оператор локально из dev-ветки (на которой фича собрана) запускает `bash deploy.sh` с настроенными `SSH_HOST` / `DEPLOY_PATH`.

Задача Claude (агента-исполнителя) — НЕ ходить на прод по SSH, НЕ запускать сам деплой и НЕ трогать секреты. По правилу "Operator handles production ops; Claude prepares, operator applies" агент готовит чёткий чек-лист и пошаговую инструкцию, отдаёт оператору, ждёт подтверждения запуска, забирает у оператора deploy-логи (текстом или скриншотом), парсит их и фиксирует факт успешного деплоя в `logs/deploy/deploy-log.md` фичи. Оператор сам решает, идёт по CI-маршруту или по ручному.

После деплоя обязательно проверить четыре критических артефакта:
- В deploy-логах есть строки про копирование всех FILES, включая ВСЕ четыре новых файла фичи: `ux-guidelines.md` (system prompt для Claude API, AC28), `claude_transcreation.py` (Claude API транскреатор, Task 3), `compute_publish_slots.py` (распределение слотов 13:00–20:00, Task 2), `outage_state.py` (state machine outage/2-ping protocol, Task 5). Если хотя бы один из четырёх отсутствует в логах — деплой считается failed, Task 18 НЕ закрывается, возврат к Task 13 на доработку deploy bundle.
- На сервере отработал `pip install -r requirements.txt` без ошибок и подтянул новые зависимости (`anthropic`, `pytz`).
- На сервере `.env` содержит все три новых переменных (`ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `TZ=Europe/Moscow`); если оператор обновлял только `.env.example`, проверить, что реальный `.env` тоже синхронизирован.
- Все четыре новых файла физически присутствуют на сервере (после flat-scp копирования: `ux-guidelines.md` в `$DEPLOY_PATH/`, остальные три — там же flat). Подтверждение через маскированный `ssh ... 'ls -la $DEPLOY_PATH/{ux-guidelines.md,claude_transcreation.py,compute_publish_slots.py,outage_state.py}'`, который запускает оператор и присылает результат.

Сам результат проверяется в следующей задаче (Task 19, post-deploy verification на живом окружении в 12:00/13:00 МСК).

### Smoke

Все проверки идут через артефакты, которые приносит оператор. Агент сам не ходит на сервер.

- В deploy-логе есть строка `Copying N files to <user>@<host>:<deploy_path>/` и N соответствует обновлённой длине FILES (после Task 13: текущие 9 → 13). Если маршрут — CI, в Actions UI шаг "Copy files to server" зелёный и в его выводе видны все четыре имени; если ручной — `scp` exit code 0 (нет `lost connection`, нет `Permission denied`) и в stdout видны все четыре файла. Если хотя бы один файл из четырёх не виден в логах — деплой считается failed, Task 18 не закрывается, возврат к Task 13.
- Server-side ls от оператора (`ssh ... 'cd $DEPLOY_PATH && ls -la ux-guidelines.md claude_transcreation.py compute_publish_slots.py outage_state.py'`) показывает все четыре файла с ненулевым размером и недавним mtime. Если хотя бы одна строка `No such file or directory` — деплой failed, диагностика в `deploy-log.md`, возврат к Task 13.
- В логе шага "Install Python dependencies on server" (CI) или соответствующего блока в выводе `deploy.sh` — нет `ERROR:`, есть `Successfully installed` со строками `anthropic-0.45.x` и `pytz-2024.x` (или `Requirement already satisfied` для них, если версии уже стояли).
- Оператор присылает результат маскированного grep-а по `.env` на сервере: видно три строки с ключами `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `TZ` (значения замаскированы как `=***`). Никаких реальных значений секретов в чате/логе фичи.
- В `logs/deploy/deploy-log.md` зафиксированы: timestamp МСК, маршрут, git SHA, список FILES, статус pip install, статус env-ключей, явный handoff на Task 19.

- Если `pip install` упал на сервере — в логе будет `ERROR: Could not find a version ...` или похожее. Не пытаться чинить через предложения оператору `pip install` локально — пусть оператор сам выберет (бывают ситуации с отсутствующим build toolchain под `anthropic` на старом Python). Зафиксировать в `deploy-log.md` и отдать оператору.
- Если `.env` на сервере уже существует с предыдущей версии и не содержит новых ключей — оператор должен дописать их РУКАМИ на сервере (не через deploy, чтобы не перезаписать реальные значения). Проверка через grep после правки.
- Никогда не выводить значения секретов в чат/лог. Все grep-команды, которые передаются оператору — обязательно с маскированием через `sed "s/=.*/=***/"` или аналогом.

**Implementation hints:**
- Опереться на `feedback_operator_prod_ops` из памяти: оператор сам применяет любые продакшн-операции; агент ТОЛЬКО готовит. Никаких попыток SSH из агента.

- `deploy-log.md` — это рабочий артефакт фичи, потом будет читаться при `done` и при ретроспективе. Краткий, структурированный, без воды.
- Если что-то непонятно из логов оператора — спросить уточняющий вопрос, не догадываться. Лучше один раз переспросить, чем зафиксировать "OK" по пустому логу.
