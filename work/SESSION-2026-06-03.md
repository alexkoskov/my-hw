## Fix shipped — orangetrack-br-paragraph-split (XS-size, write-code shortcut)

**Symptom.** 2026-05-14: orangetrack's
`/hot-wheels-2026-boulevard-mix-3-h-case-report/` rendered with the
5-item series checklist (`#151 – Toyota Alphard … #155 – …`) all
collapsed onto one line on Telegra.ph, both on prod and test.

**Root cause.** The Boulevard mix posts close with a series/case list
authored in WordPress as a single `<p>` with `<br>` between items:

```html
<p>#151 – <strong>'15 Toyota Alphard</strong>
<br>#152 – <strong>Koenigsegg CC850</strong>
<br>#153 – <strong>Datsun King Cab Baja Custom</strong>
…</p>
```

BeautifulSoup's `get_text` collapses `<br>` into a single space, so the
existing `_emit_paragraph` emitted one paragraph block with all five
items in one line. The downstream LLM splice cannot un-collapse the
list because the semantic boundary (the `<br>`) is lost by the time
the text reaches it.

**Fix.** In [`orangetrack_source.py`](../orangetrack_source.py)
`_emit_paragraph`: if `p_tag.find("br")` returns nothing, fall through
the original single-paragraph path unchanged. Otherwise walk
`p_tag.children`, slice at every `<br>`, wrap each segment in a fresh
`<p>` via `BeautifulSoup(..., "html.parser")`, run it through
`_runs_from_tag`, and emit one paragraph block per segment. Telegra.ph
then renders each on its own line.

**Whitespace normalisation.** The segment-wrap path exposed a latent
double-space: a text node ending in whitespace (`"#151 – "`) followed
by a tag (`<strong>`) produces two runs whose `" ".join(...)`
concatenation yields `"#151 –  Alphard"`. Probed the existing no-br
path with the same HTML — confirmed the bug pre-dates this change
(`'#151 –  foo'` in repl) but stayed invisible because existing tests
asserted `in` substring matches, not exact equality. Fix in the new
branch only:

```python
text = re.sub(r"\s+", " ", " ".join(r["text"] for r in runs)).strip()
```

The flattened `text` is what the renderer's
`text.find(run_text)` matches against — runs themselves stay
verbatim, so substring lookup still locates each run for inline
formatting. The no-br path keeps its existing (slightly-double-spaced)
behaviour untouched: out of scope; no prod symptom.

**Tests.** 2 new in
[`tests/test_orangetrack_source.py`](../tests/test_orangetrack_source.py),
class `TestListItemParsing`:

- `test_br_separated_p_splits_into_paragraph_blocks` — exact 5-item
  shape from the live mix-3-H article, asserts 3 paragraph blocks in
  DOM order with exact text.
- `test_p_without_br_emits_single_paragraph` — sanity that a plain
  `<p>` still emits exactly one paragraph block (no regression of the
  unchanged no-br path).

Also fixed an unrelated stale assertion in the same test class:
`assert list_items[0]["text"] == "X"` had migrated into the new
`test_p_without_br_emits_single_paragraph` body during the earlier
edit (sitting on disk since 2026-05-14, unverified). Returned it to
