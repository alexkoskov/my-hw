# Task 8: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [skills/test-master/SKILL.md](~/.claude/skills/test-master/SKILL.md)

## Description

Полный аудит качества тестов для фичи cross-source dedup. Это финальная проверка качества тестов после того, как все Wave 1 (Tasks 1-3) и Wave 2 (Tasks 4-5) задачи закодированы и прошли свои локальные ревью (включая test-reviewer на каждой задаче). Цель аудита — холистический взгляд на всю тестовую базу фичи: убедиться что тесты действительно проверяют поведение, а не просто запускают код; что критические инварианты фичи (обязательная классификация реальной пары 2026-06-03, все 4 ветви dedup-гейта, schema-pin против дрейфа) защищены тестами, которые сломаются при регрессии.

Аудитор сам и есть ревью — отдельной фазы рецензирования у этой задачи нет. Выход — отчёт в `work/cross-source-dedup/logs/audits/test-audit.md` со списком находок (severity: critical / high / medium / low / info), конкретными цитатами из тестов, рекомендациями по исправлению и общей оценкой готовности тестовой базы фичи к деплою.

Контекст риска: фича добавляет новый detection-gate в production-loop (`news_bot.job()`). Если тесты пропустят регрессию (например, пара 2026-06-03 перестанет блокироваться, soft-flag rate-limit перестанет работать, или degraded-mode перестанет пропускать статью), фича может либо начать блокировать валидный контент, либо тихо пропускать дубли — оба сценария операционно дороги (требуют ручного отката + перезапуск backfill). Поэтому аудит должен быть строгим именно к must-pass контракту калибровки, schema-pin тестам и покрытию всех веток.

## Details

**Audit dimensions (7 направлений — каждое должно быть закрыто в отчёте):**

1. **Калибровочный тест meaningfulness** — `test_calibration_accuracy` грузит фикстуру из `tests/fixtures/cross_source_dedup_pairs.py` (8 labelled pairs) и прогоняет через `extract_fingerprint` + `similarity` + классификацию по порогам. Опасность: тест может стать тавтологичным, если labels в фикстуре подгонялись под текущий вывод экстрактора (тогда экстрактор «проверяет сам себя»). Проверить, что labels фикстуры обоснованы внешне (комментариями со ссылками на code-research §14.F, реальный URL для Pair 1, чёткий human-readable rationale для каждой пары), а не «что выдаёт код, то и правильно».

2. **Калибровочный must-pass split** — `test_calibration_real_pair_must_pass` (Decision 13) — отдельный тест, который требует, чтобы Pair 1 (реальная 2026-06-03 t-hunted ↔ autoevolution) классифицировалась как `block`. Защищает load-bearing пример от поглощения 1-misclassification бюджетом в `test_calibration_accuracy` (≥7/8 floor). Проверить: (а) тест существует как отдельная функция, (б) он явно ассертит `'block'`, а не «overlap ≥ 0.50» (порог может уехать, нужна именно семантика решения), (в) Pair 1 в фикстуре действительно помечена как real-pair с источниковыми URL в комментарии.

3. **Интеграционные сценарии — покрытие всех 4 ветвей dedup-гейта** — `TestCrossSourceDedup` должен содержать ≥7 сценариев по списку tech-spec lines 312-320:
   - **block** — два mock-article с 100% overlap → второй не в pending, `mark_processed` вызван, E015 отправлен (pins Decision 8).
   - **flag** — overlap 35% → оба в pending, E014 отправлен один раз.
   - **flag rate-limit** — повтор той же пары в 7-дневном окне → второй E014 НЕ отправлен.
   - **pass с непустым fp** — non-empty fingerprint, нет матча в окне → статья в pending с populated fingerprint, никаких pings (доминирующий production-кейс, защищает от регрессии «no-match случайно блокирует или пингует»).
   - **within-source dedup (AC7)** — два article из одного source_name → второй blocked (pins Decision 9 no-source-filter против будущей «оптимизации»).
   - **empty fingerprint** — body без брендов → статья проходит, fingerprint `{"strict":[],"brands":[]}` в pending, comparison не делается.
   - **degraded mode** — `extract_fingerprint` пропатчен на raise → статья всё равно публикуется, fingerprint NULL, E016 отправлен один раз (rate-limited).
   Отчёт должен явно поставить ✓ или ✗ для каждого из 7 сценариев.

4. **TestFingerprintCarryThrough** — отдельный тест (AC2): pending row с непустым `model_fingerprint` через `move_to_published` → `published_articles.model_fingerprint` совпадает с input. Проверить, что тест ассертит именно равенство dict-объекта (после JSON-roundtrip через `_PENDING_JSON_COLS`), а не сырую строку JSON — иначе он не пинит автодеcериализацию.

5. **Schema-pin тесты ловят отсутствующую колонку** — `EXPECTED_PENDING` в `tests/test_pending_articles_repo.py` и `EXPECTED_PENDING_COLUMNS` / `EXPECTED_PUBLISHED_COLUMNS` в `tests/test_migration.py` должны содержать `model_fingerprint`. Проверить: (а) удаление одной из ALTER TABLE из миграционного блока в `pending_articles_repo.init_schema()` сломает эти тесты (т.е. тест действительно «пинит» колонку, а не просто перечисляет «все, что нашлось»), (б) double-init idempotency тест в `test_migration.py` проверяет, что повторный вызов `init_schema(conn)` на той же connection не падает (Decision 11 — `try/except sqlite3.OperationalError`).

6. **JSON-column roundtrip пин `_PENDING_JSON_COLS`** — в `test_pending_articles_repo.py` должен быть тест: `insert_pending` принимает dict в `model_fingerprint`, `get_pending`/list возвращает dict (не строку). Проверить: если разработчик случайно забудет добавить `'model_fingerprint'` в `_PENDING_JSON_COLS`, тест упадёт (значение вернётся как str вместо dict). Это критично, потому что `_row_to_dict` использует список колонок для auto-deserialize, и опечатка не вызовет исключение — просто молча вернёт строку.

7. **Моки не протекают в assertions** — пройти по `TestCrossSourceDedup` и `test_backfill_fingerprints.py` — в каждом тесте с патчингом (`patch('news_bot.fetch_full_article')`, `patch('news_bot.send_admin_notification')`, `extract_fingerprint` raise-mock, и т.д.) проверить, что assertions проверяют поведение системы (что было вставлено в pending, что было передано в `send_admin_notification`), а не возврат самих моков. Анти-паттерн: `mock.return_value = X; ...; assert mock(...) == X` (это тест на то, что mock работает как mock, а не на код).

   Особое внимание — degraded-mode тест: `extract_fingerprint` пропатчен на `side_effect=Exception('boom')`. Assertion должен проверить: (а) статья всё равно вставлена в pending с `model_fingerprint=None`, (б) `send_admin_notification` вызван с E016-alert, (в) при повторе в течение часа — E016 НЕ вызван. Если ассертится только «mock был вызван» (`mock.assert_called()`) — это слабый тест.

**E016 window-expiry — отдельная проверка:**

Тест в `test_pending_articles_repo.py` для `is_dedup_degraded_rate_limited` + `mark_dedup_degraded_pinged` должен делать 3 шага: (1) `mark_dedup_degraded_pinged(conn)`, (2) `assert is_dedup_degraded_rate_limited(conn) is True`, (3) перевести «сейчас» вперёд на >1 час (через `freeze_time` / `monkeypatch.setattr(datetime, ...)` / параметр `now=` если он есть в API), (4) `assert is_dedup_degraded_rate_limited(conn) is False`. Если тест использует `time.sleep(3601)` — это unaccept (CI flakiness + 1 час). Если тест проверяет только шаги 1-2 (без fast-forward) — окно никогда не закрывается, regression «rate-limit залип навсегда» не ловится.

**Per-pair soft-flag rate-limit — аналогично:**

Тест в `test_pending_articles_repo.py` для `is_pair_rate_limited` + `mark_pair_pinged` должен проверять: (а) две независимые пары трекаются независимо (mark пары A не делает rate-limited пару B), (б) одна и та же пара после mark остаётся rate-limited в окне 7 дней и не rate-limited после.

**Calibration fixture — содержательная проверка:**

`tests/fixtures/cross_source_dedup_pairs.py` должна содержать 8 пар, явно перечисленных в tech-spec line 304:
- Pair 1 = real 2026-06-03 (t-hunted ↔ autoevolution Car Culture Road Trip Mix) — duplicate.
- Pairs 2-4 = synthetic duplicates.
- Pair 5 = same brand different models (AC8 probe — должно быть НЕ duplicate, защита от brands-fallback over-trigger).
- Pair 6 = 1-token both sides (guard probe — НЕ duplicate, защита от 1-token brand fallback ложно срабатывающего).
- Pair 7 = different series same brand (НЕ duplicate).
- Pair 8 = industry news vs car review (НЕ duplicate, индустриальная статья без конкретной модели).

Отчёт должен явно подтвердить, что фикстура содержит все 8 пар в правильных категориях.

**Dependencies:** аудит идёт после Tasks 4 и 5 (Wave 2) — все тестовые файлы должны существовать и быть закодированы.

**Edge cases аудита:**
- Если какой-то тест из tech-spec Testing Strategy отсутствует — это finding с severity critical.
- Если тест существует, но проверяет не то, что обещает (например, `test_e016_rate_limited` без fast-forward) — finding с severity high.
- Если тест проверяет правильную вещь, но через хрупкий механизм (e.g. сравнение строкового представления dict) — finding с severity medium.
- Если тест избыточен или дублирует другой — finding с severity low/info, не блокер.

**Implementation hints:**
- Структура отчёта: краткий executive summary (2-3 предложения) → таблица или список находок по severity → секция «PASS dimensions» где явно отмечены пройденные пункты → финальный вердикт.
- Для каждого finding: путь к файлу + номер строки + цитата (3-10 строк) → что именно не так → рекомендация (что добавить / переписать / удалить).
- Аудитор НЕ правит тесты сам — только отчёт. Если найдены critical/high находки — они уходят в Task 9 (Pre-deploy QA) либо ремонтируются отдельным этапом, как решит оркестратор feature-execution.
- При сомнениях в meaningfulness калибровочной фикстуры — посмотреть на code-research §14.F (источниковый rationale для каждой пары), если документ доступен.
