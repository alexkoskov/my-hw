# Task 11: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Финальная верификация фичи cross-source dedup на живом прод-окружении (VPS). Включает два слоя:

1. **Немедленная проверка после деплоя (Task 10)** — оператор вручную запускает one-shot `backfill_fingerprints.py` на проде, чтобы закрыть холодный старт (7-day window без исторических фингерпринтов). Агент собирает stdout summary и валидирует counts по `published_articles` через sqlite3 CLI.
2. **2-недельный пассивный мониторинг** — оператор спот-чекает каждый `[E014]` и `[E015]` ping в Telegram, раз в неделю просматривает production-канал (numeric ID из `TELEGRAM_CHANNEL_ID` env на VPS, см. `deployment.md` — оператор знает точный handle; НЕ использовать `@myhwchannel123`, это тестовый инстанс) за последние 7 дней на предмет видимых дубликатов (false negatives). Агент собирает observations и фиксирует итог в `decisions.md`.

Эта задача — финальный квалити-гейт фичи. Verification result IS the review (никаких code/security/test ревьюверов — фича уже прошла все 6/7/8 аудиты в Audit Wave). Без неё фича считается недоверифицированной даже при зелёном CI и успешном деплое — потому что user-spec AC12 (calibration ≥95%) и AC3/AC4 (видимость E014/E015 для оператора) проверяются только на живом трафике.

Оператор управляет прод-операциями (SSH, sqlite3 на VPS), агент готовит инструкции и собирает отчёт.

## What to do

1. **Подготовить операторскую инструкцию для backfill-запуска на проде:**
   - Точная команда: `cd /home/hwbot/bot && python3 backfill_fingerprints.py --days 14` (путь подтвердить из `deployment.md` перед выдачей оператору).
   - Опциональный preview: `--dry-run --days 14` перед боевым запуском.
   - Ожидаемая длительность: ~5 минут (≈50 статей × ~3 сек/fetch + 1 сек sleep между fetch'ами).
   - Что оператор присылает обратно: полный stdout summary блок (Window / Processed / Skipped / Empty fp / Errors / Duration).

2. **Валидировать stdout summary backfill-скрипта:**
   - `Errors: 0` — pass. `Errors: 1-3` с операторской пометкой "Cloudflare 403 на autoevolution ID X, Y, Z" — accept с фиксацией в отчёте (известный риск из tech-spec Risks секции — backfill counts errors per row и continues; оператор может перезапустить после Cloudflare cooldown).
   - `Errors > 3` без объяснения — fail; запросить у оператора traceback (или логи `journalctl -u <bot-service> --since "10 min ago"`).
   - `Window: 14 days` — sanity check (если оператор случайно передал `--days 90`, summary это покажет).
   - `Processed + Skipped + Empty fp + Errors == Total scanned` — арифметическая консистентность.

3. **Валидировать DB-counts через sqlite3 CLI (operator-side, агент готовит запросы):**
   - Запрос 1: `sqlite3 /home/hwbot/bot/news.db "SELECT COUNT(*) FROM published_articles WHERE model_fingerprint IS NOT NULL;"` — должен равняться (Processed + Skipped + Empty fp) из summary backfill'а в 14-дневном окне.
   - Запрос 2: `sqlite3 /home/hwbot/bot/news.db "SELECT COUNT(*) FROM published_articles WHERE published_at >= datetime('now', '-14 days');"` — общее число строк в окне; разность с Запросом 1 равна Errors из summary (NULL = не attempted или transient fail).
   - Запрос 3 (empty-fp counter, устойчивый к whitespace в `json.dumps`): предпочтительно — `sqlite3 /home/hwbot/bot/news.db "SELECT COUNT(*) FROM published_articles WHERE json_extract(model_fingerprint, '$.strict') = '[]' AND json_extract(model_fingerprint, '$.brands') = '[]';"` (проверка доступности JSON-функций (на SQLite ≥ 3.38 JSON1 встроен безусловно, и `sqlite_compileoption_used('ENABLE_JSON1')` возвращает `0` даже когда `json_extract` работает; используем функциональный тест): `sqlite3 /home/hwbot/bot/news.db "SELECT json_extract('{\"test\":[]}', '$.test');"` должен вернуть `[]`). Fallback (если JSON1 недоступен) — LIKE-паттерн без зависимости от точного форматирования: `sqlite3 /home/hwbot/bot/news.db "SELECT COUNT(*) FROM published_articles WHERE model_fingerprint LIKE '%\"strict\":%[]%' AND model_fingerprint LIKE '%\"brands\":%[]%';"`. Должен равняться Empty fp из summary (computed-empty terminal state — industry news, retrospective без брендов). НЕ использовать exact-string match `model_fingerprint = '{"strict":[],"brands":[]}'` — `_dumps()` может сериализовать с пробелами после `:` или `,`, что даст false zero.
   - Если хоть один counter не совпадает в пределах ±2 (округление времени между запуском backfill'а и SELECT'ом) — описать расхождение в отчёте и попросить оператора перезапустить backfill (он идемпотентный по `WHERE model_fingerprint IS NULL`).

4. **Спланировать 2-недельный пассивный мониторинг (operator-side, agent collates):**
   - **Daily-ish:** оператор пересылает агенту каждый `[E014]` и `[E015]` ping из своего Telegram admin-чата. Агент логирует в отчёт: timestamp, тип (E014/E015), пара ссылок, % overlap, оператор-вердикт (реально дубль / ложное срабатывание).
   - **Weekly (1× за каждую из двух недель):** оператор просматривает production-канал (numeric ID из `TELEGRAM_CHANNEL_ID` env на VPS, см. `deployment.md` — оператор знает точный handle; НЕ использовать `@myhwchannel123`, это тестовый инстанс) за последние 7 дней на видимые дубли (две статьи про одну партию/модельный ряд от разных источников, не отловленные ни E014, ни E015). Каждый найденный false negative — record в отчёт с обеими ссылками и предположением о причине (брендов не было в лексиконе / similarity < 0.30 / extraction вернула пустой фингерпринт).
   - **Накопительные метрики для финального отчёта в `decisions.md`:**
     - Total E015 hard-blocks за 2 недели — ожидание: 0-3 (фича не должна молча блокировать половину контента).
     - Total E014 soft-flags за 2 недели — ожидание: 1-5; >10 указывает на слишком низкий порог 0.30 либо лексикон ловит лишнее.
     - False positives (оператор посчитал ping ошибочным) — ожидание: ≤1 за 2 недели.
     - False negatives (видимые дубли в канале без ping'а) — ожидание: 0; ≥1 означает что user-spec AC12 calibration ≥95% не выполнен на проде (CI calibration accuracy floor — 87.5%; прод-флор — 100% на критических парах вроде t-hunted↔autoevolution из 2026-06-03).
     - E016 degraded-mode pings — ожидание: 0; ≥1 означает что extractor/repo/news_bot падает в проде и фича работает в degraded-режиме (статьи публикуются без дедупа). Любой E016 ping — немедленно эскалировать оператору + открыть багфикс.

5. **Финализировать отчёт в `work/cross-source-dedup/decisions.md`:**
   - Краткий summary (3-5 строк) — фича задеплоена N-го числа, backfill отработал, 2-недельный мониторинг показал X E014 / Y E015 / Z false-negatives / W E016, вердикт pass/fail.
   - Ссылка на полный verification log (этот файл `tasks/11.md` после fill'а + ссылки на бэкап stdout summary backfill'а, если оператор скинул в логи фичи).
   - Если хоть один из counters в шаге 4 вышел за expected range — отдельный раздел "Observations & deviations" с описанием и предлагаемым follow-up (поправить лексикон / поднять/опустить порог / расширить fixture'у).

## Verification Steps

### Smoke

Backfill-запуск на проде (operator-side, агент собирает stdout):

```bash
# на VPS, оператор:
cd /home/hwbot/bot
python3 backfill_fingerprints.py --dry-run --days 14   # preview, ничего не пишет
python3 backfill_fingerprints.py --days 14             # боевой запуск
```

Ожидание: exit code 0; summary блок содержит `Window:`, `Processed:`, `Skipped:`, `Empty fp:`, `Errors:`, `Duration:`. Полный summary — приложить к verification report.

DB-counts (operator-side, агент готовит SQL):

```bash
# на VPS, оператор:
sqlite3 /home/hwbot/bot/news.db <<'SQL'
SELECT COUNT(*) AS non_null_fp FROM published_articles WHERE model_fingerprint IS NOT NULL;
SELECT COUNT(*) AS total_window FROM published_articles WHERE published_at >= datetime('now', '-14 days');
-- Empty fp counter: JSON1-предпочтительный путь (устойчив к whitespace из json.dumps)
SELECT COUNT(*) AS empty_fp FROM published_articles
  WHERE json_extract(model_fingerprint, '$.strict') = '[]'
    AND json_extract(model_fingerprint, '$.brands') = '[]';
-- Если json_extract недоступен (функциональная проверка: SELECT json_extract('{"test":[]}','$.test'); должен вернуть [])
-- использовать LIKE-fallback:
-- SELECT COUNT(*) AS empty_fp FROM published_articles
--   WHERE model_fingerprint LIKE '%"strict":%[]%' AND model_fingerprint LIKE '%"brands":%[]%';
SQL
```

Ожидание: `non_null_fp == Processed + Skipped + Empty fp` (из summary); `total_window - non_null_fp == Errors`; `empty_fp == Empty fp`.

Schema-pin (operator-side, sanity check что миграция применилась первым тиком после деплоя):

```bash
sqlite3 /home/hwbot/bot/news.db ".schema pending_articles" | grep model_fingerprint
sqlite3 /home/hwbot/bot/news.db ".schema published_articles" | grep model_fingerprint
```

Ожидание: оба grep'а возвращают строку `model_fingerprint TEXT`. Если хоть один пустой — миграция не отработала, эскалировать (это уже должно было быть отловлено в Task 10, но это финальный safety net).

### User

2-недельный пассивный мониторинг (operator-side, агент агрегирует):

- **Каждый E014/E015 ping в Telegram admin-чате** — оператор пересылает агенту, агент записывает в verification log (timestamp, тип, ссылки, %, оператор-вердикт).
- **1× в неделю (×2)** — оператор просматривает production-канал (numeric ID из `TELEGRAM_CHANNEL_ID` env на VPS, см. `deployment.md` — оператор знает точный handle; НЕ использовать `@myhwchannel123`, это тестовый инстанс) за последние 7 дней на предмет видимых дубликатов: две статьи про одну партию/один модельный ряд от разных источников. **Edge cases:**
- **Backfill Errors > 0, оператор не объяснил:** запросить traceback или последние 50 строк журнала; не accept'ить молча.
- **Backfill оператор запустил с другим `--days N`:** summary покажет `Window: N days` — переcчитать ожидаемые DB-counts на новое окно.
- **DB-counts расходятся на >2:** возможна гонка между запуском backfill'а и SELECT'ом, если за это время прошёл cron-тик и обработал новые статьи. Попросить оператора перезапустить backfill (идемпотентный) ИЛИ перепроверить counts через ~6 минут (после следующего тика).
- **Production-канал (numeric ID из `TELEGRAM_CHANNEL_ID`, см. `deployment.md`) за 2 недели пустой / опубликовано <5 статей:** недостаточно трафика для статистических метрик. Зафиксировать в отчёте, продлить мониторинг ещё на 2 недели, не закрывать таску досрочно. НЕ путать с `@myhwchannel123` (тестовый инстанс) — там может быть пусто и это норма.
- **Оператор не отвечает 2+ дня:** не закрывать таску по таймауту, постучаться через назначенный канал связи.
- **Calibration false-negative на одной из соседних пар** (не критическая 2026-06-03 пара): записать в Observations, но это **не** жёсткий fail — CI floor 87.5% допускает 1-2 промаха на 8 пар. Жёсткий fail — только если промахнулась именно критическая t-hunted↔autoevolution пара ИЛИ её ближайший аналог.

**Implementation hints:**
- post-deploy-qa скилл (загруженный по `/skill:post-deploy-qa`) даёт методологию AVP-execution: парсинг verify-полей tech-spec, MCP-тулинг (здесь не применим — все ops operator-side), агрегация observations. Этот таск — operator-driven вариант: агент готовит точные команды, оператор выполняет, агент валидирует output.
- Никаких сторонних MCP не нужно: Telegram visual review целиком operator-side; bash на VPS — operator-side; sqlite3 — operator-side.
- Главный output этого таска — **`decisions.md` запись**: 1-3 предложения вердикт + ссылки на summary backfill'а и observation log. Без этого фича не считается завершённой даже при всех зелёных метриках.
- Соотносить наблюдения с user-spec AC: AC3 (E015 visible) — есть ли E015 в мониторинге; AC4 (E014 visible) — есть ли E014; AC5 (per-pair rate-limit 7 days) — нет ли duplicate E014 на одну и ту же пару в недельном окне; AC9 (degraded mode silent fallthrough) — нет ли E016 и при этом регулярных публикаций; AC12 (≥95% calibration) — false-negative rate в канале.
