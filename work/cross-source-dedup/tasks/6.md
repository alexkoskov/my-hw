# Task 6: Code Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Полный аудит качества кода фичи cross-source-dedup. Цель — холистический обзор уже реализованной фичи (после слияния Wave 1 + Wave 2): проверить кросс-компонентную согласованность, соответствие архитектурным решениям из tech-spec и общепроектным паттернам. Аудитор НЕ пишет код и НЕ правит реализацию — выход задачи это отчёт аудита, на основании которого operator/team-lead решает, что делать с findings (отдельный fix-task, переоткрытие задачи Wave 1/2, accepted-deviation).

Аудит обязателен потому что Wave 1 (Task 1, 2, 3) и Wave 2 (Task 4, 5) проходят свои локальные ревью (code-reviewer / security-auditor / test-reviewer), но никто не смотрит на фичу целиком. Локальные ревью могут пропустить: расхождение в форме JSON между admin_alerts и repo, дублирование regex-компиляции в двух модулях, неконсистентную дисциплину обработки ошибок (один файл `except Exception`, другой `except sqlite3.OperationalError`), нарушение Shared Resources Architecture (например, второй экземпляр `_BRAND_RE` где-то по ошибке), отклонение от паттерна-зеркала `boilerplate_filter.py` для `model_extractor.py` и `outage_state.py` для bot_state-helpers.

Результат — структурированный markdown-отчёт в `work/cross-source-dedup/logs/audits/code-audit.md` с найденными проблемами по приоритетам (Critical / Major / Minor / Nit) и явным разделом «No findings» по тем измерениям, где проблем не обнаружено.

### Focus list (точки, которые tech-spec явно поднял как кросс-компонентные риски)

1. **JSON shape uniformity** — `{"strict": [...], "brands": [...]}` должна быть одинаковой во всех слоях:
   - `model_extractor.extract_fingerprint` (производитель)
   - `pending_articles_repo._PENDING_JSON_COLS` + `_dumps`/`_row_to_dict` (хранилище)
   - `admin_alerts.alert_cross_source_dupe` (потребитель, формирует `models` список)
   - `news_bot._check_cross_source_dedup` (потребитель, передаёт в `similarity`)
   - Проверить, что NULL vs `{"strict":[],"brands":[]}` различение из Decision 5 действительно реализовано (NULL = "not yet processed", пустой dict = "ran, no brands").
2. **Compiled regex singleton** — `_BRAND_RE` существует только в `model_extractor.py` на module level; нет дублирования компиляции внутри `extract_fingerprint` (это убьёт perf budget из Acceptance Criteria <10ms на 10KB).
3. **Error handling discipline** — Decision 11 говорит `except sqlite3.OperationalError` для миграции, Decision 12 говорит `except Exception` для dedup gate. Проверить, что эти разные дисциплины не перепутаны между файлами; узкий except не «съел» широкий случай и наоборот.
4. **`boilerplate_filter.py` mirror** — `model_extractor.py` следует той же структуре (module docstring → compiled regex constants → pure helper functions, no I/O)? Сравнить порядок секций, naming convention для приватных констант, форму docstrings.
5. **`outage_state.py` pattern** — bot_state хелперы (`is_pair_rate_limited`, `mark_pair_pinged`, `is_dedup_degraded_rate_limited`, `mark_dedup_degraded_pinged`) следуют тому же API-стилю (имена, сигнатура, отношение к `conn`, парсинг timestamp)?
6. **Backfill `import news_bot` ordering** — `backfill_fingerprints.py` должен импортировать `news_bot` ПЕРЕД `logging.basicConfig()` (security-review caveat из tech-spec AC + Decision 10). Это критично для `_TokenRedactingFilter` — если порядок нарушен, токены могут утечь в stdout.
7. **`deploy.sh` FILES list** — оба новых top-level файла (`model_extractor.py`, `backfill_fingerprints.py`) добавлены в bundle. Без них прод упадёт с `ImportError` на первом тике.
8. **Dedup gate position** — в `news_bot.job()` гейт стоит между `_is_text_only_checklist` и `row` assembly (Decision 14)? Не перед `_is_text_only_checklist` (потратит extract на checklist-drop), не внутри `insert_pending` (нарушит separation).
9. **`mark_processed` на hard-block** — Decision 8: `block` ветка вызывает `mark_processed(link, title, pub_date)` перед `continue`. Проверить, что эта строка есть и аргументы корректные.
10. **Schema-pin tests updated** — `tests/test_pending_articles_repo.py::EXPECTED_PENDING` и `tests/test_migration.py::EXPECTED_PENDING_COLUMNS` + `EXPECTED_PUBLISHED_COLUMNS` содержат `model_fingerprint`. Без этого следующий unrelated PR может тихо сломать миграцию.

### Severity rubric

- **Critical** — блокирует deploy: бажный код, нарушенный user-spec/tech-spec AC, потеря данных, security risk. Пример: forgotten `mark_processed` на блоке → каждый тик заново качает дубль и шлёт E015 — flood.
- **Major** — значимый отход от tech-spec/project pattern, но не валит фичу. Пример: bot_state хелперы используют другой формат timestamp, чем `outage_state.py` — работает, но операторская консистентность нарушена.
- **Minor** — стилистика, naming, mild duplication, недостаток комментариев в нетривиальной regex. Пример: docstring `extract_fingerprint` не упоминает, что year prefix отбрасывается.
- **Nit** — мелочь, можно проигнорировать. Пример: лишний пробел в literal.

### What auditor MUST NOT do

- НЕ редактировать ни один исходный файл фичи. Аудит — только чтение и запись отчёта.
- НЕ запускать тесты (это Task 8 audit-wave + Task 9 pre-deploy QA).
- НЕ дублировать работу security-auditor (Task 7) и test-master (Task 8). Если по ходу замечено что-то из их зон — оставить короткую заметку в секции «Cross-check» отчёта, без полной проработки.
- НЕ предлагать конкретный diff. Findings содержат рекомендацию словами, не патч.

### Dependencies

- Task 4 (news_bot integration) и Task 5 (backfill script) ДОЛЖНЫ быть в состоянии `done` — аудит смотрит на финальное состояние всех 5 файлов.
- Tasks 1-3 неявно done (Task 4 от них зависит).

### Edge cases

- Если по ходу аудита обнаружится Critical finding, который требует немедленного пересмотра tech-spec Decision (а не просто фикса кода) — отметить это в Recommendations и пометить severity как Critical+Spec.
- Если файл вообще не был изменён в той форме, что предполагает tech-spec (например, `deploy.sh` FILES list не обновлён) — это Critical, не Major: фича не задеплоится.

### Implementation hints

- Аудит — линейная задача: прочёл файл, проверил по чек-листу, занёс finding или «No findings». Не пытаться запускать код или тесты.
- Использовать grep для проверки singleton-условий (`grep -rn "_BRAND_RE" .` — должно быть только в `model_extractor.py`).
- Для проверки JSON-shape uniformity — выписать строки из всех 5 файлов, где упоминается `'strict'` / `'brands'` ключ, сверить.
- Не растекаться: отчёт компактный, фокус на findings и явных «No findings», без пересказа того, что и так в tech-spec.
