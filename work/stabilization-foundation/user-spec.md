# User Spec: stabilization-foundation

## Что делаем

Закрываем три базовые дыры надёжности: делаем CI безусловным и изолированным от локальных секретов и сети, запрещаем production-процессу стартовать с неверной конфигурацией, БД или VPN-маршрутом и исправляем lifecycle планировщика после блокирующего стартового тика.

Это не переписывание 5200-строчного `news_bot.py`. Пакет создаёт проверяемый фундамент, на котором последующие упрощения и отдельный надёжный delivery административных алертов можно делать без ложнозелёного CI, опасного старта и двойных тиков.

## Зачем

Сейчас CI может пропустить тесты после tracked-изменения, а локальный `.env` способен скрыть порядок-зависимый тест или направить тестовый job в настоящий OpenRouter. В production Python стартует раньше, чем sidecar меняет default route; до слабой warning-only проверки БД процесс уже может создать SQLite-файл и обратиться к Telegraph, LLM или Telegram. Планировщик, в свою очередь, регистрирует cron до блокирующего immediate job: если job пересекает 10:00, просроченный слот выполняется сразу после него вторым тиком.

Итоговый риск — ложная уверенность в проверках, прямой трафик мимо VPN, работа с пустой или чужой БД, платные внешние вызовы из тестов и задвоенная обработка лент.

## Как должно работать

### Сценарий 1. Честный hermetic CI

1. Любое tracked-изменение в pull request или push запускает полный обязательный test job. Тип файла и результат сравнения только с `HEAD~1` не могут превратить job в `skipped`.
2. Test job начинает работу без значений из repository, runner или developer `.env`, которые способны включить production-интеграции. Загрузка dotenv для тестового процесса отключена до импорта runtime-модулей.
3. Исходящие сетевые обращения запрещены по умолчанию. Неподменённый Telegram, Telegraph, LLM, OpenRouter или иной HTTP-вызов немедленно роняет тест с понятной диагностикой, а не уходит в живой сервис.
4. Каждый тест даёт тот же результат отдельно, в файле и в полном suite. В частности, Telegraph-тест не получает токен, оставленный предыдущим тестом.

### Сценарий 2. Fail-closed production startup

1. Production-контейнер до запуска Python ждёт, пока точный default route будет направлен через VPN gateway `172.28.0.2`. Ожидание ограничено по времени; timeout, неверный gateway или отсутствие маршрута завершают контейнер с ненулевым кодом. Прямого fallback нет.
2. Compose закрепляет несекретные production-инварианты: `INSTANCE_LABEL=prod`, `DB_FILE=/data/news.db`, `TZ=Europe/Moscow`. Их нельзя случайно заменить пустым или относительным значением из `.env`.
3. После route barrier, но до любого API-вызова, listener-а и записи в SQLite, процесс локально проверяет обязательную конфигурацию: Telegram bot token, channel ID, числовой admin ID, существующий Telegraph access token, явно выбранный LLM provider, ключ выбранного provider-а и model. Настройки review-кнопок остаются необязательными.
4. Затем выполняется read-only preflight БД. В обычном production-start обязаны совпасть точный путь и mount, файл должен существовать, читаться как исправная SQLite, содержать таблицу `processed_news` и хотя бы одну строку в ней. Preflight не создаёт файл, таблицы или journal и не модифицирует существующую БД.
5. Любая ошибка route/config/DB даёт redacted fatal log и ненулевой exit до health-listener-а, schema initialization, job и внешнего трафика.
6. Пустая или отсутствующая production-БД разрешается только когда одновременно заданы `ALLOW_EMPTY_PROD_DB=1` и отдельная одноразовая bootstrap/recovery-авторизация. Одного флага недостаточно. Авторизация хранится вне целевой SQLite, атомарно расходуется одной попыткой и не может быть повторно использована после рестарта.
7. Даже с авторизацией нельзя обойти неверный путь или mount, повреждённую SQLite и неполную обязательную конфигурацию. Для штатного upgrade с заполненной БД override не требуется.
8. Только после успешного preflight процесс выполняет обычную idempotent schema initialization, запускает listener, регистрирует расписание и обращается к внешним сервисам.
9. Local/test режим сохраняет относительную пустую БД и не требует VPN. Production-защита включается только явным production-контрактом, а не догадкой по наличию отдельных секретов.

### Сценарий 3. Lifecycle планировщика

1. После успешного startup blocking immediate job выполняется до регистрации ежедневных cron-слотов.
2. Если процесс стартовал до 10:00, а immediate job завершился после 10:00, просроченный 10:00 tick не исполняется следом: за этот запуск был ровно один job, а ближайший 10:00 будет завтра.
3. Если тот же immediate job завершился до 10:00, канонический 10:00 tick сохраняется. Он нужен, чтобы забрать материалы, появившиеся после быстрого startup-fetch.
4. При свежем рестарте в середине дня новый процесс снова выполняет immediate recovery job и после него вычисляет оставшиеся будущие слоты текущего дня. Постоянный маркер «сегодня уже запускались» не используется.
5. Исключение из immediate job не проглатывается: процесс завершается с ненулевым кодом, Docker может его перезапустить и тем самым повторить recovery path.

## Критерии приёмки

- [ ] Для любого tracked-изменения GitHub Actions запускает полный test job; в workflow нет content/path/extension-ветки, способной отметить обязательные тесты `skipped`.
- [ ] Полный suite проходит в чистом окружении с отключённым dotenv и заблокированной внешней сетью; целевые тесты проходят отдельно и не зависят от порядка, а намеренный неподменённый HTTP-вызов делает тест красным.
- [ ] В production Python не запускается, пока default route не указывает через `172.28.0.2`; неверный route и bounded timeout дают ненулевой exit без direct fallback.
- [ ] Compose закрепляет `INSTANCE_LABEL=prod`, `DB_FILE=/data/news.db`, `TZ=Europe/Moscow`; отсутствие или неверный формат любого обязательного config-поля останавливает startup до side effects, а секреты не попадают в лог.
- [ ] Read-only DB matrix покрывает существующую заполненную БД, отсутствующий файл, пустой ledger, отсутствие `processed_news`, corrupt SQLite, unreadable file, неверный путь и отсутствующий mount; только первый случай проходит обычный startup, остальные завершаются без создания или изменения DB-файлов.
- [ ] Пустой bootstrap проходит только с парой `ALLOW_EMPTY_PROD_DB=1` + отдельная одноразовая авторизация; повторное применение, один флаг без авторизации и попытка обойти wrong path/mount/corruption/config завершаются ошибкой.
- [ ] Local/test по-прежнему может создать относительную пустую БД без VPN и production bootstrap-авторизации; production-проверки не активируются случайно от одного локального env-поля.
- [ ] Lifecycle-тест с реальным `schedule` и контролируемым временем доказывает: старт до 10:00 с blocking job, пересёкшим 10:00, вызывает job один раз и назначает следующий 10:00 на завтра.
- [ ] Lifecycle-тесты доказывают оба сохранённых поведения: быстрый pre-10 immediate job оставляет сегодняшний 10:00 tick, а mid-day restart выполняет immediate recovery и регистрирует только будущие слоты дня; persistent daily marker отсутствует.
- [ ] Изменение не меняет reader-visible формат, дедуп-правила, alert-тексты и существующие данные; исключение immediate job выходит наружу, а все новые fatal-сообщения диагностичны и не раскрывают значения секретов.

### Краевые случаи

- Developer или CI environment содержит настоящие `OPENROUTER_API_KEY`, Telegram и Telegraph credentials — тестовый процесс всё равно их не использует.
- Тест, который раньше проходил только после другого теста, запускается первым или отдельно — результат не меняется.
- VPN sidecar ещё жив, но route отсутствует, указывает на другой gateway или появился после timeout — Python не стартует.
- `/data/news.db` отсутствует на корректном mount, существует на неверном mount, является каталогом, не читается или содержит не-SQLite данные — обычный production-start падает без записи.
- БД исправна и таблица существует, но `processed_news` пуста — обычный startup падает; bootstrap разрешён только одноразовой парой подтверждений.
- Bootstrap-авторизация расходована, а initialization затем упал — следующий запуск требует новую явную авторизацию, а не повторно использует старую.
- Выбранный LLM provider не имеет соответствующего key или model, admin ID нечисловой, Telegraph token должен был бы создаваться через сеть — startup падает локально до network.
- Старт в 09:59 завершает immediate job в 09:59:59, ровно в 10:00 или после 10:00 — тесты фиксируют границу без двойного запуска.
- Рестарт в 15:00 не подавляется фактом утреннего job: immediate recovery выполняется, прошедшие cron-слоты не догоняются, будущие сохраняются.

## Ограничения

- В scope входят только CI isolation, production route/config/DB startup gates и scheduler lifecycle.
- `reliable-admin-alert-delivery` — отдельная следующая задача. Туда входят durable delivery/retry для `[E014]`, `[E016]`, `[E038]` и outage alerts `[E010]`–`[E013]`. Новейшее решение «недоставленный `[E014]` не разрешает автопубликацию через 24 часа» заменяет старую семантику silence из `dedup-broad-precision`, но в этом пакете alert-код и approved spec не меняются.
- `[E036]` и работа с blind spots принадлежат `operator-blind-spots`; `[E017]` уже следует корректному mark-only-on-success pattern и здесь не меняется.
- Не меняются precision/content-дедуп, форматы публикаций и алертов, publication crash-gap, существующие SQLite rows и schema business data.
- Не входят большой модульный рефакторинг `news_bot.py`, off-box backup, SSH hardening и введение нового dependency lockfile.
- Новая внешняя инфраструктура не добавляется. Production остаётся одним Docker Compose instance без staging.
- Production deploy, live Telegram/LLM/Telegraph calls и изменение удалённого хоста в рамках задачи запрещены.

## Риски

- **Fail-closed остановит первый deploy или recovery с действительно пустой БД.** Митигация: документированный одноразовый bootstrap path, который требует два независимых явных сигнала и не ослабляет остальные проверки.
- **Постоянно выставленный override превратится в скрытый fail-open.** Митигация: флаг сам по себе бесполезен, отдельная авторизация расходуется атомарно и не хранится внутри разрешаемой пустой БД.
- **Route barrier создаст бесконечный restart loop при поломке VPN.** Митигация: bounded wait, точный redacted fatal reason и отсутствие direct fallback; исправляется инфраструктура, а не обходится защита.
- **Подавление overdue tick случайно уберёт полезный 10:00 fetch.** Митигация: cron регистрируется после immediate job; быстрый pre-10 запуск всё ещё получает сегодняшний слот, долгий — только завтрашний.
- **Once-per-day marker сломал бы recovery после mid-day restart.** Митигация: такой persistent marker явно запрещён; каждый новый process делает immediate recovery и заново вычисляет будущие слоты.
- **Hermetic CI сломает тесты, неявно использовавшие сеть или `.env`.** Митигация: это ожидаемое обнаружение дефекта; интеграции заменяются явными doubles, а isolation проверяется отдельным и полным запуском.
- **Production-only guard заденет локальную разработку.** Митигация: режим определяется явным production-контрактом, local/test cases входят в обязательную integration matrix.

## Технические решения

- Мы решили убрать условный skip обязательного CI job целиком, потому что классификация tracked-файлов уже пропустила `requirements*.txt` и runtime-значимые файлы внутри `.claude`.
- Мы решили отключать dotenv до импорта runtime-кода и запрещать сеть по умолчанию на уровне test harness, потому что очистка нескольких известных ключей не защищает от нового provider-а или скрытого import-time state.
- Мы решили ставить route barrier перед Python entrypoint, потому что проверка внутри `main()` уже слишком поздняя: импорт и ранняя инициализация могут иметь side effects.
- Мы решили закрепить несекретные production-инварианты в Compose, а секреты валидировать локально без печати значений, потому что hand-managed `.env` не является надёжным контрактом.
- Мы решили отделить read-only DB preflight от idempotent schema initialization, потому что `sqlite3.connect()` и schema setup способны создать или изменить именно тот файл, ошибку которого защита должна обнаружить.
- Мы решили требовать отдельную one-use authorization вне целевой SQLite и расходовать её атомарно, потому что `ALLOW_EMPTY_PROD_DB=1` сам по себе легко забыть навсегда, а маркер внутри пустой БД исчезает вместе с ней.
- Мы решили выполнять immediate job до регистрации cron, потому что библиотека тогда вычисляет `next_run` от фактического времени завершения и не создаёт overdue repeat.
- Мы решили не вводить persistent daily job marker, потому что он не различает нормальную обработку и новый process, которому после crash нужен recovery fetch.

## Тестирование

**Unit-тесты:** делаются всегда. Добавляются проверки чистого env/config validator-а, read-only DB preflight, one-use authorization и расчёта scheduler boundary.

**Интеграционные тесты:** делаем. Нужны subprocess/container-entrypoint проверки порядка route → Python → config/DB → runtime, synthetic route table, SQLite fault matrix, реальный `schedule` с контролируемым временем, сетевой запрет и полный suite без dotenv.

**E2E-тесты:** live E2E не делаем. Обращения к production Telegram, Telegraph, LLM/VPN и deployment ничего не добавляют к детерминированным инвариантам, но несут риск публикации, расходов и изменения удалённого состояния. Внешние границы проверяются doubles и статическим `docker compose config`.

## Деплой

Реализация проходит обычный dev → PR → main flow только после зелёного безусловного CI. Production deploy остаётся ручным и выполняется пользователем вне окна публикаций 10:00–20:00 МСК; текущая задача его не выполняет.

Для обычного upgrade с существующей заполненной `/data/news.db` новых секретов и override нет. Первый bootstrap или осознанное recovery пустой БД требует заранее создать отдельную одноразовую авторизацию, запустить контейнер с `ALLOW_EMPTY_PROD_DB=1`, убедиться в её расходовании и убрать временный флаг.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|---------------------|
| 1. Запустить отдельные известные isolation-тесты до и после полного файла | `pytest` с clean env | Результат одинаков, Telegraph token и другой state между тестами не протекают |
| 2. Запустить полный suite без dotenv и с network deny | `pytest` | Suite зелёный; намеренный неподменённый HTTP-вызов в контрольном тесте падает локально |
| 3. Проверить workflow на обычном и docs/config-only изменении | GitHub Actions fixture/static test | В обоих случаях обязательный полный test job имеет run, а не skipped |
| 4. Прогнать route/config startup matrix | subprocess + synthetic `ip route`/entrypoint doubles | Python marker отсутствует при wrong route/timeout; config failure предшествует listener, DB write и network |
| 5. Прогнать SQLite fault и bootstrap matrix | temporary filesystem + SQLite | Только populated production DB или однократно авторизованный empty bootstrap проходят; failed preflight не создаёт и не меняет файлы |
| 6. Прогнать scheduler lifecycle на границах времени | `pytest`, реальный `schedule`, controlled clock | Crossing-10 даёт один job и завтра; quick pre-10 сохраняет 10:00; mid-day restart делает recovery и будущие slots |
| 7. Проверить Compose-контракт и весь regression suite | `docker compose config`, `pytest` | Production invariants закреплены, route barrier стоит перед Python, весь существующий suite зелёный |

### Пользователь проверяет

- Перед будущим обычным deploy убедиться, что production volume смонтирован, `/data/news.db` заполнена, а bootstrap-флаги отсутствуют; это защищает от случайного старта с новой БД.
- После ручного rebuild/restart вне 10:00–20:00 МСК проверить redacted startup log: подтверждены VPN route, config и DB preflight, затем выполнен ровно один immediate job.
- При настоящем первом bootstrap/recovery отдельно создать одноразовую авторизацию, после запуска проверить её расходование и удалить `ALLOW_EMPTY_PROD_DB`; live-публикации и Telegram-кнопки этой задачей не проверяются.
