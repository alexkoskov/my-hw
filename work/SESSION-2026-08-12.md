# SESSION 2026-08-11 … 2026-08-12 — hotfix: autoevolution Cloudflare, [E014] keep button, forwarding-plug leak

Started as "проверь состояние бота" and turned into a three-part hotfix. Covers
two days; named by the last one per the session-log convention.

## What was wrong

**The channel had published nothing since 9 August.** The daily plan pings did
not say so — `[E008]` reports intake counters, and those looked healthy
(75 entries a day). The source that carries ~60% of publications was down and
nothing alerted.

**Root cause: autoevolution turned on a Cloudflare JS challenge for article
pages** (403 + `cf-mitigated: challenge` + "Just a moment..."). The RSS feed kept
answering 200 throughout, which is exactly why the counters looked fine.

Not an IP problem — verified from three egress points before touching code:

| Egress | Article page | RSS |
|---|---|---|
| prod (IPv6, UK, via VPN) | 403 | 200 |
| dev box (IPv6, Estonia) | 403 | 200 |
| dev box forced IPv4 | 403 | — |

The retry design made it worse over time: a failed article is not marked
processed, so it is retried every tick. Dropped-article count climbed 2 → 5 → 6
per day — i.e. the bot knocked harder each day on a door that had been shut.

## What fixed it (measured, not guessed)

Two things, both load-bearing:

1. **Browser profile.** 403 on `chrome`, `chrome136`, `chrome142`, `chrome146`,
   `safari260`; **200 on `firefox147`** and `safari184_ios`. Cloudflare targets
   the Chrome fingerprint here — when the block returns, try another *family*,
   not a newer Chrome.
2. **A warmed, reused session.** Profile alone got 3 of 6 articles. One
   `curl_cffi.Session` warmed by a home-page GET first: **6 of 6**, control run
   4 of 4. Cloudflare grants clearance on that first hit; the old code opened
   every article cold.

Plus a one-shot retry on 403 that rebuilds the session — the process outlives
the daily tick, so by the next one the clearance cookie is ~24 h old and the
tick's *first* article is the one challenged.

## Two more defects found on the way

**`[E014]` «👍 Оставить» did nothing.** The alert promised «выпустит её в
ближайший слот»; the handler only returned a status string and left
`publish_after` untouched. Proven on prod, not inferred: operator pressed it
11 Aug 10:02, the article published 12 Aug 15:00 — exactly when the 24 h window
elapsed. Now calls `pending_repo.clear_deferral`, and answers honestly when the
row is *also* content-gate-held (both marks are written in the same insert —
an assumption I got wrong first time and the code reviewer caught).

**A package-forwarding affiliate plug reached subscribers** (12 Aug, Ford Bronco
article). All five filter layers missed it. See patterns.md § "Service-text
stripping" for the structural reason and the rules that came out of it; the
short version is that all nine long patterns transcribed the opening words of an
earlier incident, so every rewording was a fresh hole. Fourth leak of that class.

Also observed and NOT fixed: the LLM rendered «não está entregando para o
**Brasil**» as «доставку в **Россию**» — it localised a geographic fact rather
than translating it. Dropping the paragraph removed this instance. One data
point, so no prompt change; recorded in patterns.md.

## Process notes worth keeping

**Five of the nine review findings were defects in this session's own work**, not
in old code. The two that mattered most:

- The ad filter deleted a 284-char paragraph of prices and model names whole,
  because a paragraph-scoped rule for a plug that sits at the END cannot be
  `^`-anchored. Moved to sentence scope.
- A test that had already caught a real bug was **deleted rather than moved**
  when the rule changed scope. The test reviewer found it by mutation testing.

**The lesson to carry forward: a test built on the captured sample proves
nothing.** The signature patterns silently never fired — the captured paragraph
matched a neighbouring phrase rule instead, so everything looked green. Only a
test fed a *reworded* plug exposed it. Any future filter work here needs one.

## Deploy

**Not deployed at time of writing.** A rebuild was run on the host at 17:43 MSK
12 Aug while these changes were still uncommitted — `git pull` reported
"Already up to date" for `main` and the rebuilt image contained the old code, so
the tick at 17:43 dropped the same six articles again. Cost nothing that day
(the queue was empty and the 15:00 slot had already fired), but it is the second
reason to keep the window rule: the restart also resets the in-process schedule.

Order that actually works: commit → push `dev` → PR `dev` → `main` → merge →
`git pull && docker compose up -d --build` on the host, **after 20:00 MSK**.
