# User Spec: author-plug-filter

## Что делаем

Двухуровневый фильтр авторских плагов в соцсети, протекающих в публикации канала `@myhwchannel123`. **Variant A** — расширяем `boilerplate_filter.py` под фразы вида «(follow me on Instagram @diecast215)»: дроп целого параграфа на стороне источника до вызова LLM. **Variant B** — новый модуль `author_plug_filter.py`, вызываемый из `_fallback_publish` после транскреации, хирургически вырезает встроенные плаги из RU-текстов (заголовка, подзаголовка, параграфов и блоков), не трогая остальное содержимое.

## Зачем

Триггер — публикация 2026-05-02 14:40, в которой в канал утекло «(подписывайтесь на меня в Instagram @diecast215 )». `ux-guidelines.md` уже относит «author social links» к разрешённым дропам (категория a), но `boilerplate_filter.py` сегодня покрывает только UI-кнопки соцшеринга (категория b). Фильтр приводит реализацию к декларированному редакционному стандарту: подписчики видят только контент, а не сторонний промо-канал автора.

## Как должно работать

1. Парсер источника (autoevolution / lamley / mattel) собирает английские параграфы и блоки из статьи.
2. Перед возвратом парсер прогоняет всё через `filter_boilerplate(...)` / `filter_blocks(...)` — это **variant A**: короткие параграфы вида «follow me on Instagram», «Instagram: @diecast215», «@handle» в одиночку, «subscribe to my channel» и т.п. дропаются целиком.
3. То, что прошло, попадает в LLM (Claude / OpenRouter / OpenAI / Gemini) или, при глобальном outage, в Google Translate. На выходе — RU-тексты.
4. В `_fallback_publish` после `transcreate_via_claude` (или `_google_translate` ветки) на собранных `ru_title`, `ru_subtitle`, `ru_paragraphs`, `ru_blocks` запускается **variant B** — новый модуль `author_plug_filter.py`. Он regex'ом находит плаги (включая зонтичный паттерн на скобочные конструкции с упоминанием платформы и `@handle`) и вырезает только эти предложения, не трогая остальной текст параграфа.
5. Каждое удалённое предложение логируется на уровне INFO с самим вырезанным фрагментом, чтобы оператор мог проверить через `journalctl -u news_bot.service` и среагировать при ложном срабатывании.
6. Variant B **не запускается** при `via_review=True` (ручной редакторский путь через `hw_review publish`) — оператор уже снимает плаги на этапе `stage` по `ux-guidelines`.
7. Очищенные тексты идут в Telegraph и Telegram-канал.

## Критерии приёмки

### Variant A — drop-paragraph фильтр (EN-сторона, до LLM)

- [ ] AC1. Стандартный плаг «(follow me on Instagram @diecast215)» отдельным коротким параграфом дропается `filter_boilerplate` до LLM.
- [ ] AC2. Сирота-handle «@diecast215» на отдельной строке дропается паттерном `^@\w+$`.
- [ ] AC3. «Instagram: diecast215» (без `@`) отдельным параграфом дропается.
- [ ] AC4. Плаг как пункт списка («Follow me on Instagram for the next reveal») дропается — соседние bullet-пункты с реальным контентом сохраняются.
- [ ] AC14. Финальный список платформ для variant A: instagram, twitter, x, tiktok, youtube, facebook, reddit, patreon, discord, linktree. Threads и OnlyFans вне scope.

### Variant B — strip-sentence фильтр (RU-сторона, после LLM)

- [ ] AC5. «(подписывайтесь на меня в Instagram @diecast215)», встроенное в более длинный RU-параграф, удаляется. Остаток параграфа сохраняется byte-identical, кроме удалённого предложения.
- [ ] AC6. Плаг в начале параграфа («Welcome back, follow me on Instagram @diecast215. Today we look at...» → «...Today we look at...») удаляется только в первом предложении.
- [ ] AC7. Каждое срабатывание variant B пишет в журнал INFO с вырезанным фрагментом, чтобы оператор мог проверить через `journalctl`.
- [ ] AC8. Variant B применяется единообразно к `ru_title`, `ru_subtitle`, `ru_paragraphs`, `ru_blocks` (поля `text` для типов `lead`/`paragraph`/`heading` и `caption` для типов `image`/`video`). Один call site в `_fallback_publish`, накрывающий обе ветки — Claude и Google Translate.
- [ ] AC13. Variant B пропускает выполнение при `via_review=True` (ручной путь через `hw_review`).
- [ ] AC15. Variant B содержит **зонтичный** regex для скобочных конструкций с упоминанием любой платформы из списка AC14 + опциональный `@handle`, **независимо от глагольного якоря**. Это покрывает Google-translated варианты типа «(посмотрите меня в Instagram @x)», которые не попадают под якоря «подписывайтесь / follow me».
- [ ] AC16. Variant B обрабатывает `ru_paragraphs` и `ru_blocks` независимо. Если `_patch_text_with_ru_paragraphs` (`_llm_common.py`) уже вшила `ru_paragraphs` в EN-каркас блоков (при `blocks=null` от LLM), плаг может дублироваться в обеих коллекциях — variant B чистит обе без предположения о их непересекаемости.

### Негативные регресс-проверки

- [ ] AC9. «The collector posted his find to Instagram and gathered 50K likes» (реальный контент с упоминанием платформы) проходит оба фильтра.
- [ ] AC10. «Коллекционер написал в Instagram, что нашёл редкий Chase» проходит variant B без срабатывания (нет глагольного якоря и нет скобочной конструкции).

### Граница

- [ ] AC11. «Follow Mattel on Instagram, X, and Facebook» (корпоративный плаг) проходит без изменений — это вне scope текущей фичи. Адресуется отдельной фичей о press-release boilerplate.

### Регресс

- [ ] AC12. Все 682 существующих теста продолжают проходить; добавлены новые юнит-тесты для обоих вариантов.

## Ограничения

- Проект в режиме наблюдения — изменения консервативные, без перепланировки соседних модулей.
- Variant A удлиняет существующий список `_BOILERPLATE_PATTERNS` без смены контракта функций (`filter_boilerplate`, `filter_blocks`). Длинная string-граница `_MAX_BOILERPLATE_LEN` бампается с 80 до 120 — единственный тест с литералом 80 ([`tests/test_boilerplate_filter.py:129`](../../tests/test_boilerplate_filter.py)) использует строку >120, ассерт переживёт.
- Variant B встраивается одной точкой вызова в `_fallback_publish` ([`news_bot.py:~1010`](../../news_bot.py)), оборачивается `try/except` — если regex упадёт, цикл публикации продолжается с оригинальными RU-текстами (publish-something лучше, чем publish-nothing).
- Зависимости: только stdlib `re`. Никаких новых пакетов, env-переменных или DB-полей.
- Безопасность: regex компилируется один раз на импорт, без катастрофического backtracking-паттерна (избегаем `(.+)+`).
- Деплой: новый файл `author_plug_filter.py` обязан быть добавлен и в `deploy.sh` `FILES`, и в `.github/workflows/deploy.yml` `FILES` (INVARIANT по `patterns.md`) — иначе сервер хватит `ImportError` на следующем cron-tick.
- Out of scope: корпоративный плаг «Follow Mattel on …» — отдельной фичей о press-release boilerplate-секциях.

## Риски

- **Риск 1: ложное срабатывание variant B (over-strip).** Regex может ошибочно вырезать содержательное предложение. **Митигация:** паттерны якорим на cue-глаголах (подписывайтесь / follow me / мой Instagram) либо на скобочной форме с `@handle`, не на голых упоминаниях платформы; каждое срабатывание логируется INFO для journalctl-наблюдения; rollback через `git revert HEAD && git push` (~3 минуты через CI).
- **Риск 2: пересечение паттернов.** Существующий `^follow us on \w+` (строка 49 в `boilerplate_filter.py`) перекрывается с новым `(follow|check) (me|us) on …`. **Митигация:** схлопываем в одну более широкую формулировку, удаляем легаси-форму. Существующие тесты не падают (новый паттерн — строгое надмножество).
- **Риск 3: бамп `_MAX_BOILERPLATE_LEN` 80→120.** Один тест ([`tests/test_boilerplate_filter.py:129`](../../tests/test_boilerplate_filter.py)) ссылается на литерал 80 в текстовом сообщении. **Митигация:** обновляем сообщение об ошибке, фикстура (>120 chars) переживает изменение порога без перетряхивания ассерта.
- **Риск 4: забытый FILES-листинг.** Новый `author_plug_filter.py` обязан попасть в обе FILES-арреи деплоя. **Митигация:** явный пункт в чеклисте tech-spec (Phase 8 → tasks).
- **Риск 5: пустой параграф после strip.** Variant B может удалить единственное предложение в параграфе. **Митигация:** для плоских `ru_paragraphs` оставляем пустую строку (Telegraph пропускает пустой `<p>`); для блоков типа `paragraph` удаляем блок целиком (нет «дырки» в DOM, соседние image/video не страдают).

## Технические решения

- Мы решили **создать отдельный модуль `author_plug_filter.py`** для variant B, потому что drop-whole-paragraph (variant A в `boilerplate_filter.py`) и strip-substring (variant B) — разные ответственности; смешивать их в одном файле — путаница.
- Мы решили **встроить variant B одной точкой вызова в `_fallback_publish`**, потому что обе ветки (Claude success + Google fallback) сходятся в одних и тех же `ru_*` локалах перед `update_staged` — это единственный канонический выход в канал. Если перенести в каждый движок — будет 4× кода и риск рассинхронизации между движками.
- Мы решили **не делить sentence-tokenizer для variant B**, а использовать regex-как-границу: паттерн ловит плаг с опциональными скобками/кавычками/терминальной пунктуацией и заменяет на пустую строку с последующим `strip()`. Это предсказуемее и без зависимости от NLP-библиотеки.
- Мы решили **пропускать variant B при `via_review=True`**, потому что оператор уже снимает плаги вручную на этапе `hw_review stage`. Двойной прогон лишь шумит в логах и теоретически способен над-стрипнуть содержимое, которое редактор намеренно оставил.
- Мы решили **добавить в variant B зонтичный паттерн** `\([^)]*<platform>\s*@?\w*[^)]*\)` поверх глагольных якорей — Google Translate переводит «(follow me on Instagram @x)» вариативно («(подпишитесь...)», «(посмотрите меня...)», «(следуйте...)»), и якоря на конкретные глаголы пропустят часть. Скобочная форма с упоминанием платформы — характерный признак плага.
- Мы решили **обернуть variant B в `try/except`** и при падении возвращать исходные `ru_*` без изменений — публикация в канал важнее, чем фильтрация плагов; ошибка логируется ERROR.
- Мы решили **не добавлять env-флаг `DISABLE_AUTHOR_PLUG_FILTER`**, потому что rollback через `git revert HEAD && push` занимает ~3 минуты через CI; постоянный шов-флаг не оправдывает один редкий сценарий.
- Мы решили **не добавлять агрегатный пинг** в plan-of-day («сегодня снято N плагов»). Пинги остаются про расписание и backlog; per-strip INFO в journalctl достаточно для проверки и постмортемов.
- Мы решили **схлопнуть существующий `^follow us on \w+`** в новый широкий `(follow|check) (me|us|our team) on (instagram|...)`, чтобы избежать дубля.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.

- В `tests/test_boilerplate_filter.py` добавляется по одному positive + одному negative кейсу на каждый новый паттерн variant A. Реюзается существующая фикстурная схема.
- Создаётся `tests/test_author_plug_filter.py` для variant B: плаг в середине / в начале / в конце параграфа, несколько плагов в одном параграфе, blocks с типами `paragraph` / `image` / `video`, негативные кейсы (реальный контент с упоминанием платформ), пустой параграф после strip, INFO-логирование, защита `try/except`.
- Smoke-тест: фактическая утечная фраза «(подписывайтесь на меня в Instagram @diecast215 )» должна быть удалена либо variant A (если standalone), либо variant B (если inline).

**Интеграционные тесты:** не делаем — `tests/test_fallback_publish_paths.py` уже покрывает обвязку `_fallback_publish`; достаточно добавить туда smoke-проверку, что variant B вызван (или замокан) на canonical-пути и не вызван при `via_review=True`.

**E2E тесты:** не делаем — фича чисто функциональная, без сетевых интеграций; полное E2E дублирует существующее покрытие пайплайна.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|---------------------|
| 1. Прогнать pytest локально | `python3 -m pytest tests/ -q` | 682 + новые тесты зелёные |
| 2. Проверить вариант A на эталонной EN-фразе | pytest unit | `is_boilerplate("(follow me on Instagram @diecast215)") == True` |
| 3. Проверить вариант B на утечной RU-фразе | pytest unit | `strip(...)` удаляет именно плаг, остаток сохраняется |
| 4. Проверить вариант B на негативной RU-фразе | pytest unit | «коллекционер написал в Instagram...» проходит без изменений |
| 5. После пуша — дождаться зелёного CI | GitHub Actions UI | `ci.yml` зелёный → `deploy.yml` запускается на `workflow_run` |
| 6. После деплоя — проверить, что новый файл доехал | `ssh user@vps "ls $DEPLOY_PATH/author_plug_filter.py"` | файл присутствует |
| 7. Дождаться следующей публикации lamley/autoevolution и сверить Telegraph URL | `curl <telegraph_url>` или ручной просмотр | плагов нет в теле статьи |
| 8. Проверить INFO-логи variant B | `ssh user@vps "journalctl -u news_bot.service -S today \| grep author_plug"` | при срабатывании — строка `stripped sentence: ...` |

### Пользователь проверяет

- Открыть 2-3 свежие публикации канала после деплоя. Подтвердить визуально, что **реальные** упоминания соцсетей в тексте (не плаги) на месте, а **плаги** отсутствуют. Это ловит ложные срабатывания, которые автоматический regex-тест мог не вычислить — у живых статей бывают неожиданные формулировки.
