Four parallel review agents: (1) app-code security, (2) infra/deploy security,
(3) code readiness/completeness, (4) test completeness. Findings deduplicated and
re-prioritized below. Severity is *operational impact*, not the agents' internal labels.

## Verdict
The product is genuinely solid — parameterized SQL (test-enforced), layered secret
redaction, SSRF allowlists in 4/5 parsers, escaped-node-tree Telegraph, a healthy
**1153-passing** test suite, verified-inert disarmed `deploy.yml`, correct `%q` ssh
escaping. **No remotely-exploitable Critical.** But finalization is **not** ready:
the Docker/Moscow migration silently dropped three operational safety nets, and the
audit surfaced two real prod bugs. Fix the blockers below first.

**Theme:** most blockers are migration fallout — prod moved hosts, but the host-side
backup cron, the alive-but-stuck watchdog, and the DB-path assumptions did not move.

## 🔴 Finalization blockers (fix before calling it done)

### B1 — No DB backups on Moscow prod (data-loss risk) · CRITICAL
`scripts/backup_db.sh:18` hardcodes the OLD NL path `DB=/home/hwbot/bot/news.db`,
ignores `DB_FILE`, and is wired nowhere in the container (not in Dockerfile/compose/
cron/FILES). The single `./data:/data` bind-mount is now the **only** copy of
`processed_news`/`published_articles`/`pending_articles`. Losing `news.db` → the bot
re-publishes months of RSS backlog to the live channel.
**Fix:** host-side nightly `sqlite3 .backup` of `/data/news.db` + rotation + off-box
copy; parameterize `backup_db.sh DB=` from `DB_FILE`/arg. *(agent 4 C1)*

### B2 — No startup guard that the DB path is real/non-empty · HIGH
`DB_FILE` is correctly env-overridable everywhere (news_bot.py:116, pending_articles_repo:177,
outage_state:111, backfill_fingerprints:232 — the "DB_FILE inconsistent" worry is
**refuted**). But the default `"news.db"` is *relative* → ephemeral `/app/news.db`,
and prod's `.env` is hand-copied. Nothing asserts at startup that the resolved DB is
under `/data` or non-empty; `init_db()` happily creates an empty one anywhere. One
dropped `.env` line on the next redeploy → empty `processed_news` → channel re-flood.
**Fix:** startup health check (mirror the TZ check at news_bot.py:2418) → admin ping
if `DB_FILE` isn't absolute/under `/data` or `processed_news` is unexpectedly empty;
make `DB_FILE` a required compose env. *(agent 4 H4)*

### B3 — lamley's entire anti-WAF path is DEAD in production · HIGH
`lamley_source.py:332,340` catch `requests.HTTPError`/`RequestException`, but on the
prod path `session is None` → `_cffi_requests`, so `raise_for_status()` raises a
**curl_cffi** exception (verified at runtime: not a subclass of `requests.*`). It
escapes and is swallowed by `fetch_full_article`'s `except Exception: return None`
(news_bot.py:1642). So `_record_429`, the strike counter, the per-URL blacklist, the
1h cool-down, and `alert_lamley_fetch_error` **never run in prod** — the exact WAF
lockout this file exists to prevent. CI is green because tests inject `requests` mocks.
**Fix:** also catch `curl_cffi.requests.exceptions.RequestsError` (import-guarded), or
branch on `response.status_code` instead of `raise_for_status()`. *(agent 4 H1)*

### B4 — In-slot retry can double-post to the channel · HIGH
`_publish_with_retries` (news_bot.py:1863) retries the **same** in-memory `row` up to
4×; `_fallback_publish` reads `telegraph_url` from `row` but never writes it back after
`mark_telegraph_published`. On retry it's stale-`None`: a failure after the teaser send
(:1580) but before `move_to_published` (:1587, e.g. `database is locked`) → the retry
re-sends the channel post (up to 4× duplicates) and orphans Telegraph pages. Defeats
the Decision-9 idempotency the cross-*slot* path relies on (the top guard can't catch
it — the move failed, so the link isn't in `published_articles`).
**Fix:** re-fetch via `get_pending(link)` before each retry and/or set
`row['telegraph_url']` after `mark_telegraph_published`; add a `teaser_sent` marker to
never re-send. *(agent 4 H2; related to B5)*

### B5 — Alive-but-stuck watchdog lost in the container · HIGH
`watchdog.sh` is COPY'd into the image but **nothing invokes it** — no in-container
cron, no compose `healthcheck`, no host cron for Moscow. `job()` still writes the
heartbeat to the ephemeral `~/.cache/news_bot/last_tick.ts` (news_bot.py:2340) that no
process reads. `restart: unless-stopped` only reacts to process *exit*; a hung-but-alive
process (the 2026-06-08 feedparser-hang class) goes undetected — the bot can go dark for
a full day with zero alert.
**Fix:** Docker `HEALTHCHECK` on heartbeat mtime (move `_HEARTBEAT_PATH` onto `/data`),
or run `watchdog.sh` via host cron + `docker exec`. *(agent 4 H3)*

## 🟠 Important (security + robustness — fix soon)

- **S1 · SSRF via autoevolution fetch** — the autoevolution parser fetches
  `entry['link']` with **no host allowlist**, and the dispatcher matches by substring
  (`'autoevolution.com' in domain`). Bypassable (confirmed): `http://autoevolution.com@169.254.169.254/…`
  → server-side GET to internal/metadata endpoints from prod. Only parser of 5 without an
  allowlist. **Fix:** exact-host allowlist (mirror the other parsers) + disable/re-validate
  redirects; make the dispatcher use exact hostname, not substring. *(agent 1)*
- **S2 · sudoers → root privesc (NL box)** — `journalctl`/`systemctl status` in the
  NOPASSWD rule spawn a pager as root → `!sh` → root shell (GTFOBins). Grants `hwbot`
  full root on the box that hosts the test bot + other bots. **Fix:** drop `journalctl`/
  `status` (workflows only need `restart`) or force `--no-pager`; `runas=(root)`. *(agent 2 H1)*
- **R1 · No exception supervisor around `job()`/scheduler loop** — news_bot.py:2440-2445
  is unguarded; unguarded DB reads inside `job()` + `pending_articles_repo._connect` has
  **no `busy_timeout`** (unlike outage_state). A transient `database is locked` crashes
  the daemon → restart re-runs `job()` → crash loop. **Fix:** wrap `job()` body in
  try/except (log + admin ping + continue); add `PRAGMA busy_timeout` for parity. *(agent 4 M1)*
- **R2 · Container runs as root + unpinned base images** — no `USER` in Dockerfile;
  `alpine:latest`/`python:3.13-slim` by tag. The `route-setup` sidecar holds `NET_ADMIN`
  in the bot's netns — a poisoned `latest` could MITM all egress incl. the token. **Fix:**
  non-root `USER`, `cap_drop:[ALL]` on `news-bot`, digest-pin images, SHA-pin
  `webfactory/ssh-agent` (it consumes the SSH key). *(agent 2 M1/M2/M3)*
- **R3 · teaser→move duplicate-on-kill window** — even single-attempt: a hard kill
  between the send (:1580) and `move_to_published` (:1587) → duplicate next tick (crash
  guard can't prevent it). **Fix:** persist `teaser_sent_at` + short-circuit, or accept
  + document. *(agent 4 M2 — same root cause as B4)*
- **R4 · autoevolution (biggest source) has no admin alerting** — failures are log-only;
  a sustained outage silently stops posts. **Fix:** wire a notifier like orangetrack's. *(agent 4 M3)*
