## The deploy landed inside the publication window — benign this time

Restart at 13:26 MSK, i.e. inside 10:00–20:00. It cost nothing, and the reason
is worth writing down because it is a property of the code rather than luck:
`compute_fixed_slots` keeps a slot eligible for only `grace_minutes=5` after its
wall-clock time. The restart fell between slots, so the re-run of `job()`
recomputed the day as `[15:00, 19:30]` and the already-fired 10:00 slot did not
repeat.

**The actual sharp edge is narrower than the window rule suggests**: a restart
within 5 minutes AFTER 10:00, 15:00 or 19:30 re-fires that slot and the day
produces four publications instead of three. The window rule stays as-is — it is
the memorable version, and the operator should not have to do this arithmetic —
but "deployed at 13:26 and nothing broke" is not a counterexample to it.

Side effect the operator sees: `job()` re-runs on startup, so the restart
produced a second `[E008]` plan-of-day ping. Expected, not a fault.

## The balance trap, measured on prod

The point of the two-ceiling change was that one number cannot tell you whether
both probes work. So both were read separately:

```
account   = 4.1855
key_limit = 10          key_left = 4.19592731
```

**The two ceilings are one cent apart.** The account is currently the binding
one, which is exactly why the old account-only code looked correct — it was
reading a number that happened to be right. `/auth/key` answers fine for the
ordinary key (unlike `/activity`, which 403s), so the new path is live and not
silently degraded to account-only.

The failure this now covers is one top-up away: add $50 and the account reads
$54 while the key still dies at $4.20 — the alert would have gone quiet exactly
when it was needed.

Spend rate, as a sanity check: $4.29 on 13 Aug → $4.19 today, ≈$0.10 over four
days. Consistent with the measured ~$0.0056 per published article at three
publications a day plus retries. The `[E019]` threshold is $1, so the runway is
long and the silence is correct silence.
