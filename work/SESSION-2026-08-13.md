# SESSION 2026-08-13 — closing the three items the August outage left open

Follow-up to `SESSION-2026-08-12.md`. That session fixed the autoevolution
block itself; this one fixes the three things that let it run for four days
without anyone noticing, plus one unrelated finding from looking at the image.

## 1. The balance alert was watching the wrong number

`[E019]` compared `OPENROUTER_MIN_BALANCE_USD` against the **account** balance
(`/credits`). That is only one of two ceilings. The API key has its own spending
limit, and either one stops translation on its own.

Measured on 2026-08-13: account $4.29 left; key limit $10 with $4.30 left. The
two agreed **by coincidence**, so the alert worked by accident. Top the account
up by $50 and the account figure jumps to $54 while the key still dies after the
same $4.30 — the alert goes quiet exactly when it is needed, and the operator is
told everything is fine while the channel stops. That is the 2026-07-14 402
incident with an extra step.

`get_remaining_credits()` now probes both and returns the **smaller**. A null
`limit` means the key is uncapped and contributes no ceiling — reading it as
zero would alarm every tick. Both probes are best-effort and the function still
never raises; the key rides in the header, never the URL or the logs.

Cost figures established while checking this, so nobody re-derives them from the
account total: prod runs `google/gemini-2.5-flash` and a published article costs
**~$0.0056** (measured over two consecutive publications). The account's
lifetime `total_usage` ($25.71) is NOT the bot's spend — the bot's key had used
$5.70. Per-model breakdown needs a provisioning key; the ordinary key gets 403
on `/activity`.

## 2. The dry-spell alert sat out the entire outage

`DRY_SPELL_ALERT_DAYS` was 3, lowered to 2. The arithmetic is unforgiving,
because the tick runs once a day and the gap only reaches the threshold on the
day *after* it is crossed:

```
9 авг   publication            gap 0
10 авг  silence                gap 1  — under 3
11 авг  silence                gap 2  — under 3, and the last tick before
                                        the queue recovered
12 авг  one deferred article   gap 0  — reset; three days never reported
```

At 2 the 11 August tick fires, which is the whole point.

Considered and rejected: counting "consecutive days that published nothing" in
`bot_state`. It is the same number — a publication resets the streak exactly as
it resets the gap — so it adds state and a restart-safety problem (`job()`
re-runs on every container restart) while catching nothing new. The genuinely
different signal, "the feed had fresh entries and none reached the queue", is
per-SOURCE and stays on the open list.

## 3. The retry cap — and the restart trap inside it

A link that cannot be fetched is deliberately not marked processed, so the next
tick retries. Under a real block that becomes escalating hammering: 9–12 August
the same articles failed every tick and the per-tick count climbed 2 → 5 → 6 as
more piled up.

New `fetch_failures` table (link, attempts, first/last_failed_at) and
`FETCH_RETRY_CAP = 3`. Past the cap the link is written to `processed_news` and
given up on — the deliberate price of not knocking on a door that has said no
~20 times. Three properties that are load-bearing:

- **Consecutive, not lifetime.** `clear_fetch_failure` on every successful fetch
  is what makes `attempts` mean "in a row". Lifetime counting would retire a
  link that fails once a month on some unrelated day — the wrong-attribution
  trap `reset_hold_counts_below` exists to avoid for holds.
- **At most one increment per calendar day.** This is the non-obvious one. `job()`
  runs daily, but it *also* runs on every container restart — prod restarted four
  times on 13 August alone. A plain `+1` would have retired six live articles
  within the hour instead of after three days. Same-day repeats refresh the
  timestamp and leave the count alone, which is what keeps `attempts` readable
  as "days".
- **Bookkeeping failure must never cost an article.** If the counter write
  raises, the code logs and falls back to the old forever-retry behaviour.
  Losing a story to a SQLite hiccup would be a worse bug than the one the cap
  fixes.

## 4. Unrelated: the live database was inside every Docker image

`.dockerignore` had `*.db`, which matches only at the top level. The live
database sits in the bind-mount source (`/root/hw-news/data/news.db` on prod) —
inside the build context — so 1.2 MB of stale production data was copied into
every image at `/app/data/news.db`, dated whenever the image was last built.

Harmless today because `DB_FILE` is the absolute `/data/news.db` from the
mounted volume. It is a loaded gun: anything that ever resolved the DB path
relatively would read a week-old copy and repost the channel from it. Added
`data/`.
