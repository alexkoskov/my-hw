# Task 8: Security Audit

## Required Skills

## Description

Полный security-аудит фичи `dedup-review-buttons` — первого в истории бота **входящего** Telegram-пути. До этой фичи бот только отправлял сообщения; теперь появляется фоновый long-poll поток (`bot.get_updates`), который принимает нажатия inline-кнопок из публичного Telegram и на их основании удаляет строки из очереди `pending_articles`. Это новая поверхность атаки: любой пользователь Telegram может послать боту callback_query, поэтому корректность аутентификации (только числовой админ, fail-closed) и безопасность разбора `callback_data` — критичны.

Задача — прочитать весь исходный код фичи (реализованный в волнах 1-6) целостно и проверить его против OWASP Top 10, с фокусом на новых рисках, которые вносит входящий путь. Это аудит **только для анализа**: агент не меняет код, а пишет отчёт с находками (severity + issue + fix) для последующего исправления реализационными задачами. Аудит идёт параллельно с Task 7 (code audit) и Task 9 (test audit) в Audit Wave.

Фича трогает секреты (bot token, admin id), выполняет запись в SQLite из второго потока и редактирует сообщения в чате оператора — все три области требуют отдельной проверки на утечки и на нарушение инвариантов проекта (редакция логов через `_TokenRedactingFilter`/`_redact_text`, санитизация ошибок через `sanitize_error_message`, отсутствие сырого `str(exc)` в пингах).

## What to do

Провести сквозной security-аудит всех компонентов фичи и выдать отчёт с находками. Конкретные направления:

1. **Собрать поверхность фичи.** Определить все файлы, созданные/изменённые фичей, по tech-spec «Implementation Tasks» (Files to modify) и по записям в `decisions.md`. Как минимум: `news_bot.py` (listener `_run_review_listener`, `resolve_dedup_callback`, E014 send-site, `send_admin_notification`, `main()` wiring), `admin_alerts.py` (`build_dedup_review_keyboard`), `pending_articles_repo.py` (`_connect` busy_timeout + token-хелперы), `.env.example`. Прочитать эти файлы в их фактическом послереализационном состоянии.

2. **Аутентификация callback (A01 Broken Access Control).** Проверить, что `resolve_dedup_callback` сравнивает `from_user.id` (int) с `int(TELEGRAM_ADMIN_ID)` и что не-админ → «ignored», без изменения состояния БД и без раскрытия информации. Проверить fail-closed: нечисловой `TELEGRAM_ADMIN_ID` (дефолт `@sunny413x`) должен полностью запрещать запуск listener'а, а не «пропускать» или падать неоднозначно. Убедиться, что нет обходного пути, где действие выполняется до проверки админа.

3. **Утечка секретов (A02 Cryptographic Failures / A09 Logging).** Проверить, что ни bot token, ни admin id, ни review-токены, ни ссылки не утекают в логи и в редактируемые сообщения в обход `_redact_text` / `_TokenRedactingFilter` / `sanitize_error_message`. Особое внимание — логирование решения оператора (cancel/keep + link + status) в listener'е (tech-spec требует INFO-лог): убедиться, что оно проходит через принятые в проекте фильтры и не печатает сырой `str(exc)` при ошибках `get_updates`/`edit_message_text`.

4. **Разбор и инъекции callback_data (A03 Injection).** Проверить парсер `dd:<c|k>:<token>`: некорректный/чужой/переполненный `callback_data` должен безопасно игнорироваться (не бросать необработанное исключение, не убивать поток). Убедиться, что токен из callback_data используется только как ключ поиска в `bot_state` (`review_token:<token>`) через параметризованный SQL, а не конкатенируется в запрос; что `link`, полученный из БД по токену, не интерпретируется как что-то исполняемое.

5. **SQL / запись в SQLite (A03 Injection + целостность).** Проверить все новые обращения к БД (token put/get/delete, `_connect` с `busy_timeout=5000`) на параметризацию и на безопасность конкурентной записи из фонового потока: отдельное соединение на поток, отсутствие гонок, которые могли бы удалить не ту строку (Decision 3 — токен вместо переиспользуемого rowid). Подтвердить, что cancel идёт через существующий идемпотентный `skip_pending`.

6. **DoS публичного get_updates пути (A05/A04).** Оценить, что необслуживаемый поток нажатий от произвольных пользователей не приводит к отказу: не-админские апдейты дёшево отбрасываются, ошибки в цикле обёрнуты try/except с backoff и **не** роняют publish-процесс (daemon-поток изолирован), нет неограниченного роста `bot_state` от чужих токенов (токены создаёт только send-site, чужой callback_data не создаёт строк). Оценить, что offset обновляется корректно, чтобы поток не зациклился на «ядовитом» апдейте.

7. **OWASP Top 10 sweep по остальным категориям.** Пройти оставшиеся категории (A06 уязвимые зависимости — фича не добавляет пакетов; A07 identification/auth; A08 integrity; A10 SSRF — есть ли новые исходящие запросы по данным из callback) и отметить неприменимые с обоснованием.

8. **Написать отчёт.** Сформировать security-audit отчёт в `work/dedup-review-buttons/logs/working/task-8/security-audit.md` (сначала `mkdir -p`): перечень находок с полями `severity` (Critical/High/Medium/Low — шкала security-auditor skill), `issue` (что не так, где — файл:строка), `fix` (что предлагается). Явно указать, какие из ключевых рисков tech-spec «Risks» (shared token 409, non-admin press, stale token, listener crash isolation, callback_data > 64 байт) закрыты, а какие требуют доработки. Если критичных находок нет — прямо это констатировать. Краткий итог — в decisions.md согласно Post-completion (без дампа находок).

- Все ошибки в пингах/логах идут через `sanitize_error_message` — не сырой `str(exc)` (прецедент SSRF-guard в patterns.md: «notifier messages format only exception type + safe scalars»).

**Edge cases для проверки:**
- Не-админ шлёт валидный `dd:c:<token>` → никакого изменения БД, пустой answer, без edit.
- Нечисловой `TELEGRAM_ADMIN_ID` → listener не стартует (fail-closed), стартовый warning.
- Мусорный/переполненный/чужой `callback_data` → безопасно проигнорирован, поток жив.
- Устаревший/двойной токен → идемпотентно «устарела/недоступна», без падения.
- Гонка на границе слота (нажатие в момент публикации) → не удаляется не та строка; идемпотентность `skip_pending` + `_fallback_publish`.
- Ошибка внутри listener-цикла → try/except + backoff, publish-процесс жив (daemon, изоляция).
- `REVIEW_BUTTONS_ENABLED` off → ни кнопок, ни потока (test-инстанс не 409'ит прод).
