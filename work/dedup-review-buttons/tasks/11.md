## Description

Финальная волна фичи `dedup-review-buttons`: подготовить деплой и написать
операторский runbook. Кода здесь **не пишем** — вся реализация уже сделана в
Wave 1–3 и прошла Pre-deploy QA (Task 10). Задача Claude — (1) подтвердить, что
инвариант деплоя не нарушен (в `news_bot.py` не добавлен ни один новый
first-party import → списки FILES в `deploy.sh` / `deploy.yml` / `deploy_test.yml`
править не нужно), и (2) выдать оператору точный, пошаговый набор команд для
раскатки на тест и на прод.

Ключевой контекст фичи: слушатель нажатий (`get_updates` long-poll) запускается
**только на одном инстансе**. Токен Telegram-бота общий для прод и теста —
второй потребитель `get_updates` получит **409 Conflict**. Поэтому листенер
включается флагом `REVIEW_BUTTONS_ENABLED=1` строго на ОДНОМ инстансе (прод), а
тот же флаг гейтит и отрисовку кнопок — так на тесте не будет ни поллинга, ни
«мёртвых» кнопок.

**Разделение ролей (важно):** Claude ГОТОВИТ команды; ВСЕ серверные операции
(push веток, SSH на прод, правка прод `.env`, `docker compose`) выполняет
ОПЕРАТОР. Claude не ходит по SSH и не деплоит сам.

Живая проверка нажатий на проде — отдельная задача (Task 12, post-deploy).

## What to do

1. **Подтвердить инвариант FILES (без правок).** Проверить, что фича не добавила
   в `news_bot.py` новый first-party import (по Decision 8 весь код лёг в уже
   деплоящиеся `news_bot.py`, `admin_alerts.py`, `pending_articles_repo.py`).
   Убедиться, что все три файла присутствуют в обоих массивах FILES
   (`deploy.sh`, `.github/workflows/deploy.yml`) и в `deploy_test.yml`. Вывод:
   правок в списки FILES и в deploy-скрипты НЕ требуется. Зафиксировать этот
   вывод в runbook явно (чтобы оператор не искал изменения деплоя, которых нет).
   Новый env `REVIEW_BUTTONS_ENABLED` документирован в `.env.example` (Task 6),
   а `.env.example` уже в FILES → на тест уедет автоматически.

2. **Собрать runbook для ТЕСТА (dev, авто-деплой).** `git push origin dev` →
   `ci.yml` (pytest) → на зелёном `deploy_test.yml` (SCP FILES → NL VPS
   `/home/hwbot/bot_test/` + `pip install` + `sudo systemctl restart
   news_bot_test.service`). Явно указать: на тесте `REVIEW_BUTTONS_ENABLED`
   НЕ выставляется (strip-then-append в `deploy_test.yml` управляет только
   LLM-ключами + TZ; этот флаг не в списке и вручную на тесте не задан) → флаг
   по умолчанию OFF → листенер НЕ стартует, кнопки НЕ рисуются. Ожидание: кнопки
   на тесте «спят», 409 нет. Проверка оператором: `journalctl -u
   news_bot_test.service` — чистый старт, БЕЗ строки «review listener active».

3. **Собрать runbook для ПРОДА (Moscow Docker, вручную, ВНЕ окна публикаций).**
   Строго ВНЕ окна **10:00–20:00 МСК** (рестарт контейнера сбрасывает
   in-process расписание слотов 10:00 / 15:00 / 19:30). Шаги:
   - Промоут `dev → main`: `git checkout main && git merge dev && git push origin main`.
   - На хосте `ssh root@45.90.216.165` отредактировать **hand-managed прод `.env`**
     (`/root/hw-news/.env`, его грузит compose через `env_file: - .env`):
     - добавить `REVIEW_BUTTONS_ENABLED=1`;
     - убедиться, что `TELEGRAM_ADMIN_ID` — **числовой** chat_id (не `@username`).
       Auth fail-closed: нечисловой id → листенер откажется стартовать. Если сейчас
       стоит `@sunny413x` — заменить на числовой id администратора.
   - Раскатка: `cd /root/hw-news && git pull && docker compose up -d --build`.
   - Проверка оператором: `docker logs hw-news-bot` — чистый старт, строка
     «review listener active», без `[E018]` DB-guard пинга.

4. **Явно выделить инвариант единственного листенера.** Ровно ОДИН инстанс может
   включать `REVIEW_BUTTONS_ENABLED=1` (прод). Тест держать OFF. Двойное включение
   → два потребителя `get_updates` на общий токен → **409 Conflict**. Строка
   «review listener active» в логах делает случайное двойное включение заметным.

5. **Отдать runbook оператору** как единый блок «сначала тест → проверка → потом
   прод (вне окна)». Дождаться, что оператор применит серверные шаги. Claude сам
   ничего на серверах не выполняет.
