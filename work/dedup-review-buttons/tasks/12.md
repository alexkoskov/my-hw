# Task 12: Post-deploy verification (operator-driven)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [.claude/skills/post-deploy-qa/SKILL.md](../../../.claude/skills/post-deploy-qa/SKILL.md)

## Description

Живая проверка фичи `dedup-review-buttons` на **прод-инстансе** после того, как оператор
применил деплой из Task 11. Это единственная возможная сквозная проверка кнопок: слушать
входящие нажатия (`get_updates`) на общем бот-токене может только один потребитель, и это
прод — на тесте сценарий «палец в Telegram» не воспроизвести (см. user-spec «Пользователь
проверяет»).

Задача **operator-driven**: агент готовит команды и просит оператора их выполнить/нажать
кнопки, затем разбирает возвращённый вывод. Агент **не** ходит по SSH сам и никогда не
печатает секреты (бот-токен, ключи). Прод-операции применяет оператор (см. память проекта:
«Operator handles production ops; Claude prepares, operator applies»).

Цель — подтвердить на живом проде четыре вещи:
1. Слушатель нажатий поднялся (в логе прод-контейнера есть строка «review listener active»).
2. По реальному/синтетическому алерту **«[E014] Похож на дубль»** нажатие «🚫 Не публиковать»
   до слота убирает статью из очереди — в свой слот она НЕ выходит в канал, а кнопки в
   сообщении сменяются на **«✅ Отменено оператором»**.
3. На другом «[E014]» нажатие «👍 Оставить» ничего не отменяет — статья выходит в свой слот,
   а кнопки сменяются на **«👍 Оставлено»**.
4. Тест-инстанс НЕ поднял слушатель — в его логах нет конфликта 409 (`Conflict: terminated by
   other getUpdates request`) и нет строки «review listener active».

## What to do

1. **Проверить, что слушатель активен на проде.** Подготовить оператору однострочную команду
   чтения лога прод-контейнера и попросить прислать вывод; убедиться, что при загрузке бот
   написал «review listener active», нет `[E018]` DB-guard пинга, старт чистый.
2. **Дождаться алерта «[E014] Похож на дубль»** на прод-канале (реального в утреннем прогоне
   ~10:00 МСК или синтетического — стейджинг похожей пары к утреннему отбору). Проверка может
   растянуться на несколько дней — это нормально, фиксируем частичный результат и продолжаем.
3. **Сценарий «Не публиковать» (до слота).** На пришедшем «[E014]» оператор (администратор,
   числовой `TELEGRAM_ADMIN_ID`) жмёт **«🚫 Не публиковать»** ДО слота публикации (слоты 15:00
   и 19:30 МСК). Сразу проверить: кнопки в сообщении заменились на **«✅ Отменено оператором»**,
   повторное нажатие невозможно (клавиатуры больше нет). Затем В/ПОСЛЕ слота убедиться, что
   статья НЕ появилась в прод-канале, строка ушла из `pending_articles`, и в логе есть INFO о
   решении оператора (cancel + ссылка + статус).
4. **Сценарий «Оставить».** На другом «[E014]» оператор жмёт **«👍 Оставить»**. Проверить: кнопки
   сменились на **«👍 Оставлено»**, статья выходит в свой слот как обычно, в логе INFO о решении
   (keep + ссылка).
5. **Проверить отсутствие 409 на тесте.** Подготовить оператору однострочную команду чтения
   журнала тест-инстанса; убедиться, что там НЕТ конфликта getUpdates (409) и НЕТ строки «review
   listener active» — тест кнопки не обслуживает.
6. **(Опционально, если доступен Telegram MCP)** использовать Telegram MCP для чтения сообщения
   с кнопками и/или нажатия от имени администратора; иначе всё делает оператор руками, а агент
   разбирает присланный вывод/скриншот.
7. Свести результат по каждому пользовательскому критерию приёмки (см. Acceptance Criteria):
   PASS / FAIL / отложено (если подходящий «[E014]» ещё не пришёл).

## Acceptance Criteria

- [ ] В логе прод-контейнера при старте есть строка «review listener active»; старт чистый (нет `[E018]`).
- [ ] Под «[E014] Похож на дубль» на прод-канале видны две кнопки: «🚫 Не публиковать» и «👍 Оставить».
- [ ] Нажатие «Не публиковать» ДО слота → статья не выходит в канал в свой слот; строка удалена из `pending_articles`.
- [ ] После нажатия «Не публиковать» кнопки в сообщении заменены на «✅ Отменено оператором»; повторно нажать нельзя.
- [ ] Нажатие «Оставить» не отменяет публикацию → статья выходит в слот; кнопки заменены на «👍 Оставлено».
- [ ] В логе прода есть INFO-запись решения оператора (cancel/keep + ссылка + статус) для каждого нажатия.
- [ ] В логе тест-инстанса НЕТ 409 (`Conflict: terminated by other getUpdates request`) и НЕТ строки «review listener active».
- [ ] Публикации по расписанию не сорваны — приём нажатий шёл параллельно, обычная работа бота не пострадала.
- [ ] Результат по каждому критерию зафиксирован (PASS/FAIL/отложено) с указанием, чем подтверждён.

## Verification Steps

Проверочная задача без кода — «Automated» подраздел неприменим (автотесты покрыты в Task 10
Pre-deploy QA). Ниже — исполняемые проверки логов (Smoke) и живые проверки нажатий (User).

### Smoke
Исполняемые проверки логов. Агент готовит однострочные команды, оператор выполняет и присылает
вывод (агент по SSH сам не ходит; секреты не печатаем).

- **Прод — слушатель активен:**
  `ssh root@45.90.216.165 "docker logs hw-news-bot 2>&1 | grep -i 'review listener'"`
  → ожидаем строку про активный слушатель («review listener active»). Пусто → FAIL.
- **Прод — чистый старт:**
  `ssh root@45.90.216.165 "docker logs hw-news-bot 2>&1 | grep -iE '\[E018\]|Traceback|review listener'"`
  → нет `[E018]`, нет трейсбэков.
- **Прод — INFO решения оператора (после нажатий):**
  `ssh root@45.90.216.165 "docker logs hw-news-bot 2>&1 | grep -iE 'Отменено|Оставлено|cancel|keep'"`
  → есть записи по нажатиям.
- **Тест — нет 409 и нет слушателя:**
  `ssh root@148.135.207.54 "journalctl -u news_bot_test.service -S today | grep -iE 'Conflict|getUpdates|409|review listener'"`
  → ожидаем ПУСТО (тест не слушает, конфликта нет). Читаем журнал под `root`: NOPASSWD
  `journalctl` у `hwbot` снят при hardening 2026-07-07 (GTFOBins), journalctl теперь запускает
  оператор от root; `root@148.135.207.54` документирован в deployment.md. Команду выполняет
  оператор — агент по SSH сам не ходит.

### User
Живые нажатия и наблюдение канала — просим оператора (администратора) выполнить, агент
разбирает результат. При наличии Telegram MCP часть шагов агент может выполнить сам от имени
администратора.

- Дождаться «[E014] Похож на дубль» на прод-канале (`-1004027529994`). На нём нажать
  **«🚫 Не публиковать»** ДО слота (15:00 / 19:30 МСК) → убедиться, что кнопки сменились на
  **«✅ Отменено оператором»**, а в свой слот статья НЕ вышла в канал.
- На другом «[E014]» нажать **«👍 Оставить»** → кнопки сменились на **«👍 Оставлено»**, статья
  вышла в свой слот как обычно.
- (Регресс поведения) Убедиться, что остальные публикации в этот день вышли по расписанию —
  приём нажатий не задержал и не сорвал работу бота.

## Details

**Files:** нет файлов на изменение — задача только проверочная (наблюдение живого прода).

**Runtime факты (из deployment.md):**
- Прод: Docker-контейнер `hw-news-bot`, Moscow VPS `45.90.216.165`, репозиторий `/root/hw-news`,
  ветка `main`, состояние на bind-mount `/root/hw-news/data/news.db`, прод-канал `-1004027529994`.
  Логи: `docker logs hw-news-bot` (json-file, 10 MB × 3).
- Тест: systemd `news_bot_test.service`, NL VPS `148.135.207.54`, канал `@myhwchannel123`,
  ветка `dev`. Логи: `journalctl -u news_bot_test.service`.
- Слоты публикации: 15:00 и 19:30 МСК; утренний отбор (и алерт «[E014]») ~10:00 МСК — окно
  действия кнопки «Не публиковать» лежит между алертом и слотом.

**Dependencies:** Task 11 (Deploy) применён оператором — на проде выставлены
`REVIEW_BUTTONS_ENABLED=1` и числовой `TELEGRAM_ADMIN_ID`, контейнер пересобран `git pull &&
docker compose up -d --build` ВНЕ окна 10:00–20:00 МСК.

**Edge cases:**
- Подходящий «[E014]» может не прийти сразу — проверка растягивается на дни; фиксируем частичный
  PASS/отложено и продолжаем позже. Синтетический алерт — стейджинг похожей на уже вышедшую пары
  к утреннему отбору.
- Пограничная гонка «нажатие ровно в момент публикации» → допустимый исход «⚠️ Уже опубликовано,
  отменить нельзя» (пост остаётся), не FAIL.
- Устаревшая/повторная кнопка (бот перезапускался, строки уже нет) → бот отвечает понятным
  статусом и не падает — тоже ожидаемое поведение.
- Нажатие от НЕ-администратора → молча игнорируется, очередь не меняется.

**Implementation hints:**
- Агент по SSH сам не ходит: готовит однострочные `ssh …` команды, оператор выполняет и
  присылает вывод (память проекта: серверные команды — одной строкой через ssh; операции на
  проде применяет оператор).
- Никогда не печатать/логировать бот-токен и ключи; при показе логов оператору напомнить, что
  токен в логах не должен появляться (httpx/httpcore заглушены до WARNING).
- Никаких рестартов прод-контейнера в окне 10:00–20:00 МСК — для этой проверки перезапуск не
  нужен вовсе (только чтение логов + нажатия).
- Telegram MCP — использовать «если доступен»; иначе полностью полагаться на ручные нажатия
  оператора и присланный вывод/скриншот.
- Отменённую статью проверять двусторонне: (а) её нет в прод-канале в слот, (б) строки нет в
  `pending_articles` (можно косвенно — по INFO-логу «Отменено» + отсутствию поста).
