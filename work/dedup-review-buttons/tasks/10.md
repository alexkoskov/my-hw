# Task 10: Pre-deploy QA

## Required Skills

## Description

Приёмочное тестирование фичи `dedup-review-buttons` **до** деплоя — без живого окружения.
Фича добавляет под алерт `[E014] «Похож на дубль»` две inline-кнопки «🚫 Не публиковать» /
«👍 Оставить» и первый в проекте входящий Telegram-путь (фоновый long-poll `get_updates`),
позволяющий оператору отменить подозрительный дубль из чата до слота публикации.

Задача — прогнать полный набор pytest, затем пройтись по **каждому** критерию приёмки из
`user-spec.md` (пользовательские) и `tech-spec.md` (технические) и вынести по каждому вердикт
`passed` / `failed` / `not_verifiable` с доказательством (имя теста, путь в коде, вывод).
Часть критериев принципиально требует живого бота (реальный тап в Telegram, конфликт 409 на
общем токене) — их помечаем `not_verifiable` и передаём в пост-деплой проверку (Task 12), а не
проваливаем. Результат: JSON-отчёт для оркестратора + краткая запись в decisions.md.

Это терминальная проверка волны: она не пишет код и не имеет ревьюеров — её собственный отчёт
и есть выход.

- [ ] U4. «Оставить» не отменяет публикацию; кнопки заменяются на «👍 Оставлено».

## Details

**Рабочая директория для тестов:** `/workspaces/debian-2/my-hw` (там лежит `tests/`, конфиг pytest отсутствует — запуск простой `pytest tests/`). Прогоняется весь набор целиком; точное число покажет `pytest tests/ --collect-only` (на момент написания ~1284 теста).

**Files (scope приёмки — свести из tech-spec «Files to modify» задач 1-6):**
- `pending_articles_repo.py` — `PRAGMA busy_timeout=5000` в `_connect()`; token-хелперы `put_review_token` / `get_review_token_link` / `delete_review_token` поверх `bot_state`. Тест: `tests/test_pending_articles_repo.py`.
- `admin_alerts.py` — `build_dedup_review_keyboard(token)` (две кнопки `dd:c:`/`dd:k:`). Тест: `tests/test_admin_alerts.py`.
- `news_bot.py` — `reply_markup` в `send_admin_notification`; минт токена + клавиатура в E014-ветке `job()`; `resolve_dedup_callback(action, token, from_user_id)`; `_run_review_listener()` + запуск из `main()` под гейтом. Тесты: `tests/test_admin_ping.py`, `tests/test_integration.py`.
- `.env.example` — новый `REVIEW_BUTTONS_ENABLED` (default-off, prod-only).
- PK `architecture.md` / `deployment.md` — обновлены (Task 6); проверять как документацию, не как код.

**Dependencies:** зависит от задач 7 (Code Audit), 8 (Security Audit), 9 (Test Audit) — приёмка идёт после аудитов. Волна 5 (Final). Новых пакетов нет: `python-telegram-bot==21.10` + stdlib `secrets`.

**Edge cases (обязаны иметь тест — иначе `major`):**
- Устаревший/неизвестный токен → «устарела», без падения (U6/T3).
- Нажатие не-админа → игнор, состояние не меняется (U7/T4).
- Отмена после публикации → «уже опубликовано», published-строка цела (U5/T5).
- Конкурентная запись publish-loop ↔ cancel → нет `database is locked` (U9/T6).
- Гейт: `REVIEW_BUTTONS_ENABLED` off ИЛИ не-числовой admin id → потока нет (U8/T7, fail-closed).
- Listener упал → публикация продолжается (T8).

**Что принципиально `not_verifiable` без живого окружения (→ пост-деплой Task 12, НЕ проваливать):**
- Реальный тап пальцем в Telegram и фактический `edit_message_text` в чате (визуальная часть U3/U4/U5). Логику статус-текста при этом проверяет автотест `resolve_dedup_callback`.
- Фактический конфликт 409 на общем токене / что «слушает только прод» на живых инстансах (U8). Автотестом проверяется только логика гейта.
- Строчка «review listener active» в `docker logs` при старте (T7 в рантайме).

**Implementation hints:**
- Классификация: `passed` — критерий выполнен, есть доказательство; `failed` — фича есть, но критерию не соответствует; `not_verifiable` — нельзя проверить без живого окружения/MCP.
- Статус отчёта: `passed` при 0 critical, иначе `failed`. Упавший тест или проваленный критерий приёмки = `critical`.
- Не путать `not_verifiable` с `failed`: отсутствие живого бота — это `not_verifiable`, а не провал.
- Доказательство для каждого `passed` — конкретное имя теста или путь в коде, не общие слова.
