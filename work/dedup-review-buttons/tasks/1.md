# Task 1: DB concurrency guard + review-token store

## Description

Фундамент фичи «кнопки под алертом [E014]». Задача чисто на уровне слоя доступа к данным (`pending_articles_repo.py`), без Telegram-логики — её потребят задачи Wave 2/3.

Две независимые, но связанные части:

**(a) Защита от `database is locked`.** Фича вводит **второй одновременный писатель** в `news.db`: фоновый listener-поток будет вызывать `skip_pending(link)` в тот момент, когда основной поток (`job()` / слот-цикл публикации) уже держит write-lock. Сейчас `pending_articles_repo._connect()` (строки ~174-177) — это «голый» `sqlite3.connect(news_bot.DB_FILE)` **без `busy_timeout`**, поэтому конкурентная запись падает с `sqlite3.OperationalError: database is locked` мгновенно (0 мс ожидания). Соседний модуль `outage_state._connect()` (строки 105-115) уже решает ровно эту проблему выставляя busy-timeout 5000 мс. Переносим ту же защиту (5 с) в repo, но реализуем её через параметр `sqlite3.connect(..., timeout=5.0)` (эквивалент `busy_timeout=5000`) — единая точка `_connect()`, малый радиус поражения, и без лишнего `execute()`, который сдвинул бы счётчик в fault-injection тесте (tech-spec Decision 4; см. What to do п.1-2).

**(b) Хранилище review-токенов.** `callback_data` в Telegram ограничен 64 байтами, а PK статьи в очереди — это её полный URL (обычно длиннее лимита). Поэтому под кнопку кладём короткий токен `secrets.token_urlsafe(9)`, а соответствие `токен → link` храним в **уже существующей** таблице `bot_state(key TEXT PRIMARY KEY, value TEXT)` под ключом `review_token:<token>`. Нужны три тонких helper-а поверх `bot_state`: `put_review_token(token, link)`, `get_review_token_link(token) -> Optional[str]`, `delete_review_token(token)`. Новой таблицы/миграции НЕТ (tech-spec Decision 3, Data Models).

## What to do

1. **`_connect()` → busy_timeout (5000 мс).** В `pending_articles_repo._connect()` выставить busy-timeout 5 секунд. **Предпочтительный способ — параметр `timeout`:** `sqlite3.connect(news_bot.DB_FILE, timeout=5.0)`. Он эквивалентен `PRAGMA busy_timeout = 5000` (Python-параметр `timeout` задаётся в секундах и напрямую конфигурирует busy-timeout SQLite; `PRAGMA busy_timeout` на таком соединении читается как `5000`), но **не добавляет лишнего вызова `execute()`** в `_connect()`. Это важно: см. пункт про fault-injection тест ниже. Вариант «через `PRAGMA` execute()» (как в `outage_state._connect()`) тоже даёт 5000, но добавляет `execute()` внутрь `_connect()` и потому ломает счётчик в существующем тесте — используй параметр `timeout`.
   Эффект тот же: все существующие вызовы repo (`skip_pending`, `list_pending`, `move_to_*`, `retry_from_failed` и т.д.) начинают ждать блокировку до 5 с вместо мгновенного падения `database is locked` — это ожидаемо и безопасно.

2. **Проверить/поправить fault-injection тест `test_move_to_published_rollback_on_error`.** Этот тест (`tests/test_pending_articles_repo.py`, ~L700) подменяет `repo.sqlite3.connect` на `WrappingConn`, который считает КАЖДЫЙ `execute()` на соединении и бросает на **3-м** (внутри `move_to_published`: 1 SELECT → 2 INSERT published → **3 INSERT processed_news** → 4 DELETE). Если busy-timeout поставить через `conn.execute("PRAGMA busy_timeout=5000")` внутри `_connect()`, этот PRAGMA станет `execute()` №1 на том же обёрнутом соединении → вся нумерация сдвинется, и тест начнёт падать не в той точке транзакции (сломается его смысл). Параметр `timeout=5.0` (пункт 1) `execute()` НЕ добавляет → счётчик не сдвигается → тест остаётся зелёным без правок. Если по какой-то причине выберешь путь через PRAGMA — обязательно синхронно поправь порог/комментарии в этом тесте. По умолчанию: идём через `timeout=5.0` и оставляем тест как есть, но всё равно ПРОГОНЯЕМ его и убеждаемся, что он зелёный.

3. **Ключ-префикс.** Добавить модульную константу префикса ключа `review_token:` рядом с остальными `bot_state`-ключами (строки ~43-53, где живут `_KEY_SOFTFLAG_PAIR_PREFIX` / `_KEY_DEDUP_DEGRADED`). Не хардкодить строку `'review_token:'` внутри helper-ов.

4. **Три helper-а над `bot_state`.** Добавить в `pending_articles_repo.py`, в секцию `bot_state`-хелперов дедупа (~L898-1007, т.е. в конце модуля рядом с `mark_pair_pinged` / degraded-хелперами):
   - `put_review_token(token, link)` — UPSERT строки `bot_state`: ключ `review_token:<token>`, значение = `link`. Повторный put тем же токеном перезаписывает значение.
   - `get_review_token_link(token) -> Optional[str]` — вернуть сохранённый `link` или `None`, если токена нет.
   - `delete_review_token(token)` — удалить строку токена; вызов для несуществующего токена — безопасный no-op (не бросает).
   Все три **сами открывают своё соединение** через `_connect()` и сами управляют транзакцией (сигнатуры БЕЗ параметра `conn`) — этого требует smoke-контракт tech-spec (`r.put_review_token('t','http://x')` вызывается без соединения). Это паттерн `outage_state._get` / `_set`, а не `conn`-принимающий паттерн `mark_pair_pinged`. SQL — только через `?`-плейсхолдеры (иначе упадёт `TestSqlAudit::test_parameterized_queries_only`).

5. **Тесты** (сначала — см. TDD Anchor) в `tests/test_pending_articles_repo.py`:
   - тест-класс на `_TmpDbCase` (tempfile-DB + `init_schema`, как у `TestPairRateLimit` / `TestDedupDegradedRateLimit`) для round-trip / unknown / delete / overwrite токен-стора;
   - отдельная проверка, что `_connect()` реально даёт `busy_timeout = 5000` (чтение `PRAGMA busy_timeout` на выданном соединении);
   - **тест конкурентной записи двух писателей** (carry-forward из tech-spec Integration tests): «publish-loop писатель» и «cancel писатель» бьют в один и тот же tempfile-DB одновременно — под busy_timeout вторая запись ДОЖИДАЕТСЯ блокировки и завершается без `sqlite3.OperationalError: database is locked` (см. TDD Anchor `test_two_writers_no_database_locked`).

6. Прогнать весь набор repo-тестов и полный `pytest` — существующие тесты (в т.ч. `PRAGMA table_info` инварианты схемы и fault-injection `test_move_to_published_rollback_on_error`, см. пункт 2) должны остаться зелёными: новой таблицы не добавляем.

## TDD Anchor

Тесты пишем ДО реализации: пишем → запускаем → падают → пишем код → проходят. Все — в `tests/test_pending_articles_repo.py` (новый класс `TestReviewTokenStore(_TmpDbCase)`; busy_timeout и конкурентная запись — отдельный класс/метод, т.к. проверяют `_connect()`, а не `bot_state`).

- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_put_get_roundtrip` — `put_review_token('tok','http://x/a')` → `get_review_token_link('tok')` возвращает ровно `'http://x/a'`.
- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_get_unknown_token_returns_none` — `get_review_token_link('never-stored')` → `None` (без исключения).
- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_delete_removes_token` — после `put` → `delete_review_token('tok')` → `get_review_token_link('tok')` == `None`.
- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_delete_unknown_token_is_noop` — `delete_review_token('nope')` на отсутствующем токене не бросает (идемпотентно).
- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_put_overwrites_existing` — два `put` с одним токеном и разными link → `get` возвращает второй link.
- `tests/test_pending_articles_repo.py::TestReviewTokenStore::test_token_stored_under_prefixed_key` — после `put('tok', link)` строка лежит в `bot_state` под ключом `review_token:tok` (прямой SELECT), не под голым `tok`.
- `tests/test_pending_articles_repo.py::TestConnectBusyTimeout::test_connect_sets_busy_timeout` — соединение из `repo._connect()` на `PRAGMA busy_timeout` возвращает `5000`.
- `tests/test_pending_articles_repo.py::TestConcurrentWriters::test_two_writers_no_database_locked` — **carry-forward из tech-spec** (Integration tests / Risks «database is locked»). Реальный tempfile-DB (`_TmpDbCase`) + два конкурентных писателя: один держит write-lock (модель publish-loop писателя — например, открытая `BEGIN IMMEDIATE`-транзакция или `insert_pending`/`move_to_*`), второй в это время выполняет запись cancel-пути (`skip_pending(link)` либо `put_review_token(...)`) через `repo._connect()`. Ассертим: второй писатель ДОЖИДАЕТСЯ освобождения блокировки в пределах busy_timeout и завершается БЕЗ `sqlite3.OperationalError` с текстом `database is locked`. Контроль — что без busy_timeout тот же сценарий падал бы мгновенно (можно зафиксировать в комментарии; сам негативный прогон не обязателен, чтобы тест не был флэки).

**Edge cases:**
- Токен неизвестен / истёк / бот перезапускался → `get_review_token_link` возвращает `None` (обработку «устарела» делает Wave 3, здесь только `None`).
- Повторный `delete` того же токена → no-op, без исключения.
- Повторный `put` тем же токеном → перезапись (UPSERT).
- `link` содержит `:` и `/` — это значение, не ключ, поэтому проблем экранирования нет; в ключе только сам токен (`token_urlsafe` — безопасный алфавит).

**Implementation hints** (указатели на образцы, НЕ псевдокод — конкретный код пишешь по TDD):
- busy-timeout: задать через параметр `timeout` у `sqlite3.connect` (эквивалент `busy_timeout=5000`, без лишнего `execute()`); значение/семантику 5 с сверить с `outage_state._connect()`, где та же константа уже принята в проекте.
- helper-ы токен-стора: **бери за модель `outage_state._get` / `_set`** (L122-153) — тот же контур «сам открываю соединение через `_connect()`, сам владею транзакцией, сам закрываю в `finally`»: read-хелпер = один параметризованный SELECT + `fetchone()`; write/delete = UPSERT / DELETE по ключу в одной коммит-транзакции. Форму SQL и обработку транзакции копируй из `_get`/`_set`, не изобретай — здесь важно повторить паттерн, а не переписать его словами.
- НЕ давать helper-ам параметр `conn` — smoke-контракт вызывает их без соединения (в отличие от `mark_pair_pinged`, который `conn` принимает).
- весь SQL — только через `?`-плейсхолдеры; ключ строить из константы-префикса + токена, не хардкодить литерал внутри функций.
- Не трогать DDL/схему и `EXPECTED_*` инварианты — таблица `bot_state` уже создаётся в `init_schema` (L197).
- Для `TestConcurrentWriters` образец организации tempfile-DB — тот же `_TmpDbCase`; модель «держим write-lock на одном соединении, второе пишет и дожидается» — короткий поток/`threading` вокруг реальных repo-вызовов; конкретную механику подбери сам, цель — детерминированно (не флэки) показать отсутствие `database is locked`.
