# Task 7: Code Audit

## Required Skills

## Description

Целостный аудит качества кода всей фичи `dedup-review-buttons` — первого случая, когда бот
начинает **принимать** входящие из Telegram (фоновый long-poll `get_updates` рядом с
блокирующим `schedule`/publish-циклом). К этому моменту весь код фичи написан (задачи 1–6),
задачи в waves ревьюились по отдельности. Этот таск смотрит на результат **как на единое
целое**: как новый listener-поток сосуществует с publish-циклом, как разделяются общие
ресурсы (`news.db`, общий бот-токен), нет ли расхождений в паттерне инициализации `Bot`, и
изолирован ли listener так, что его падение не убивает публикацию.

Это **аудит — только анализ, без правок кода**. Результат — отчёт с находками (severity +
точное место + доказательство + рекомендация). Исправления, если понадобятся, делаются
отдельно (fix-режим соответствующей задачи или новый таск) — не здесь.

Границы, чтобы не дублировать смежные аудиты Audit-волны:
- **Безопасность** (auth администратора, утечки токена/секретов, инъекции в `callback_data`,
  DoS публичного `get_updates`) — это **Task 8 (Security Audit)**. Здесь безопасность трогаем
  только там, где она пересекается с корректностью кода; глубокий OWASP-разбор — не сюда.
- **Качество тестов** (покрытие ветвей `resolve_dedup_callback`, concurrency-тест,
  cancel→не-опубликовано, gate/fail-closed) — это **Task 9 (Test Audit)**. Тест-файлы читаем
  для контекста и как доказательство поведения, но их полноту оценивает Task 9.

Фокус Task 7 — **качество кода и архитектурная корректность** (concurrency, разделяемые
ресурсы, дрейф паттернов, изоляция ошибок, читаемость/поддерживаемость, соответствие
Architecture и Patterns проекта).

## Details

**Природа задачи:** аудит (анализ, без правок). Ревьюеров нет — этот таск сам является ревью.

**Dependencies:** зависит от Task 1–6 (весь код фичи должен быть написан — аудит читает
фактическое состояние файлов, а не tech-spec как «как должно быть»; расхождение spec↔код само
по себе является находкой). Идёт в Audit-волне (wave 4) параллельно с Task 8 (Security Audit) и
Task 9 (Test Audit) — все три analysis-only, по правкам не пересекаются, общего мутабельного
ресурса нет.

**Шкала severity (одна на весь отчёт):** `blocker / major / minor / nit` — как в
аудите-прецеденте `work/dedup-model-series/tasks/7.md`, согласовано со шкалой скилла
code-reviewing (Issue Categorization: critical / major / minor). Для этой фичи:
- **blocker** — блокирующая проблема, обязательная к фиксу: ломает публикацию / убивает listener
  так, что падает и publish-цикл / молча теряет решения оператора.
- **major** — значимая проблема, которую надо адресовать: нарушает инвариант фичи (thread-safety,
  гейт `REVIEW_BUTTONS_ENABLED`, изоляция listener, Bot-init), но обходится.
- **minor / nit** — ценные, но опциональные улучшения: читаемость, дублирование, мелкая
  несогласованность.

**Файлы фичи (что где смотреть):**
- `pending_articles_repo.py` — новый `PRAGMA busy_timeout=5000` в `_connect()` (влияет на ВСЕХ
  вызывающих репозиторий — оценить blast radius) и token-store поверх `bot_state`
  (`put_review_token`/`get_review_token_link`/`delete_review_token`). Сверить с `outage_state.py`.
- `admin_alerts.py` — `build_dedup_review_keyboard(token)`: чистая функция, две кнопки,
  `callback_data` `dd:c:<token>`/`dd:k:<token>`; не должна трогать текст-якорь «Похож на дубль».
- `news_bot.py` — 4 точки: (1) `send_admin_notification(..., *, reply_markup=None)` проброс в
  `send_message`; (2) E014 send site (~L2359-2397) — mint token, `put_review_token`, клавиатура,
  гейт `REVIEW_BUTTONS_ENABLED`; (3) `resolve_dedup_callback(action, token, from_user_id)` —
  чистая логика решения; (4) `_run_review_listener()` + запуск из `main()` под гейтом.
- `.env.example` — `REVIEW_BUTTONS_ENABLED` (default off, prod-only) — сверить формулировку с
  Decision 6 и deployment.md.
- `architecture.md` / `deployment.md` — обновления PK; проверить, что описанное поведение
  совпадает с фактическим кодом (не разошлись ли доки и реализация).

**Фокус-измерения (главное для Task 7):**
1. **Thread-safety listener vs publish loop.** sqlite3-соединения не thread-safe → каждый поток
   ОБЯЗАН иметь свой `_connect()`; убедиться, что listener не переиспользует соединение
   main-потока и наоборот. `busy_timeout=5000` должен реально сериализовать двух писателей
   (listener `skip_pending` vs `job()` publish/insert). Проверить, нет ли общего мутабельного
   состояния (offset, кэши, `Bot`-инстансы), которое гоняется между потоками без защиты.
2. **Shared-resource compliance (Architecture).** Сверить с таблицей Shared resources в
   tech-spec: `news.db` — 1 файл / N per-thread соединений; токен — 1 аккаунт, polling только
   на проде. Код должен гейтить И listening, И attachment клавиатуры одним флагом
   `REVIEW_BUTTONS_ENABLED`, чтобы не-прод не 409-ил и не рисовал мёртвые кнопки.
3. **Bot-init drift.** listener создаёт свой `Bot(token=TELEGRAM_BOT_TOKEN)`. Сравнить с
   `send_admin_notification._send()` (`Bot(token=...)` per call): один и тот же источник токена,
   консистентное конструирование, нет копипаст-дрейфа/раздвоения конфигурации.
4. **Error isolation.** Цикл `_run_review_listener` должен быть обёрнут в try/except с backoff;
   любое исключение (сеть, TelegramError, 409, БД) логируется/пингуется, но поток daemon и его
   смерть НЕ роняет publish-процесс. Оценивать по общему принципу изоляции: прямого
   thread-isolation прецедента в `patterns.md` → Error Isolation нет (там только single-threaded
   per-feed try/catch), поэтому сверять с духом секции, а не как с готовым паттерном; плюс с
   риском «Listener thread crashes» в tech-spec.

**Общие измерения (в границах Task 7):** читаемость, дублирование, корректность обработки
ошибок, консистентность с конвенциями проекта, обратная совместимость send-пути (существующие
позиционные вызовы `send_admin_notification` не должны сломаться из-за keyword-only
`reply_markup`), отсутствие мёртвого/недостижимого кода, разумность логирования решения
оператора (INFO: cancel/keep + link + статус).

**Границы (НЕ делать в Task 7):** глубокий security-разбор → Task 8; оценка полноты/качества
тестов → Task 9. При пересечении — коротко отметить и сослаться на смежный аудит, не
