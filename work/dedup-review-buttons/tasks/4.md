## Description

Добавляем в `news_bot.py` **чистую** функцию `resolve_dedup_callback(action, token, from_user_id)` — «мозг» обработки нажатия кнопки под алертом `[E014] «Похож на дубль»`. Функция принимает уже разобранные поля callback-запроса (действие, токен, id нажавшего) и **не делает никакого Telegram-I/O**: она проверяет права администратора, резолвит состояние очереди по токену и возвращает пару строк `(status_text, answer_text)`, которые вызывающий (listener из Task 5) применит через `edit_message_text` + `answer_callback_query`.

Это ядро фичи: именно здесь принимается решение «отменить / уже опубликовано / недоступно / оставлено / устарело» и здесь же выполняется единственная запись в БД — `skip_pending(link)` на отмене. Вынесение логики в pure-функцию делает все ветки полностью unit/integration-тестируемыми на реальной SQLite без живого бота (user-spec: E2E «палец в Telegram» невозможен как автотест).

Функция реализует Decisions 2 (переиспользуем `skip_pending`), 5 (числовой admin, fail-closed), 9 (отмена окончательна), 10 (детект «уже опубликовано» по состоянию БД, не по таймеру) и listen-путь из раздела «How it works» тех-спека.

## What to do

Добавить в `news_bot.py` функцию `resolve_dedup_callback(action, token, from_user_id)`, которая по порядку:

> **Контракт `action` (согласовано с Task 5 и тех-спеком, раздел «Listen»).** Listener из Task 5 разбирает `callback_data` по грамматике `dd:<c|k>:<token>` и **до** вызова этой функции мапит букву в полное слово: `c → 'cancel'`, `k → 'keep'`. Поэтому `resolve_dedup_callback` ветвится строго по **полным словам** `action == 'cancel'` / `action == 'keep'` (НЕ по сырым буквам `'c'` / `'k'` — иначе реальное нажатие в проде молча ничего не сделает, хотя изолированные тесты каждой задачи будут зелёными). Любое иное значение `action` — безопасный no-op / «устарела», без падения.

1. **Проверка администратора (fail-closed).** Сравнивает `from_user_id` (int из Telegram) с числовым `int(TELEGRAM_ADMIN_ID)`. Если `TELEGRAM_ADMIN_ID` не приводится к числу (например дефолт `@sunny413x`) — считать это отказом (fail-closed, никаких действий). Не-администратор или нечисловой admin-id → вернуть результат «игнорировано» (без изменения состояния, без правки сообщения). `TELEGRAM_ADMIN_ID` читать как модульный атрибут во время вызова, чтобы тесты могли его патчить.

2. **Резолв токена.** Через `pending_repo.get_review_token_link(token)` получить `link`. Если `None` (токен неизвестен — бот перезапускался, токен уже удалён, или мусорный callback) → терминальный статус «⚠️ Кнопка устарела», без записи в БД.

3. **Действие `keep` (`action == 'keep'`).** Никаких изменений состояния → статус «👍 Оставлено». Удалить токен (терминальный исход).

4. **Действие `cancel` (`action == 'cancel'`).** Определить состояние статьи на момент нажатия (Decision 10 — по состоянию БД):
   - `link` ещё в `pending_articles` (`pending_repo.get_pending(link)` не `None`) → вызвать `pending_repo.skip_pending(link)` → статус «✅ Отменено оператором».
   - иначе если `link` есть в `published_articles` (`pending_repo.get_published(link)` не `None`) → статус «⚠️ Уже опубликовано, отменить нельзя» (пост в канале не трогаем).
   - иначе → статус «⚠️ Статья уже недоступна».
   - Во всех терминальных исходах отмены удалить токен (`pending_repo.delete_review_token(token)`).

5. **Возврат.** Вернуть `(status_text, answer_text)`: `status_text` — строка для дописывания в сообщение через edit (или сигнал «не редактировать» для игнора не-админа); `answer_text` — короткий текст для `answer_callback_query`. Формат согласовать с ожиданиями Task 5 (listener подставляет `edit_message_text(original + "\n\n" + status_text)`), зафиксировать контракт в docstring.

Написать TDD-тесты в `tests/test_integration.py`, покрывающие **каждую** ветку на реальной SQLite (см. TDD Anchor).

## TDD Anchor

- `tests/test_integration.py::TestResolveDedupCallback::test_non_admin_press_ignored_no_state_change` — `from_user_id`, не равный admin-id → результат «игнорировано», строка в `pending_articles` не тронута, `skip_pending` не вызывался, токен не удалён.
- `tests/test_integration.py::TestResolveDedupCallback::test_cancel_pending_row_skips_and_returns_cancelled` — `action='cancel'`, `link` в `pending_articles` → строка исчезла из `pending_articles`, появилась в `processed_news`; статус «✅ Отменено оператором»; токен удалён.
- `tests/test_integration.py::TestResolveDedupCallback::test_cancel_then_slot_publish_does_not_publish` — интеграционный: стейджим pending-строку → `resolve_dedup_callback('cancel', token, admin_id)` убирает её из `pending_articles` → затем прогоняем slot/publish-путь (берём «следующую к публикации» через `pending_repo.list_pending()`; отправку в канал / сайд-эффект `_fallback_publish` застабить) → отменённый `link` отсутствует в `list_pending()`, не появляется в `published_articles`, публикация в канал по нему НЕ вызывается (user-spec «в свой слот она не выходит в канал»). Единственный анкер, затрагивающий publish-путь; сама `resolve_dedup_callback` остаётся без Telegram/publish-I/O.
- `tests/test_integration.py::TestResolveDedupCallback::test_cancel_published_returns_already_published` — `link` только в `published_articles` → статус «⚠️ Уже опубликовано, отменить нельзя»; published-строка не тронута; `skip_pending` не вызывался.
- `tests/test_integration.py::TestResolveDedupCallback::test_cancel_missing_returns_unavailable` — токен валиден, но `link` отсутствует и в pending, и в published → статус «⚠️ Статья уже недоступна»; ошибок нет.
- `tests/test_integration.py::TestResolveDedupCallback::test_keep_returns_kept_no_state_change` — `action='keep'`, строка в `pending_articles` → статус «👍 Оставлено»; строка в очереди осталась; токен удалён.
- `tests/test_integration.py::TestResolveDedupCallback::test_stale_token_returns_expired` — неизвестный/удалённый токен → статус «⚠️ Кнопка устарела»; изменений состояния нет.
- `tests/test_integration.py::TestResolveDedupCallback::test_non_numeric_admin_id_fail_closed` — `news_bot.TELEGRAM_ADMIN_ID='@sunny413x'` (нечисловой), нажатие даже с «правильным» id → fail-closed, результат «игнорировано», состояние не меняется.

## Details

**Files:**

Логичное место — рядом с `send_admin_notification` (~L469-530), в секции admin/notification-хелперов; Task 5 (listener) будет её вызывать. Импорты не нужны: `pending_articles_repo` уже импортирован как `pending_repo` (L66); `TELEGRAM_ADMIN_ID` — модульный конфиг (L102, дефолт `@sunny413x` — нечисловой). Внутри функции читать `TELEGRAM_ADMIN_ID` через модульный атрибут (не кэшировать в аргументе), чтобы тесты патчили `patch('news_bot.TELEGRAM_ADMIN_ID', '12345')`.
- `pending_articles_repo.py` (только чтение, менять не надо):
  - `skip_pending(link)` (L727-757) — идемпотентно: `SELECT` по `link`, если нет — ранний возврат; иначе `INSERT OR IGNORE INTO processed_news` + `DELETE FROM pending_articles`, один commit. Именно это вызывает ветка cancel.
  - `get_pending(link)` (L389-401) → dict или `None` — признак «ещё в очереди».
  - `get_published(link)` (L404-415) → dict или `None` — признак «уже опубликовано».

- `tests/test_integration.py` — новый класс `TestResolveDedupCallback(_IntegrationBase)`. Базовый `_IntegrationBase.setUp` (L69-79) поднимает tempfile-SQLite и вызывает `news_bot.init_db()`; `patch('news_bot.DB_FILE', tempfile)` достаёт и `news_bot`, и `pending_articles_repo` (оба читают `news_bot.DB_FILE` в момент вызова). Стейджить строки прямым `INSERT` в `pending_articles`/`published_articles` (или через существующие repo-хелперы), токены — через `put_review_token`. Проверять `skip_pending`-вызов можно и по факту (строка исчезла из `pending_articles` + появилась в `processed_news`), и/или через `patch('news_bot.pending_repo.skip_pending')` для веток, где он НЕ должен вызываться (published/missing/non-admin).

**Контракт возврата (зафиксировать в docstring и согласовать с Task 5):**
- `status_text` — строка-статус для дописывания в сообщение через `edit_message_text` на терминальном исходе; для «игнорировано» (не-админ / нечисловой admin-id) — сигнал «не редактировать сообщение» (напр. `None`), чтобы listener ничего не менял.
- `answer_text` — короткий текст для `answer_callback_query`; для «игнорировано» — пусто/`""`.

**Тексты статусов (точные, из user-spec / тех-спека):** «✅ Отменено оператором», «⚠️ Уже опубликовано, отменить нельзя», «⚠️ Статья уже недоступна», «👍 Оставлено», «⚠️ Кнопка устарела».

**Dependencies:**
- Task 1 (token store: `get_review_token_link` / `delete_review_token`, `busy_timeout` в `_connect()`). Пакеты новые не нужны (stdlib + уже установленный `python-telegram-bot`, но I/O здесь нет).

**Edge cases:**
- Нечисловой `TELEGRAM_ADMIN_ID` (дефолт `@sunny413x`) → fail-closed: любое нажатие игнорируется, состояние не меняется (Decision 5).
- Устаревший/повторный токен (бот перезапускался, строки нет) → «устарела/недоступна», без исключений (Decision 9, user-spec критерий про повторное нажатие).
- Отмена статьи, которая уже успела опубликоваться в свой слот → «уже опубликовано», пост в канале не трогаем (Decision 10).
- Гонка «pending → published» между проверкой и `skip_pending` не критична: `skip_pending` идемпотентен и не пишет в `published_articles`.
- Неизвестное `action` (не `'cancel'`/`'keep'`) — listener (Task 5) фильтрует грамматику `dd:<c|k>:<token>` и мапит `c → 'cancel'` / `k → 'keep'` до вызова; функция может трактовать любое иное значение как безопасный no-op/«устарела», но пусть не падает.

**Implementation hints (НЕ псевдокод):**
- Держать функцию строго без Telegram-I/O — только чтение конфига, вызовы `pending_repo.*` и возврат строк. Всё сетевое (edit/answer/get_updates) — в Task 5.
- Удаление токена делать один раз на терминальном исходе (keep + три ветки cancel), не на игнорировании и не на устаревшем токене (там удалять нечего).
- Логирование решения оператора (cancel/keep + link + статус) на INFO — это делает listener в Task 5 (user-spec: «записываем в лог решение»); в pure-функции достаточно вернуть данные для лога либо оставить лог вызывающему. Не логировать токен/секреты (см. `test_no_token_leak_in_logs`).
