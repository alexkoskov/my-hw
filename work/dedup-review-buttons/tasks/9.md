**Файлы:**
- `tests/test_pending_articles_repo.py`, `tests/test_admin_alerts.py`, `tests/test_admin_ping.py`, `tests/test_integration.py` — прочитать целиком (в части, относящейся к фиче), оценить покрытие. Это набор из tech-spec «Files to modify» задач 1–5; сверить с фактом по `decisions.md`.
- `pending_articles_repo.py`, `admin_alerts.py`, `news_bot.py` — прочитать реализацию, чтобы судить о покрытии веток по коду, а не по названиям тестов.

**Матрица покрытия для сверки (из tech-spec Testing Strategy + Acceptance Criteria):**
- `build_dedup_review_keyboard` → две кнопки, точные `callback_data` `dd:c:<token>` / `dd:k:<token>`, лейблы с эмодзи, `callback_data` ≤ 64 байт.
- `send_admin_notification(reply_markup=...)` → форвардит markup в `send_message`; без него — вызов байт-в-байт как раньше (keyword-only параметр, старые позиционные тесты зелёные).
- token store → `put`/`get`/`delete` round-trip; `get` неизвестного токена → None.
- `resolve_dedup_callback` → 6 веток: non-admin, stale, keep, cancel-pending (`skip_pending`), cancel-published («уже опубликовано»), cancel-missing («недоступна»); + `delete_review_token` после терминального исхода.
- gate → не-числовой `TELEGRAM_ADMIN_ID` → нет слушателя (fail-closed); `REVIEW_BUTTONS_ENABLED` off → нет потока.
- integration (реальный SQLite) → cancel до слота: строка удалена из `pending_articles`, есть в `processed_news`, слот не публикует; cancel после публикации: «уже опубликовано», опубликованная строка цела.
- concurrency → publish-writer + cancel-writer против одной БД с `busy_timeout` → нет `database is locked`.
- error isolation → падение слушателя не роняет publish-loop (проверить, есть ли тест на это; это отдельный AC).
- логирование решения оператора (cancel/keep + link + статус) на INFO — проверить, покрыто ли тестом.

**Dependencies:** волны 1–3 (Tasks 1–5) должны быть выполнены и смёржены — иначе тестов ещё нет. Task 6 (docs) в depends_on для порядка волны, на тесты не влияет. E2E не автоматизируется (общий токен → слушает только прод) — это ожидаемо, не считать пробелом; отметить как «покрыто ручной пост-деплой проверкой оператора (Task 12)».

**Edge cases для отдельного внимания:**
- Ложно-зелёные тесты: cancel-ветки, которые ассертят только возвращённый текст, но не проверяют фактическое изменение БД (или наоборот).
- Concurrency-тест, который лишь формально дергает две записи последовательно и не доказывает работу `busy_timeout`.
- Тесты, полагающиеся на реальное время/сеть/`get_updates` без мока — недетерминизм.
- «Никакой другой алерт не несёт кнопки» — проверить, есть ли негативный тест на это, или это только утверждение спека.

**Implementation hints:** severity-шкала (по методологии test-master, `references/test-quality-review.md`) — critical (непокрытая ветка с риском для данных, напр. cancel-published не проверяет целостность published-строки) / high (непокрытый AC) / medium (слабый ассерт) / low (стиль). По каждой находке — поля `severity`, `issue`, `evidence` (`файл:строка` / имя теста), `fix`; список отсортировать по severity. Итог — явный вердикт «go / no-go» для Pre-deploy QA.
