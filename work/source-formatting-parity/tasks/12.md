# Task 12: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [.claude/skills/test-master/SKILL.md](../../../.claude/skills/test-master/SKILL.md) — методология качества тестов: осмысленность ассертов, пирамида, что делает тест «пиннящим поведение», а не тавтологически зелёным. Файлы фичи лежат под `my-hw/`, поэтому используется scoped-скилл `my-hw:test-master`, а не глобальный.

## Description

Целостный аудит качества тестового слоя ВСЕЙ Phase 1 фичи `source-formatting-parity` —
всего, что написали Task 1–9, как единого набора. Задача — только анализ. Ни код, ни тесты
не меняются. Результат — audit-отчёт: вердикт (pass / pass-with-findings / fail) + находки
(severity + `файл:строка` или имя теста + в чём дефект + предлагаемый фикс). Blocker/major
чинит fixer, которого запускает lead этапа; сам аудит не правит.

### Главный вопрос аудита

Не «много ли тестов», а: **краснеет ли этот набор, когда фича сломана?**

Зелёный набор доказывает ровно ноль, пока не показано, что он умеет быть красным. У этого
проекта есть три задокументированных способа получить зелёный набор, который ничего не
проверяет, и **все три уже случались здесь, а не в учебнике**. Аудит ищет именно их.

**Способ 1 — пустой `-k`-селектор.** `pytest -k`, не собравший ни одного теста, выходит с
кодом 0. Значит проверка вида «`pytest -k image_limit` → зелено» проходит и тогда, когда
теста не существует вовсе. Tech-spec сам это фиксирует отдельной строкой в § Testing
Strategy: «Every `-k` selector named above must match at least one collected test». Хуже
того — селектор может собирать ЧУЖИЕ тесты и быть зелёным ещё до того, как написана первая
строка фичи: создатель Task 8 это измерил и записал — селектор из tech-spec
`-k "mismatch or aligned"` без указания файла собирает **8 тестов на немодифицированном
коде** (TZ-алерты и paragraph-count в движках — ни один не про рассинхрон блоков). Аудит
обязан проверить на этот класс дефекта **все** селекторы фичи, а не только тот.

**Способ 2 — ассерт по строке, которая есть в статичном тексте.** 2026-08-04 этот проект
выпустил два таких теста в один день, и поймала их только мутационная проверка:

- тест алерта искал `'402'` — а builder сам упоминает «402 / Insufficient credits» в
  строке-подсказке; тест проходил на реализации, которая причину вообще не получала;
- тест времени отложения выводил ожидаемое значение из **той же константы**, что и код:
  поставь `HOLD_DEFER_HOURS = 0` — меняются обе стороны, тест зелёный, а фича в проде не
  работает вовсе.

Урок записан дословно: проверять надо по строке, **которой в статичном тексте быть не
может**, и по свойству, а не по значению, выведенному из проверяемой же константы. Обе
формы искать в тестах этой фичи — здесь для них идеальные условия: капы 30/10, границы
`_MAX_TEXT_FOR_RUNS`/`_MAX_RUNS_PER_BLOCK`, уровни заголовков 3/4 и тексты WARNING.

**Способ 3 — односторонний инвариант (урок 2026-07-28).** Проверен только «положительный»
полюс, а противоположный отказ не покрыт. Tech-spec § Testing Strategy ссылается на этот
урок прямо и требует два конкретных контроля:
- **негативные контроли эвристики заголовка** — эвристика с одними положительными тестами
  штампует ложные заголовки, и никто этого не увидит;
- **контроль ложного срабатывания страховки выравнивания** — всегда срабатывающая
  страховка ТИХО отключает фичу на 100 % публикаций, при этом каждый позитивный тест
  («рассинхрон → блоки отброшены») остаётся зелёным.

### Почему цена ошибки здесь высокая

Deploy запрещён 10:00–20:00 МСК, все три слота публикации внутри окна, а Decision 3b
делает **каждый** режим отказа этой фичи молчаливым: ни пинга, ни ошибки — только плоский
текст. Значит в проде некому заметить, что фича не работает; тестовый набор здесь
единственный наблюдатель. Молча отключившаяся фича выглядит ровно как исправно работающая
фича на статье без разметки.

**Границы аудита.** Качество продакшн-кода и межкомпонентная согласованность — периметр
Task 10; безопасность — периметр Task 11. При пересечении достаточно строки со ссылкой на
смежный аудит. Исключение, о котором стоит помнить: **отсутствие теста на инвариант из
Decisions — это находка ЭТОГО аудита**, даже если сам инвариант в коде выполнен, потому что
незакреплённое поведение исчезает в следующем рефакторинге.

## Verification Steps

### Automated

Прогоны ниже — **инструмент аудита и доказательства для отчёта**, а не приёмка задачи;
приёмка меряется полнотой отчёта. Полная сверка набора с базовой линией — Task 13
(Pre-deploy QA). Запускать из `/workspaces/debian-2/my-hw`.

- Заземление: `python3 -m pytest -q` — зафиксировать число собранных/прошедших как контекст
  отчёта. **Внимание:** tech-spec называет базовой линией **1626 passed**, но это цифра от
  2026-08-03; на 2026-08-05 набор собирает **1693** теста (работы 2026-08-04 добавили
  тесты). Если tech-spec к моменту аудита не обновлён — это находка уровня informational,
  адресованная Task 13, который иначе сравнит с устаревшим числом.
- Сбор по каждому селектору — обязательно в двух формах:
  `python3 -m pytest -q -k "<селектор>" --collect-only | tail -3` и то же с указанием файла
  (`python3 -m pytest -q tests/test_<файл>.py -k "<селектор>" --collect-only | tail -3`).
  Разница между формами и есть «однофамильцы».
- Имена собранного, а не только количество:
  `python3 -m pytest -q -k "<селектор>" --collect-only | head -20` — глазами убедиться, что
  тесты принадлежат этой фиче.

### Форма 1 урока 2026-08-04 — ассерт по строке, которая есть в статичном тексте

Механика дефекта: тест ищет подстроку в выходе, но эта же подстрока присутствует в
шаблоне/подсказке/docstring, поэтому ассерт проходит на реализации, которая искомого
поведения не имеет вовсе.

Где искать в этой фиче:

- **WARNING страховки выравнивания.** Если тест ищет `"blocks"`, `"paragraphs"` или само
  слово «mismatch» — эти строки почти наверняка есть в статичном шаблоне сообщения.
  Осмысленный ассерт цепляется за **числа конкретного случая** (например, 12 против 13) или
  за факт, что `blocks` в собранной строке стало `None`, — то есть за то, чего в статичном
  тексте быть не может.
- **WARNING границы request-пути.** Та же форма.
- **Эвристика заголовка.** Ассерт вида «в результате есть текст заголовка» проходит и тогда,
  когда абзац остался абзацем — текст-то тот же. Осмысленный ассерт — `type == "heading"`
  и `level`, а не наличие текста.
- **Предпросмотр (AC12).** Ассерт `"<strong>" in html` слаб, если в статичном CSS/шапке
  что-то похожее уже есть; и он не отличает «жирное отрисовано» от «жирное отрисовано, но
  слово потеряно» — а это ровно тот баг, который чинили 2026-07-28 (неизвестный тег
  дропался ВМЕСТЕ С ДЕТЬМИ, и слово пропадало). Осмысленный ассерт проверяет и тег, и что
  слово внутри него на месте.

Метод: для каждого подозрительного ассерта открыть реализацию и поискать искомую подстроку
в её статичных строках (`grep -n "<подстрока>" <модуль>.py`). Совпадение = находка.

### Форма 2 того же урока — ожидание, выведенное из проверяемой константы

Механика: тест импортирует константу и строит из неё ожидание, поэтому мутация константы
двигает обе стороны сравнения и тест остаётся зелёным, хотя фича в проде выключена
(`HOLD_DEFER_HOURS = 0` — точный прецедент).

Где искать в этой фиче:

- `tests/test_llm_common.py` — тесты границ, если вход строится как
  `_MAX_RUNS_PER_BLOCK + 1` и ожидание тоже выражено через ту же константу. Мутация
  `_MAX_RUNS_PER_BLOCK = 0` обязана уронить хотя бы один тест «под границей»; если не
  роняет — тестов «нижнего полюса» нет.
- **Кап картинок.** Tech-spec прямо требует «нижний контроль, чтобы единый захардкоженный
  10 падал»: значит t-hunted должен проверяться литералом **30**, lamley/orangetrack — **10**,
  и обе стороны не должны браться из одного и того же конфига источника, иначе подмена
  конфига на единый дефолт останется незамеченной.
- **Уровни заголовков.** Ожидание `level == 3` литералом, а не через ту же таблицу
  соответствия тегов, которую проверяем.
- **Golden-файл.** Здесь форма 2 безопасна по построению — сравнение строковое, а сам golden
  сгенерирован на до-экстракционном коммите; но проверить, что тест не перегенерирует golden
  на лету (тогда он сравнивает выход с самим собой и не краснеет никогда). Это тот же дефект
  в самой чистой форме.

### Обязательные негативные контроли

Из tech-spec § Testing Strategy — пять по эвристике заголовка (все пять названы там
поимённо, поэтому отсутствие любого это находка, а не вкусовщина):

1. частично жирный короткий абзац → НЕ заголовок;
2. целиком жирный абзац, заканчивающийся `.` → НЕ заголовок;
3. целиком жирный **длинный** абзац → ЗАГОЛОВОК (закреплено намеренно, чтобы возврат
   лимита длины ронял тест, а не проходил молча);
4. `<p><strong>Part</strong> and <strong>two</strong></p>` → НЕ «целиком жирный» —
   механически нагруженный случай слияния спанов;
5. `<p><strong>Ford</strong> vs Ford</p>` — слияние построено на `text.find`, повторная
   подстрока не должна имитировать полное покрытие.

Плюс:

6. **эвристика ВЫКЛ для orangetrack, ВКЛ для t-hunted** — асcерт на источник, а не общий;
7. **контроль ложного срабатывания страховки:** на выровненной статье страховка НЕ
   срабатывает, блоки доезжают; различие `None` vs `[]` проверено явно (оно живое для
   потребителей). Без этого контроля всегда срабатывающая страховка тихо отключает фичу на
   100 % публикаций при полностью зелёном наборе;
8. **контроль флага:** флаг выключен → t-hunted блоков не отдаёт, **orangetrack отдаёт**;
9. **негатив host-гейта:** не-YouTube хост с YouTube-подобным путём НЕ оборачивается; Vimeo
   оборачивается;
10. **нижний контроль капа:** статья с числом картинок ниже капа не урезается;
11. **AC4:** жирный, добавленный переводчиком там, где в оригинале его не было, НЕ срезается
    (поведение живёт в проде с 2026-07-28 — фича не должна его регрессировать).

### Edge cases аудита

- **Тест, зелёный и до, и после фичи.** Самый частый дефект здесь. Проверять приростом
  относительно измеренной базы, а не фактом «зелено».
- **Интеграционный тест, где рассинхрон сфабрикован словарём.** Tech-spec требует достигать
  его через РЕАЛЬНЫЙ парсер по расхождению title-dedup (`t_hunted_source.py:198`). Словарь
  проверяет страховку, но не проверяет, что рассинхрон вообще возникает — и молча переживёт
  устранение причины.
- **Golden-гейт, который перегенерирует golden.** См. форму 2.
- **`tests/test_orangetrack_source.py` отредактирован.** AC10 гарантируется этими тестами
  «без правок»; любая правка обнуляет гейт. Проверяется `git diff`, а не чтением.
- **Корпус подменён синтетикой.** Decision 9 существует потому, что `tests/fixtures/`
  раньше не содержал ни одного HTML, а все числа спека были невоспроизводимы. Тест, который
  вместо корпусной страницы парсит трёхстрочный HTML, возвращает ровно ту проблему.
- **Покрытие по `-k` есть, а по AC нет.** Селектор может собирать тест, который проверяет
  не то, что требует AC. Сверять по смыслу критерия, а не по имени теста.

### Implementation hints (для аудитора)

- Severity калибровать по **последствию молчания**: дефект, из-за которого фича может быть
