# Task 9: Сквозной набор тестов форматирования (Phase 1)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [.claude/skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Закрепить тестами всю цепочку форматирования для t-hunted — от парсера до узлов
Telegraph — и зафиксировать в ней четыре поведения, каждое из которых уже
оплачено реальной аварией или явным решением оператора.

Цепочка: **парсер → очередь (`pending_articles`, JSON в SQLite) → перевод (кодирование
`**жирного**` в запрос и декодирование из ответа) → `telegraph_publisher` (узлы)**.
До этой задачи каждое звено проверено по отдельности (Task 5 — модуль, Task 7 —
парсер, Task 8 — guard, Task 6 — рендер), но НИ ОДИН тест не проходит их подряд.
Именно на стыках жила вся боль этой фичи: раны, пережившие парсер, терялись в
JSON-раунд-трипе; выравнивание ломалось не в парсере, а между двумя списками;
кап картинок не применялся, потому что рендер блоков просто не знал о нём.

Пять сценариев (tech-spec § Testing Strategy → Integration tests, Phase 1 = только t-hunted):

1. **Форматирование выживает всю цепочку.** Жирный спан, подзаголовок и элемент
   списка, извлечённые парсером из реальной фикстуры, доезжают до узлов Telegraph
   как `<strong>`, `<h3>` и `<p>• …</p>`.
2. **Потерянные LLM маркеры деградируют молча.** Перевод вернулся без единого
   `**` — статья публикуется простым текстом, и оператору НИЧЕГО не приходит.
3. **Статья, залитая жирным, не теряет ни одного спана.** Порога «слишком много
   жирного» нет и не должно появиться (AC7, отказ оператора).
4. **Пер-сайтовый кап картинок держится, и держится по значению.** t-hunted = 30
   плюс контроль с ДРУГИМ (меньшим) капом на той же статье.
5. **Статья у самого пола «checklist» не начинает выпадать.** Извлечение блоков
   меняет то, как выводится плоский список абзацев, — и не должно ни столкнуть
   пограничную статью под пол, ни изменить вердикт по сравнению с выключенным флагом.

**Почему пункт 2 — требование, а не приятная мелочь.** Словарь алертов проекта уже
плотный: E001–E038. Пинг на каждую статью, где LLM не вернула жирный, приучит
оператора пролистывать пинги не глядя — и следующий настоящий E011 или E015
утонет в этом шуме. Поэтому Decision 3b формулирует деградацию как молчаливую и
безусловную, а тест обязан проверять **ОТСУТСТВИЕ** уведомления, а не наличие
какого-нибудь мягкого. Утверждение об отсутствии — самый хрупкий вид теста, ему
нужен позитивный контроль (см. Details, «Ловушки»).

**Почему пункт 4 — про контроль, а не про число.** Тест, который проверяет только
дефолт (30 для t-hunted), пройдёт и против намертво зашитой в рендер константы —
то есть против ровно того дефекта, который Decision 5 запрещает: «a single
hard-coded default would violate AC9 for somebody». Доказывает проводку значения
только ВТОРОЙ прогон той же статьи с другим капом.

**Почему пункт 5 — про аварию 2026-05-31.** Тогда все 4 слота t-hunted упали с
«paragraphs total content too short» на однопараграфных фото-галерейных постах;
починка (`tests/test_llm_common.py::TestSanityFloorRelaxation`) сняла санити-пол
для входа из <2 абзацев. Эта фича трогает ровно тот вход: блочный проход заново
выводит плоский список абзацев, и любой сдвиг числа абзацев или суммарной длины
текста бьёт по ДВУМ порогам сразу — по `_is_text_only_checklist`
(`_CHECKLIST_BODY_TEXT_FLOOR = 500`, отсев на приёмке) и по санити-полу
`_parse_response` (включается при `expected_paragraph_count >= 2`, отсев на
переводе). Однопараграфный галерейный пост, у которого после извлечения блоков
стало два абзаца, снова получит включённый пол — и авария повторится дословно.

**Задача ТОЛЬКО тестовая.** Единственный файл, который правим, —
`tests/test_integration.py`. Продовый код не трогаем. Если тест не проходит без
правки прода — это находка для аудитной волны (Tasks 10-12) и запись в
`decisions.md`, а не тихая правка. Тихая правка прода здесь особенно опасна: этот
набор — последний шлюз Phase 1 перед деплоем, и «подогнанный» под код тест
означает, что шлюза нет вообще.

   жирным статья, статья у пола «checklist», статья с картинок больше капа),
   собери минимальный HTML прямо в тесте — рядом с тестом, чтобы форма входа была
   видна из него самого.
3. **Напиши сквозной сценарий (пункт 1).** Реальный парсер t-hunted →
   `insert_pending` → чтение строки обратно из БД → перевод → `publish_article`,
   пойманный на уровне `telegraph_publisher._api_call`, чтобы увидеть НАСТОЯЩЕЕ
   дерево узлов. Проверяй звенья по отдельности и целиком: раны живы после
   раунд-трипа через SQLite; в запрос к LLM ушли `**маркеры**`; в узлах есть
   `<strong>`, `<h3>` и элемент списка ровно с одним буллетом.
4. **Напиши сценарий молчаливой деградации (пункт 2)** с позитивным контролем на
   том же каркасе — иначе «уведомления не было» может значить «код до пинга
   вообще не дошёл».
5. **Напиши сценарий залитой жирным статьи (пункт 3):** число `<strong>`-узлов
   равно числу жирных спанов источника; текст статьи целый, абзацы не потеряны.
   Держи фикстуру ВНУТРИ ресурсных границ (Decision 8) — иначе тест проверит
   ограничитель, а не сохранность форматирования.
6. **Напиши сценарий капа (пункт 4):** дефолт t-hunted и контроль с меньшим
   значением на ТОЙ ЖЕ статье; проверь, что количество картинок в узлах следует
   за значением, и что герой-картинка остаётся при сработавшем капе.
7. **Напиши сценарии порогов (пункт 5):** пограничная «checklist»-статья не
   выпадает; вердикт с флагом ВКЛ и ВЫКЛ совпадает; однопараграфный галерейный
   пост остаётся однопараграфным; настоящий голый список по-прежнему отсеивается
   (негативный контроль).
8. **Проверь каждый тест на мутации.** Для каждого утверждения временно сломай
   механизм, который он охраняет (см. Details, «Мутационная проверка»), убедись,
   что тест краснеет, и верни код как было. Тест, который не краснеет ни на одной
   мутации, ничего не охраняет — удали или переписывай.
9. **Прогони полный набор** и убедись, что регрессий нет и что каждый `-k`
   селектор из плана верификации собирает хотя бы один тест.
10. **Ничего, кроме `tests/test_integration.py`, не меняй.** Всё, что просится в
    прод, — в отчёт.

## TDD Anchor

Здесь тесты — это и есть продукт задачи, поэтому обычный цикл «красный → зелёный»
инвертирован: код (Tasks 5-8) уже написан, и новый тест обязан быть зелёным сразу.
Зелёный с первой попытки ничего не доказывает, поэтому **каждый тест проходит
мутационную проверку**: временно ломаем механизм, который тест охраняет, убеждаемся,
что он краснеет, откатываем. Конкретные мутации — в Details.

Все тесты — в `tests/test_integration.py`, новыми классами в конце файла, на
существующих базах `_IntegrationBase` / `_PrepPhaseBase`. Имена классов и тестов
ниже — ориентир; сохраняй смысл, а не буквы, если приземлившийся код Tasks 6-8
диктует иное.

### Ловушки (каждая уже кого-то поймала)

- **Мок на `publish_article` делает весь набор пустым.** Существующие тесты подменяют
  `news_bot.telegraph_publisher.publish_article` целиком — при такой подмене рендерер
  не запускается, узлов не существует, и любое утверждение про `strong`/`h3`/`figure`
  проверяет собственную фикстуру. Подменять надо на уровень глубже —
  `telegraph_publisher._api_call` — и разбирать `json.loads(data['content'])`.
- **Утверждение об отсутствии зелено и тогда, когда код не выполнялся.** Для
  `assert_not_called` обязательны: (а) `reset_mock()` непосредственно перед
  проверяемым действием, чтобы не считать пинги из подготовки, и (б) позитивный
  контроль на том же каркасе.
- **`_decode_bold_markers` в публикаторе делает жирный из голых `**`.** Тест «жирный
  доехал» может пройти на маркерах, а не на ранах — то есть мимо всей фичи. Проверяй
  ОБА уровня: раны на строке (`ru_blocks`) и узлы в дереве.
- **Кап на дефолте проходит против зашитой константы.** Спасает только второй прогон
  с другим значением; сравнивай числа между прогонами, а не только с ожидаемым.
- **Ресурсные границы маскируются под потерю форматирования.**
  `_MAX_RUNS_PER_BLOCK = 100` и `_MAX_TEXT_FOR_RUNS = 100_000` в публикаторе плюс
  граница запроса из Task 4: фикстура «залитая жирным» ДОЛЖНА быть внутри них, иначе
  тест краснеет или зеленеет по причине, к AC7 отношения не имеющей. Заведи отдельный
  тест-самопроверку фикстуры.
- **RU-фильтры выкидывают блоки.** Тексты фикстур делай нейтральными: похожее на
  боилерплейт или на плаг автора вырежется в `_fallback_publish`, и блок «потеряется»
  не там, где его ищет тест.
- **Пороги: не перепутай два разных.** `_CHECKLIST_BODY_TEXT_FLOOR = 500` в `news_bot` —
  отсев на приёмке, считается по сумме длин абзацев. Санити-пол в `_parse_response` —
  отсев на переводе, включается при `expected_paragraph_count >= 2`. Извлечение блоков
  может задеть оба; тесты нужны на оба, и в отчёте называй их по имени, чтобы ревьюер
  не гадал, какой именно пол проверен.
- **Подъём подзаголовка меняет число абзацев.** `t_hunted_source` при
  `len(paragraphs) >= 2` забирает первый абзац в `subtitle`. Сдвиг числа абзацев на
  единицу двигает и вердикт по полу, и выравнивание.
- **`None` vs `[]` в `blocks` — живое различие.** Проверяй явно: `assertFalse` их не
  различает.

### Мутационная проверка

Каждая мутация делается временно поверх рабочего дерева и откатывается сразу после
прогона. Ожидание — соответствующий тест краснеет.

- Убрать `runs` из блоков перед `insert_pending` → падают сквозной тест и тест
  раунд-трипа.
- Заставить `_encode_format_markers` возвращать текст без изменений → падает тест про
  маркеры в запросе.
- Вставить вызов `send_admin_notification` на путь «маркеров нет» → падает тест про
  отсутствие пинга (заодно доказывает, что он вообще способен покраснеть).
- Зашить в рендере кап числом вместо переданного значения → падает контроль с меньшим
  капом, а тест на дефолт остаётся зелёным. Это и есть демонстрация, зачем нужен
  контроль.
- Понизить `_CHECKLIST_BODY_TEXT_FLOOR` до 50 → падает негативный контроль про
  настоящий голый список.
- Сделать подъём подзаголовка безусловным → падает тест про однопараграфный
  галерейный пост.

### Implementation hints

- **Ловим дерево узлов:** `patch('telegraph_publisher._api_call')` с `side_effect`,
  который складывает `json.loads(data['content'])` в список и возвращает
  `{'url': 'https://telegra.ph/…', 'path': '…'}`. Токен — через
  `patch.dict(os.environ, {'TELEGRAPH_ACCESS_TOKEN': 'x'})`. Не забудь
  `patch('news_bot.time.sleep')`: `_fallback_publish` спит на прогрев кэша Telegraph.
- **Проверка узлов** — простым рекурсивным обходом дерева со сбором тегов. Заведи один
  локальный помощник (`_tags(nodes)` / `_count_tag(nodes, 'strong')`) и переиспользуй
  его во всех классах.
- **Реалистичный перевод без сети:** подменяй `news_bot.transcreate_via_claude`
  функцией, которая берёт вход и возвращает `paragraphs` с маркерами в нужных местах
  (или БЕЗ них — сценарий 2). Если нужно пройти и настоящий разбор ответа, вызывай
  реальный `transcreate_via_claude` с `client=MagicMock()`: клиент инжектится
  параметром, идиома есть в `tests/test_claude_transcreation.py`.
- **Фикстуры из корпуса** читай по абсолютному пути от `__file__`, как это уже делают
  тесты парсеров; синтетический HTML для остальных сценариев держи рядом с тестом
  константой класса, чтобы форма входа читалась из самого теста.
- **Ссылки в фикстурах** — только `https://t-hunted.blogspot.com/…`, иначе SSRF-гейт
  парсера вернёт `None` и тест «пройдёт» на пустоте. Для пограничной
  «checklist»-статьи следи, чтобы в URL НЕ было `case-contents-checklist` — иначе
  сработает безусловный триггер и проверишь не то, что собирался.
- **Наружу не ходим нигде:** сеть парсера подменяется на уровне сессии `requests`,
  LLM — подменой функции или клиента, Telegraph — на `_api_call`.
- **Не расширяй охват.** Lamley и autoevolution — Phase 2, их здесь нет. Юнит-тесты
  `dom_blocks` — Task 5, тесты guard'а — Task 8, превью — Task 6. Увидел их дефект —
  пиши в отчёт, а не в код.
