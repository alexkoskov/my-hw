## Description

Продвинуть `dev` → `main` через PR и передать оператору однострочную команду деплоя.
Кода задача не пишет: она проверяет готовность к выкатке, оформляет релиз и готовит
оператору всё, что тот выполнит на сервере сам.

### Четыре правила этого проекта, которые нельзя нарушить

**1. Деплой — только ВНЕ окна 10:00–20:00 МСК.** Это не стилистика, а механизм
(deployment.md § Scheduling → «⛔ The no-deploy window»): дневное расписание живёт в
процессе (`schedule`, в памяти), перезапуск контейнера его уничтожает, а `main()`
вызывает `job()` **немедленно** на старте (`news_bot.py:4645`) — бот не ждёт следующего
10:00, а перепланирует день от `now` и публикует в остаток окна. Ничего не падает и
дублей не будет (идемпотентность держит), поэтому эффект легко не заметить. Три
фиксированных слота: **10:00 / 15:00 / 19:30 МСК** (вечерний — 19:30, не 19:00).
Хост живёт в **UTC**, то есть окно = 07:00–17:00 по часам сервера; проверять `date` на
сервере, а не настенные часы в Москве.

**2. Прод правит оператор, не агент.** deployment.md § Access Information: «Operator runs
all server-side ops (SSH, deploy, restart); Claude prepares the commands». Агент **никуда
не ходит по SSH** и ничего не перезапускает — он готовит однострочники вида
`ssh root@45.90.216.165 "…"` и отдаёт их оператору. Прод крутится в Docker
(`docker logs hw-news-bot`, `docker exec`); systemd-юнита и правила sudoers больше нет
(остались только в истории NL-хоста, списанного 2026-07-25). Секреты не эхо-ить и не
логировать ни при каких условиях.

**3. Продвижение в `main` — через PR.** Решение оператора 2026-08-03 (patterns.md
§ Git Workflow): голые локальные merge-коммиты запрещены, потому что деплой ручной и
страница PR — последнее место, где можно прочитать, что именно едет на прод, ПЕРЕД тем
как зайти на сервер. Тело PR = релизная заметка: что изменилось и за чем следить после
выката. Гейт — зелёный CI на PR. Сам merge деплоем не является (оба deploy-workflow
обезврежены, `if: false`), поэтому merge окном 10:00–20:00 не ограничен — ограничена
только пересборка на хосте.

**4. Новые модули обязаны быть во ВСЕХ ТРЁХ манифестах.** Фича добавляет
`dom_blocks.py` и `feature_flags.py`; их регистрируют Task 2 и Task 5 в `deploy.sh`,
`.github/workflows/deploy.yml` и `.github/workflows/deploy_test.yml`. Модуль, не попавший
в манифест, однажды уже дал **38 крашлупов подряд с `ModuleNotFoundError`** (авария при
выкатке `t_hunted_source.py`, разбор — в
`work/completed/t-hunted-pt-source/decisions.md`). Сторож — `tests/test_deploy_files_invariant.py`,
и он обязан быть зелёным. Честная оговорка из deployment.md: сегодня прод собирается
`COPY . .` (`Dockerfile:18`), поэтому в образ попадает всё содержимое репозитория
независимо от манифеста — манифест важен для SCP-пути и как машиночитаемый список, а
инвариант-тест был усилен 2026-08-03. Проверять надо и то и другое: тест зелёный **и**
`grep` находит оба модуля в трёх файлах.

### Что оператор получает на руки

Один блок готовых однострочников: зафиксировать текущий прод-SHA (цель отката), выкатить,
прочитать логи, поставить тег. Плюс маршрут отката и напоминание про аварийный
выключатель `SOURCE_FORMATTING_ENABLED=0` — с честной оговоркой, что его применение тоже
требует перезапуска, а перезапуск в окне запрещён (tech-spec § Risks: выключатель не
спасает в реальном времени внутри окна — именно поэтому важно, когда деплоить).

## Details

### Блок для оператора (готовые однострочники)

Отдавать одним сообщением, в этом порядке. Все команды — с префиксом `ssh`, чтобы их не
пытались выполнить на своём Mac. Пароль root — в менеджере паролей оператора; в переписку
и логи он не попадает.

```
# 1. точка отката (ЗАПИСАТЬ вывод!)
ssh root@45.90.216.165 "cd /root/hw-news && git rev-parse --short HEAD"

# 2. время на сервере (хост в UTC; окно 10:00-20:00 МСК = 07:00-17:00 UTC)
ssh root@45.90.216.165 "date -u"

# 3. выкат — ТОЛЬКО вне окна 10:00-20:00 МСК
ssh root@45.90.216.165 "cd /root/hw-news && git pull && docker compose up -d --build"

# 4. логи загрузки
ssh root@45.90.216.165 "docker logs hw-news-bot --tail 200"
```

После подтверждённой успешной пересборки — тег ставит агент, локально:
`git tag -a prod-YYYY-MM-DD -m "source-formatting-parity Phase 1" && git push origin prod-YYYY-MM-DD`.

### Когда деплоить: почему «после 20:00 МСК» лучше «до 10:00»

Оба варианта легальны, но ведут себя по-разному, потому что `job()` стартует немедленно:

- **После 20:00 МСК** — все три слота дня (10:00 / 15:00 / 19:30) уже прошли больше чем на
  5 минут и отбрасываются grace-правилом. Немедленный `job()` ничего не публикует: бот
  спокойно поднимается, логи можно прочитать без спешки, первая публикация — завтра в
  10:00, когда оператор на месте и готов делать Task 15. Рекомендуемый вариант.
- **До 10:00 МСК** — все три слота впереди, и день пойдёт с новой вёрсткой целиком: три
  публикации подряд. Приемлемо, если оператор готов смотреть канал весь день, но цена
  ошибки выше.
- **Внутри окна** — запрещено: перепланирование от `now` публикует в остаток окна, а
  выключить фичу без ещё одного перезапуска нельзя.

### Откат

**Route A — вернуть прод на известный хороший коммит (быстро, без пуша).** Вне окна:
`ssh root@45.90.216.165 "cd /root/hw-news && git fetch && git checkout <good-sha> && docker compose up -d --build"`.
Оставляет detached HEAD — нормальное состояние, контейнеру безразлично. Возврат на ветку
после того, как фикс доехал до `main`:
`ssh root@45.90.216.165 "cd /root/hw-news && git checkout main && git pull && docker compose up -d --build"`.
~3–4 минуты вместе со сборкой. Цель отката — SHA из шага 1 блока выше или предпоследний
тег `git tag -l 'prod-*' | tail -2 | head -1`.

**Route B — откатить изменение на `main`.** ⚠️ Ключевая ловушка: продвижение делается
merge'ем, поэтому HEAD `main` — **merge-коммит с двумя родителями**, и простой
`git revert HEAD` откажется работать («commit is a merge but no -m option was given»).
Нужно `git revert -m 1 <merge-sha> && git push origin main` — `-m 1` значит «оставить
первого родителя, сторону `main`, и отменить всё, что принёс merge». Проверить, merge ли
это: `git rev-list --parents -n 1 <sha>` — три SHA в строке значит merge, два — нет
(`-m 1` на не-merge коммите это ошибка). Вторая ловушка: после отката merge'а git считает
ветку уже влитой, и повторный merge `dev` работу НЕ вернёт — нужен revert реверта или
новая ветка.

**Откат БД не нужен** — фича не трогает схему и не пишет миграций.

**Третий путь, самый дешёвый — аварийный выключатель.** Добавить
`SOURCE_FORMATTING_ENABLED=0` в `/root/hw-news/.env` (файл правится только руками) и
перезапустить контейнер. Честная оговорка, которая должна быть проговорена оператору:
**перезапуск — тоже перезапуск**, то есть внутри окна 10:00–20:00 МСК он запрещён ровно
так же, как деплой. Tech-spec § Risks фиксирует это как принятый оператором компромисс:
выключатель не спасает в реальном времени в течение публикационного дня. Отсюда и
рекомендация деплоить после 20:00 — чтобы первая живая публикация случилась утром, с
целым днём впереди на реакцию.

**Files:** задача не меняет код. Возможные изменения ограничены артефактами релиза: тело
PR, тег, запись в `work/source-formatting-parity/decisions.md`. Если по ходу выката
выяснится, что `deployment.md` расходится с реальностью (например, изменился порядок
команд), — обновить `deployment.md`: это требование скилла и стоячее правило проекта
(«любое инфраструктурное изменение отражается в project-knowledge»).

**Dependencies:**
- **Task 13** (жёсткая) — деплой стартует только при `passed` и нуле criticals.
- Транзитивно Task 2 и Task 5 — именно они кладут новые модули в манифесты; эта задача их
  проверяет, но не чинит. Если модуля нет в манифесте — это возврат в Task 2/5, а не
  правка «на лету» в деплой-задаче.
- Task 15 (пост-деплой проверка) стартует после подтверждённого выката.

**Edge cases:**
- Оператор недоступен вечером → выкат переносится; merge PR при этом можно сделать
  (деплоем он не является). Не «дожимать» выкат в окне.
- CI зелёный, но job `test` пропущен `check-skip` → зелёная галка ничего не доказывает.
- `git pull` на сервере конфликтует (кто-то правил файлы на хосте) → не решать удалённо
  вслепую: попросить у оператора `git status`, разобрать, при необходимости — Route A на
  известный хороший коммит.
- Прод оказался в detached HEAD после прошлого отката → `git pull` не тянет ничего;
  нужен `git checkout main` перед pull.
- Контейнер поднялся, но в логах `ModuleNotFoundError` → немедленно Route A, разбор потом;
  это ровно тот класс аварии, что дал 38 крашлупов.
- В логах `Temporary failure in name resolution` / `Network is unreachable` → это DNS/сеть
  сервера, а не отказ LLM-провайдера (известный ложный след `[E011]`); не чинить фичу по
  этому симптому.
- Оператор просит выкатить «прямо сейчас», а сейчас 14:00 МСК → отказать и объяснить
  механизм, а не согласиться.

**Implementation hints:**
- Не выполнять серверные команды. Не предлагать «я сам зайду по SSH». Формат передачи —
  готовый однострочник, который оператор копирует целиком.
- Никаких секретов в командах, выводе и записях: токены и пароли живут в `.env` на сервере
  и в менеджере паролей. Если вывод логов, присланный оператором, содержит что-то похожее
  на токен — не цитировать его в `decisions.md`.
- Тело PR писать простым языком: это то, что оператор читает перед тем, как трогать прод.
  Обязательно назвать изменение вывода orangetrack (меньше картинок на галерейных постах)
  — оно одобрено, но должно быть ожидаемым, а не сюрпризом в канале.
- Тег ставится ПОСЛЕ успешной пересборки, а не вместе с merge'ем: тег фиксирует то, что
  доехало до прода. Merge без выката тега не получает — это и есть смысл правила.
- Если что-то в `deployment.md` разошлось с реальностью — правка документа входит в эту
  задачу, а не откладывается.
