# Task 8: Refactor `job()` for distributed-publish loop + cron change

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Это центральная задача волны 4 — мы переключаем `news_bot.py` с интервал-ориентированного prep-phase tick (`schedule.every(12).hours`) на ежедневный cron в фиксированное время (`12:00 МСК`) и переписываем тело `job()` под новую модель «фетч + распределённое расписание + поэтапная публикация в окне 13:00–20:00».

Что попадает в эту задачу (по tech-spec, Wave 4 / Task 8 + Architecture «How it works» + Decisions 2, 4, 9, 14, 15):

- **Decision 2 + 4** — cron-триггер становится `schedule.every().day.at("12:00", tz=pytz.timezone("Europe/Moscow")).do(job)`. Используется `pytz`, не stdlib `zoneinfo` (важно: `schedule==1.2.1` принимает только `str` IANA name или `pytz.BaseTzInfo`, иначе `ScheduleValueError`).
- **Decision 9** — crash-loop guard: на входе в `job()` читать `MAX(published_at)` из `published_articles`. Если `now - last_published < MIN_INTERVAL_MINUTES (40)`, спать до `last_published + 40min` перед тем как продолжить. Защита от burst-публикаций при систематических рестартах контейнера.
- **Decision 14** — startup health checks в `main()` ДО регистрации cron: (1) `claude_transcreation.health_check()` возвращает `True` (публичный API из Task 3, контракт `health_check() -> bool` — `True` если Claude API достижим И `ux-guidelines.md` загружаем; `False` если поймали `ClaudeOutageError` или ошибку загрузки промпта; функция НЕ бросает) — если `False`, делаем admin-ping + `outage_state.set_fallback_active(True)`; (2) `os.getenv('TZ') == 'Europe/Moscow'` — иначе admin warning ping.
- **Decision 15** — window-end guard: перед каждым `time.sleep` до следующего slot проверять `if slot > window_end: break`. Excess slots становятся carry-over.

После crash-loop guard и фетча `job()` запускает distributed-publish loop (см. Architecture «How it works» step 7 и code-research §14.5):

1. `compute_publish_slots(count_pending(), now_msk, window_start=13:00, window_end=20:00, min_interval_min=40)` → `(slots, carry_over)`.
2. Admin ping с планом дня (suppress на N=0); при `count_pending() > 50` — дополнительный backlog-warning (AC20, см. tech-spec).
3. Для каждого `slot`: `time.sleep((slot - now).total_seconds())` → `pending_repo.list_pending()[0]` → если `outage_state.is_fallback_active()` — публикация через Google-only путь, иначе через рефакторнутый `_fallback_publish` (Wave 3 / Task 7) с Claude primary + per-article Google fallback.
4. На `ClaudeOutageError` (state machine уже записал событие и роутил статью через Google) — продолжаем со следующего slot.
5. На прочих исключениях — стандартный 3-strikes flow через `pending_repo.increment_attempt` / `move_to_failed`.

Manual-review путь (`hw_review`) не трогаем — если оператор опубликовал статью локально между cron и слотом, `move_to_published` уже убрал её из `pending_articles`, и `list_pending()` её просто не вернёт.

Зачем: эта задача реализует AC1, AC3, AC4, AC7, AC8 из user-spec (фиксированный cron, окно 13–20, минимальный интервал 40 минут, container restart mid-window, crash-loop guard) и связывает воедино модули Wave 1–3 (`compute_publish_slots`, `outage_state`, рефакторнутый `_fallback_publish`).

## What to do

1. **Импорты + константы.** В `news_bot.py` добавить импорт `pytz` и (если ещё не импортированы) `compute_publish_slots`, `outage_state`. Завести/использовать существующую константу `MIN_INTERVAL_MINUTES = 40` (если нет — добавить в верхней секции модуля). Завести константы `WINDOW_START = "13:00"`, `WINDOW_END = "20:00"` или в виде `dt.time(13, 0)` / `dt.time(20, 0)` — единый источник истины для окна. `BACKLOG_WARNING_THRESHOLD = 50` для AC20.
2. **`main()` — startup health checks (Decision 14).** До регистрации cron: вызвать публичный API `claude_transcreation.health_check()` (из Task 3 — функция с контрактом `health_check() -> bool`, возвращает `True` если Claude API достижим И `ux-guidelines.md` загружаем; `False` если поймали `ClaudeOutageError` или прочую ошибку — функция сама НЕ бросает). Если `health_check()` вернул `False` — залогировать, отправить admin-ping (просто факт degraded-mode без exception class в видимой части — у нас нет exception, только bool; формулировка вида "Claude probe failed at startup, switching to Google-only for the day"), установить `outage_state.set_fallback_active(True)` чтобы день шёл через Google. **Не использовать try/except ImportError fallback** — Task 3 (claude_transcreation) обязан быть готов до Task 8 по wave-последовательности; ImportError здесь должен пробросить наверх как реальная ошибка деплоя. Затем проверить `os.getenv('TZ') == 'Europe/Moscow'` — на mismatch отправить admin warning ping (не блокирует запуск, cron всё равно сработает корректно через explicit pytz).
3. **`main()` — cron change (Decision 2 + 4).** Удалить `schedule.every(12).hours.do(job)`. Заменить на `schedule.every().day.at("12:00", tz=pytz.timezone("Europe/Moscow")).do(job)`. Сохранить непосредственный вызов `job()` после регистрации (для first-boot / тестов), как сейчас. Цикл `while True: schedule.run_pending(); time.sleep(60)` оставить.
4. **`job()` — crash-loop guard (Decision 9).** В самом начале (после `init_db()`): прочитать `MAX(published_at)` из `published_articles` (через существующий repo helper или прямой SQL — выбрать чище). Если `last_published is not None` и `now_msk - last_published < timedelta(minutes=MIN_INTERVAL_MINUTES)` — посчитать `wait_seconds = (last_published + 40min - now).total_seconds()`, залогировать причину и `time.sleep(wait_seconds)`. После сна продолжить.
5. **`job()` — fetch + insert_pending.** Сохранить шаги (2)+(3)+(5) из текущего prep-phase tick: итерация по `SOURCES`, `filter_new_entries`, дедуп против `pending_articles`, `fetch_full_article`, `insert_pending`. Удалить шаги (1a) idle heads-up, (1b) overdue auto-publish, (4) overflow fast-track из тела `job()` (полное удаление `_overflow_fast_track`/throttle/idle-fallback — отдельная задача 9; здесь они просто перестают вызываться из `job()`, чтобы не дублировать публикации).
6. **`job()` — compute schedule.** После insert_pending: `now_msk = datetime.now(pytz.timezone("Europe/Moscow"))`; `n = pending_repo.count_pending()` (или `len(pending_repo.list_pending())`); `slots, carry_over = compute_publish_slots(n, now_msk)`. На N=0 — admin ping должен быть suppressed (см. шаг 7).
7. **`job()` — admin ping с планом дня.** Если `n > 0`: одна консолидированная ping в формате «Зафетчил X новых, в очереди M, расписание сегодня: HH:MM, HH:MM, …; carry-over: K». Если `n > BACKLOG_WARNING_THRESHOLD (50)`: дополнительная warning-ping (AC20). На N=0 — пинг подавлен.
8. **`job()` — distributed-publish loop.** Для каждого `slot in slots`:
   - **Window-end guard (Decision 15):** если `slot > window_end_dt` — `break`. Защита от случая, когда предыдущая публикация заняла больше slot interval.
   - `wait_seconds = max(0, (slot - datetime.now(msk_tz)).total_seconds())`; `time.sleep(wait_seconds)`.
   - `row = pending_repo.list_pending()[0] if pending_repo.list_pending() else None`. Если `None` (всё опубликовано / удалено через manual-review) — `break`.
   - Try: если `outage_state.is_fallback_active()` — Google-only path (использовать существующий путь через `transcreate_text` напрямую или helper `_publish_via_google` если такой будет введён в Task 7); иначе `_fallback_publish(row, via_review=False)` — внутри Claude primary + per-article Google fallback.
   - На `ClaudeOutageError` (приходит из `_fallback_publish` когда state machine сработал; статья УЖЕ опубликована через Google как побочный эффект): залогировать, продолжить к следующему slot.
   - На прочее `Exception`: стандартный 3-strikes flow — `safe = sanitize_error_message(exc)`; `new_count = pending_repo.increment_attempt(row['link'], safe)`; if `new_count >= 3`: `pending_repo.move_to_failed(row['link'], safe)`.
9. **Logging.** Каждый slot логировать `[slot N/M] publishing row {link}` на INFO; на завершение цикла — `[job] done. Published K, carry-over C, queue size now S`.
10. **Tests.** Добавить unit-тесты на crash-loop guard, TZ-aware schedule registration, window-end guard, и интеграционный тест на полный flow (3 статьи → 3 слота → 3 публикации). См. TDD Anchor.

**Edge cases:**
- N=0 после фетча → `compute_publish_slots` возвращает `(slots=[], carry_over=0)` → loop не запускается, admin-ping suppressed. Поведение проверяется TDD-тестом `test_admin_ping_suppressed_on_zero_pending`.

- Container restart в 21:00 МСК (после окна) → `compute_publish_slots(N, 21:00)` возвращает `(slots=[], carry_over=N)` → loop пуст, всё переносится на завтра. Window-end guard в loop не нужен в этом случае (slots пустой), но он же страхует и при `now=19:55` если предыдущий publish задержался.
- `outage_state.is_fallback_active() = True` на старте дня → loop сразу идёт через Google для всех slots. Recovery probe — на каждом следующем cron tick (passive recovery, см. user-spec AC16).
- `pending_repo.list_pending()` возвращает пустой список во время slot (manual-review preemption между cron и slot) → `row is None` → loop делает `break`. Слоты, оставшиеся в `slots`, просто не используются (это нормально).
- `_fallback_publish` бросает unexpected exception → 3-strikes counter; на 3-м `move_to_failed`. Loop продолжается со следующим slot.
