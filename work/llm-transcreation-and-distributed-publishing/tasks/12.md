# Task 12: Create tests/test_distributed_schedule_integration.py

## Required Skills

Перед выполнением задачи загрузи:

## Description

Финальный интеграционный пласт для новой distributed-publish-фичи. После того как Wave 1–6 ввели в строй три новых модуля (`compute_publish_slots`, `claude_transcreation`, `outage_state`), переписали `_fallback_publish` под Claude-primary + Google-per-article-fallback и `job()` под cron@12:00 + публикационный цикл, нужно поверх юнит-тестов отдельных компонентов закрыть end-to-end-сценарии: что весь цикл `job()` действительно прогоняет статьи через все слои в правильном порядке, что состояния и расписание корректно сцеплены, что manual-review-путь по-прежнему совместим.

Цель файла `tests/test_distributed_schedule_integration.py` — ~4 интеграционных теста, эмулирующих полный путь от cron-tick до записи в `published_articles`, с замоканными внешними зависимостями (anthropic SDK, telegraph, telegram, `time.sleep`, `schedule`). Эти тесты ловят регрессии, которые нельзя поймать на уровне отдельных модулей: ошибки склейки `job()` ↔ `compute_publish_slots` ↔ `_fallback_publish` ↔ `outage_state`, неверный порядок шагов, забытые ветки. Покрывает user-spec AC1–AC8, AC14–AC17, AC21.

Сценарии (по одному тесту на каждый):

1. **Full happy path.** Cron-tick в `12:00 МСК`. Источники замоканы под N=3 готовых к публикации статей. Тест проверяет: вызвано 3 публикации, в порядке/таймстемпах, согласованных с `compute_publish_slots(3, now=12:00)`, через Claude (а не Google), `pending_articles` пуст, `published_articles` содержит 3 строки с `telegraph_url`, `bot_state` показывает no-outage (через `outage_state` геттеры), admin-сообщения соответствуют контракту (как минимум — план дня в начале; точное число определяется тем, как Wave 1–6 решил, пинговать ли каждую публикацию).

2. **API-level outage during slot mid-day (advances state machine + reroutes article).** N=3, нормальная инициализация. На втором слоте mock `claude_transcreation.transcreate_via_claude` поднимает `OutageError` (обёрнутый `RateLimitError` из anthropic SDK — это API-level класс ошибки по Decision 5). Per Decision 5 и user-spec AC14: API-level OutageError ОДНОВРЕМЕННО (a) advances state machine — `outage_state.record_outage_event` вызывается, `bot_state.ping_count == '1'`, `outage_started_at` записан, admin получает ping #1 — И (b) рерутит ИМЕННО эту одну статью на Google (через `news_bot.transcreate_text` identity-stub) в этом же слоте, чтобы канал не оставался без публикации в этом слоте. `published_articles` имеет 3 строки (slot 1 — Claude, slot 2 — Google fallback после OutageError, slot 3 — Claude). Третий слот (после клиринга мока) снова идёт через Claude → success → `record_recovery_event` отрабатывает → `bot_state.ping_count is None`, `outage_started_at is None`, recovery-ping отправлен. Покрывает AC14 (API-level → 2-ping protocol) и AC16 (auto-recovery).

   **Дополнительный sub-scenario (или отдельный 5-й тест, на усмотрение исполнителя — допустимо расширить файл до 5 тестов): per-article failure (refusal/malformed JSON).** N=3, на втором слоте `transcreate_via_claude` поднимает `ClaudeTranscreationError` (per-article класс по Decision 5 — НЕ outage). 3. **Container restart mid-window.** Симулировать перезапуск контейнера: предзаполнить БД 4 pending-строками, выставить `now` внутри окна публикации (например, во второй его половине, через freezegun или эквивалент), вызвать `job()`. Точные числа сверять с `compute_publish_slots` контрактом и user-spec AC4 (мин-интервал) — не хардкодить. Покрывает AC7, AC8.

4. **Manual-review preemption.** N=3 pending. Тест устраивает мутацию: между слотом 1 и слотом 2 во временный SQLite одна из «следующих» pending-строк перемещается в `published_articles` способом, эквивалентным локальному hw_review-публикатору (через `move_to_published` или `pending_articles_repo`). Триггер мутации — на усмотрение исполнителя (см. Implementation hints). Бот на втором слоте берёт следующую доступную pending-строку. Тест проверяет: `_fallback_publish` вызван для авто-пути ожидаемое число раз, slot 2 публикует ту строку, которая стала следующей после удаления (по link). Никаких дублей, никаких ошибок. Покрывает AC21.

Применять через `@freeze_time('YYYY-MM-DD HH:MM:SS', tz_offset=3)` либо `with freeze_time(...)` поверх теста. Обоснование: в `news_bot.py` сейчас `from datetime import datetime` (line 15) — то есть `news_bot.datetime` это сам КЛАСС `datetime`, и патчить `datetime.now` напрямую через `unittest.mock.patch('news_bot.datetime.now', ...)` нельзя (datetime — C-extension, его методы immutable). Альтернативы: (a) патчить весь модуль `news_bot.datetime = MagicMock()` — ломает остальные обращения к `datetime(...)` конструктору; (b) ввести в `news_bot.py` indirection-функцию `_now(tz)` и патчить её — требует правки production-кода в task 8, чего мы не делаем в task 12. `freezegun` — это правильный инструмент: подменяет `datetime.now()` на уровне всего процесса безопасно, понимает tz-aware datetimes (через `tz_offset` или `move_to(...)`). Если `freezegun` нельзя добавить — вернуться к варианту (b) и скоординироваться с task 8 о добавлении `_now()` indirection.
- Никаких других новых пакетов. Используем `unittest`, `unittest.mock` (stdlib).

**Edge cases (которые тесты обязаны покрыть):**
- N=3 ровно (классический happy path с тремя одинаково-распределёнными слотами).
- API outage между слотами (а не на первом — чтобы продемонстрировать переход между состояниями).
- Recovery на слоте сразу после outage (не на следующем cron tick'е).
- Crash-loop guard срабатывает (последняя публикация ближе минимального интервала к `now`) → бот выдерживает остаток интервала. Точные числа сверять с `compute_publish_slots`/guard-контрактом.
- Manual-review preemption: строка исчезает между слотами, bot не падает, берёт следующую.
- Уже опубликованные сегодня строки не публикуются повторно (idempotency через `published_articles.telegraph_url`).

**Implementation hints (не псевдокод, общие подсказки):**
- `setUp` повторяет паттерн `tests/test_integration.py` (db_patcher, token_patcher, channel_patcher, admin_patcher, notify_patcher) + добавляет patch на `time.sleep` (no-op либо счётчик-MagicMock с capture call_args_list) + patch на `claude_transcreation.transcreate_via_claude` + использует `freezegun.freeze_time` для контроля `now` (см. Time-mocking decision выше).
- `time.sleep` мокается так, чтобы цикл проходил мгновенно. Аргументы захватываются для последующих ассертов на ожидаемые межслотовые задержки (форма проверки — на исполнителе: точные секунды, диапазон, порядок; см. user-spec AC3–AC6 и `compute_publish_slots` контракт за источником истины).
- Outage scenario: на mock `transcreate_via_claude` сконфигурировать поведение, при котором ОДИН (не первый и не последний) слот поднимает API-level outage-исключение (через `RateLimitError` из anthropic SDK или эквивалент, обёрнутый в `OutageError` модулем — уточнить по Wave 1 коду), а остальные слоты возвращают валидные RU-словари. Конкретный механизм (`side_effect`-список / `side_effect`-функция / контекстный switch) — на исполнителе. Главное — соблюдена последовательность: success → outage → success на трёх разных слотах.
- Manual-review scenario: между слотом 1 и слотом 2 БД мутируется так, как если бы строку #2 опубликовал внешний оператор (`move_to_published` для конкретной link, либо эквивалентный путь `pending_articles_repo`). Триггер мутации — выбор исполнителя: callback на mock'е, явный вызов между шагами теста, любой другой механизм, при котором эффект «строка исчезла из `pending` до того, как бот забрал её на втором слоте» наступает детерминированно. Не делать sleep-ом реального таймера.
- Container restart scenario: предзаполнить БД pending-строками + уже-опубликованными today-строками (имитация прошлой попытки до рестарта), затем зафиксировать `now` внутри окна публикации, вызвать `job()`. Проверить recompute поведение и crash-loop guard.
- Расчёт расписания для каждого теста — НЕ хардкодить ожидаемые таймстемпы и не воспроизводить формулу из спека. Источник истины — `compute_publish_slots(...)` модуль (Task 1). В тесте: вызвать `compute_publish_slots` с теми же входами и сравнить аргументы `time.sleep` (или `_fallback_publish` timestamps) с ожидаемым результатом этого вызова. Это автоматически покрывает AC3–AC6 и устойчиво к будущим уточнениям округления/cap'а внутри модуля.
- Все теневые admin-ping должны проверяться по фрагменту/семантике (по ключевым подстрокам, типу события, счётчику), не по точному совпадению — оставит запас на стилистические правки текста сообщений в Wave 1–8.
- **Two distinct mock shapes** (важно — `_fallback_publish` принимает full-article shape, не RSS-entry shape):
  - `_create_mock_rss_entry(link, title, ...)` — копия из `tests/test_integration.py` (shape: `{link, title, published, summary}`). Используется как return-value для `mock_fetch_rss.side_effect = [[entry, ...], ...]` и для `mock_fetch_mattel_news.return_value`. Это вход в pipeline.
