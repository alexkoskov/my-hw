## Description

Финальный интеграционный пласт для новой distributed-publish-фичи. После того как Wave 1–6 ввели в строй три новых модуля (`compute_publish_slots`, `claude_transcreation`, `outage_state`), переписали `_fallback_publish` под Claude-primary + Google-per-article-fallback и `job()` под cron@12:00 + публикационный цикл, нужно поверх юнит-тестов отдельных компонентов закрыть end-to-end-сценарии: что весь цикл `job()` действительно прогоняет статьи через все слои в правильном порядке, что состояния и расписание корректно сцеплены, что manual-review-путь по-прежнему совместим.

Цель файла `tests/test_distributed_schedule_integration.py` — ~4 интеграционных теста, эмулирующих полный путь от cron-tick до записи в `published_articles`, с замоканными внешними зависимостями (anthropic SDK, telegraph, telegram, `time.sleep`, `schedule`). Эти тесты ловят регрессии, которые нельзя поймать на уровне отдельных модулей: ошибки склейки `job()` ↔ `compute_publish_slots` ↔ `_fallback_publish` ↔ `outage_state`, неверный порядок шагов, забытые ветки. Покрывает user-spec AC1–AC8, AC14–AC17, AC21.

## What to do

Создать новый файл `tests/test_distributed_schedule_integration.py`. Файл содержит 4 теста — по одному на каждый сценарий ниже. Каждый тест полностью изолирует внешние эффекты: реальная БД временный SQLite (`tempfile.mkstemp` + `init_schema()` + `outage_state` schema), сетевых вызовов нет.

Сценарии (по одному тесту на каждый):

1. **Full happy path.** Cron-tick в `12:00 МСК`. Источники замоканы под N=3 готовых к публикации статей. После фетча `count_pending() == 3`. `job()` рассчитывает 3 слота в окне 13:00–20:00 МСК (равномерно), отправляет admin-ping с расписанием, в каждом слоте публикует одну статью через Claude (ответ замокан валидным RU-словарём). Тест проверяет: вызвано 3 публикации, в правильные timestamps, через Claude (а не Google), `pending_articles` пуст, `published_articles` содержит 3 строки с `telegraph_url`, `bot_state.fallback_active is None`, отправлено ровно 4 admin-сообщения (план дня + 3 публикации не пингуют отдельно — только schedule ping в начале).

2. **Outage during slot mid-day.** N=3, нормальная инициализация. На втором слоте `anthropic.Anthropic.messages.create` возвращает `RateLimitError`. Ожидание: `outage_state.record_outage_event` отрабатывает, `bot_state.ping_count == '1'`, `outage_started_at` записан, admin получает ping #1; статья 2-го слота публикуется через Google (как per-article fallback в этом цикле, потому что state machine форсит немедленный fallback на этой же статье), `published_articles` имеет 3 строки. Третий слот (после клиринга мока) снова идёт через Claude → success → `record_recovery_event` отрабатывает → `bot_state.ping_count is None`, `outage_started_at is None`, recovery-ping отправлен. Покрывает AC14, AC16.

3. **Container restart mid-window.** Симулировать перезапуск контейнера: предзаполнить БД 4 pending-строками, выставить `now = 16:00 МСК` (через мок `datetime.now` или freeze-time), вызвать `job()`. Ожидание: `compute_publish_slots(4, now=16:00)` вернёт слоты с интервалом ≈ (20:00-16:00)/3 ≈ 80 мин, но capped at 40 → 4 слота с шагом 80 мин начиная с 16:00; цикл публикует все 4. Также `published_articles` уже содержит 2 строки за сегодня (от прошлой попытки до рестарта) — они НЕ ререролятся. Crash-loop guard: установить `MAX(published_at) = now - 5min` → проверить, что `time.sleep` вызван с ≈35 мин до старта первого слота. Покрывает AC7, AC8.

4. **Manual-review preemption.** N=3 pending. Тест мокает `time.sleep` так, что между слотом 1 и слотом 2 во временный SQLite вручную выполняется `move_to_published(row_2.link, ...)` (имитация локального hw_review-публикатора). Бот в слоте 2 вызывает `list_pending()[0]` — т.к. строка 2 уже удалена из `pending_articles`, бот забирает строку 3 (бывшую очередную). Тест проверяет: `_fallback_publish` вызван 2 раза для авто-пути (slots 1 и 2), при этом slot 2 публикует именно строку 3 (по link). Никаких дублей, никаких ошибок. Покрывает AC21.

Общая структура теста:
- `setUp`/`tearDown`: tempfile-БД, `init_schema()` + ensure `bot_state` table, патчи на `news_bot.DB_FILE` и `outage_state` connection target, мок-токены, мок `send_admin_notification` для introspection.
- Замокать всё внешнее: `news_bot.fetch_rss`, `news_bot.fetch_full_article`, `news_bot.load_feeds`, `news_bot.fetch_mattel_news`, `news_bot.send_telegraph_teaser`, `news_bot.telegraph_publisher.publish_article` (возвращает фейковый telegraph_url), `claude_transcreation.transcreate_via_claude` (возвращает валидный dict либо raises указанное исключение), `news_bot.transcreate_text` (для Google-fallback ветки — identity-stub), `time.sleep` (no-op либо счётчик с захватом аргументов), `datetime.now` где нужно (через `freezegun.freeze_time` или patch на utility-функцию).
- Использовать те же fixture-паттерны, что и `tests/test_integration.py` (см. `setUp`/`tearDown` там — DB_FILE patcher, token patchers, notify patcher).
- Каждый тест — `unittest.TestCase` метод; ассерты на: количество и содержимое строк в `pending_articles` / `published_articles`, состояние `bot_state` через `outage_state` геттеры, последовательность вызовов `_fallback_publish` (через `mock.call_args_list`), содержимое admin-ping сообщений (через захват из `mock_notify`), таймстемпы аргументов `time.sleep`.

**Dependencies:**

**Edge cases (которые тесты обязаны покрыть):**
- N=3 ровно (классический happy path с тремя одинаково-распределёнными слотами).
- API outage между слотами (а не на первом — чтобы продемонстрировать переход между состояниями).
- Recovery на слоте сразу после outage (не на следующем cron tick'е).
- Crash-loop guard срабатывает (last_published < 40min ago) → sleep ≈ 35min.
- Manual-review preemption: строка исчезает между слотами, bot не падает, берёт следующую.
- Уже опубликованные сегодня строки не публикуются повторно (idempotency через `published_articles.telegraph_url`).

**Implementation hints (не псевдокод, общие подсказки):**
- `setUp` повторяет паттерн `tests/test_integration.py` (db_patcher, token_patcher, channel_patcher, admin_patcher, notify_patcher, mattel_patcher) + добавляет patch на `time.sleep` (no-op либо счётчик-MagicMock с capture call_args_list) + patch на `claude_transcreation.transcreate_via_claude` + patch на `datetime.datetime.now` через `freeze_time`-стиль или прямой `unittest.mock.patch` (помни про tz: возвращай `datetime.datetime(2026, 4, 27, 12, 0, tzinfo=pytz.timezone('Europe/Moscow'))`).
- Между слотами `time.sleep` мокается так, чтобы цикл проходил мгновенно. Аргументы захватываются для проверки timestamps (тест 1 + тест 3).
- Outage scenario использует `side_effect = [valid_dict_1, RateLimitError(...), valid_dict_3]` на mock `transcreate_via_claude`.
- Manual-review scenario использует `side_effect`-функцию на `time.sleep`, которая на первом вызове (между слотами 1 и 2) выполняет `pending_articles_repo.move_to_published(row_2_link, fake_telegraph_url, ...)` напрямую в тестовой БД.
- Container restart scenario: предзаполнить БД через `insert_pending` × 4 + `move_to_published` × 2 (имитация прежней публикации), затем зафиксировать `now = 16:00 МСК`, вызвать `job()`.
- Расписание для теста 1 (now=12:00, N=3, window 13:00–20:00, min_interval=40): по формуле `floor((20:00-13:00)/N+1) = 7h/3 ≈ 140 min`, capped at min_interval — interval 140 мин, слоты 13:00, 15:20, 17:40. Перепроверь по `compute_publish_slots(3, ...)` в setUp с реальными числами.
- Все теневые admin-ping должны проверяться по фрагменту строки (`assertIn("Fetched", call_args)`, `assertIn("ping #1", ...)`), не по точному совпадению — оставит запас на стилистические правки в Wave 1–8.
- Reuse `_create_mock_entry` helper из `tests/test_integration.py` (можно скопировать или выделить в общий fixture-модуль, но для одной задачи — копия проще).
