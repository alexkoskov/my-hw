# Task 19: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Финальная верификация фичи `llm-transcreation-and-distributed-publishing` на живой production-VPS после успешного деплоя (Task 18). Цель — на реальном окружении убедиться, что весь suite of daily events из user-spec работает: 12:00 МСК cron tick фетчит источники и шлёт admin-пинг → 13:00 МСК открывается окно публикаций → Telegraph-страницы соответствуют формату (emoji-title, без boilerplate, маркер `↳ автоперевод` перед футером) → channel teaser остаётся `#<source> #news` → следующие слоты идут с интервалом ≥40 минут → за 24 часа очередь `pending_articles` не растёт неконтролируемо и в admin-чате нет неожиданных ошибок.

Эта задача закрывает AC31 (manual smoke post-deploy) из user-spec и cross-проверяет AC2, AC3, AC4, AC10, AC11, AC18, AC19, AC22 на live-окружении. Также подбирает любые AC, помеченные QA-шагом (Task 17) как «deferred to post-deploy» — например, поведение, требующее реальных Anthropic-токенов, реального Telegraph и реального канала.

Это non-code задача: артефакт — текстовый отчёт `logs/qa/post-deploy-verification.md` с результатами по каждому шагу AVP, статусом каждого AC (pass / fail / N/A) и решением о финализации фичи (`done` skill готов к запуску либо required follow-ups).

## What to do

1. Прочитать tech-spec.md (раздел Agent Verification Plan) и user-spec.md (AC31 + раздел «Как проверить → Агент проверяет», шаг 7) — зафиксировать чеклист пунктов, которые надо проверить вживую.
2. Прочитать отчёт Task 17 (`logs/qa/pre-deploy-qa-report.md` либо аналог) — выписать все AC с пометкой «deferred to post-deploy» и добавить их в чеклист.
3. Подтвердить через оператора, что Task 18 (Deploy) завершён успешно и сервис на VPS перезапущен на новой версии. Получить от оператора имя production-канала и admin-чата (или подтверждение что используется test-канал).
4. Дождаться ближайшего 12:00 МСК cron tick'а на VPS. До тика — подготовить ssh-доступ к VPS, проверить что `sqlite3` либо Python с `sqlite3` модулем доступны на сервере.
5. В 12:00 МСК — открыть Telegram admin-чат, дождаться admin-пинга. Проверить структуру: «Зафетчил N новых статей, в очереди M, расписание: HH:MM, HH:MM, ...».
6. По ssh на VPS: подтвердить запуск тика — `journalctl`/`docker logs` контейнера за окно 11:59–12:01 МСК показывают строки про `cron tick`, fetch sources, schedule computed.
7. По ssh: SELECT'ом из `pending_articles` подтвердить, что строки добавились (count после ≥ count до). SELECT из `bot_state` подтвердить отсутствие активного outage state.
8. Дождаться 13:00 МСК — первой публикации.
9. Открыть тизер в канале, перейти по ссылке Instant View / Telegraph URL первой автопубликации. Визуально проверить:
   - Title с emoji prefix (например, `🏎️ Mattel ...`).
   - Body без boilerplate (нет «Share on Facebook», «Trending», «Read more», блоков соц-кнопок).
   - Маркер `↳ автоперевод` присутствует и стоит непосредственно перед футером «Источник: ...».
   - Тизер в канале — одна строка ровно `#<source> #news`.
10. По ssh: SELECT из `published_articles` подтвердить запись со свежим `published_at`, наличие `telegraph_url`, `via_review=0`.
11. По ssh: проверить логи на observability-строки про Claude API call (input/output token counts, latency, model version) — AC19.
12. Дождаться 13:40 МСК (или расчётного второго слота из admin-пинга) — проверить, что вторая публикация прошла, интервал ≥40 минут.
13. Проверить admin-чат на отсутствие unexpected error messages, OutageError-пингов, missing-file warning'ов.
14. Запустить 24-часовое наблюдение: каждые 2-3 часа открывать admin-чат, периодически делать ssh + SELECT count(*) `pending_articles`. Зафиксировать в отчёте: размер очереди в начале, в середине, в конце окна; количество публикаций; любые admin-пинги между 12:00 МСК первого дня и 12:00 МСК следующего дня.
15. На следующий 12:00 МСК тик — подтвердить второй cron tick: admin-пинг приходит, расписание перерасчитано относительно carry-over + новый фетч.
16. Если в течение наблюдения возник outage / error — задокументировать и эскалировать оператору, не пытаться чинить из этой задачи (ремонт — отдельная фича либо hotfix-таска).
17. Свести результаты в `logs/qa/post-deploy-verification.md`: чеклист AC со статусом, найденные отклонения, рекомендация — финализировать фичу через `/done` skill либо открыть follow-up задачу.

## Verification Steps

### Smoke

Все шаги — на live production-VPS, не в dev-среде. Команды-примеры даны для типовой VPS-конфигурации; точные пути уточнить у оператора.

- Подтверждение деплоя:
  - `ssh <vps> "systemctl status hw-news-bot || docker ps | grep hw-news"` — сервис running, версия свежая (uptime ≈ время после Task 18).
  - `ssh <vps> "cat /opt/hw-news/.env | grep -E 'ANTHROPIC_MODEL|TZ='"` — нужные переменные присутствуют (значения не выводить в отчёт открытым текстом).
- 12:00 МСК cron tick:
  - В Telegram admin-чате — вручную проверить присутствие admin-пинга в окне 12:00–12:01 МСК.
  - `ssh <vps> "journalctl -u hw-news-bot --since '11:59' --until '12:02' | grep -i 'cron\\|fetch\\|schedule'"` — строки про tick присутствуют.
  - `ssh <vps> "sqlite3 /opt/hw-news/data/news.db 'SELECT COUNT(*) FROM pending_articles;'"` — N после > N до тика (или равно если ничего нового не зафетчилось — допустимо).
- 13:00 МСК первая публикация:
  - Telegram-канал — визуально: тизер `#<source> #news` (одна строка).
  - Открыть Telegraph-ссылку из тизера — визуально проверить title/body/marker.
  - `ssh <vps> "sqlite3 /opt/hw-news/data/news.db \"SELECT id, telegraph_url, via_review, published_at FROM published_articles ORDER BY published_at DESC LIMIT 1;\""` — свежая запись, `via_review=0`, `telegraph_url` непустой.
  - `ssh <vps> "journalctl -u hw-news-bot --since '12:59' --until '13:02' | grep -iE 'claude|tokens|latency|model'"` — observability-строка для Claude API call присутствует.
- Второй слот (≈13:40 МСК или согласно расписанию из admin-пинга):
  - Канал — второй пост появился; время разницы с предыдущим — ≥40 минут.
  - SQLite — count(`published_articles`) увеличился ровно на 1 относительно прошлой проверки.
- 24-часовое наблюдение:
  - Каждые 2-3 часа: открыть admin-чат, зафиксировать любые пинги.
  - В 19:50–20:05 МСК: подтвердить, что после 20:00 МСК новых публикаций нет (окно закрылось).
  - На следующий 12:00 МСК тик: повторить admin-ping check.
  - `ssh <vps> "sqlite3 /opt/hw-news/data/news.db 'SELECT COUNT(*) FROM pending_articles;'"` — финальный размер очереди задокументирован.

### User

Оператор подтверждает (через переписку либо синхронно):
- Production-канал и admin-чат — те самые, которые планировались (не test-канал случайно), либо явно зафиксировано, что верификация шла на test-канале и production будет проверен отдельным окном.
- Качество транскреации первой публикации устраивает (RU title живой, без канцелярита; тон совпадает с manual-постами).
- Согласие финализировать фичу через `/done` либо просьба открыть follow-up на найденные отклонения.

## Details

**Files:**
- `work/llm-transcreation-and-distributed-publishing/logs/qa/post-deploy-verification.md` — новый markdown-отчёт. Структура: header (дата, оператор, версия деплоя), чеклист AC с pass/fail/N/A и комментарием, лог найденных отклонений, рекомендация на финализацию.

**Dependencies:** Task 18 (Deploy) должен быть `done`. Task 17 (Pre-deploy QA) — желательно `done`, чтобы подобрать deferred AC; если QA-отчёта нет — отметить в финальном отчёте и проверить все AC с нуля.

**Tools:** `bash`, `ssh` к VPS, `sqlite3` (CLI на сервере либо Python `sqlite3` модуль), Telegram-клиент (mobile/web/desktop) для визуальной проверки канала и admin-чата. MCP не нужен — backend-сервис без UI-поверхности.

**Edge cases:**
- Cron tick задержался на минуту-две (TZ-drift, контейнер только что рестартанул) — допустимо, главное чтобы в течение 5-минутного окна 12:00–12:05 пинг пришёл. Зафиксировать факт задержки в отчёте.
- В очереди 0 статей после фетча (источники ничего нового не дали) — admin-пинг должен прийти всё равно с N=0, расписание пустое, публикаций в этот день не будет. Это валидный outcome — задокументировать и продолжить наблюдение в следующий день.
- В 13:00 публикация задержалась на минуту-две (network latency Anthropic API) — допустимо. Если задержка >5 минут — отметить как minor finding, не блокировать.
- В первый день после деплоя сработал outage protocol (Claude API rate-limit / network) — это валидное поведение AC14, но требует отдельного теста (см. user-spec «Пользователь проверяет → outage drill»). В этой задаче — фиксируем факт срабатывания, не валим верификацию.
- Оператор публикует статью вручную через `hw_review` параллельно с auto-окном — auto должен скипнуть её на следующем тике (AC21). Не блокирует верификацию, лишь добавляет шум.
- Если что-то пошло не так (crash, missing ux-guidelines, неверный формат маркера) — НЕ фиксить из этой задачи. Зафиксировать в отчёте, эскалировать оператору, открыть follow-up.

**Implementation hints:**
- 24-часовое окно — длительная задача. Разумно вести наблюдение асинхронно: первая активная фаза до 14:00 МСК (cron tick + первые две публикации), затем периодические check-in'ы каждые 2-3 часа.
- Все секреты (`ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, ssh-ключи) — НЕ копировать в отчёт. В отчёте — только метаданные (присутствует / отсутствует, длина, redacted).
- Для проверки маркера `↳ автоперевод` — открывать Telegraph-страницу в desktop-браузере, не Instant View (IV может скрыть некоторые элементы при кешировании). Скриншот в отчёт — опционально, но желательно.
- При 24-часовом наблюдении полезно один раз перезапустить сервис (если возникнет окно для тестирования crash-loop guard AC8) — но только по согласованию с оператором, и не в рамках этой задачи если не было предварительной договорённости.
