# Task 17: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Финальный приёмочный QA перед деплоем фичи `llm-transcreation-and-distributed-publishing`. Задача — убедиться что вся фича целиком (волны 1–9 + аудиты 14–16) удовлетворяет всем критериям приёмки из user-spec (AC1–AC31) и тех-спека (10 технических ACs), что весь тестовый набор зелёный, и что pre-deploy smoke-проверки против реального Claude API и логирующего фильтра проходят. Аудиторы из Audit Wave (tasks 14–16) уже написали свои отчёты — здесь сводим результаты, фиксируем deferred items для post-deploy verification (Task 19) и формируем QA-отчёт, на основании которого оператор принимает go/no-go решение по деплою.

В отличие от аудиторов, которые читают код и ищут проблемы, QA здесь именно проверяет: гоняет полный pytest suite, прогоняет таргетированные новые тестовые файлы, инвокает реальный `claude_transcreation.transcreate_via_claude` против sample-статьи (cost ~$0.01 — приемлемо), синтетически проверяет `_TokenRedactingFilter` на sample anthropic key. По итогам пишет отчёт в `work/llm-transcreation-and-distributed-publishing/logs/qa/pre-deploy-qa.md` с traceability matrix AC → test/проверка → результат, и явно отмечает что нельзя проверить до деплоя (post-deploy AC — например AC31, часть AC25, часть AC27/AC28).

## Verification Steps

### Automated

- `pytest tests/ -q` → 0 failures, отчёт по pass/skip/время.
- `pytest tests/test_compute_publish_slots.py tests/test_claude_transcreation.py tests/test_outage_state.py tests/test_distributed_schedule_integration.py -v` → все зелёные.
- `pytest tests/test_no_token_leak_in_logs.py tests/test_migration.py tests/test_integration.py tests/test_job_prep_phase.py tests/test_translation.py tests/test_fallback_publish_paths.py -v` → все зелёные.

### Smoke

- **Claude API live smoke:** инвокать `claude_transcreation.transcreate_via_claude` против sample EN-статьи (минимум 3 paragraphs; см. fixtures в tests/test_claude_transcreation.py для образца структуры — `source_name`, `title`, `subtitle`, `paragraphs`, `blocks`). Убедиться что вернулся валидный RU dict со всеми требуемыми ключами: `title` (с emoji), `alts` длиной 2–3, `subtitle`, `paragraphs` той же длины что и input. Засечь elapsed time (<30s) и зафиксировать input_tokens / output_tokens / latency_ms из лога (AC19). Конкретный синтаксис вызова — на усмотрение исполнителя.
- **Token redaction smoke:** проверить, что `_redact_text` (хелпер из news_bot, создан в Task 4) или `_TokenRedactingFilter` корректно скрывает оба варианта sk-ant-* ключа: prod-shape вида `sk-ant-api03-...` и sandbox-shape с символами `=`/`.` вида `sk-ant-sandbox_test=.value...`. Подать оба варианта на вход (через прямой вызов хелпера или через `_TokenRedactingFilter.filter()` на синтетическом `LogRecord`), убедиться что в выходе нет plain-text ключа — должно быть `[REDACTED]` или эквивалент. Конкретный способ инвокации — на усмотрение исполнителя.
- **AC traceability check:** просмотреть user-spec AC1–AC31 + tech-spec technical ACs, для каждого зафиксировать тест/smoke которые его проверяют. Записать в отчёт.

**Dependencies:**

- Все предыдущие волны (1–8) завершены и закоммичены — иначе тестовый прогон будет на половине фичи.
- В окружении dev доступен валидный `ANTHROPIC_API_KEY` для live smoke (стоимость ~$0.01 за один вызов Haiku с короткой статьёй — приемлемо).

**Edge cases:**
- Smoke #1 fail из-за rate-limit/network — зафиксировать в отчёте, повторить через несколько минут; если повтор тоже падает — это блокер до выяснения причины (вероятно проблема с API key или сетью dev-контейнера).
- pytest показывает flaky test (один из integration тестов) — не маскировать, разобраться откуда нестабильность; если тест действительно зависит от внешнего ресурса — это open issue, не блокер для деплоя но в отчёт.
- Audit reports содержат critical findings которые в коде не пофикшены — QA report делает no-go, явно описывает что нужно починить до повторного QA.
- AC покрытие неполное — некоторые AC окажутся untestable в pre-deploy окружении (AC31 — живой cron, часть AC27 — реальный scp на сервер). Это нормально, помечаем deferred.

**Implementation hints:**
- QA-отчёт пишется в свободной форме markdown с разделами; не нужно строгого формата JSON. Главное — go/no-go рекомендация в Summary в самом начале, чтобы оператор увидел её первой.
- Traceability matrix удобно делать таблицей: `| AC | Источник проверки | Статус | Комментарий |`. Для AC покрытых тестами — указывать `tests/file.py::test_name`. Для smoke-проверок — указывать шаг smoke. Для deferred — указывать «post-deploy task 19».
- `pytest tests/ -q` выводит summary в конце — захватить эту строку и приклеить в отчёт. Если есть failures — приложить full output релевантных fail-кейсов.
- Live smoke стоит ~$0.01 в токенах — но не злоупотреблять циклами (1–2 вызова достаточно для proof). Не перегонять весь suite через live API.
- Для token redaction smoke не нужно живых ключей — синтетический mock-key вида `sk-ant-api03-AbCd...` достаточен, regex pattern всё равно его поймает.
- Если live smoke вернул ответ но с edge-case проблемой (например title без emoji — должен вставиться wrapper, не Claude напрямую) — это не блокер, это AC11 safety net работает; зафиксировать в отчёте как «AC11 verified live».
