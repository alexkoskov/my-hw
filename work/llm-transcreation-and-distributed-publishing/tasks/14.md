# Task 14: Code Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-reviewing` — [skills/code-reviewing/SKILL.md](~/.claude/skills/code-reviewing/SKILL.md)

## Description

Полный аудит качества кода фичи `llm-transcreation-and-distributed-publishing` после прохождения всех 13 имплементационных задач (Wave 1–8). Аудитор читает все исходники и тесты, созданные/модифицированные в рамках фичи, и пишет отчёт о соответствии тех-спеку и user-spec. Цель аудита — отдельный взгляд на качество и целостность реализации перед Final Wave (pre-deploy QA + deploy + post-deploy verification): убедиться, что атомарные ревью отдельных задач не пропустили cross-task проблем (нарушение инвариантов, leftover ссылки на удалённые символы, неконсистентность state machine). Аудитор НЕ исправляет — только пишет отчёт. Если найдены critical/high находки — их разбирает оператор, решает кому отправить на доработку.

В фокусе семь критических областей:

1. **Decision 9 idempotency preservation в `_fallback_publish`** — рефакторинг шага 1 (translate) не должен сломать идемпотентность шагов 2–5 (Telegraph create → URL persist → Telegram send → DB move). Telegraph URL должен по-прежнему сохраняться ДО Telegram-send, чтобы повторный вызов после краша между этими шагами не создавал дубликат публикации. Это инвариант, унаследованный от feature `manual-review-workflow`.
2. **Decision 5 SDK exception classification в `claude_transcreation`** — все 9 классов исключений Anthropic SDK классифицируются строго по таблице: API-level (`APIConnectionError`, `APITimeoutError`, `RateLimitError`, `InternalServerError`, `AuthenticationError`, `PermissionDeniedError`, `NotFoundError`) поднимают `OutageError`; per-article (`BadRequestError`, `UnprocessableEntityError`, `APIStatusError`, `ClaudeTranscreationError`) поднимают `ClaudeTranscreationError`. Никакого `except Exception` поверх SDK-вызова, который бы маскировал классификацию.
3. **State machine в `outage_state`** — переходы соответствуют таблице из tech-spec / code-research §14.4: `no_outage → ping_1_sent → ping_2_sent → google_fallback_active → recovery_pending → no_outage`. `BEGIN IMMEDIATE` обязателен для пишущих хелперов (`record_outage_event`, `record_recovery_event`). `PRAGMA busy_timeout = 5000` установлен. Чтение несуществующего ключа возвращает `None`, не падает.
4. **Алгоритм `compute_publish_slots`** — соответствует user-spec AC3 (равномерное распределение в окне 13:00–20:00 МСК), AC4 (никаких публикаций после 20:00), AC5 (минимальный интервал 40 минут, posts_today = min(N, 11), carry_over = max(0, N - posts_today)). Граничные случаи: N=0, N=1, N=11, N=12+, container restart (now > window_start), now > window_end.
5. **Нет leftover-ссылок на удалённые символы** — grep по всему репо: ни одного упоминания `_overflow_fast_track`, `_idle_fallback_publish`, `FALLBACK_THROTTLE_SECONDS`, `QUEUE_CAP`, `IDLE_TIMEOUT_HOURS`, `GRACE_WINDOW_HOURS` (кроме changelog/архивов спеков). Удалённые тесты (`test_overflow.py`, `test_idle_fallback.py`) физически отсутствуют. Импорты в новых модулях не тянут устаревшие константы.
6. **Decision 8 flat-path fallback в `_load_prompt`** — `claude_transcreation._load_prompt` пробует subdir-путь (`.claude/skills/project-knowledge/references/ux-guidelines.md`) первым, потом flat fallback (`<DEPLOY_PATH>/ux-guidelines.md`). Без этого деплой через `scp` положит файл в неправильное место и runtime-загрузка промпта молча провалится.
7. **Manual-review path call sites не сломаны** — рефакторинг `news_bot.py` (особенно `_fallback_publish`, `job()`, удаление `_overflow_fast_track`) не повредил вызовы со стороны `hw_review.py` и других CLI-точек входа. `move_to_published`, `list_pending`, `count_pending`, формат channel teaser `#<source> #news` — байт-идентичны старому поведению.

## What to do

1. Прочитать tech-spec.md (Architecture, Decisions 1–16, Implementation Tasks) и user-spec.md (AC1–AC31) — иметь под рукой, на что мапить находки.
2. Прочитать decisions.md фичи — отчёты по Wave 1–8 (что разработчики решили во время реализации, отклонения от плана если были).
3. Прочитать все исходники и тесты, перечисленные в Context Files и Details. Понять текущее состояние кода фичи целиком, а не пер-task.
4. Прогнать grep по всему репо на удалённые символы (см. фокус-область 5) и зафиксировать любые находки.
5. По каждой из 7 фокус-областей пройтись методически: открыть упомянутый файл, проверить инвариант, записать в отчёт «PASS» / «FAIL» с цитатой кода и ссылкой на строку, либо «N/A с обоснованием».
6. Дополнительно прогнать по 11 review dimensions из `code-reviewing` skill (correctness, design, naming, error handling, perf, security-touchpoints, testability, maintainability, docs, simplicity, reuse) — для всех новых модулей (`claude_transcreation.py`, `compute_publish_slots.py`, `outage_state.py`) и затронутых функций (`_fallback_publish`, `job()`, `main()`, `transcreate_text`, `_TokenRedactingFilter`, `_redact_text`).
7. Зафиксировать все находки в `logs/audit/code-audit.md` (новый файл в директории фичи), с разбивкой по severity:
   - **critical** — блокирует деплой (нарушение инварианта; сломан manual-review path; leak секрета).
   - **high** — требует фикса перед деплоем (нарушение Decision; некорректная классификация исключений).
   - **medium** — рекомендуется починить (некрасивое именование, дублирование, отсутствие docstring).
   - **low/nit** — на усмотрение оператора.
8. В конце отчёта — раздел «Verdict»: PASS / PASS-WITH-FIXES / FAIL — с краткой аргументацией.
9. **Аудитор не пишет код, не правит файлы фичи.** Только отчёт.

## Verification Steps

### Automated

Аудитор сам не запускает тесты (это задача Pre-deploy QA в Final Wave). Но фиксирует в отчёте: были ли тесты во всех релевантных файлах зелёные на момент окончания Wave 8 (по логам review-сессий или по последнему commit-сообщению).

Если у аудитора есть сомнение в тестах — отметить в отчёте находкой severity=medium «recommend re-run before deploy: pytest tests/ -q».

### Smoke

Не применимо: задача — статический аудит. Никакого исполнения кода.

## Details

**Files:**
- `work/llm-transcreation-and-distributed-publishing/logs/audit/code-audit.md` — новый. Структурированный отчёт по 7 фокус-областям + 11 review dimensions + раздел Verdict в конце. Markdown.
- Все файлы из Context Files — read-only.

**Dependencies:**
- Task 13 завершён (последняя имплементационная задача Wave 8: deploy bundle update + PK docs).
- Параллельно с этой задачей выполняются Task 15 (Security Audit) и Task 16 (Test Audit). Аудиторы НЕ читают чужие отчёты — каждый смотрит со своего угла. Оператор сводит три отчёта вручную после Audit Wave.

**Edge cases:**
- Если Wave 8 ещё не закрыт по факту (один из reviewers задержал approve) — задача всё равно стартует, но аудитор должен в отчёте чётко указать «по состоянию на commit X / branch Y». Не блокировать на ожидании.
- Если в decisions.md фичи нет отчёта по какой-то задаче (разработчик забыл) — это само по себе medium-находка для отчёта.
- Если grep на удалённый символ возвращает совпадение в `work/completed/manual-review-workflow/` или в архивных спеках — это ОК (исторический контекст), не находка. Совпадения только в живом коде/тестах/деплое.
- Если фокус-область 7 (manual-review call sites) частично пересекается с Test Audit — не страшно, фиксировать вывод независимо.

**Implementation hints:**
- Использовать 11 review dimensions из `code-reviewing` skill как чек-лист, не как формальность — для каждой dimension есть смысл написать одно предложение «такого-то рода проблем не нашёл» или «нашёл вот эти».
- Цитировать код в отчёте короткими блоками (3–5 строк), не дампить функции целиком — отчёт должен быть читаем оператором за 10–15 минут.
- Тон отчёта: технический, без эмодзи, без воды. Severity и file:line — обязательно у каждой находки.
- Раздел Verdict в конце даёт оператору одну из трёх формулировок: PASS (можно деплоить), PASS-WITH-FIXES (есть medium/low, не блокеры), FAIL (есть critical/high — стоп-машина, отдать обратно ответственному за соответствующую Wave).
- Аудитор работает один (без reviewers). Это важно: его отчёт сам по себе и есть deliverable. Если аудитор в чём-то неуверен — не молчать, а написать в отчёте «UNCERTAIN: <аргументация>».
