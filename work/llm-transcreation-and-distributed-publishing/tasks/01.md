# Task 1: Add bot_state migration

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Добавить idempotent SQLite-миграцию для новой таблицы `bot_state` — простой key/value-стор, в котором будет жить состояние outage state machine (timestamps первого outage-события, счётчик отправленных пингов, флаг активного Google fallback и timestamp последнего health-check'а Claude API). Таблица создаётся в `pending_articles_repo.init_schema()` рядом с уже существующими DDL для `pending_articles` / `published_articles` / `failed_articles`.

Это foundation Wave 1: таблица должна появиться раньше, чем модуль `outage_state` (Task 5) начнёт с ней работать. Schema минимальная — `(key TEXT PRIMARY KEY, value TEXT)` — чтобы не пересматривать миграции при будущих расширениях state machine. Миграция полностью идемпотентна: `CREATE TABLE IF NOT EXISTS` отрабатывает корректно и при первом запуске после deploy на сервере, где БД уже содержит все остальные таблицы, и при повторных запусках без изменений в данных.

Покрытие тестом обязательно: тех-спек AC «Schema & migration» и user-spec AC24 требуют, чтобы PRAGMA table_info таблицы `bot_state` показывала ровно две колонки правильных типов с PRIMARY KEY на `key`, плюс idempotency регрессионно проверялась (повторный `init_db()` не уничтожает уже записанные значения и не падает).

## What to do

1. В `pending_articles_repo.py` добавить новую DDL-константу `_BOT_STATE_DDL` с телом `CREATE TABLE IF NOT EXISTS bot_state (key TEXT PRIMARY KEY, value TEXT)`. Положить её рядом с `_PENDING_DDL` / `_PUBLISHED_DDL` / `_FAILED_DDL`, в том же стиле (триплет-кавычки SQL, без trailing whitespace).
2. Расширить `init_schema(conn)` так, чтобы он дополнительно выполнял `_BOT_STATE_DDL` — одной строкой `conn.execute(_BOT_STATE_DDL)` перед общим `conn.commit()`. Никакие сигнатуры/параметры функции не меняются.
3. В `tests/test_migration.py` добавить (а) пункт `bot_state` в `test_all_tables_created`, (б) новый тест `test_bot_state_schema` — он создаёт DB через `news_bot.init_db()` и через `PRAGMA table_info(bot_state)` проверяет: ровно две колонки, `key TEXT PK`, `value TEXT`, PRIMARY KEY на `key`. (в) Расширить `test_init_db_idempotent`: между двумя вызовами `init_db()` вставить строку в `bot_state` (например `INSERT INTO bot_state (key, value) VALUES ('outage_started_at', '2026-04-26T12:00:00')`), второй вызов `init_db()` не должен ни падать, ни менять row-count.
4. Зелёный `pytest tests/test_migration.py -v`.

## Details

**Files:**
- `pending_articles_repo.py` — текущее состояние: три DDL-константы (`_PENDING_DDL`, `_PUBLISHED_DDL`, `_FAILED_DDL`) и функция `init_schema(conn)`, которая выполняет все три и коммитит. Что сделать: добавить четвёртую константу `_BOT_STATE_DDL` (минимальная схема `key TEXT PRIMARY KEY, value TEXT`) и одну строку `conn.execute(_BOT_STATE_DDL)` в `init_schema` перед `conn.commit()`. Сигнатура `init_schema(conn)` не меняется.
- `tests/test_migration.py` — текущее состояние: класс `TestMigration` с тестами `test_all_tables_created`, `test_processed_news_schema_unchanged`, `test_pending_articles_has_expected_columns`, `test_init_db_idempotent`. Что сделать: (а) в `test_all_tables_created` добавить `self.assertIn('bot_state', tables)`; (б) добавить новый метод `test_bot_state_schema`, который через `_pragma_columns('bot_state')` проверяет shape двух колонок; (в) в `test_init_db_idempotent` расширить блок seed-данных INSERT'ом одной строки в `bot_state` и в финальной проверке row-counts добавить `'bot_state'` к списку проверяемых таблиц с ожидаемым `count == 1`.

**Dependencies:** none (Wave 1 foundation). Не блокирует другие задачи; Task 5 (`outage_state.py`) опирается на наличие этой таблицы как pre-requisite.

**Edge cases:**
- Повторный вызов `init_schema` на той же DB — `CREATE TABLE IF NOT EXISTS` отрабатывает no-op, существующие строки в `bot_state` сохраняются.
- Запуск на свежей DB (нет файла) — `news_bot.init_db()` создаёт файл и все четыре + `processed_news` таблицы; `bot_state` появляется среди них.
- Запуск на DB после prod deploy (старая БД с тремя manual-review таблицами + `processed_news`, без `bot_state`) — миграция добавляет одну новую таблицу, остальные не трогает.
- При сбое миграции (диск полный, lock) — exception пробрасывается из `init_schema`; обработка этой ситуации (admin-ping в `news_bot.main()`) лежит на Task 8, не на этой задаче.

**Implementation hints:**
- Соблюдай стиль соседних DDL-констант: триплет-кавычки, тело SQL с переводами строк и indentation на 4 пробела внутри скобок (см. `_PENDING_DDL`).
- Для тестов `_pragma_columns` уже определён в файле — переиспользовать как есть. Ожидаемая shape для `bot_state`:
  - `key`:   `{'type': 'TEXT', 'notnull': 0, 'dflt_value': None, 'pk': 1}` — SQLite quirk: для `TEXT PRIMARY KEY` без явного `NOT NULL` PRAGMA вернёт `notnull=0`. Это согласуется со стилем `pending_articles.link` / `published_articles.link` в этом же репозитории — не добавляй явный `NOT NULL`, чтобы не отступать от существующей конвенции.
  - `value`: `{'type': 'TEXT', 'notnull': 0, 'dflt_value': None, 'pk': 0}`.
- Убедись, что в `test_init_db_idempotent` финальный цикл проверки row-counts получает обновлённый список таблиц (включая `bot_state`).
