## Description

Создаём новый pure-функциональный модуль `compute_publish_slots.py` — алгоритм распределения публикаций в окне 13:00–20:00 МСК. Это foundation-модуль (Wave 1), от которого зависит refactor `job()` в Task 8: новый distributed-publish loop в news_bot.py будет вызывать `compute_publish_slots(count_pending(), now_msk)` после фетча и публиковать статьи по полученному списку datetime-слотов.

Цель — реализовать **адаптивный** алгоритм с floor=40 минут: интервал считается от **оставшегося окна** на момент вызова (не от полных 420 минут), что естественно покрывает и cron-tick из 12:00 (полное окно 7ч от 13:00), и container restart mid-window (остаток окна от now до 20:00). Двухветочная формула:

```
remaining_minutes = (window_end - effective_start) в минутах
                    где effective_start = max(window_start, now)
raw_interval      = remaining_minutes / N   (если N > 0)
interval          = max(raw_interval, MIN_INTERVAL_MINUTES)   # floor=40
```

Cap=11 публикаций/день получается **естественно** из floor=40 в окне 7ч: `floor(420 / 40) + 1 = 11`. Никаких отдельных явных констант-cap'ов в формуле — счёт выпадающих в окно слотов делается через `floor(remaining_minutes / interval) + 1`, и при interval=40 это даёт максимум 11. Excess (если N > slots_count) carry-over в pending до следующего дня.

Функция должна корректно работать на:

- **Cron tick в 12:00** (now < window_start) — `effective_start=13:00`, `remaining_minutes=420`. N=7 → interval=60 → 7 слотов 13:00…19:00.
- **Container restart mid-window** (now=16:00, N=5) — `effective_start=16:00`, `remaining_minutes=240`. raw=48 → interval=48 → 5 слотов 16:00, 16:48, 17:36, 18:24, 19:12. carry_over=0. (Это и есть ключевое отличие от наивной 420/N: при restart мы пересчитываем темп под остаток окна, не под полное.)
- **Container restart late-window** (now=19:50, N=5) — `remaining_minutes=10`, raw=2, floor применяется → interval=40, max_publishable=floor(10/40)+1=1, 1 слот в 19:50, 4 в carry_over.
- **Cron tick после 20:00** — пустой список, всё в carry_over.
- **TZ-naive datetime на входе** — ValueError (инвариант: scheduler работает только с MSK-aware datetime).

Модуль чисто stdlib (`datetime`, `typing`), без внешних зависимостей, без сайд-эффектов — идеально тестируется и реюзается в integration-тестах Task 12.

13 тестов покрывают граничные значения N (0, 1, 4, 7, 10, 11, 15, 20), restart-сценарии и TZ-инвариант. Это обеспечит, что любая регрессия в формуле или инварианте поймается до того как сломает production cron.

## What to do

1. Создать новый файл `compute_publish_slots.py` в корне репозитория (рядом с `news_bot.py`, `pending_articles_repo.py`).
2. Объявить module-level константы: `WINDOW_START = time(13, 0)`, `WINDOW_END = time(20, 0)`, `MIN_INTERVAL_MINUTES = 40`. Никакой `MAX_POSTS_PER_DAY` константы — cap=11 это естественное следствие floor=40 в окне 7ч (`floor(420/40)+1=11`); добавлять отдельную константу значило бы дублировать инвариант и ломать кастомизацию через параметры (например, нестандартный `min_interval_min`).
3. Реализовать функцию `compute_publish_slots(n, now, window_start=WINDOW_START, window_end=WINDOW_END, min_interval_min=MIN_INTERVAL_MINUTES) -> Tuple[List[datetime], int]` с **адаптивным** алгоритмом:
   - Валидация: `now.tzinfo is None` → `ValueError("compute_publish_slots requires tz-aware datetime")`.
   - Если `n == 0` → return `([], 0)`.
   - `window_start_dt = combine(now.date(), window_start, tzinfo=now.tzinfo)`.
   - `window_end_dt = combine(now.date(), window_end, tzinfo=now.tzinfo)`.
   - Если `now >= window_end_dt` → return `([], n)` (всё carry-over).
   - `effective_start = max(window_start_dt, now)`.
   - `remaining_minutes = (window_end_dt − effective_start).total_seconds() / 60` (всегда `>= 0` после предыдущей проверки).
   - **Адаптивная формула** (двухветочная по факту, единая по форме): `raw_interval = remaining_minutes / n` — это даёт корректное поведение на обоих сценариях:
     - Когда `now <= window_start` (cron-tick): `effective_start = window_start`, `remaining_minutes = 420` → raw_interval = 420/n. Полное окно.
     - Когда `now > window_start` (restart mid-window): `effective_start = now`, `remaining_minutes = window_end − now` → raw_interval адаптируется к остатку. Например, restart at 16:00, N=5 → remaining=240, raw=48 → interval=48.
   - `interval = max(raw_interval, min_interval_min)`.
   - `max_publishable_now = floor(remaining_minutes / interval) + 1` (как минимум 1 слот в `effective_start`, дальше столько, сколько влезает в остаток окна с шагом `interval`).
   - `slots_count = min(n, max_publishable_now)` — без отдельного `MAX_POSTS_PER_DAY` cap'а; floor=40 при полном окне даёт ровно 11, что и нужно.
   - `slots = [effective_start + timedelta(minutes=interval * i) for i in range(slots_count)]`.
   - `carry_over = n − len(slots)`.
   - Возвращаемые datetime'ы наследуют tzinfo из `now`.
4. Создать файл `tests/test_compute_publish_slots.py` с 13 тестами (см. TDD Anchor). Использовать tz-aware datetime через `datetime.timezone(timedelta(hours=3))` (МСК = UTC+3 круглогодично с 2014) — это избегает зависимости от pytz, который добавится в Task 6, и не привязывает тесты модуля к внешней либе.
5. Убедиться, что `pytest tests/test_compute_publish_slots.py -v` проходит зелёным (все 13 тестов) и `pytest tests/ -q` не показывает регрессий.

**Edge cases:**

- `n == 0` → `([], 0)` без обращения к window_start.
- `n == 1, now < window_start` → 1 слот в `window_start` (effective_start), не в `now`.
- `now >= window_end` (т.е. 20:00 или позже) → `([], n)` — всё переносится на завтра. NB: используем строгий `now >= window_end` (не `>`), чтобы ровно в 20:00 не публиковать (граница окна — exclusive по верху, спека AC3 «после 20:00 ни одна публикация»).
- `now > window_start` (restart mid-window) → `effective_start = now`; интервал считается от `remaining_minutes = window_end − now` (не от полных 420). Это и есть адаптивная ветвь — пример из user-spec: restart at 16:00, N=5 → remaining=240, raw=48, interval=48, 5 слотов 16:00…19:12.
- `now == window_start` (ровно 13:00) → `effective_start = max(13:00, 13:00) = 13:00`, `remaining_minutes = 420`. Полное окно — формула эквивалентна 420/N.
- `n > 11` (при cron-tick из 12:00, полное окно) → raw_interval=420/n < 40 → interval=40 (floor) → max_publishable=floor(420/40)+1=11 → slots_count=11, carry_over=n−11. Cap получается естественно из floor=40, без отдельной константы.
- `n > capacity` при позднем restart (например, 19:50 + N=5) → remaining=10, max_publishable=1, slots_count=1, carry_over=4.
- TZ-naive `now` → `ValueError`. Не silently aware-ить — явно фейлить.
- Window crosses midnight (window_start > window_end) — out of scope в этой задаче, текущее окно 13–20 интра-day.

**Implementation hints:**

- `datetime.combine(date, time, tzinfo=now.tzinfo)` — корректный способ построить window_start/end на дату now с тем же tzinfo. Не использовать `replace(hour=..., minute=...)` — теряет читаемость намерения.
- Floor-divide через `int(remaining_minutes // interval)` — целочисленное деление. `math.floor` тоже подойдёт.
- Для `interval`: всегда `float` (не int) — `remaining_minutes / 11 = 38.18…` округлится при int-делении. Сохранять float для precision; финальный `timedelta(minutes=interval * i)` принимает float корректно.
- Адаптивность формулы — это просто следствие того, что `effective_start = max(window_start, now)` и `remaining_minutes = window_end − effective_start`. Когда `now <= window_start`, `effective_start = window_start` и `remaining_minutes = 420`, формула вырождается в 420/N. Когда `now > window_start`, формула пересчитывается под остаток. Никакого явного `if now < window_start: ...` ветвления в коде не нужно — оно встроено в `max()`.
- Не возвращать numpy arrays / generators — только plain `list[datetime]`.
- Docstring с примерами из user-spec («cron-tick 12:00, N=7 → 7 постов через час 13:00…19:00»; «restart at 16:00, N=5 → 5 слотов с интервалом 48 мин»; «N=15 → 11 сегодня + 4 завтра») сильно помогает читателю.
