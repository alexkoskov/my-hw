# Task 5: Create `outage_state.py` + tests

## Required Skills

Перед выполнением задачи загрузи:

## Description

Создать новый модуль `outage_state.py` — SQLite-backed key/value access layer для таблицы `bot_state` (создаётся в Task 1 через `pending_articles_repo.init_schema()`). Модуль реализует state-machine для протокола недоступности Claude API: переходы между состояниями `no_outage` → `ping_1_sent` → `ping_2_sent` → `google_fallback_active` → recovery, с переживанием перезапусков контейнера.

Этот модуль — фундамент для outage protocol (user-spec AC11–AC17): когда Claude API падает (auth/rate-limit/network/server), бот должен послать оператору 2 пинга с интервалом 1 час, выждать grace 2 часа, и потом переключиться на Google Translate fallback. State хранится в БД, потому что контейнер может рестартнуть посреди outage и счётчик пингов должен сохраниться (user-spec Constraints: «Outage state persists across restart»).

API модуля будет вызываться из `_fallback_publish` (Task 7) при ловле Claude SDK exceptions и из `job()` (Task 8) для проверки текущего состояния и для recovery probe. Нижестоящий код будет полагаться на атомарность state-machine helpers — два параллельных вызова `record_outage_event` не должны двойным образом инкрементировать `ping_count`, поэтому используется `BEGIN IMMEDIATE`.

## What to do

1. Создать новый файл `outage_state.py` на корне проекта (рядом с `pending_articles_repo.py`).
2. Реализовать connection helper, который открывает короткоживущее `sqlite3.connect(news_bot.DB_FILE)` соединение per call (тот же паттерн что в `pending_articles_repo._connect`), и применяет `PRAGMA busy_timeout = 5000;` сразу после открытия (Decision 16: 5-секундный таймаут поглощает контеншн между cron-писателями и hw_review CLI).
3. Реализовать публичные геттеры/сеттеры для каждого ключа из таблицы `bot_state`:
   - `get_outage_started_at()` / `set_outage_started_at(dt)` — ISO-8601 string ↔ tz-aware MSK datetime, или None.
   - `get_last_ping_sent_at()` / `set_last_ping_sent_at(dt)` — то же.
   - `get_ping_count()` / `increment_ping_count()` — int, хранится как строка `'0'`/`'1'`/`'2'`/`'3'`. Чтение отсутствующего ключа возвращает 0.
   - `is_fallback_active()` / `set_fallback_active(active: bool)` — `'0'`/`'1'`.
   - `get_last_health_check_at()` / `set_last_health_check_at(dt)`.
   - `clear_outage_state()` — атомарно (одной транзакцией) удаляет все ключи outage в БД (вызывается на recovery).
4. Реализовать high-level state-machine helpers:
   - `record_outage_event(now: datetime) -> dict` — вызывается из `_fallback_publish` после Claude API outage error. Внутри открывает соединение, делает `BEGIN IMMEDIATE`, читает текущее состояние (`outage_started_at`, `ping_count`, `last_ping_sent_at`, `fallback_active`), вычисляет следующее состояние согласно transition table из code-research §14.4, записывает изменения, COMMIT'ит. Возвращает dict `{'state': '<state>', 'pings_to_send': [<message>, ...], 'fallback_now': <bool>}`. Caller использует `pings_to_send` для отправки в Telegram, и `fallback_now` чтобы решить, перевести ли THIS article через Google.
   - `record_recovery_event(now: datetime) -> dict` — вызывается когда Claude call успешен после outage. Если `outage_started_at IS NULL` → return `{'was_active': False, 'pings_to_send': []}`. Иначе одной `BEGIN IMMEDIATE` транзакцией: clear all outage keys; return `{'was_active': True, 'pings_to_send': ['✓ Claude API recovered, switching back from Google Translate fallback.']}`.
5. Все писатели (setters + state-machine helpers) используют `BEGIN IMMEDIATE` для read-then-write последовательности; геттеры — обычное чтение.
6. Чтение отсутствующих ключей возвращает Python `None` (для timestamps), `0` (для counters), `False` (для flags). Никаких exception на missing keys.
7. Парсинг datetime значений: использовать `datetime.fromisoformat()`. На `ValueError` (corrupted DB content) — вернуть `None` и залогировать warning. Никогда не падать на чтении (AC из tech-spec: «`bot_state` value reads tolerate corrupted/unexpected text — return None or default; never crash startup»).
8. Создать `tests/test_outage_state.py` — ~6 тестов, покрывающих state transitions, persistence across simulated container restart, и concurrency.

- `tests/test_outage_state.py` (новый, ~6 тестов) — текущее состояние: файла нет.

**Dependencies:**
- Task 1 (`bot_state` migration в `pending_articles_repo.init_schema()`) должна быть merged до начала. Этот модуль читает/пишет таблицу, создаваемую Task 1.
- stdlib only: `sqlite3`, `datetime`, `threading` (тесты), `logging`, `typing`, `contextlib` (опционально). Никаких новых пакетов.

**Edge cases:**
- БД не существует или таблица `bot_state` отсутствует — этот модуль НЕ создаёт таблицу сам (это ответственность Task 1 / `init_schema`). Тесты должны вызывать `pending_articles_repo.init_schema(conn)` в setUp/fixture перед использованием outage_state.
- Чтение отсутствующего ключа: `SELECT value FROM bot_state WHERE key=?` → `cursor.fetchone() is None` → вернуть default (`None` для timestamps, `0` для int counters, `False` для bool flags).
- Corrupted ISO timestamp string в БД: `datetime.fromisoformat(...)` raises `ValueError` → catch, log warning ("corrupted bot_state value at key=X"), return `None`. Бот не падает на startup.
- Конкурентный writer (cron + hw_review): `BEGIN IMMEDIATE` блокирует второго писателя на 5s (busy_timeout); если первый коммитит за <50ms — второй просто продолжает. Если первый завис на >5s → второй получит `OperationalError: database is locked` — это корректное поведение (deadlock surfacing вместо тихой потери данных).
- Recovery event при свежей БД (`outage_started_at IS NULL`): `record_recovery_event` возвращает `{'was_active': False, 'pings_to_send': []}` без записей в БД (no-op).
- Datetime tz: caller передаёт tz-aware MSK datetime (`pytz.timezone('Europe/Moscow').localize(...)`); сохраняем через `.isoformat()` (включает offset). Чтение через `datetime.fromisoformat()` возвращает tz-aware datetime. Naive datetime от caller — out of contract, можно raise ValueError или принять и сохранить (выбор реализации, но желательно raise — symmetric с `compute_publish_slots` из Task 2).

**Implementation hints:**
- Используй простой `_get(key) -> Optional[str]` / `_set(key, value)` private helpers в основе модуля; публичные геттеры/сеттеры — тонкие обёртки с парсингом/сериализацией типов.
- `clear_outage_state` реализуй как `DELETE FROM bot_state WHERE key IN (...)` одной statement'ой внутри транзакции — простительно для 5 ключей.
- State-machine логику оформи отдельной чистой функцией `_compute_next_state(current_state_dict, now) -> (next_state_dict, pings, fallback_now)` — принимает уже прочитанные значения, возвращает то что нужно записать. Это упрощает unit-тестирование и держит SQL-плоскость отделённой от логики переходов.
- Текст admin-пингов хранить как module-level константы (`_PING_1_TEXT`, `_PING_2_TEXT`, `_PING_3_TEXT`, `_RECOVERY_TEXT`) — тестируемо, переводимо.
- Для concurrent test используй `threading.Barrier(2)` чтобы оба thread'а гарантированно стартовали одновременно; assertion на `ping_count == 1` после `barrier.wait()` + два `t.join()`.
- Импортируй `news_bot.DB_FILE` lazily внутри `_connect()` (как `pending_articles_repo._connect`) — это позволяет тестам подменять `news_bot.DB_FILE` через monkeypatch на tempfile.

**Reference: state machine transition table (code-research §14.4):**

| Current state | Trigger (now-based) | Next state | Pings to send |
|---|---|---|---|
| `no_outage` | outage error | `ping_1_sent` | ping #1 (немедленно) |
| `ping_1_sent` | outage error AND now-t0 ≥ 1h | `ping_2_sent` | ping #2 (через 1ч) |
| `ping_1_sent` | outage error AND now-t0 < 1h | `ping_1_sent` | (никаких) |
| `ping_2_sent` | outage error AND now-t0 ≥ 2h | `google_fallback_active` | ping #3 («Переключился на Google») |
| `ping_2_sent` | outage error AND now-t0 < 2h | `ping_2_sent` | (никаких) |
| any active state | recovery (Claude succeeds) | `no_outage` | recovery ping |

`fallback_now` semantics: `False` only on the very first transition `no_outage → ping_1_sent` (caller сделает retry на Claude); `True` во всех остальных outage events (caller роутит этот article через Google).

> **Note on `fallback_now` vs `is_fallback_active()`:** это разные понятия. `fallback_now` (поле в return dict из `record_outage_event`) — per-call решение «роутить ЭТУ статью через Google прямо сейчас?», действует только на текущий вызов. `is_fallback_active()` (геттер из `bot_state` row `fallback_active='1'`) — persistent flag «бот в режиме `google_fallback_active`?», взводится только на финальном переходе `ping_2_sent → google_fallback_active` и сбрасывается на recovery. То есть `fallback_now=True` может быть верно ещё до того, как `is_fallback_active()` стало True (например, во время `ping_2_sent` window).
