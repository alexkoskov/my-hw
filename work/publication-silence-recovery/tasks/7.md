# Task 7: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](../../../.claude/skills/security-auditor/SKILL.md)

## Description

Провести финальный offline security-аудит двух реализованных контуров фичи: review-release scheduler и tri-state publication watcher. Аудит не изменяет implementation и тесты; его единственный deliverable — `work/publication-silence-recovery/logs/audit/security-audit.json`.

Проверка должна трассировать trust boundaries от Telegram callback и Telegraph response до SQLite, logs и GitHub issue transitions. Особое внимание: admin authorization до DB-read, kind-scoped review tokens, dual gates, parameterized/atomic SQL, единственный publisher, bounded parsing недоверенного JSON, tri-state fail-safe behavior, immutable action pin, checkout outcome gate, least privilege, изоляция `TELEGRAPH_ACCESS_TOKEN` от repository code и санитация logs.

## What to do

1. Убедиться, что Tasks 3 и 4 завершены и все файлы из audit scope существуют. Сверить implementation с approved user-spec/tech-spec и зафиксировать исходные checksums всех read-only scope files в runner-temporary файле.
2. Протрассировать review callback: untrusted `from_user_id`/action/token → auth → token-kind validation → SQLite transition → status/log. Проверить fail-closed authorization, non-consumption token при unauthorized/wrong-kind/unknown-action, idempotency, CR/LF/URL redaction и отсутствие callback-side publish.
3. Проаудировать SQLite contour: все изменённые queries parameterized/static; scheduler snapshot собирается одним statement; held/deferred/publishable categories не дают gate bypass; fallback не создаёт release opportunity и пропагирует second failure.
4. Протрассировать watcher: untrusted Telegraph bytes → bounded stdin/JSON parse → path/date classifier → `fresh|stale|inconclusive` → issue transition. Проверить лимит 1 MiB + sentinel, recursive/malformed/ambiguous data, aware-clock contract, отсутствие raw evidence в stdout/stderr/logs и no-op для `inconclusive`.
5. Проаудировать workflow supply chain и secrets: full-SHA `actions/checkout`, explicit default-branch ref, `persist-credentials: false`, `fetch-depth: 1`, checkout `continue-on-error`, classifier gate только по successful outcome, minimal permissions, independent SSH verdict. `TELEGRAPH_ACCESS_TOKEN` доступен только fetch step и не попадает в URL/output/temp evidence/repository process.
6. Выполнить offline hardcoded-secret scan всего scope, включая workflow и fixtures. Отличить GitHub expressions и явно synthetic test values от credentials; никакие suspicious values не копировать в отчёт.
7. Пройти все OWASP Top 10 (2021) categories и dependency/data-integrity surface. Учесть CLI/bot/workflow-архитектуру и не превращать неприменимые web-категории в false-positive findings. Не скачивать vulnerability DB и не устанавливать scanner: у фичи нет новых Python packages; action integrity проверяется по pinned workflow и tech-spec provenance.
8. Сверить security assertions в тестах с implementation, но не принимать сам факт наличия теста за доказательство защиты. Проверить negative paths и resulting state/output.
9. Записать единственный JSON report по схеме security-auditor. Findings снабдить severity, OWASP/dependency category, точной `file:line`, impact, actionable recommendation и CWE, когда applicable. Повторить checksums и доказать, что source/test/workflow файлы не изменены аудитором.

- [ ] Никакая валидация не делает network request, live Telegram/Telegraph/GitHub call, DB mutation вне tempfile, deploy, restart или publish.

## Details

**Files:**
- `work/publication-silence-recovery/logs/audit/security-audit.json` — new and only writable deliverable. Use the exact security-auditor JSON shape; an empty result is `findings: []` with all counts zero, not prose.
- `pending_articles_repo.py` / `news_bot.py` — inspect post-Task-3 code, especially new snapshot query, fallback boundary, release loop, callback statuses and decision-log identifiers.
- `publication_watch.py` / `.github/workflows/uptime.yml` — inspect post-Task-4 executable classifier/workflow boundary; do not audit only the proposed tech-spec.
- Test files — use as security evidence and gap detectors. Assertions must establish state/output, not merely mock call counts.

**Dependencies:**
- Requires Tasks 3 and 4. Their dependencies supply scheduler/repository and classifier foundations.
- No reviewer follows this task (`reviewers: [none]`); Task 9 consumes this report. Do not silently fix findings: remediation is a separate orchestrated task/round.
- No new package and no network-backed vulnerability database. Review the changed dependency surface and immutable action pin offline.

**Edge cases:**
- An unauthorized press must perform zero DB reads; wrong-kind/unknown-action input must neither mutate state nor consume the valid token.
- A link used in logs may contain CR/LF, URL userinfo or query credentials; callback token and raw exception text must never be logged.
- Dual-gate rows stay blocked after either single gate-clear order. Snapshot/fallback errors must not create an unknown release path.
- Exactly 1 MiB evidence versus one byte over, deep JSON/`RecursionError`, malformed shape, future ambiguous date and naive time all fail safely without raw-body diagnostics.
- Checkout can fail while SSH verdict still completes. Repository code must not run after a partial/failed checkout, and `inconclusive` must never raise or resolve a publication issue.
- Synthetic token-shaped fixtures are acceptable only when obviously fake and asserted absent from output; never repeat a matched candidate in the report.

**Implementation hints:**
- Start from trust-boundary/data-flow tracing, then map observations to OWASP categories; this avoids checklist-only false positives.
- Use exact post-implementation line numbers. If a concern cannot be demonstrated from code/tests, label the uncertainty and recommendation precisely instead of asserting exploitation.
- `status` is based on critical findings only per the loaded skill; major/minor findings still remain fully actionable in `findings`.
- Keep the report machine-readable: no Markdown fences, comments, trailing commas or extra text outside the JSON document.
