# Task 3: Review-release scheduler integration

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](../../../.claude/skills/code-writing/SKILL.md)

## Description

Интегрировать примитивы из Task 1 в ежедневный `news_bot.job()`, чтобы дневной план описывал только уже публикуемые статьи, а runtime сохранял оставшиеся фиксированные возможности при deferred/held backlog. Это закрывает production-гонку: пустое чтение в 10:00 не завершает весь цикл, и `[E014] keep` / `[E036] approve` могут освободить строку к 15:00 или 19:30, но не публикуют её из callback-потока.

Также callback-статусы для строк с двумя gate должны называть оставшуюся причину, а журнал решений — не раскрывать untrusted URL и callback-токены. Тесты работают на реальной временной SQLite при замоканных Telegram, Telegraph и LLM.

## What to do

1. До implementation добавить RED-тесты полных `[E014]`/`[E036]` timeline, mixed backlog, cutoff, fallback, observability и safe callback logging.
2. Заменить три раздельных queue-чтения в `job()` одним `get_schedule_backlog_counts()` и явно развести publishable, deferred и held backlog.
3. Разделить operator-facing `planned_slots`/`carry_over` и runtime `execution_slots`: план считать только по publishable rows, а все remaining fixed opportunities удерживать только при deferred/held snapshot backlog.
4. Для удержанных release opportunities пропускать только текущее empty read; для ordinary/пустого snapshot без reviewable backlog сохранить early break.
5. Реализовать точный fallback: snapshot error логируется через `sanitize_error_message()`, внутри planning fallback boundary `count_pending()` вызывается ровно один раз для ordinary plan, release opportunities не создаются; fallback error пропагируется. Существующее отдельное `count_pending()` в конце `job()` для `final_queue_size` telemetry остаётся без изменений и не входит в этот счёт.
6. Сохранить observability: E008/E009 получают только `planned_slots`, empty opportunities не меняют E034/carry-over, dry-spell/heartbeat выполняются после ограниченного loop; развести backlog/outcome counters.
7. Сделать `[E036] approve` симметричным `[E014] keep`: после снятия hold повторно проверить `publish_after` и не обещать ближайший слот при активной отсрочке.
8. Санитизировать article identifier в decision log: исключить CR/LF, URL userinfo, query/fragment, ограничить длину; callback token и raw exception text не логировать.
9. Прогнать focused и regression suites offline, без production DB, network, restart и deploy.

## Acceptance Criteria

- [ ] `job()` один раз читает atomic `(publishable, deferred, held)` snapshot; Task 1 categories не пересчитываются раздельными SELECT.
- [ ] `planned_slots`/`carry_over` считаются по publishable count и попадают в operator plan; withheld counts остаются отдельными строками.
- [ ] При `deferred + held > 0` loop получает все remaining fixed times с той же grace/cutoff policy; без reviewable backlog `execution_slots == planned_slots`.
- [ ] Empty retained opportunity делает `continue`, ordinary empty read сохраняет early `break`.
- [ ] E014 timeline публикует exact row один раз в 15:00 после `keep`; E036 `approve` симметричен, callbacks не вызывают publisher.
- [ ] Cancel/reject дают ноль публикаций; E014 silence освобождается только после expiry, E036 silence остаётся held.
- [ ] Dual-gate row не попадает в `list_pending()` после снятия одного gate; оба callback-статуса называют оставшийся gate.
- [ ] Mixed snapshot публикует ordinary row в 10:00 и released row в 15:00 без duplicate selection и plan drift.
- [ ] Решение после 19:30 оставляет row pending до 10:00 следующего дня; restart в 16:00 не догоняет прошедшие slots.
- [ ] Один `job()` не использует больше трёх remaining fixed opportunities и не публикует вне них.
- [ ] Snapshot error вызывает `count_pending()` ровно один раз в planning fallback boundary, создаёт ordinary plan без release opportunities; fallback error пропагируется. Финальное telemetry-чтение `count_pending()` для `final_queue_size` остаётся отдельным и неизменным.
- [ ] Empty checks не входят в E034 и не меняют carry-over; dry-spell и heartbeat выполняются после loop.
- [ ] Decision logs не содержат CR/LF, URL userinfo/query/fragment и callback token; new exception logs проходят через sanitizer.
- [ ] Focused и regression tests проходят offline; production/network/restart/deploy не используются.

## Details

**Files:**

- `news_bot.py` — сейчас `job()` читает `count_pending()`, `count_deferred()` и `list_held()` раздельно, передаёт publishable+deferred в один `compute_fixed_slots()` и делает `break` при первом пустом `list_pending()`. Нужны atomic snapshot, plan/execution lists, условное continuation, exact fallback, разные counters, truthful E036 status и safe review identifier.
- `news_bot.py` уже делает ещё одно `count_pending()` после slot loop для `final_queue_size` в `[job] done` telemetry. Это не planning fallback, его не удалять и не переносить в atomic snapshot без отдельного spec-решения.
- `tests/test_job_distributed_publish.py` — использовать `_DistribLoopBase`, tempfile DB и существующие source/time seams. Publish double обязан двигать exact row и тесты должны утверждать табличное state, не только calls.
- `tests/test_integration.py` — расширить `TestResolveHoldCallback` и `TestReviewListener`; не ослаблять admin-first, kind-scoping, stale-token и idempotency assertions.

**Dependencies:**

- Task 1 добавляет `remaining_fixed_slots(...)` и `pending_articles_repo.get_schedule_backlog_counts()`. Эта задача не дублирует их grace/category logic.
- Новых пакетов, schema/migration нет; `admin_alerts.py` остаётся неизменным consumer planned values.

**Edge cases:**

- Callback commit до/после `list_pending()` определяет current/next fixed time; in-memory signal не нужен.
- Snapshot до callback видит withheld row, после callback — publishable row; cancel/reject после snapshot может оставить только безвредную лишнюю wake-up opportunity.
- Held категория доминирует при dual gate; `clear_deferral`/`clear_hold` не ослабляют второй SQL predicate.
- После 19:30 remaining helper возвращает `[]`; callback только меняет SQLite, next-day `job()` подбирает row.
- Snapshot error не доказывает reviewable backlog, поэтому fail-safe не создаёт additional opportunities.
- Empty opportunity — не publish attempt, hold, failure или carry-over unit.
- Untrusted link не должен вставлять новую строку журнала или раскрывать URL credentials/query.

**Implementation hints:**

- Переиспользовать Task 1 helper; не подменять remaining-times API вызовом `compute_fixed_slots(3, ...)`.
- Явные имена `planned_slots`, `execution_slots`, `held_backlog_count`, `held_outcome_count` и release flag снижают риск смешать plan с wake-ups.
- Сохранить `list_pending()` единым eligibility source на каждом fixed time; callbacks остаются state-only.
- Для log identifier использовать stdlib URL parsing с safe fallback на malformed input; не логировать raw link в error branch.
- При mock `datetime` помнить, что SQLite `CURRENT_TIMESTAMP` живёт по реальным UTC; expiry/cutoff fixtures должны согласовывать clocks или явно обновлять timestamps.
- Snapshot-fallback тест должен различать фазы: проверять, что один fallback-вызов произошёл до `compute_fixed_slots()`/до loop и создал ordinary plan, а после-loop telemetry осталась отдельной. Не требовать `count_pending.call_count == 1` за весь `job()`; использовать ordered side effects, phase marker или отдельный seam.
