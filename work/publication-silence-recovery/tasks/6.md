# Task 6: Code Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-reviewing` — [SKILL.md](../../../.claude/skills/code-reviewing/SKILL.md)

## Description

Провести read-only холистический code audit завершённой фичи `publication-silence-recovery`: scheduler primitives, SQLite backlog partition, orchestration/callback integration, tri-state classifier, GitHub Actions integration и согласованность обновлённого Project Knowledge. Предыдущие задачи ревьюились по отдельности; этот аудит проверяет межфайловые контракты и системные инварианты, которые видны только в собранной реализации.

Единственный изменяемый артефакт задачи — JSON-отчёт `work/publication-silence-recovery/logs/audit/code-audit.json`. Код, workflow, тесты и PK не исправлять: найденные проблемы должны получить severity, точное доказательство и actionable recommendation, после чего feature lead запускает отдельный fixer.

Границы смежных аудитов: глубокий security-анализ checkout/secrets/untrusted evidence/логов выполняет Task 7; качество, полнота и фрагментацию тестов оценивает Task 8. В Task 6 эти области рассматриваются только настолько, насколько они доказывают или нарушают архитектурную и cross-file корректность production code.

## What to do

1. Убедиться, что Tasks 3–5 завершены, затем прочитать утверждённые user/tech specs, decisions и все source/config/test/PK файлы из Context Files целиком в их фактическом итоговом состоянии.
2. Определить реальный feature diff и сверить его с Implementation Tasks, Decisions, Shared resources и Acceptance Criteria tech-spec; любое незадокументированное отклонение оценить как потенциальную находку.
3. Пройти все 11 измерений `code-reviewing` skill с приоритетом Architecture, Separation of Concerns, Error Handling, Readability/Maintainability, Cross-file Consistency, Performance и Resource Management.
4. Проверить scheduler contour end-to-end: единый fixed-time policy, атомарную partition query, разделение planned/execution values, точный snapshot fallback, empty-opportunity control flow, callback state-only invariant и отсутствие обхода существующих gates/counters.
5. Проверить watcher contour end-to-end: один classifier source для Python tests и workflow, согласованные tri-state/CLI contracts, bounded failure behavior, отсутствие дублирующей inline policy, корректные outcome gates и независимость host/publication orchestration.
6. Сверить функции, импорты, типы, outputs/env names и error semantics между вызывающими и вызываемыми файлами; отдельно искать copy/paste drift, мёртвые legacy branches, избыточную сложность и ложные комментарии после рефактора.
7. Использовать тесты как evidence фактического поведения и запустить focused regression baseline, но не превращать Task 6 в повторный Test Audit.
8. Записать валидный JSON-отчёт по exact reviewer schema, согласовать status с severity matrix и проверить, что counts совпадают с массивами findings.

- [ ] Status соответствует deterministic matrix: `approved` при 0 critical/major; `approved_with_suggestions` при 0 critical и 1–2 major либо только minor; `changes_required` при ≥1 critical или ≥3 major. Metrics counts совпадают с findings.
- [ ] Ни один implementation, workflow, test или PK file не изменён Task 6; единственные допустимые записи — audit report и стандартный post-completion summary в `decisions.md`.

## Details

**Files:**
- `work/publication-silence-recovery/logs/audit/code-audit.json` — новый единственный audit deliverable. Создать `logs/audit/` при необходимости; писать plain JSON без Markdown fences и без копирования больших code excerpts.
- Все остальные перечисленные файлы — read-only evidence. На момент декомпозиции `publication_watch.py`, `tests/test_publication_watch.py` и `tests/test_uptime_workflow.py` ещё отсутствуют; зависимые Tasks 2/4 обязаны создать их до запуска аудита.

**Dependencies:** Task 3 завершает scheduler integration, Task 4 — watcher workflow, Task 5 — PK consistency. Аудит начинается только после их reviews/fixes. Он может выполняться параллельно с Security Audit и Test Audit, потому что все три создают разные report files и не меняют implementation.

**Report schema:** использовать exact JSON contract из `.claude/agents/code-reviewer.md`:
- `status`: `approved | approved_with_suggestions | changes_required`.
- `summary`: 2–3 предложения с общим verdict и наиболее важным cross-file выводом.
- `criticalIssues[]`: `file`, `line`, `severity: critical`, `category`, `issue`, `impact`, `recommendation`.
- `suggestions[]`: `file`, `line`, `severity: major|minor`, `category`, `suggestion`, `benefit`, `optional` (`false` для обязательного major, `true` для optional improvements).
- `metrics`: `filesReviewed`, три severity counts и `testCoverageAssessment: adequate|insufficient|excellent`.

**Edge cases:** snapshot/callback commit на границе; held+deferred dual gate; empty first opportunity; ordinary queue without review backlog; aggregate fallback itself failing; callback immediately after 19:30; exactly 1 MiB/oversized/recursive evidence; failed or partial checkout; unexpected classifier stdout; open и closed publication alarm при `inconclusive`; host-down одновременно с publication state.

**Implementation hints:**
- Начать с tech-spec Decisions/Shared resources, затем пройти producer→consumer chains: scheduling helper → `job()`, repository tuple → caller, callbacks → SQL gates, classifier CLI → workflow outputs → alarm branch.
- Читать полные функции и соседние control-flow branches, а не только feature diff: ошибка часто находится в старом caller/counter/comment, который новый helper изменил семантически.
- Для каждого import/call/output проверить реальное определение и exact signature/name. Cross-file mismatch, который даёт runtime failure, классифицировать `critical` по reviewer contract.
- Отличать accepted complexity от accidental complexity: три fixed times, tri-state verdict и один aggregate query являются approved design; новый generic scheduler, service или persistence layer не предлагать без доказанной необходимости.
- Не дублировать Security/Test Audit. Если проблема одновременно security/test-related и ломает production correctness, включить её с узким cross-file impact и сослаться в summary на смежный аудит.
- У finding должен быть воспроизводимый code/config evidence и точная строка; vague preferences без material impact не добавлять.
- Если findings отсутствуют, оставить массивы пустыми, counts нулевыми и явно подтвердить ключевые инварианты в summary; не придумывать suggestions ради заполнения отчёта.
