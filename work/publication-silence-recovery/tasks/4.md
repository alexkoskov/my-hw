# Task 4: Tri-state workflow integration

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [SKILL.md](../../../.claude/skills/deploy-pipeline/SKILL.md)

## Description

Заменить встроенную Python-классификацию публикаций в GitHub Actions workflow на протестированный `publication_watch.py` из Task 2 и провести tri-state verdict до существующего контура alert/recovery. Неубедительные данные, ошибка checkout или недоступный classifier должны сохранять текущее состояние publication alarm: не открывать новый issue/alert и не закрывать уже открытый.

При этом внешний watch остаётся двумя независимыми сигналами. SSH greeting по-прежнему проверяет доступность хоста и управляет только host alarm, а host-down подавляет publication transition. Telegraph secret принадлежит только fetch-step и не должен становиться доступным checkout-коду или repository classifier.

Task 4 изменяет только `.github/workflows/uptime.yml`, `tests/test_uptime_workflow.py` и task-unique артефакты в `work/publication-silence-recovery/logs/working/task-4/`. Общие `decisions.md`, `user-spec.md`, `tech-spec.md` и Project Knowledge остаются read-only: зависимая Task 5 единолично консолидирует итоги Tasks 1–5 и синхронизирует PK после завершения параллельных Tasks 3/4.

## What to do

1. Сначала создать offline static contract tests для целевого workflow и убедиться, что они падают на текущем inline boolean-контракте.
2. Сохранить SSH greeting probe независимым от checkout, Telegraph fetch и classifier failures.
3. Добавить immutable checkout default branch после SSH-пробы: официальный `actions/checkout` по полному SHA, с явным `id`, выключенным persistence credentials, минимальной depth и безопасным `continue-on-error`.
4. Разделить Telegraph fetch и classification на разные steps. Fetch-step единолично получает secret, сохраняет только bounded response evidence в фиксированный файл runner temp и не раскрывает token или body через logs/outputs.
5. Запускать `publication_watch.py` только после успешного checkout. Missing/partial checkout, missing helper, failed/oversized evidence, ошибка процесса и unexpected stdout должны давать `inconclusive` без исполнения repository code при неуспешном checkout.
6. Передавать дальше только допустимый `pub_state` и заменить boolean publication branch на матрицу: `stale` открывает alarm, `fresh` закрывает существующий alarm, `inconclusive` ничего не меняет.
7. Обновить устаревшие workflow-комментарии, связанные с отсутствием checkout и boolean `pub_down`, не меняя cadence, permissions, тексты алертов, issue-dedup или Telegram-first semantics.
8. Прогнать focused workflow/classifier tests локально, без workflow dispatch, сети и production-действий.
9. Применить явный task-scope override к обычной documentation-фазе `deploy-pipeline` skill: в Task 4 не обновлять `architecture.md`, `patterns.md`, `deployment.md` или другие Project Knowledge файлы. Все PK-изменения от scheduler/watcher contours отложены до зависимой Task 5, которая единолично владеет этими файлами после завершения Tasks 3–4.
10. После implementation/review записать task-unique handoff `work/publication-silence-recovery/logs/working/task-4/completion-summary.md`: concise summary, commit SHA/link (либо явное `not created`), ссылки на все reviewer rounds и proposed deviation/status. Task 5 читает этот отчёт и единолично переносит краткий итог Tasks 1–5 в `decisions.md`.

## Acceptance Criteria

- [ ] `.github/workflows/uptime.yml` больше не содержит второй реализации date/freshness policy и вызывает CLI из `publication_watch.py`, созданный Task 2.
- [ ] SSH greeting probe остаётся самостоятельным первым внешним сигналом; checkout, fetch или classification failure не препятствуют формированию host verdict и host alarm transition.
- [ ] Checkout использует `actions/checkout@11d5960a326750d5838078e36cf38b85af677262`, имеет явный `id`, `ref: ${{ github.event.repository.default_branch }}`, `persist-credentials: false`, `fetch-depth: 1` и `continue-on-error: true`.
- [ ] Repository classifier исполняется только при успешном outcome checkout-step; при failed/partial checkout workspace code не импортируется и publication state становится `inconclusive`.
- [ ] Только Telegraph fetch-step получает `${{ secrets.TELEGRAPH_ACCESS_TOKEN }}`. Token не записывается в evidence, logs или step outputs и не присутствует в env classifier-step.
- [ ] Fetch-step передаёт только API response через фиксированный runner-temporary файл, отклоняет evidence больше 1 MiB до classification и не переносит raw JSON через command line или GitHub output.
- [ ] Missing secret, curl/API failure, empty/oversized evidence, отсутствующий helper, classifier exception и stdout вне `fresh|stale|inconclusive` безопасно приводятся к `inconclusive`.
- [ ] Verdict/alert contour передаёт tri-state без сведения к boolean: `stale -> raise`, `fresh -> resolve`, `inconclusive -> no-op` независимо от того, открыт publication issue или закрыт.
- [ ] При `host_down=true` publication transition полностью подавлена; при здоровом хосте host alarm recovery и publication state обрабатываются раздельно.
- [ ] Существующие cadence, concurrency, least-privilege permissions, alert titles/text, Telegram-first delivery и best-effort GitHub issue dedup не ухудшены; устаревший комментарий «job has no actions/checkout» исправлен.
- [ ] `tests/test_uptime_workflow.py` проверяет production YAML offline и не выполняет Actions, `curl`, SSH, `gh`, Telegram или Telegraph запросы.
- [ ] Изменение workflow начинает действовать только после будущего merge в default branch; эта задача не выполняет dispatch, merge, server rebuild/restart или runtime deploy.
- [ ] Scope override соблюдён: Task 4 изменяет только `.github/workflows/uptime.yml`, `tests/test_uptime_workflow.py` и task-unique `logs/working/task-4/` review/handoff artifacts; documentation-update phase из `deploy-pipeline` skill намеренно отложена до Task 5.
- [ ] `decisions.md`, `user-spec.md`, `tech-spec.md`, Project Knowledge, `publication_watch.py`, CI и остальные context files не изменены Task 4.
- [ ] `logs/working/task-4/completion-summary.md` содержит 1–3 предложения итога, commit SHA/link или явное отсутствие commit, ссылки на каждый reviewer JSON round и proposed deviation/status для Task 5; Task 4 сам не пишет общий decisions log.
- [ ] Любое material spec deviation останавливает completion и эскалируется feature lead/user через handoff; approved `user-spec.md`/`tech-spec.md` не редактируются в этой задаче.

## Details

**Files:**
- `.github/workflows/uptime.yml` — сейчас SSH probe работает отдельно, но publication probe содержит inline Python, сводит fresh и inconclusive к `ok=true`, а alert-step получает boolean `PUB_DOWN`; заменить только publication evidence/classification/verdict integration и связанные комментарии.
- `tests/test_uptime_workflow.py` — новый offline structural suite; файла сейчас нет.
- `publication_watch.py` — отсутствует на момент декомпозиции и является результатом обязательной Task 2; перед реализацией Task 4 использовать фактический CLI/stdin/stdout contract, а не копировать его логику в YAML.
- `.github/workflows/ci.yml` — workflow/YAML или Python change запускает полный `tests/` suite на Python 3.13; в этой задаче файл не менять.
- `work/publication-silence-recovery/logs/working/task-4/completion-summary.md` — task-unique handoff для Task 5: concise summary, commit reference, linked review rounds и deviation proposal/status. Это не общий feature decision log.
- Все остальные Context Files, включая `decisions.md`, approved specs, Project Knowledge, `publication_watch.py` и CI workflow, используются только для чтения/reality check.

**Dependencies:** Task 2 должна быть завершена и её focused tests должны быть зелёными. Новые Python/GitHub Actions packages не добавляются. Единственная новая workflow dependency — официальный `actions/checkout` v4.4.0, закреплённый полным SHA из tech-spec. Tasks 3 и 4 выполняются параллельно и не имеют общих mutable files; Task 5 зависит от обеих, читает их task-unique handoff/review artifacts и является единственным writer `decisions.md` для Tasks 1–5.

**Task-scope override:** `deploy-pipeline` skill обычно требует синхронно обновить `architecture.md`, `patterns.md` и `deployment.md`. Для этой декомпозиции этот шаг явно не принадлежит Task 4: зависимая Task 5 запускается после Tasks 3/4, сверяет уже фактическую реализацию обоих contours и является единственным владельцем всех трёх PK-файлов. Поэтому implementation files Task 4 ограничены `.github/workflows/uptime.yml` и `tests/test_uptime_workflow.py`, а дополнительные записи — только task-unique review/handoff artifacts под `logs/working/task-4/`; PK и shared feature docs здесь только read-only context.

**Edge cases:** отсутствующий GitHub secret; Telegraph timeout или empty body; response ровно 1 MiB и больше лимита; checkout с failure outcome; helper отсутствует после partial checkout; CLI падает или печатает пустую/лишнюю строку; publication issue уже открыт или закрыт при `inconclusive`; host down одновременно с `fresh`/`stale`; degraded `gh` issue bookkeeping.

**Implementation hints:**
- Структурные тесты должны извлекать именованные step blocks/branches и проверять содержательный контракт, не привязываясь к номерам строк или полному byte-equality YAML.
- Оставить `${{ }}` expressions вне shell interpolation для значений, которые доходят до `run:`: переносить собственные verdict outputs через `env`, как в текущем hardened alert-step.
- Использовать один стабильный checkout `id` и ссылаться на его `.outcome`; `.conclusion`/пустой output не должны ошибочно разрешать запуск workspace code.
- Не передавать Telegraph body через env, argv или `$GITHUB_OUTPUT`. Runner-temp file является единственной границей между fetch и classifier steps.
- Сначала устанавливать `inconclusive` как безопасный default, затем заменять его только на точный допустимый stdout classifier-а; unexpected output не считать `fresh` или `stale`.
- Сохранить `GH_REPO: ${{ github.repository }}`: checkout credentials намеренно не persist-ятся, а явный repo нужен `gh issue` независимо от git remote. Обновить только ставшее ложным объяснение «checkout отсутствует».
- Не менять disarmed deploy workflows и не добавлять deploy job: merge этого workflow-контра активирует watcher в default branch, но не разворачивает runtime bot на VPS.
- Если workflow integration требует material deviation от approved spec, не адаптировать spec и не продолжать молча: записать proposed deviation, impact и blocker в `completion-summary.md`, остановить completion и эскалировать feature lead/user. Non-material implementation note также передаётся Task 5 через этот task-unique report.
