## Description

Обновить Project Knowledge после завершения runtime scheduler contour (Task 3) и external watcher contour (Task 4), чтобы документация снова описывала фактическую production-архитектуру. Зафиксировать условные release opportunities для reviewable backlog, tri-state publication watch и разные границы активации/отката этих двух изменений.

Каждый факт должен жить в одном каноническом месте: scheduler/data-flow — в `architecture.md`, уникальные правила безопасного изменения scheduler — в `patterns.md`, operational activation, secrets, monitoring и rollback — в `deployment.md`. Не копировать function-level реализацию, тестовые матрицы или tech-spec целиком; использовать ссылки между PK-файлами.

## What to do

1. После завершения Tasks 3 и 4 перечитать фактические `news_bot.py` и `.github/workflows/uptime.yml`, а также утверждённые user/tech specs; не документировать предполагаемые имена или поведение из незавершённого плана.
2. В `architecture.md` обновить project structure, scheduler Data Flow и queue-state описание: атомарный backlog snapshot, отличие operator-facing planned slots от conditional execution opportunities, свежий `list_pending()` на каждом времени и callbacks как state-only операции.
3. В `patterns.md` заменить устаревший паттерн `count_deferred()`/over-allocation/early `break` на фактический release-opportunity invariant, сохранив архитектурные детали только по ссылке на canonical Data Flow.
4. В `deployment.md` описать tri-state watcher (`fresh`, `stale`, `inconclusive`), immutable default-branch checkout, secret isolation, no-op semantics для inconclusive и независимость SSH alarm.
5. В `deployment.md` явно развести activation и rollback contours: workflow-код начинает действовать после merge в default branch без server restart, runtime scheduler — только после отдельного ручного Docker rollout вне 10:00–20:00 МСК; откатываются они независимо.
6. Удалить или исправить ставшие ложными формулировки и line-number claims вокруг boolean `pub_down`, inline classifier, skipped-as-healthy, `count_pending + count_deferred` и «empty queue всегда завершает loop».
7. Проверить отсутствие противоречий и ненужного дублирования между тремя PK-файлами, затем выполнить concrete offline verification.

## Acceptance Criteria

- [ ] `architecture.md` называет фактические scheduler/watch components и не ссылается на отсутствующий или устаревший production path.
- [ ] Canonical scheduler Data Flow описывает один атомарный `(publishable, deferred, held)` snapshot и взаимоисключающие queue categories без новой таблицы или schema migration.
- [ ] `architecture.md` явно различает `planned_slots`/carry-over для publishable rows и bounded execution/release opportunities для deferred/held rows; пустая release-check не считается запланированным или опубликованным постом.
- [ ] Документация сохраняет single-publisher invariant: каждый retained time заново читает SQLite, callbacks только снимают/удаляют gates и никогда не публикуют; решение после 19:30 ждёт следующего дня.
- [ ] `patterns.md` больше не утверждает, что `count_deferred()` покупает количество слотов или что безусловный `break` на первом пустом read безопасен; вместо этого зафиксирован проектный invariant conditional release opportunities с ссылкой на `architecture.md`.
- [ ] `deployment.md` описывает watcher как tri-state: `stale` открывает publication alarm, `fresh` закрывает существующий, `inconclusive` не меняет открытое или закрытое состояние; host-down по-прежнему подавляет publication transition.
- [ ] Operational docs объясняют, что SSH probe остаётся независимым, classifier исполняется только после immutable explicit-default-branch checkout, а Telegraph secret доступен только fetch-step и не передаётся repository code.
- [ ] Missing secret, API/evidence/checkout/classifier failure больше не документированы как healthy recovery или boolean skip; их фактический результат — publication `inconclusive` при сохранённом host verdict.
- [ ] Activation boundary сформулирована однозначно: merge workflow change в default branch активирует watcher без VPS rebuild, но scheduler code достигает единственного production container только после отдельного user-run rollout вне no-deploy window.
- [ ] Rollback guidance разделяет default-branch workflow revert и runtime Docker rollback; задача не заявляет, что merge автоматически развернул runtime bot.
- [ ] Между `architecture.md`, `patterns.md` и `deployment.md` нет трёх копий алгоритма, тестовой boundary matrix или function-level псевдокода; подробности находятся в соответствующем каноническом разделе и связаны ссылками.
- [ ] Все изменённые ссылки, имена модулей/состояний и operational claims сверены с фактическими файлами после Tasks 3–4; whitespace/diff checks и focused implementation tests проходят offline.

## Details

**Files:**
- `.claude/skills/project-knowledge/references/architecture.md` — текущий Data Flow всё ещё описывает `compute_fixed_slots(count_pending())`, исключает held/deferred rows из slot computation и не содержит нового `publication_watch.py`; привести component tree, scheduler steps и queue partition к фактической реализации Task 3.
- `.claude/skills/project-knowledge/references/patterns.md` — текущий hold-cap раздел утверждает, что `count_deferred()` добавляется в sizing и что over-allocation безопасен из-за немедленного `break` на empty queue; заменить этот уже опровергнутый production-инцидентом паттерн, не дублируя полный алгоритм из Architecture.
- `.claude/skills/project-knowledge/references/deployment.md` — текущий External uptime watch описывает boolean/skipped behavior и старую диагностику inline classifier-а; обновить tri-state, checkout, secret boundary, activation и independent rollback guidance.

**Dependencies:** Tasks 3 и 4 должны быть завершены и reviewed до начала этой задачи. Новые документы, зависимости, env vars, secrets, migrations или deployment jobs не добавляются.

**Edge cases:** фактические имена после implementation могут отличаться от draft tech-spec; held row может оставлять job живым до последней фиксированной возможности; release после 19:30 переносится на следующий день; `inconclusive` должен сохранять как открытый, так и закрытый publication alarm; workflow и runtime активируются в разное время; line numbers в старых docs могут уже не совпадать после code changes.

**Implementation hints:**
- Следовать documentation-writing principle «что существует, что делает и почему»: не вставлять кодовые блоки, SQL, shell branches, псевдокод или полную test matrix в PK.
- В Architecture дать один краткий canonical scheduler flow и high-level queue partition; в Patterns оставить только опасные для будущего изменения инварианты и ссылку на Architecture.
- В Deployment сохранить operational детали: default-branch activation, GitHub secret ownership, independent SSH/publication signals, future verification и два rollback contours.
- Не описывать `inconclusive` как «успешно», «пропущено» или `fresh`: это неизвестность, которая намеренно не меняет durable issue state.
- Сверить claims с реализованными именами и тестами, но избегать хрупких line-number references для недавно изменённых участков.
- Не изменять README/CLAUDE.md, user-spec, tech-spec или implementation files в этой задаче, если фактическая реализация не выявила spec deviation; deviation сначала зафиксировать по Post-completion rules.
