## Description

Обновить Project Knowledge после завершения runtime scheduler contour (Task 3) и external watcher contour (Task 4), чтобы документация снова описывала фактическую production-архитектуру, и последовательно закрыть feature handoff для Tasks 1–5 в `decisions.md`. Зафиксировать условные release opportunities для reviewable backlog, tri-state publication watch и разные границы активации/отката этих двух изменений.

Каждый факт должен жить в одном каноническом месте: scheduler/data-flow — в `architecture.md`, уникальные правила безопасного изменения scheduler — в `patterns.md`, operational activation, secrets, monitoring и rollback — в `deployment.md`, а ordered implementation/review handoff — в `decisions.md`. Эти четыре файла образуют один связный documentation/handoff outcome: три PK-представления объясняют текущее устройство проекта, а один последовательный feature log связывает их с конкретными commits и review artifacts Tasks 1–5. Это не набор несвязанных implementation-правок. Не копировать function-level реализацию, тестовые матрицы или tech-spec целиком; использовать ссылки между PK-файлами и краткие ссылки из feature log.

2. Перечитать фактические реализации foundations из Tasks 1/2 (`compute_publish_slots.py`, `pending_articles_repo.py`, `publication_watch.py`) и integrations из Tasks 3/4 (`news_bot.py`, `.github/workflows/uptime.yml`), а также утверждённые user/tech specs; не документировать предполагаемые имена или поведение из незавершённого плана.
3. Провалидировать каждый handoff по exact shared schema: top-level fields ровно `task`, `status`, `summary`, `commit`, `reviews`, `verification`, `proposedDeviation`; номер `task` совпадает с каталогом; `status` равен `done` или `blocked`; `summary` содержит 1–3 предложения; `commit` — SHA или `null`; `reviews` состоит из объектов `reviewer`/`round`/`status`/`report-path`; `verification` — из объектов `command`/`result`; `proposedDeviation` — `null` либо объект `reason`/`impact`/`decision-needed`.

Любой missing/malformed handoff, отсутствующий reviewer report по `report-path` или `status: blocked` является blocker: записать в `decisions.md` только краткий linked blocker/deviation status, отметить Task 5 blocked и эскалировать feature lead. 5. Только если все четыре handoff валидны и имеют `status: done`, в `architecture.md` обновить project structure, scheduler Data Flow и queue-state описание: фактический fixed-time helper, атомарный backlog aggregate и порядок его категорий, отличие operator-facing planned slots от conditional execution opportunities, свежий `list_pending()` на каждом времени и callbacks как state-only операции.
6. В `patterns.md` заменить устаревший паттерн `count_deferred()`/over-allocation/early `break` на фактический release-opportunity invariant, сохранив архитектурные детали только по ссылке на canonical Data Flow.
7. В `deployment.md` описать фактический classifier/CLI contract из `publication_watch.py`, tri-state watcher (`fresh`, `stale`, `inconclusive`), immutable default-branch checkout, secret isolation, no-op semantics для inconclusive и независимость SSH alarm.
8. В `deployment.md` явно развести activation и rollback contours: workflow-код начинает действовать после merge в default branch без server restart, runtime scheduler — только после отдельного ручного Docker rollout вне 10:00–20:00 МСК; откатываются они независимо.
9. Удалить или исправить ставшие ложными формулировки и line-number claims вокруг boolean `pub_down`, inline classifier, skipped-as-healthy, `count_pending + count_deferred` и «empty queue всегда завершает loop».
10. В `decisions.md` последовательно добавить короткие entries для принятых Tasks 1, 2, 3 и 4 только из schema-valid handoffs: `summary`, `commit` и ссылки/статусы финальных reviewer reports из `reviews`, без переноса verification dumps, full findings или других handoff fields. После проверки и собственного review добавить таким же кратким форматом отдельную запись Task 5.
11. Проверить отсутствие противоречий и ненужного дублирования между тремя PK-файлами и feature handoff log, затем выполнить concrete offline verification.

## Acceptance Criteria

- [ ] `architecture.md` называет фактические scheduler/watch components и не ссылается на отсутствующий или устаревший production path.
- [ ] Canonical scheduler Data Flow описывает один атомарный `(publishable, deferred, held)` snapshot и взаимоисключающие queue categories без новой таблицы или schema migration.
- [ ] `architecture.md` явно различает `planned_slots`/carry-over для publishable rows и bounded execution/release opportunities для deferred/held rows; пустая release-check не считается запланированным или опубликованным постом.
- [ ] Документация сохраняет single-publisher invariant: каждый retained time заново читает SQLite, callbacks только снимают/удаляют gates и никогда не публикуют; решение после 19:30 ждёт следующего дня.
- [ ] `patterns.md` больше не утверждает, что `count_deferred()` покупает количество слотов или что безусловный `break` на первом пустом read безопасен; вместо этого зафиксирован проектный invariant conditional release opportunities с ссылкой на `architecture.md`.
- [ ] `deployment.md` описывает watcher как tri-state: `stale` открывает publication alarm, `fresh` закрывает существующий, `inconclusive` не меняет открытое или закрытое состояние; host-down по-прежнему подавляет publication transition.

- `.claude/skills/project-knowledge/references/deployment.md` — текущий External uptime watch описывает boolean/skipped behavior и старую диагностику inline classifier-а; обновить tri-state, checkout, secret boundary, activation и independent rollback guidance.
- `work/publication-silence-recovery/decisions.md` — единственный последовательный feature handoff log: добавить краткие linked entries Tasks 1–4 из их task-unique artifacts, затем entry Task 5 после собственного verification/review.

**Four-file cohesion:** это одна документационная передача результата, а не четыре независимых изменения. `architecture.md`, `patterns.md` и `deployment.md` дают три канонических представления одной завершённой feature (structure/data flow, change invariants, operations), а `decisions.md` сохраняет их проверяемую последовательность происхождения через summary, commits и reviewer links Tasks 1–5.

**Exact write boundary:** deliverable writes разрешены ровно в `.claude/skills/project-knowledge/references/architecture.md`, `.claude/skills/project-knowledge/references/patterns.md`, `.claude/skills/project-knowledge/references/deployment.md` и `work/publication-silence-recovery/decisions.md`. Для обязательного review разрешён только task-unique process artifact `work/publication-silence-recovery/logs/working/task-5/code-reviewer-{round}.json`. Все task-1…4 artifacts, implementation/workflow/tests, `user-spec.md`, `tech-spec.md`, README/CLAUDE и прочие файлы — строго read-only.

**Exact handoff consumer:** принимать только `work/publication-silence-recovery/logs/working/task-1/completion-summary.json`, `work/publication-silence-recovery/logs/working/task-2/completion-summary.json`, `work/publication-silence-recovery/logs/working/task-3/completion-summary.json` и `work/publication-silence-recovery/logs/working/task-4/completion-summary.json`. Каждый файл обязан иметь ровно top-level поля `task`, `status`, `summary`, `commit`, `reviews`, `verification`, `proposedDeviation`, правильный task number и exact nested object fields из tech-spec. После schema validation прочитать каждый reviewer JSON по `reviews[].report-path`. Любой missing/malformed/blocked handoff или missing report — blocker; альтернативный filename/schema не угадывать и не нормализовать.

**Ordered handoff:** только когда все четыре handoff валидны и имеют `status: done`, добавить в `decisions.md` для Tasks 1–4 ровно краткий summary, commit SHA и final review links/status, сохраняя порядок 1→4; после собственного review добавить Task 5 тем же форматом. Не переносить verification array, full findings или остальные process payloads. При blocker записать только concise linked blocker status, отметить Task 5 blocked и эскалировать feature lead вместо изменения approved specs или объявления неподтверждённой реализации canonical.

**Dependencies:** Tasks 1 и 2 должны предоставить reviewed foundation implementations, а Tasks 3 и 4 — завершённые integrations; все четыре фактических результата перечитываются до первой PK-правки. Формально Task 5 зависит от Tasks 3/4, которые уже зависят от 1/2, но это не отменяет прямую reality-check сверку foundation-файлов. Новые документы, зависимости, env vars, secrets, migrations или deployment jobs не добавляются.

**Edge cases:** фактические имена после implementation могут отличаться от draft tech-spec; held row может оставлять job живым до последней фиксированной возможности; release после 19:30 переносится на следующий день; `inconclusive` должен сохранять как открытый, так и закрытый publication alarm; workflow и runtime активируются в разное время; line numbers в старых docs могут уже не совпадать после code changes.

**Implementation hints:**
- Следовать documentation-writing principle «что существует, что делает и почему»: не вставлять кодовые блоки, SQL, shell branches, псевдокод или полную test matrix в PK.
- В Architecture дать один краткий canonical scheduler flow и high-level queue partition; в Patterns оставить только опасные для будущего изменения инварианты и ссылку на Architecture.
- В Deployment сохранить operational детали: default-branch activation, GitHub secret ownership, independent SSH/publication signals, future verification и два rollback contours.
- Не описывать `inconclusive` как «успешно», «пропущено» или `fresh`: это неизвестность, которая намеренно не меняет durable issue state.
- Сверить claims с реализованными именами и тестами, но избегать хрупких line-number references для недавно изменённых участков.
- Task 5 является единственным владельцем трёх PK-файлов и `decisions.md` после Tasks 3/4. Не изменять README/CLAUDE.md, approved user-spec/tech-spec, implementation/workflow/test files или любую другую документацию; при материальном deviation зафиксировать linked blocker, остановить задачу и эскалировать отдельное решение.
