## Description

Полнофункциональный security-аудит фичи `mattel-parser-rewrite` по результатам Task 01 (rewrite-parser). Это AUDIT-задача: security-auditor ЧИТАЕТ код и пишет JSON-отчёт; код НЕ модифицируется. Если найдены критичные/major findings — оркестратор `feature-execution` развернёт отдельный fix-таск.

Аудит охватывает: основной модуль `mattel_news_source.py` (ядро security-контролов), новый builder-модуль `tests/fixtures/mattel_flight_builder.py` (placeholder-defaults / supply-chain), тестовый файл `tests/test_mattel_news_source.py` (наличие `TestSsrfGuard` и тест-покрытие 8 security ACs из tech-spec), и `news_bot.py` (verifies module-level log-suppression loops at `news_bot.py:184` and `:227` — sets `WARNING` on `httpx`/`httpcore`/`urllib3`/`requests` и attaches `_TokenRedactingFilter` — НЕ тронуты переписанным Mattel-модулем; Decision 8 §6). ## Acceptance Criteria

Manual security-review checklist (каждый пункт — отдельная строка отчёта; обязательна evidence-цитата для каждого pass/fail; пункты соответствуют 8 Security ACs tech-spec + 3 кросс-проверки):

- [ ] **SSRF guard active (Decision 8 §1 / ES10)** — `fetch_mattel_article` валидирует `link.startswith(ARTICLE_URL_PREFIX)` ДО любого HTTP-вызова; mismatch → `MattelNewsError("invalid article link prefix")` → notifier с сообщением, которое НЕ эхо-ит `link`; функция возвращает `None`. Нет кодовой ветки, где `requests.get(link, ...)` вызывается до этой проверки.
- [ ] **Linear-time regex (Decision 8 §2)** — `_FLIGHT_PUSH_RE` использует character-class form `(?:[^"\\\\]|\\\\.)*` (или эквивалент); НЕТ `(.+?)` lazy quantifier'а; regex JS-string-literal-correct против escaped `\"`. Скомпилирован один раз на module level.
- [ ] **JSON depth/recursion guard (Decision 8 §3)** — ВСЕ `json.loads` вызовы в `mattel_news_source.py` обёрнуты в `try / except (json.JSONDecodeError, RecursionError, ValueError)` → ES5-ветка (notifier + return `[]` для listing / `None` для article). Нет голых `json.loads` вне except-блока.
- [ ] **Hex-length cap (Decision 8 §4 / ES9c)** — `_resolve_body_html` парсит hex length и отвергает значения > `MAX_RESPONSE_SIZE` (returns `""` → content-empty path); attacker-supplied `int("ffffffff", 16)` не может вызвать OOM-slice.
- [ ] **Bracket-match safety (Decision 8 §4 / ES4)** — `_extract_listing_entries` bracket-match depth-AND-string-aware (skips inside `"..."` runs и `\\` escapes), max-iter cap = `len(unescaped)`; EOF без depth-zero → ES4 (notifier + return `[]`). Нет неограниченного while-loop без cap'а.
- [ ] **Notifier sanitisation (Decision 8 §5)** — все вызовы `_notify(notifier, msg)` форматируют ТОЛЬКО exception type + safe scalars (sizes, anchor names, slugs). Голый `str(exc)` НЕ передаётся в notifier message. Нет ветки, где `f"...: {exc}"` или `f"...: {e}"` попадает в notifier (исключение: `<type>` через `type(exc).__name__` — это допустимо).
- [ ] **`allow_redirects=False` (Decision 8 §6)** — оба `requests.get(...)` вызова в модуле (listing path и article path) передают `allow_redirects=False`. Никаких `requests.get(url)` без этого параметра.
- [ ] **Log-suppression preserved (Decision 8 §6)** — module-level log-suppression loops at `news_bot.py:184` and `:227` (sets `WARNING` on `httpx`/`httpcore`/`urllib3`/`requests` и attaches `_TokenRedactingFilter`) НЕ тронуты переписанным `mattel_news_source.py` Task 01: `httpx`, `httpcore`, `urllib3`, `requests` loggers всё ещё подавлены до `WARNING` и `_TokenRedactingFilter` всё ещё прикреплён. `mattel_news_source.py` не вызывает `logging.basicConfig()` / `logging.getLogger("httpx").setLevel(...)` / иные глобальные log-config мутации, которые могли бы перекрыть эти module-level loops.
- [ ] **Builder placeholder-only defaults (round-2 finding #1, A06)** — default arguments `_make_flight_listing` / `_make_flight_article` в `tests/fixtures/mattel_flight_builder.py` используют ТОЛЬКО placeholder-значения (`example.com`, `placeholder.invalid`, `fake-` / `FAKE_` префиксы или явно-синтетические детерминированные строки). Нет реальных `corporate.mattel.com` URL, реальных Contentstack CDN URL, или реальных Mattel-handle паттернов (`hot-wheels-[a-z0-9]{3,}`). Реальные URL допустимы только когда caller явно их передаёт.
- [ ] **TestSsrfGuard test coverage** — в `tests/test_mattel_news_source.py` существует класс `TestSsrfGuard` (или эквивалент) с тестом, который передаёт evil-link (например, `https://evil.example.com/news/foo`) в `fetch_mattel_article` и проверяет: (а) функция возвращает `None`; (б) notifier вызван; (в) сообщение notifier'а НЕ содержит саму malicious-URL подстроку. Это поведенческая верификация AC «SSRF guard rejects link…».
- [ ] **Audit report written** — JSON-отчёт записан по адресу `/workspaces/debian-2/my-hw/work/mattel-parser-rewrite/logs/tasks/security-audit-report.json` со структурой из «What to do» п. 8. Содержит: round1_closure_verification (8 entries для round-1 #1–#8; для каждого закрытого finding — verification в коде; для любого `not_addressed`-entry — отметка `closure_rejected` с rationale-цитатой, без code-verification), полный checklist (11 пунктов), owasp_sweep (минимум A01/A03/A05/A06/A09/A10), additional_findings (даже если пустой массив), summary 1–3 предложения.

Если статус — `closed` (round-2 явно закрыла finding), записать `verdict`: `honored` (код реализует обещание спека), `partial` (часть реализована), `not-honored` (код противоречит обещанию). Если статус — `not_addressed` (round-2 явно отвергла closure / оставила открытым), записать `verdict: closure_rejected` + `rationale` (цитата из round-2 / tech-spec обоснования) и НЕ выполнять code-verification для этого entry — фиксируем фактическое состояние, не пытаемся «закрыть» rejected-finding. Round-1 finding по placeholder-defaults — даже если в round-2 closure статус `not_addressed`, отдельно покрыт checklist-пунктом 9 (там верифицируем код напрямую через прочтение builder-модуля).
- Для OWASP sweep — каждая категория получает короткий verdict без длинного evidence. Finding'и идут в `additional_findings`, не в sweep.
