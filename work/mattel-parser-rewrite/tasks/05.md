## Description

Финальная Wave фичи `mattel-parser-rewrite`: pre-deploy приёмочное тестирование. Это QA-задача: агент ЗАПУСКАЕТ команды (тестовый набор + smoke-команды), верифицирует результаты против AC-чеклиста (AC1–AC13 user-spec + tech-spec security ACs из Decision 8 + tech-spec verification ACs), консолидирует выводы трёх audit-отчётов из Wave 2 (Task 02 code-audit, Task 03 security-audit, Task 04 test-audit) и пишет финальный QA-отчёт в JSON.

Цель — независимое подтверждение, что код, написанный в Task 01 (rewrite-parser), готов к деплою: все автоматизируемые AC покрыты прохождением тестов; все non-automatable AC (например, AC13 live smoke при недоступности сети, или операторские post-deploy наблюдения за 7-дневным окном) явно помечены `deferred-to-post-deploy` с причиной.

Этот таск НЕ модифицирует код, тесты, конфиги или документацию. Если хотя бы один шаг QA-чеклиста падает — отчёт пишется со статусом `fail`, перечисляет, что нужно починить, и оркестратор `feature-execution` разворачивает fix-таск. Если все шаги pass (или явно deferred) — статус `pass` (или `pass-with-deferrals`), фича готова к operator-side `bash deploy.sh`.

**Edge cases / decision boundaries:**
- **Network unavailable во время Step 4.** Mattel вернул 5xx, или DNS resolve fail, или connection timeout. Это AC13 — допустимо `deferred-to-post-deploy` с конкретной operator-side инструкцией, как повторить smoke на VPS после деплоя. Не fail.
- **HW=0 в листинге Step 4.** Это нормальный сценарий — Mattel редко выпускает HW-посты, gaps по неделям. `fetch_mattel_news()` возвращает `[]`, STDERR clean. Step 4 = pass, Step 5 = not-applicable (нет ссылки для article smoke).
- **Snapshot файлы `/tmp/mattel_*.html` отсутствуют.** Это нормально для CI / fresh dev environment. Step 6 = not-applicable, не fail. Anti-drift coverage в этом случае обеспечивается skip-guarded `pytest`-тестами из Decision 7 (которые в Step 1 либо запустились, либо skipped — в любом случае Step 1 green).
- **Audit-gate fail.** Один из трёх audit-отчётов = `fail` или содержит critical finding. Step 1–6 не запускаем (нет смысла QA-ить known-broken implementation). Пишем QA-отчёт = `fail` с blocker'ом → ссылка на failing audit report. Оркестратор fix-таск разворачивает по failing audit report'у.
- **`pass-with-findings` в audit-отчётах с non-critical severity.** Допустимо — продолжаем к Step 1–6. Финальный QA-status может быть `pass-with-deferrals` если есть defer'ы, или `pass` если все green.
- **STDERR содержит INFO-логи (не parsing-error).** Это нормально — `httpx`/`urllib3`/`httpcore` могут писать debug в stderr. Проверка — на конкретные строки `Mattel news parsing error`, `Mattel article fetch error`, `Mattel news HTTP error` (по error matrix ES1–ES10), не на сам факт наличия stderr-вывода.
- **Test count незначительно отличается от 32+3=35.** Если Task 01 добавил/объединил тесты по обоснованной причине (Task 04 audit это уже зафиксировал), QA accept'ит actual count если он >= 35 и все green. Не fail.
