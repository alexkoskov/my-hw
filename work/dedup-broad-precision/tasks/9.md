# Task 9: Manual production deployment

## Required Skills

Before starting, load:
- `/skill:deploy-pipeline` — [SKILL.md](../../../.claude/skills/deploy-pipeline/SKILL.md)

## Description

Release the approved, green build through the repository's manual production procedure. Deployment is a separately authorized operational action and must preserve a known-good rollback target, the database volume and the protected publication window.

## What to do

- Obtain explicit deployment authorization after Task 8 reports `ready` and CI is green on the promoted commit.
- Confirm the deployment is outside the protected publication window and record the current known-good rollback commit without environment details.
- Follow the existing manual pull/rebuild procedure without changing runtime configuration or database state.
- Verify the service starts cleanly, expected review listener state is unchanged, and no startup/schema/E016 regression appears.
- Roll back immediately through the documented route if the startup gate fails and write a sanitized deployment report.

## Acceptance Criteria

- [ ] Deployment starts only after explicit user authorization, green pre-deploy QA and green CI.
- [ ] The release occurs outside the protected publication window and preserves the existing database volume/configuration.
- [ ] The service is running after rebuild with no startup, schema, E016, duplicate poller or configuration regression.
- [ ] A known-good rollback target is recorded and rollback is executed if any startup gate fails.
- [ ] `deploy-report.json` contains only sanitized outcome and commit metadata, no commands with coordinates, raw logs, tokens or private identifiers.

## Verification Steps

### Automated

- `docker compose ps --status running` on the authorized production host → the news service reports running.
- `docker compose logs --tail=200 news-bot` on the authorized production host → clean startup with no E016, schema, token, or duplicate-poller regression.

### Smoke

- Repeat the documented container status and bounded startup-log checks → the deployed process is healthy without triggering a tick or injecting an article.

### User

- Confirm the release is outside the protected publication window and authorize rollback if startup verification fails.

## Details

**Files:** Writes only `work/dedup-broad-precision/logs/working/deploy-report.json`; repository runtime/config files are not deployment outputs.

**Dependencies:** Task 8 plus explicit user authorization. Uses existing deployment tooling and adds no CI/CD or infrastructure change.

**Edge cases:** Protected-window overlap, stale remote checkout, failed rebuild, detached rollback checkout, unexpected scheduler tick on restart, duplicate Telegram poller, database mount absence, and secret-bearing log lines.

**Implementation hints:** Use the procedure already owned by `deployment.md`; bound and sanitize evidence before recording it; treat any database-volume uncertainty as a stop condition.
