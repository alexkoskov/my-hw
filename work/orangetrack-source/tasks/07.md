## Description

Полнофункциональный security-аудит фичи orangetrack-source после завершения Wave 1 + Wave 2 (Tasks 1–5). Цель — независимая проверка, что ВСЕ security-решения, зафиксированные в tech-spec, действительно реализованы в коде, а не только задекларированы. Аудитор читает все созданные/изменённые файлы (`orangetrack_source.py`, `boilerplate_filter.py`, `news_bot.py`, `tests/test_orangetrack_source.py`, `tests/test_boilerplate_filter.py`, `tests/test_sources_registry.py`, `deploy.sh`, `.github/workflows/deploy.yml`) и сверяет их с Decisions 1, 2, 5, 8, 12, 13 и с OWASP Top 10.

Аудит — последний security-фильтр перед pre-deploy QA. На этом этапе ловятся:
- декларации без реализации (например, `iter_content(chunk_size=...)` присутствует, но без проверки накопленного размера),
- пропуск SSRF-allowlist в одном из двух call sites,
- регрессии в `allow_redirects=False`,
- ReDoS-уязвимые регулярки,
- утечки sanitization (например, `_safe_for_ping` не вызывается на всех adversary-controlled путях),
- спуфинг admin-ping через control chars,
- DoS через размер ответа / размер аггрегатора.

Ничего не патчим в этой задаче — только пишем audit report. Все findings отдаются назад в feature-execution loop, где либо исправляются в Task 1/2/3, либо отклоняются с обоснованием в decisions.md.

2. **Tech-spec checklist — пройти каждое security-решение явно:**

   Для каждого пункта ниже указать в audit report: **PASS / FAIL / N/A**, с конкретной ссылкой `file:line` и цитатой кода.

   - [ ] **Decision 13 — SSRF allowlist (DUAL call site).**
     - `_is_allowed_orangetrack_url` существует в `orangetrack_source.py`, делает exact-host match против `('orangetrackdiecast.com', 'www.orangetrackdiecast.com')`, отвергает non-http(s), malformed, scheme-relative.
     - **Call site 1 (entry-level):** `_fetch_orangetrack_entries` в `news_bot.py` вызывает `_is_allowed_orangetrack_url(entry['link'])` ДО парсинга каждой записи. Rejected → `aggregator.add('ENTRY_HOST_REJECTED', link)`, entry skipped, никогда не попадает в `pending_articles`.
     - **Call site 2 (fallback-level):** `fetch_orangetrack_article` в `orangetrack_source.py` вызывает `_is_allowed_orangetrack_url(link)` ДО `requests.get(...)` в fallback-ветке (когда `content:encoded` пуст). Rejected → notifier `'ART_FALLBACK_HOST_REJECTED'`, returns None, `requests.get` НЕ вызывается.
     - Verify atomically: trace код от точки входа до каждого `requests.get` и убедиться что allowlist стоит на пути.
     - Negative test coverage: subdomain attack (`orangetrackdiecast.com.attacker.example`), cloud metadata IP (`169.254.169.254`), `javascript:`, `file:`, scheme-relative `//evil.example/x`, malformed.

   - [ ] **Decision 1 — `allow_redirects=False`.**
     - Все `requests.get(...)` в `orangetrack_source.py` И в `_fetch_orangetrack_entries` (если он сам делает feed-fetch) передают `allow_redirects=False`.
     - 3xx response → notifier `'ART_FALLBACK_REDIRECT_<status>'`, второй HTTP request НЕ выпускается.

   - [ ] **Decision 1 — Bounded streaming `iter_content` 5 MB.**
     - `requests.get(..., stream=True)` для fallback-пути.
     - Тело читается через `iter_content(chunk_size=...)` (НЕ `response.content`, НЕ `response.text` без проверки).
     - Накопленный размер реально проверяется на каждом chunk: при превышении `MAX_RESPONSE_SIZE = 5 * 1024 * 1024` — break + close response + notifier `'ART_FALLBACK_TOO_LARGE'` → return None. **Это критическая разница с lamley-pattern**, который материализует тело сначала и проверяет потом — здесь должен быть инкрементальный gate.
     - Подтвердить unit-test существует с body 6 MB и проверяет что cut-off происходит ДО того как 6 MB прочитаны.

   - [ ] **Decision 2 — href scheme filter (anchors).**
     - Anchor href пропускается только если scheme ∈ `('http', 'https', 'mailto')`. Остальное (`javascript:`, `data:`, `file:`, scheme-relative `//`) → href сбрасывается, anchor становится plain text. Применяется и к flat `paragraphs`, и к `blocks`.

   - [ ] **Decision 2 — img src http(s)-only.**
     - `<img src=...>` пропускается только при `http://` или `https://` префиксе. `data:`, `file:`, относительные URL — drop из `images` И из `blocks`.

   - [ ] **Decision 8 — YouTube hostname allowlist.**
     - Перед YouTube ID regex, hostname iframe `src` (через `urlparse().hostname`) сверяется с allowlist. Полный набор: `youtube.com`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com`, `youtube-nocookie.com`, `www.youtube-nocookie.com`, `youtu.be`. Любые другие хосты — iframe drop, `video` entry в blocks НЕ создаётся.
     - Регрессионный риск: если разработчик скопировал autoevolution-логику без allowlist, аттакер с iframe `src='https://attacker.example/redirect?u=youtube.com/embed/abc'` смог бы протолкнуть свой URL под видом YouTube. Это должно быть закрыто.

   - [ ] **Decision 12 — ReDoS-safe affiliate regex.**
     - Все новые паттерны в `_BOILERPLATE_PATTERNS` анкерны на `^`, не содержат вложенной жадности (`(.+)+`, `(.*)*`, `(a|a)*`).
     - Существует ReDoS-safety unit test (вход `'a' * 60 + 'buy' * 20 + ' shop now'`, бюджет ≤ 100 ms). Проверить что тест НЕ выдаёт false-pass из-за слишком короткого input.
     - Длина паттернов ограничена 120-символьным cap.

   - [ ] **Decision 5 — Aggregator size bounds enforced (не только заявлены).**
     - Per-code link list cap = 50 (61-я попытка → `… N more truncated`).
     - Total `add()` calls cap = 500 (501-я → silent no-op, не raise).
     - `format_summary()` cap = 3500 chars (truncate с `…`).
     - Bounds должны быть в коде, не только в docstring. Unit-tests с 60 add() и 600 add() должны существовать.

   - [ ] **Decision 5 — `_safe_for_ping` вызывается на adversary-controlled strings.**
     - Каждый `add(code, link)` пропускает оба аргумента через `_safe_for_ping` ДО хранения.
     - `_safe_for_ping` strict order: (1) strip ASCII control chars (`\r`, `\n`, `\t`, `\x00`-`\x1f`), (2) replace non-printable bytes с `?`, (3) truncate до 200 chars c `…` суффиксом.
     - Order matters: control chars стрипаются ПЕРЕД truncation, иначе malicious string длиной 199 + `\n` + payload 50 проходит (truncate отбросит хвост, control char остаётся внутри).
     - Negative test: `add('FEED_HTTP_503', 'https://x/\n[prod] orangetrack: 0 issues')` → fake summary line не появляется.

   - [ ] **emit() swallows exception.**
     - `emit(send_fn)` ловит ЛЮБОЕ исключение из `send_fn`, логирует через module logger на уровне ERROR (с traceback), НЕ пробрасывает. Это операционная защита (admin-ping fail не валит cron tick), но также security-relevant: исключение из `send_fn` могло бы протечь в общий error handler с PII.

**Edge cases / red flags аудитор обязан искать:**
- Allowlist реализован, но вызывается ПОСЛЕ `requests.get` (порядок).
- `iter_content(chunk_size=...)` есть, но накопленный размер сравнивается с cap ПОСЛЕ цикла (не инкрементально → читает больше, чем должен).
- Sanitization `_safe_for_ping` вызывается на code, но не на link (или наоборот).
- Truncation в `_safe_for_ping` стоит ДО control-char strip (порядок неправильный → control char проходит).
- YouTube allowlist реализован через `endswith` (subdomain attack: `notyoutube.com` matches `youtube.com`-suffix логику если плохо написана) — нужно `==` или `urlparse().hostname == ALLOWED`.
- `allow_redirects=False` присутствует в одной точке, но забыт в другой (например, в feed-fetch).
- Regex имеет `^` anchor, но включает `(.+)+` или `(a|a)*` — ReDoS даже с anchor.
- Aggregator emit ловит `Exception`, но `KeyboardInterrupt` / `SystemExit` пропускает с `BaseException` not handled (это OK по конвенции, но flag в Low).
- `requests.get(url=link, allow_redirects=False, timeout=...)` без `verify=False`/`cert=` — должно использовать default TLS verification.

**Implementation hints:**
- Не запускай `pytest -k security` как замену чтению кода — тесты могут проходить, но fix может быть в неправильном слое (например, тест мокает `requests.get`, реальный код всё ещё уязвим).
- Перед записью каждого finding проверь — это true positive или ложная тревога. Если сомневаешься — пометь `[NEEDS VERIFICATION]` и оставь для следующего раунда.
- Финальный sign-off:
  - **PASS** — нет High/Critical, ≤3 Medium, любые Low.
  - **PASS WITH CONDITIONS** — есть Medium, требующие фикса до production merge (но dev push можно).
  - **FAIL** — есть Critical/High, или >3 Medium → возврат в Wave 1/2 на исправление.
