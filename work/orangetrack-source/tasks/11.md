## Description

После того как Task 10 (`git push origin dev` → CI зелёный → `deploy_test.yml` успешно отдеплоил FILES list на `/home/hwbot/bot_test/` и рестартанул `news_bot_test.service`), нужно убедиться, что фича orangetrack-source реально работает на живом окружении. Это финальный gate перед merge в main.

Проверяем три уровня:
1. **Health тестового сервиса** — бот стартанул без `ImportError` (новый модуль `orangetrack_source.py` корректно импортируется), фид orangetrack успешно зафетчен на ближайшем cron-tick.

3. **Отсутствие admin-ping flood** — если admin-пинги были, расшифровать коды по таксономии Decision 5 и убедиться, что они sensible (не feed-bug, не SSRF-flood, не аномалия).

Это не code-таска: агент не пишет код, а проводит верификацию по чеклисту через bash + journalctl + Telegram MCP (или operator-visual). Результат — отчёт PASS/FAIL в `work/orangetrack-source/logs/qa/post-deploy-qa.md`.

## Details

**Tools / commands:**
- `bash` — общие операции (запись отчёта, парсинг логов).
- `journalctl -u news_bot_test.service -n 200 --since "<timestamp Task 10 deploy>"` — operator-side; ищем строки старта сервиса, фетча orangetrack-фида, ошибок.
- `journalctl -u news_bot_test.service --since "<deploy time>" | grep -iE "orangetrack|importerror|traceback|exception"` — фокусированный grep.
- `journalctl -u news_bot_test.service --since "<deploy time>" | grep -E "FEED_|ENTRY_HOST|ART_FALLBACK|ART_PARSE"` — поиск кодов аггрегатора в логах (перед тем, как смотреть admin-ping).
- **Telegram MCP** — чтение test channel `@myhwchannel123` и admin-чата (если MCP доступен); fallback — operator-visual (оператор присылает скриншоты / описывает пост).

**Service unit name:** `news_bot_test.service` (test instance). НЕ `news_bot.service` — этот для prod. Test instance путь: `/home/hwbot/bot_test/`. Это важно — путать с prod недопустимо.

**Окно публикации:** orangetrack статьи выходят в обычном расписании канала, в окне 10:00–20:00 МСК, по слотам распределённого расписания. Первая orangetrack-публикация может занять до 24 часов после деплоя (зависит от того, есть ли в pending новые orangetrack-статьи и сколько слотов до них). Если за 24 часа ни одна orangetrack-статья не опубликовалась — отметить в отчёте «no orangetrack content in pending», это не FAIL, а ожидание контента; поверка возобновляется на следующий день.

**SSH:** не пытаться. По методологии (operator_prod_ops) operator сам делает live ops, агент готовит. Если нужен live `journalctl` — попросить оператора выполнить и прислать вывод.

**Decision 5 admin-ping таксономия (cheatsheet для расшифровки):**
- `FEED_HTTP_<status>` — фид-уровень HTTP-ошибка (e.g., `FEED_HTTP_503` — WordPress.com даёт 503, sensible если редко).
- `FEED_TIMEOUT` — таймаут на фетче фида.
- `FEED_XML_PARSE` — feedparser упал на XML.
- `ENTRY_HOST_REJECTED` — SSRF allowlist отклонил `<link>` в entry (poisoned feed); sensible если редко, ALARM если часто.
- `ART_FALLBACK_HTTP_<status>` — fallback HTTP scrape вернул статус (e.g., 404, 503).
- `ART_FALLBACK_TIMEOUT` — fallback timeout.
- `ART_FALLBACK_HOST_REJECTED` — SSRF allowlist отклонил URL fallback'а.
- `ART_FALLBACK_REDIRECT_<status>` — fallback увидел 3xx (redirect-bypass attempt).
- `ART_FALLBACK_TOO_LARGE` — fallback body превысил 5 MB cap.
- `ART_FALLBACK_PARSE_EMPTY` — fallback HTTP ОК, но парсер ничего не извлёк.
- `ART_PARSE_EXCEPTION` — неожиданное исключение в парсере; ALARM (регрессия).

**Edge cases:**
- Test slot не успел сработать в течение окна проверки → отчёт с пометкой «pending», возобновить на следующем cron-tick.
- Первая orangetrack-статья опубликовалась без видео (post без YouTube embed) → блок-path всё равно должен быть populated; visual check без `video` блока — это нормально, не FAIL.
- Если RU-перевод визуально подстрочный — это FAIL по AC; root cause скорее всего в LLM transcreation pipeline, НЕ в новом orangetrack коде; зафиксировать как finding, эскалировать оператору.
- Inline `*QUICK LINK!*` внутри настоящего параграфа — НЕ FAIL (Q5 = I, deferred).

**Implementation hints:**
- Не делать verification по таймеру в одном run'е — если контент не вышел, лучше остановить run и вернуться позже, чем держать сессию открытой 24 часа.
- При записи отчёта — Telegraph URL обязательно (load-bearing для дальнейшей проверки оператором).
- Если не было ни одного orangetrack-поста за окно, но всё остальное PASS — отчёт со статусом «PARTIAL PASS — no orangetrack content yet, infrastructure healthy, awaiting first publication».
