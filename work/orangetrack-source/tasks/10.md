# Task 10: Deploy via dev push (CI auto-fires test deploy)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](~/.claude/skills/deploy-pipeline/SKILL.md)

## Description

Запушить ветку `dev` с изменениями фичи orangetrack-source — в результате CI выполнит pytest, и при зелёном CI workflow_run триггерит `deploy_test.yml`, который SCP'ит FILES list на test-инстанс `/home/hwbot/bot_test/` и рестартит `news_bot_test.service`.

Это финальная волна: Pre-deploy QA (Task 9) уже прошла, все изменения готовы. Эта задача — оператор-стороне-минимальный шаг между pre-deploy QA и post-deploy verification (Task 11). Если CI красный — деплой блокируется автоматически (workflow_run триггерится только при `conclusion == 'success'`); фиксим pytest и перепушиваем.

Контекст инвариантов: `deploy.sh` и `.github/workflows/deploy.yml` (через `deploy_test.yml`) FILES list ОБА должны включать `orangetrack_source.py` (синхронизировано в Task 5). Если хоть один файл забыт — `news_bot_test.service` упадёт с `ImportError: No module named 'orangetrack_source'` при следующем рестарте, и деплой считается провалившимся.

## What to do

1. **Подготовка коммита.** На локальной ветке `dev` (или из feature-branch замёрдженной в `dev`) проверить `git status` — все изменения из Tasks 1-5, отчёты аудитов из Tasks 6-8 (под `work/orangetrack-source/logs/audit/`) и QA-отчёт из Task 9 (под `work/orangetrack-source/logs/tasks/`) застейджены. Файлы кода: `orangetrack_source.py`, `news_bot.py`, `boilerplate_filter.py`, `deploy.sh`, `.github/workflows/deploy.yml`, `tests/test_orangetrack_source.py`, `tests/test_boilerplate_filter.py`, `tests/test_sources_registry.py`. Спросить оператора подтверждение перед коммитом+пушем (по правилу memory: "Ask before commit+push, then do both").
2. **Коммит.** `git commit` с summary-message, описывающим фичу: "feat: add orangetrackdiecast.com as 4th news source" + 1-2 строки про parser, aggregator, SSRF allowlist, FILES list update. Pre-commit хуки должны пройти зелёными (gitleaks, whitespace, EOF, merge-conflict markers).
3. **Push.** `git push origin dev`. Зафиксировать commit SHA для отчёта.
4. **Мониторинг GitHub Actions.** Через `gh run list --branch dev --limit 5` или `gh run watch <run-id>` дождаться завершения `ci.yml`. Если красный — прочитать логи через `gh run view <run-id> --log-failed`, починить, перепушить (новый коммит, не amend). При зелёном `ci.yml` — workflow_run триггерит `deploy_test.yml`; дождаться его завершения тем же `gh run`.
5. **Проверка статуса в UI.** Оба workflow (`ci.yml` и `deploy_test.yml`) должны быть зелёными в GitHub Actions UI на ветке `dev` для последнего коммита. URL запусков обоих workflow зафиксировать для отчёта.
6. **Запросить у оператора post-deploy log check.** Operator-side команда: `journalctl -u news_bot_test.service -n 100 --since "5 minutes ago"`. Цель — увидеть: бот стартовал без `ImportError`, не упал на старте, цикл инициализации прошёл. Сохранить excerpt в отчёт. Если бот упал с `ImportError: No module named 'orangetrack_source'` — значит FILES list рассинхронизирован между `deploy.sh` и `.github/workflows/deploy.yml`; вернуться в Task 5 контекст и пофиксить.
7. **Acceptance criteria check (operator-side).** Спросить оператора подтвердить, что `ls /home/hwbot/bot_test/orangetrack_source.py` отвечает (файл доехал на test-инстанс). Если оператор недоступен — допустимо принять подтверждение через `journalctl` (бот импортировал модуль => файл присутствует).
8. **Отчёт.** Записать `work/orangetrack-source/logs/deploy/deploy.md` с полями: commit SHA, ветка (`dev`), URL `ci.yml` run, URL `deploy_test.yml` run, excerpt из journalctl (первые ~30 строк после рестарта), статус `PASS` / `FAIL`, любые отклонения.

**Files NOT staged:** `feeds.json` (по Decision 4 — orangetrack feed URL живёт как module-level constant).

**Pipeline trigger chain:**
- Push на `dev` → `ci.yml` (`on: push: branches: [main, dev]`) → pytest.
- При success `ci.yml` → `deploy_test.yml` (`on: workflow_run` filter `conclusion == 'success'` + branch `dev`) → SCP FILES → `systemctl restart news_bot_test.service`.

**Edge cases:**
- CI красный → `deploy_test.yml` НЕ запускается. Чинить pytest на локали, пушить новый коммит. Не делать `git commit --amend` после публичного push (по правилу memory: всегда новый коммит, не amend).
- `deploy_test.yml` падает на SCP step → проверить GitHub secrets (TEST_HOST, TEST_USER, TEST_KEY и аналоги — точные имена в `.github/workflows/deploy_test.yml`). Это операторская ответственность; сообщить, не лезть в secrets.
- `news_bot_test.service` падает с `ImportError: orangetrack_source` → FILES list рассинхрон. Проверить `deploy.sh` vs `.github/workflows/deploy.yml` побайтно для строки `orangetrack_source.py`. Это указывает на дефект в Task 5; вернуть в работу.
- `news_bot_test.service` стартует, но падает позже (например, в первом cron tick) → это уже область Task 11 (post-deploy verification), не блокер для Task 10. Зафиксировать в отчёте, передать в Task 11.
- Конкуренция с другими push на `dev` — если другой коммит проскочил между `git push` и проверкой workflow run, использовать commit SHA из локального `git rev-parse HEAD` сразу после push, чтобы матчить правильный run.

**Implementation hints:**
- Использовать `gh run list --branch dev --commit <SHA> --json databaseId,name,conclusion,url` для надёжного матчинга по SHA.
- Для long-running ожидания обоих workflow можно `gh run watch <run-id>` — блокирующая команда. Для CI типичное время ~3-5 мин, для deploy_test ~1-2 мин.
- Не пытаться SSH'ить на test-инстанс самостоятельно (по правилу memory: "Operator handles production ops; Claude prepares, operator applies"). Все journalctl / systemctl / ls — через оператора.
- Никогда не выводить secrets в чат/отчёт.
- Перед push дать оператору diff+тесты и спросить "коммитить и пушить?" (по правилу memory: "Ask before commit+push, then do both" — один объединённый gate).
