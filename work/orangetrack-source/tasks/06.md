## Description

Full-feature code quality audit фичи `orangetrack-source` после Wave 2. Цель — холистический cross-component review результата Tasks 1-5: новый `orangetrack_source.py`, изменения в `news_bot.py`, изменения в `boilerplate_filter.py`, обновлённые тесты, обновлённый `deploy.sh` и `.github/workflows/deploy.yml`.

Задача — найти проблемы, которые НЕ видны при per-task review: дублирование логики между парсерами (orangetrack vs autoevolution / lamley), нарушения границ класса `OrangetrackPingAggregator` (state leak, неверный lifecycle), inconsistency в naming (`orangetrack` / `orangetrackdiecast` / `orange-track` / `OrangeTrack`), полнота error-handling (все ли коды из Decision 5 реально эмитятся в правильных местах?), мёртвый код (неиспользуемые импорты, helpers без call site), и расхождения с рекомендациями `code-research.md`.

Аудитор сам — review (никто его не ревьюит). Результат — отчёт `work/orangetrack-source/logs/audit/code-audit.md` с findings по severity, file:line ссылками и рекомендациями.

5. Провести аудит по dimensions из `code-reviewing` skill, с фокусом на cross-component:
   - **Duplicate logic across parsers.** YouTube wrapper (`_video_embed_url`) — действительно ли это локальная копия + hostname allowlist (Decision 8), или скопировано как есть с уязвимостью autoevolution? Image extraction / dedup — дублирует ли логику autoevolution / lamley или вынесено отлично (или должно быть вынесено)? Boilerplate filter call — единый ли pattern с другими парсерами?
   - **Aggregator class boundaries.** `OrangetrackPingAggregator` — правда ли function-local в `_fetch_orangetrack_entries` (Decision 4)? Module-level singleton не появился? Lifecycle — try/finally корректно охватывает emit на пути исключений? GC чистый? Notifier callback (parameter) не утекает в other scopes?
   - **Naming consistency.** Все ли наименования соблюдают конвенцию `orangetrack` (короткое внутреннее) vs `orangetrackdiecast` (хэштег / netloc) vs `orange-track` (если где-то проскочило — это баг). Module name, function names, source_name value, SOURCE_LABEL value, hashtag — всё ли согласовано (Decision 10). Не должны быть переменные / константы с case-различиями типа `orangeTrack`, `OrangeTrack`, `Orangetrack`, кроме явно класс-имени `OrangetrackPingAggregator`.
   - **Error-handling completeness.** Каждый код таксономии Decision 5 (`FEED_HTTP_<status>`, `FEED_TIMEOUT`, `FEED_XML_PARSE`, `ENTRY_HOST_REJECTED`, `ART_FALLBACK_HTTP_<status>`, `ART_FALLBACK_TIMEOUT`, `ART_FALLBACK_HOST_REJECTED`, `ART_FALLBACK_REDIRECT_<status>`, `ART_FALLBACK_TOO_LARGE`, `ART_FALLBACK_PARSE_EMPTY`, `ART_PARSE_EXCEPTION`) — действительно ли есть call site, который его эмитит? Нет ли «забытых» путей (например, `connection refused` уходит в exception без notifier-вызова)? `emit()` swallow-on-error логирует ERROR в module logger?
   - **Dead code.** Неиспользуемые import-ы (`from urllib.parse import ...` — всё ли реально используется?), helper-функции без call site, неиспользуемые helper-аргументы, dead branches в if-цепочках.
   - **Code-research mismatches.** Где Tasks 1-5 разошлись с рекомендациями `code-research.md`? (Например, code-research §2 предлагал «NOT needed: SOURCES registry — orangetrack arrives via existing `_fetch_rss_entries`», но Decision 4 сделал отдельный fetcher — это документированное расхождение, не bug.) Любое другое расхождение — флаг для проверки: либо документировано в Decisions, либо реальный недосмотр.
6. Записать отчёт `work/orangetrack-source/logs/audit/code-audit.md` со следующей структурой:
   - **Summary** — 2-4 предложения: общая оценка качества кода, главные риски, общий вердикт (готово к деплою / нужны фиксы).
   - **Scope** — список файлов, реально прочитанных (с версией / commit hash, если возможно).
   - **Findings by severity** — `Critical`, `High`, `Medium`, `Low`, `Nit`. Для каждого finding: file:line, краткое описание, почему это проблема, рекомендуемый фикс. Без дампов кода — только ссылки.
   - **Cross-component observations** — наблюдения, которые не привязаны к одной строке: дублирование, aggregate ownership, naming inconsistency, etc.
   - **Code-research divergences** — таблица «recommendation → implementation → status (documented / undocumented)».
   - **Recommendations** — приоритизированный список действий. В первую очередь то, что блокирует деплой; затем — улучшения, которые можно сделать после.
7. Если найдено НИЧЕГО критичного — отчёт всё равно создаётся (фикс — пустой раздел Critical / High, явное «всё чисто» в Summary).

## Details

**Files:**
- `work/orangetrack-source/logs/audit/code-audit.md` — создать (новый файл, директорию создать если её нет).

**Dependencies:**
- Tasks 1-5 должны быть в статусе `done`. Без их результатов аудитировать нечего.
- Skill `code-reviewing` загружен — используем его 11 dimensions как чек-лист, но с акцентом на cross-component (см. список в What to do).

**Edge cases:**
- Если `code-research.md` рекомендует что-то, что Decisions явно отклоняют (как Decision 4 vs code-research §2) — это `documented divergence`, отмечается, но не finding.
- Если Decision 5 коды эмитятся не в том месте, где описано (например, `ART_FALLBACK_TIMEOUT` в branch `connection refused` вместо отдельного кода) — это finding, severity = Medium (admin не видит точную причину).
- Если `_FEED_URL` оказался в `feeds.json` (а не module-level constant) — это finding High (Decision 4 нарушено, шанс duplicate fetch и silent drop).
- Если `deploy.sh` и `.github/workflows/deploy.yml` FILES list НЕ совпадают побайтно — finding Critical (deploy сломается).
- Если в `news_bot.py` появился module-level `_active_aggregator` или другая глобальная state — finding High (Decision 5 / Decision 4 нарушены).
- Если YouTube wrapper не имеет hostname allowlist gate — finding Critical (Decision 8 — security regression, content-spoofing primitive).

**Implementation hints:**
- Перед написанием отчёта можно сделать `git diff` на feature-branch против `dev` baseline, чтобы быстро увидеть scope изменений.
- Severity calibration: `Critical` = блокирует деплой / security regression; `High` = баг или нарушение Decision; `Medium` = error-handling неполнота / observable degradation; `Low` = code smell без runtime impact; `Nit` = стиль / комментарии.
- Не дублировать findings, которые уже найдены per-task review-ерами (code-reviewer, security-auditor, test-reviewer на каждой задаче). Audit ищет cross-component — то, что один reviewer на одной таске не увидит.
- Если что-то всё же повторяется с per-task finding — упомянуть со ссылкой на тот review (не пере-описывать).
