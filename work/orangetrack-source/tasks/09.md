# Task 9: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Acceptance testing — финальный pre-deploy gate перед `git push origin dev`. Задача проверяет, что фича `orangetrack-source` готова к выкатке на test-инстанс и в продакшен:

- Все unit-тесты (существующие + новые из Task 1-5) проходят зелёным.
- Все Acceptance Criteria из user-spec (16 критериев) и tech-spec выполнены — проверка идёт чтением кода + smoke-командами.
- Pre-commit hooks (gitleaks, whitespace, EOF, merge conflicts) проходят на staged изменениях.
- INVARIANT-проверка: `orangetrack_source.py` присутствует в FILES list **обоих** файлов деплоя — `deploy.sh` и `.github/workflows/deploy.yml` — побайтно идентично. Это критический инвариант проекта: дрейф между двумя файлами обрушит прод-cron при следующем рестарте через `ImportError`.
- Audit-отчёты из Wave Audit (Task 6 Code Audit, Task 7 Security Audit, Task 8 Test Audit) — чистые, либо оставшиеся findings явно зафиксированы как acceptable + задокументированы.

QA — это GATE: при любом FAIL фиксируем это в отчёте и блокируем деплой. Зелёный результат разрешает Task 10 (push на dev → CI auto-deploy).

## What to do

1. **Запустить полный набор тестов:** `pytest tests/` — все существующие + новые тесты из Tasks 1-5 должны быть зелёными. Зафиксировать exit code и количество passed/failed.
2. **Прочитать tech-spec ACs (Acceptance Criteria, ~17 пунктов) и user-spec ACs (Критерии приёмки, 16 пунктов).** Для каждого AC — определить способ верификации:
   - Code-AC (например «`_is_allowed_orangetrack_url` реализован, вызывается в двух местах»): открыть соответствующие файлы (`orangetrack_source.py`, `news_bot.py`), найти call sites, убедиться что код реализует контракт.
   - Behavior-AC (например «парсер возвращает blocks с типизированными элементами»): найти подтверждающий unit-тест в `tests/test_orangetrack_source.py`.
   - Smoke-AC (например «модуль импортируется без ошибок»): выполнить smoke-команду из tech-spec Layer 2.
3. **Проверить pre-commit hooks:** `pre-commit run --all-files` (или `pre-commit run` на staged) — все hooks зелёные (gitleaks, trailing-whitespace, end-of-file-fixer, check-merge-conflict).
4. **FILES list invariant — manual diff:**
   - Извлечь из `deploy.sh` блок FILES list и нормализовать (sort + uniq).
   - Извлечь из `.github/workflows/deploy.yml` блок FILES list и нормализовать.
   - Команда: `diff <(grep -E '^\s*orangetrack_source\.py' deploy.sh) <(grep -E '^\s*orangetrack_source\.py' .github/workflows/deploy.yml)` → no output.
   - Дополнительно: убедиться, что `orangetrack_source.py` присутствует в обоих файлах (grep на каждом).
5. **Audit findings review:** прочитать отчёты из Tasks 6/7/8 (Code Audit, Security Audit, Test Audit) в `work/orangetrack-source/logs/audit/` (или соответствующие пути). Для каждого finding:
   - Severity high/critical → должен быть исправлен. FAIL если остался.
   - Severity medium/low → допустим если задокументирован в `decisions.md` как acceptable.
6. **Smoke checks (Layer 2 из tech-spec AVP):**
   - `python3 -c "import orangetrack_source; print(orangetrack_source.fetch_orangetrack_article)"` → печатает не-None символ.
   - `python3 -c "from orangetrack_source import OrangetrackPingAggregator; a = OrangetrackPingAggregator('test'); a.add('FEED_HTTP_503', 'https://example/x'); print(a.format_summary())"` → печатает корректный формат с `[test] orangetrack: 1 issues this tick` и буллет-строкой.
   - `python3 -c "import news_bot; assert news_bot.NETLOC_TO_SOURCE.get('orangetrackdiecast.com') == 'orangetrack'; assert any(f.__name__ == '_fetch_orangetrack_entries' for f in news_bot.SOURCES); print('OK')"` → печатает OK.
7. **Записать QA-отчёт** в `work/orangetrack-source/logs/qa/pre-deploy-qa.md`:
   - Шапка: `Status: PASS` или `Status: FAIL`, дата, версия (HEAD commit hash).
   - Раздел «Test results»: pytest exit code, passed/failed/skipped counts, перечисление падений если есть.
   - Раздел «User-spec ACs (16)»: чек-лист каждого AC с Yes/No/N/A + краткое подтверждение (ссылка на файл:строка или тест).
   - Раздел «Tech-spec ACs»: то же.
   - Раздел «Pre-commit hooks»: список hooks + status каждого.
   - Раздел «FILES list invariant»: diff-вывод + grep-подтверждение по обоим файлам.
   - Раздел «Audit findings»: список findings из Task 6/7/8 + статус (resolved / accepted / open).
   - Раздел «Blockers»: пусто если PASS, иначе перечень что блокирует деплой.
8. **Решение:** если все разделы зелёные → Status: PASS, фича готова к Task 10. Если есть FAIL — НЕ передавать в Task 10, возвращать список blockers оператору.

## Verification Steps

### Automated
- `pytest tests/ -v` → exit code 0, все passed.
- `pre-commit run --all-files` → exit code 0, все hooks зелёные.

### Smoke
- `python3 -c "import orangetrack_source; print(orangetrack_source.fetch_orangetrack_article, orangetrack_source.OrangetrackPingAggregator)"` → не-None символы.
- `python3 -c "from orangetrack_source import OrangetrackPingAggregator; a = OrangetrackPingAggregator('test'); a.add('FEED_HTTP_503', 'https://x/y'); print(a.format_summary())"` → ожидаемый формат `[test] orangetrack: 1 issues this tick\n  • FEED_HTTP_503 (1×) — https://x/y`.
- `python3 -c "import news_bot; assert news_bot.NETLOC_TO_SOURCE.get('orangetrackdiecast.com') == 'orangetrack'; assert any(f.__name__ == '_fetch_orangetrack_entries' for f in news_bot.SOURCES); print('OK')"` → печатает `OK`.
- FILES list invariant (трёх файлов — учётом quoted entries): `diff <(grep -oE '"orangetrack_source\.py"' deploy.sh) <(grep -oE '"orangetrack_source\.py"' .github/workflows/deploy.yml) && diff <(grep -oE '"orangetrack_source\.py"' deploy.sh) <(grep -oE '"orangetrack_source\.py"' .github/workflows/deploy_test.yml)` → no output.
- FILES list presence: `grep -c '"orangetrack_source\.py"' deploy.sh` → ≥1; то же для `deploy.yml` и `deploy_test.yml`.
- `feeds.json` invariant: `python3 -c "import json; data = json.load(open('feeds.json')); assert isinstance(data, list) and len(data) == 3 and not any('orangetrackdiecast' in url for url in data); print('feeds.json unchanged: 3 URLs, no orangetrack')"` → подтверждает: файл — bare-list из 3 URL (не dict), URL orangetrack НЕ попал в feeds.json (Decision 4).

## Details

**Files:**
- Создаётся: `work/orangetrack-source/logs/qa/pre-deploy-qa.md` — QA-отчёт. Если папки `logs/qa/` нет — создать через `mkdir -p`.
- Читаются (без модификации): все файлы из секции Context Files выше.

**Dependencies:**
- Tasks 6, 7, 8 (Audit Wave) должны быть `done`. QA читает их отчёты как input.
- Tasks 1-5 (Wave 1 + Wave 2) должны быть `done`. QA проверяет результаты их кода.

**Edge cases:**
- Если `pytest` падает на флейки (например network-related) — повторить 1 раз. Если стабильно красный — FAIL.
- Если pre-commit hooks падают на изменениях, которые уже закоммичены — нужно понять чьи это изменения. Если это файлы фичи — FAIL. Если файл вне фичи (legacy) — задокументировать в отчёте и не блокировать.
- Если `decisions.md` ещё не содержит записей о accepted findings из Task 6/7/8 — пометить findings как «open» и FAIL.
- Если `feeds.json` модифицирован вопреки Decision 4 — FAIL (нарушает архитектурное решение, риск duplicate-fetch бага).
- Если smoke `python3 -c "import orangetrack_source"` падает — критический FAIL (модуль не импортируется → прод обрушится).

**Implementation hints:**
- QA-агент НЕ модифицирует код. Только читает + запускает тесты + пишет отчёт.
- При проверке AC «парсер возвращает blocks с правильными типами» — НЕ нужно писать новый ad-hoc test; убедиться, что соответствующий тест из `TestPrimaryPath` уже существует и зелёный.
- Для AC, требующих verbal-only verification (например «парсер устойчив к WordPress drift»): найти и упомянуть конкретный тест-кейс из `TestWPBlockDriftMitigation`.
- Audit findings структура: каждый отчёт это отдельный файл; парсить severity и описание; составить сводную таблицу в финальном QA-отчёте.
- Команда для git status проверки на staged changes (для pre-commit context): `git status --short`.
