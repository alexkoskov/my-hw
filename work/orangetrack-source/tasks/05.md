# Task 5: Deploy FILES list synchronization

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](~/.claude/skills/deploy-pipeline/SKILL.md)

## Description

Добавить новый модуль `orangetrack_source.py` в FILES list **трёх** деплой-файлов: `deploy.sh`, `.github/workflows/deploy.yml` (prod) и `.github/workflows/deploy_test.yml` (test). Это часть orangetrack-source feature — без deploy plumbing новый источник не доедет на сервер. **`deploy_test.yml` обязателен**, не опционален — у него собственный FILES array; без синхронизации test-инстанс упадёт с `ImportError` при следующем push в `dev`.

**Почему синхронность обязательна.** Это проектный INVARIANT, явно документированный в комментариях обоих файлов и в [deployment.md](../../../.claude/skills/project-knowledge/references/deployment.md) "Files deployed" секции:

> The list lives in two places — `.github/workflows/deploy.yml` and `deploy.sh` — and is asserted byte-for-byte identical by the headline comments. **INVARIANT:** any new first-party import added to `news_bot.py` MUST be mirrored into both FILES arrays. Otherwise the server hits `ImportError` on the next cron tick with no CI signal beforehand.

Если файл попадёт только в один из двух: либо `deploy.sh` (manual fallback) тихо разойдётся с GitHub Actions путём, либо CI-деплой пропустит модуль и при следующем рестарте `news_bot.service` (а он перезапускается каждый деплой) прод/тест упадёт с `ImportError: No module named 'orangetrack_source'` — без сигнала на CI-стороне, потому что pytest проходит локально.

Задача атомарна: один логический unit — добавить ровно одну строку в каждый из двух массивов FILES, обеспечить идентичность.

## What to do

1. Открыть `deploy.sh`. Найти массив `FILES=(...)` (начинается на строке ~37). Добавить строку `    "orangetrack_source.py"` в массив. Логичная точка вставки — рядом с другими source-парсерами (`autoevolution_source.py`, `mattel_news_source.py`, `lamley_source.py`), сохраняя существующий порядок группировки.

2. Открыть `.github/workflows/deploy.yml`. Найти второй массив `FILES=(...)` внутри step "Copy files to server" (начинается на строке ~117). Добавить ту же строку `"orangetrack_source.py"` в той же позиции относительно других source-парсеров. Соблюсти YAML-блочную индентацию (12 spaces в `deploy.yml` против 4 spaces в `deploy.sh` — это нормально, отступы — артефакт обёрток).

3. Убедиться что добавленная строка побайтно идентична между двумя файлами по содержимому имени файла (т.е. сама строка `"orangetrack_source.py"` без отступов идентична — отступы разные из-за YAML vs bash контекста, это ожидаемо и не нарушает invariant).

4. Открыть `.github/workflows/deploy_test.yml`. Найти массив `FILES=(...)` (расположение аналогично deploy.yml). Добавить ту же строку `"orangetrack_source.py"` в той же позиции. ОБЯЗАТЕЛЬНО — без этой правки следующий push в `dev` сломает test-инстанс.

## Verification Steps

### Automated

Нет автоматических pytest-тестов на этой задаче (deploy-config файлы не покрываются юнит-тестами в проекте). Smoke-проверка ниже выступает в роли functional check.

### Smoke

Регулярка должна матчить **quoted entries** (строки массива имеют вид `    "orangetrack_source.py"`):

```
diff <(grep -oE '"orangetrack_source\.py"' deploy.sh) <(grep -oE '"orangetrack_source\.py"' .github/workflows/deploy.yml) && \
diff <(grep -oE '"orangetrack_source\.py"' deploy.sh) <(grep -oE '"orangetrack_source\.py"' .github/workflows/deploy_test.yml)
```

Ожидание: команда даёт пустой вывод (exit 0) — запись `"orangetrack_source.py"` присутствует во всех трёх файлах.

> **Важно:** ранее предлагался regex `^\s*orangetrack_source\.py` без кавычек — он **НЕ матчит** реальные quoted entries (строки имеют формат `    "orangetrack_source.py"`), даёт false-negative «всё ок» даже когда файла в массиве нет. Использовать `'"orangetrack_source\.py"'` (кавычки внутри regex) — корректный матч.

Дополнительно — sanity-проверки:

```
grep -c 'orangetrack_source.py' deploy.sh                          # ожидается: 1
grep -c 'orangetrack_source.py' .github/workflows/deploy.yml       # ожидается: 1
grep -c 'orangetrack_source.py' .github/workflows/deploy_test.yml  # ожидается: 1
bash -n deploy.sh                                                  # syntax-check bash, должен пройти молча
```

Опционально — если `yamllint` установлен: `yamllint .github/workflows/deploy.yml` для проверки YAML-синтаксиса после правки.

## Details

**Files:**
- `deploy.sh` — добавить `"orangetrack_source.py"` в bash-массив FILES (строка ~37+). Текущее состояние: 19 файлов в массиве, последний — `.claude/skills/project-knowledge/references/ux-guidelines.md`. Источники-парсеры сгруппированы вверху сразу после `news_bot.py` (`autoevolution_source.py`, `mattel_news_source.py`, `lamley_source.py`). Добавляем 20-й файл рядом с ними.
- `.github/workflows/deploy.yml` — добавить `"orangetrack_source.py"` в YAML-вложенный bash-массив FILES внутри step "Copy files to server" (строка ~117+). Содержание массива идентично `deploy.sh`'у по списку имён файлов. Добавляем туда же.
- `.github/workflows/deploy_test.yml` — добавить `"orangetrack_source.py"` в FILES array (аналогично `deploy.yml`). ОБЯЗАТЕЛЬНО — этот файл имеет независимый FILES array, без правки test-инстанс упадёт с `ImportError` при следующем `git push origin dev`.

**Dependencies:**
- Task 1 (создание `orangetrack_source.py`) должна быть завершена до этой — иначе деплой упадёт на pre-flight check `if [[ ! -f "$file" ]]; then echo "$file not found" exit 1` (оба файла имеют такой guard перед SCP).
- Никаких pip-пакетов или внешних инструментов не нужно.

**Edge cases:**
- Если `orangetrack_source.py` ещё не существует в репо — pre-flight check в deploy.sh / deploy.yml упадёт ДО SCP (это и есть правильное поведение, защита от частичных деплоев). Но этот task запускается в Wave 2, после Task 1, поэтому файл будет существовать.
- Drift между `deploy.sh` и `deploy.yml` уже на момент задачи — маловероятно (последняя проверка показала идентичный список из 19 файлов). Если drift всё-таки обнаружится — НЕ исправлять его в этом task, флагнуть в decisions.md как отдельную находку и оставить как есть, чтобы scope задачи остался атомарным.
- YAML-индентация: в `deploy.yml` массив FILES внутри `run: |` блока с 10-space базовой индентацией + 2 на содержимое массива = 12 spaces. В `deploy.sh` это просто 4 spaces. Этот разброс — артефакт обёрток (YAML vs bash), а не нарушение byte-for-byte invariant — invariant документирован как идентичность *списка имён файлов*, не отступов.
- `deploy_test.yml`: проверить существование через `ls .github/workflows/deploy_test.yml`. Если есть и содержит свой FILES array — синхронизировать. Если deploy_test.yml импортирует FILES из deploy.yml через include или composite action (маловероятно, но возможно) — отдельная синхронизация не нужна.

**Implementation hints:**
- Использовать Edit tool с уникальным `old_string` (например, последняя строка существующего FILES перед `)`), чтобы вставка попала ровно в нужное место.
- НЕ переформатировать массив (не сортировать, не удалять комментарии). Минимальная диффа = одна добавленная строка на файл.
- После правки прогнать smoke-команду из Verify → Smoke, сохранить вывод для отчёта в decisions.md.
- Не трогать никакие другие секции `deploy.yml` (env-vars step, sudoers-комментарии, secrets verification) — это вне scope.

**Security notes (для security-auditor):**
- Нет работы с секретами в этом task. Не модифицируется `.env`-handling, не добавляются новые secrets, не меняется sudoers-rule.
- Сам файл `orangetrack_source.py` создан в Task 1 со SSRF-allowlist (Decision 13) и scheme-filtering (Decision 2) — security-сторона предсуществует на момент деплоя.
