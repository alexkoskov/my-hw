# Task 3: Wire orangetrack into `news_bot.py`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Завершить интеграцию orangetrack в основной runtime, подключив парсер из Task 1 (`orangetrack_source.py`) к `news_bot.py`. Это включает:

1. Добавление двух хост-вариантов (apex + www) в `NETLOC_TO_SOURCE` так, чтобы `_resolve_source_name` возвращал `'orangetrack'` для обоих, и записей в `SOURCE_EMOJI` / `SOURCE_LABEL` для отображения в admin-ping.
2. Создание новой функции `_fetch_orangetrack_entries`, которая по Decision 4 владеет полным циклом: создаёт **функционально-локальный** инстанс `OrangetrackPingAggregator`, получает RSS-ленту, на каждой entry применяет entry-level SSRF-guard (`_is_allowed_orangetrack_url` per Decision 13), вызывает `orangetrack_source.fetch_orangetrack_article(entry, notifier=aggregator.add)` для разрешённых entries, прикрепляет parsed body fields к entry dict, в `try/finally` гарантирует `aggregator.emit(send_admin_notification)` при `not is_empty()`.
3. Регистрация функции в `SOURCES` registry list (после `_fetch_mattel_entries`).
4. Добавление в `fetch_full_article` ветки **pass-through** для `orangetrackdiecast.com` — она читает уже-заполненные body fields с entry dict и возвращает каноничный dict (`{'title','subtitle','paragraphs','images','blocks'}`) **без второго HTTP-запроса**. Это критично, потому что aggregator живёт только во время `_fetch_orangetrack_entries`; перепарсинг в b3-фазе не имел бы куда репортить ошибки и нарушил бы single-ping-per-tick инвариант.

Что **не делается** (по Decision 4): shared `_fetch_rss_entries` остаётся нетронутым; `feeds.json` не модифицируется (orangetrack feed URL живёт как module-level constant `_FEED_URL` внутри `orangetrack_source.py`).

После Task 3 интеграция готова к Task 4 (registry-set assertion) и Task 5 (deploy FILES list sync).

## What to do

1. В `news_bot.py` найти `NETLOC_TO_SOURCE` (на строке ~745) и добавить два ключа: `'orangetrackdiecast.com': 'orangetrack'` и `'www.orangetrackdiecast.com': 'orangetrack'`. Регистр ключей — lowercase (соответствует тому, как `_resolve_source_name` нормализует netloc через `.lower()`).
2. В `SOURCE_EMOJI` (строка ~777) добавить `'orangetrack': '\U0001F535'` (синий круг). В `SOURCE_LABEL` (строка ~782) добавить `'orangetrack': 'orangetrack'`.
3. В `fetch_full_article` (строка ~1265) добавить новую ветку **перед** `logger.warning` fallback — для домена `orangetrackdiecast.com` (apex и www) функция читает с entry dict pre-populated поля (`title`, `subtitle`, `paragraphs`, `images`, `blocks`), собранные `_fetch_orangetrack_entries` на предыдущем шаге, и возвращает каноничный dict. Никаких `requests.get` в этой ветке. Если поля отсутствуют (defensive — может произойти, если запись попала через нестандартный путь), вернуть `None` и залогировать на WARNING (не raise).
4. Создать новую функцию `_fetch_orangetrack_entries(notifier=None)` рядом с `_fetch_mattel_entries`. Она:
   - импортирует `orangetrack_source` (top-of-file import добавить вместе с существующими `lamley_source`, `autoevolution_source`),
   - создаёт **функционально-локальный** `aggregator = orangetrack_source.OrangetrackPingAggregator(instance_label=os.getenv('INSTANCE_LABEL'))`,
   - всю последующую логику оборачивает в `try: ... finally: if not aggregator.is_empty(): aggregator.emit(send_admin_notification)`,
   - получает RSS через `feedparser.parse(orangetrack_source._FEED_URL)` (или существующий хелпер `fetch_rss`, если он годится — но НЕ через `load_feeds()`/`_fetch_rss_entries`); HTTP-ошибки/timeout/XML-parse → `aggregator.add('FEED_HTTP_<status>'/'FEED_TIMEOUT'/'FEED_XML_PARSE', _FEED_URL)` и `return []`,
   - для каждой entry в feed:
     - **entry-level guard (Decision 13):** если `not orangetrack_source._is_allowed_orangetrack_url(entry.get('link'))` → `aggregator.add('ENTRY_HOST_REJECTED', entry.get('link') or '')` и `continue` (entry никогда не доходит до pending_articles),
     - вызывает `article = orangetrack_source.fetch_orangetrack_article(entry, notifier=aggregator.add)`. Если `article is None` → пропускает entry (notifier уже вызван внутри парсера),
     - иначе формирует **plain dict** с полями: `link`, `title`, `published`, `summary` (как делает `_fetch_rss_entries`) + добавляет `subtitle`, `paragraphs`, `images`, `blocks` из `article` (НЕ заменяет уже существующие поля entry, только добавляет body), стампует `feed_url=_FEED_URL` и `source_name='orangetrack'`, append в `entries`,
   - возвращает `entries`.
5. В `SOURCES` (строка ~1363) добавить `_fetch_orangetrack_entries` в конец списка. Порядок — после `_fetch_mattel_entries`, чтобы новый источник был последним в логе (как сделано с Mattel при его добавлении).
6. Убедиться, что top-level импорты включают `orangetrack_source` рядом с другими source-модулями.

## Details

**Files:**
- `news_bot.py` — добавить:
  1. top-level `import orangetrack_source` (рядом с `import lamley_source`, `import autoevolution_source`),
  2. два ключа в `NETLOC_TO_SOURCE` (~745),
  3. одну запись в `SOURCE_EMOJI` (~777) и одну в `SOURCE_LABEL` (~782),
  4. ветку pass-through в `fetch_full_article` (~1265, перед `logger.warning` fallback),
  5. новую функцию `_fetch_orangetrack_entries(notifier=None)` (рядом с `_fetch_mattel_entries`, ~1347),
  6. добавление функции в список `SOURCES` (~1363).

**Dependencies:**
- Task 1 (`orangetrack_source.py`) должен быть готов и иметь публичные: `_FEED_URL`, `fetch_orangetrack_article(entry, notifier=None)`, `_is_allowed_orangetrack_url(link) -> bool`, `OrangetrackPingAggregator`.
- Существующая в `news_bot.py` функция `send_admin_notification` (используется как target для `aggregator.emit`).
- `os.getenv('INSTANCE_LABEL')` (env var опциональна; если не задана, aggregator формирует summary без bracketed-prefix).

**Edge cases:**
- Entry без `link` (None или пустая строка) — entry-level guard должен корректно вернуть `False` (т.е. `_is_allowed_orangetrack_url(None)` возвращает `False` без исключения; обеспечивается Task 1).
- Entry с link `https://orangetrackdiecast.com.attacker.example/payload` — обе защиты должны её отвергнуть. Однако: substring `'orangetrackdiecast.com' in 'orangetrackdiecast.com.attacker.example'` равно `True`, поэтому если новая ветка `fetch_full_article` использует substring `in` (как существующие ветки lamley/mattel/autoevolution), subdomain-attack пройдёт через диспетчер и попадёт в pass-through. Решение: для НОВОЙ ветки использовать exact-host check (`urlparse(link).netloc.lower() in {'orangetrackdiecast.com', 'www.orangetrackdiecast.com'}`) — это устраняет substring-ловушку без расширения blast radius на существующие ветки. Тест `test_fetch_full_article_subdomain_attack_not_routed_to_orangetrack` фиксирует поведение.
- Двойной вызов `_fetch_orangetrack_entries` (например, retry) — каждый вызов создаёт свежий aggregator; нет cross-call state-leak.
- Exception внутри iteration по entries — `try/finally` гарантирует, что `aggregator.emit` будет вызван если в bag есть события; exception пробрасывается дальше для обработки в `news_bot.job()` (как это делается с другими sources).
- `INSTANCE_LABEL` env var отсутствует — aggregator формирует summary без `[<label>]` prefix (поведение реализовано в Task 1 в `OrangetrackPingAggregator.__init__`).
- Empty feed (`entries=[]` после успешного fetch) — функция возвращает `[]`, aggregator пуст, `emit` не вызывается.

**Implementation hints:**
- Избежать substring `in` для роутинга в новой ветке `fetch_full_article`. Использовать exact match на основе `urlparse(link).netloc.lower()`. Существующие ветки lamley/mattel/autoevolution оставить без изменений, чтобы не расширять blast radius.
- При создании entry dict в `_fetch_orangetrack_entries` следовать стилю `_fetch_rss_entries` (строки 1330-1343 news_bot.py): plain dict с явным выбором полей, не `dict(entry)` (избегаем feedparser internals, которые не JSON-serialisable для `pending_articles.paragraphs`/`pending_articles.blocks`).
- `fetch_rss` (если используется) — проверить, поддерживает ли он напрямую URL-аргумент или ожидает запись из feeds.json. Скорее всего проще использовать `feedparser.parse(_FEED_URL)` напрямую с try/except вокруг network errors, как делает `fetch_mattel_news`.
- Импорт `os` уже есть в news_bot.py (используется в job-scheduling); добавлять не нужно.
- `OrangetrackPingAggregator` инстанцируется ВНУТРИ функции, не на module-level. Это критичный инвариант (Decision 4 / 5): function-local lifetime гарантирует, что (а) нет cross-tick state leak, (б) GC через try/finally чистит инстанс даже при exception.
