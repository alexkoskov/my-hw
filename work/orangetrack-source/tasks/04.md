## Description

После Task 3 (wiring orangetrack в `news_bot.py` — записи в `NETLOC_TO_SOURCE` / `SOURCE_EMOJI` / `SOURCE_LABEL`, добавление `_fetch_orangetrack_entries` в `SOURCES`) существующие set-assertion'ы в `tests/test_sources_registry.py` будут падать: код регистра расширен, тесты — нет. Эта задача синхронизирует тесты с новой реальностью. Decision 11 техспека прямо требует выполнить апдейт в одном коммите с регистрационными изменениями (для нашего флоу — в той же волне), чтобы `pytest tests/` оставался зелёным после Wave 2.

Важно: это чисто tests-only апдейт. `feeds.json` НЕ модифицируется (Decision 4 — `_FEED_URL` живёт как module-level constant в `orangetrack_source.py`, а не в `feeds.json`). Никакого продакшн-кода эта задача не трогает.

Конкретно нужно расширить три точки в `tests/test_sources_registry.py`:

1. `TestNetlocToSource.test_has_exactly_the_five_keys` (текущее множество — 5 ключей: autoevolution × 2, lamley × 2, mattel × 1) — теперь 7 ключей: добавляются `'orangetrackdiecast.com'` и `'www.orangetrackdiecast.com'`. Имя метода теряет смысл («five») — переименовать в нейтральное (например, `test_has_exactly_the_expected_keys`). Doc-string класса (`"""Decision 4 — the five explicit netloc keys."""`) подровнять под новую реальность («the explicit netloc keys for known sources» или эквивалент без числа).
2. `TestNetlocToSource.test_values_are_only_the_three_source_names` — целевое множество values становится `{'autoevolution', 'lamley', 'mattel', 'orangetrack'}` (это и есть тот самый Decision 11 set-assertion). Имя метода тоже устаревает («three») — переименовать (например, `test_values_are_the_expected_source_names`).
3. `TestSourcesRegistry.test_sources_registry_shape` — ожидаемый список расширяется до `['_fetch_rss_entries', '_fetch_mattel_entries', '_fetch_orangetrack_entries']`. Порядок: новый фетчер третьим, в конец списка (та же конвенция, как добавлялся `_fetch_mattel_entries` в Task 6 manual-review-workflow).

Остальные тесты файла (`TestResolveSourceName`, `TestFetchRssEntries`, `TestFetchMattelEntries`, `TestSourcesRegistry::test_sources_are_callables`, `TestSourcesRegistry::test_sources_accept_notifier_kwarg`) НЕ должны меняться по поведению и продолжать проходить.

Переименовать метод (например, `test_values_are_the_expected_source_names`).
  - `TestSourcesRegistry.test_sources_registry_shape` (строки ~322-327, тело — `assert [f.__name__ for f in SOURCES] == ['_fetch_rss_entries', '_fetch_mattel_entries']`): расширить список до `['_fetch_rss_entries', '_fetch_mattel_entries', '_fetch_orangetrack_entries']`.

**Dependencies:**
- Task 3 (wiring в `news_bot.py`) — должен быть применён ДО запуска тестов этой задачи. До Task 3 наш апдейт сделает тесты красными (код всё ещё имеет старые 5 ключей и 2 фетчера, тесты ожидают 7 / 3). С точки зрения волн: мы Wave 2, Task 3 — тоже Wave 2 (`depends_on: [3]`). Лидер фичи должен убедиться, что код-апдейт в `news_bot.py` (Task 3) уже в рабочем дереве перед тем как агент Task 4 запустит pytest — иначе red-stage будет неинформативным (упадёт по другой причине).

**Edge cases:**
- Имена тестов содержат числа («five», «three»). Сохранить старые имена и просто расширить множества — оставить намеренно вводящие в заблуждение имена. Лучше переименовать.
- Порядок `SOURCES` в `news_bot.py` после Task 3 ожидается `[_fetch_rss_entries, _fetch_mattel_entries, _fetch_orangetrack_entries]` — новый фетчер в конец, по проектному соглашению (см. как `_fetch_mattel_entries` был добавлен в Task 6 manual-review-workflow). Если Task 3 поставит фетчер в другой позиции, `test_sources_registry_shape` поломается — это сигнал, что нужно или поправить порядок в `news_bot.py`, или подстроить ожидания в тесте; первое предпочтительнее (соглашение сильное).
- `TestSourcesRegistry::test_sources_accept_notifier_kwarg` итерирует `SOURCES` и вызывает `fetcher(notifier=None)`. Тест уже monkeypatch'ит `news_bot.load_feeds`, `news_bot.fetch_rss`, `news_bot.fetch_mattel_news` — но НЕ `news_bot.fetch_orangetrack` или какой-либо его эквивалент. Если `_fetch_orangetrack_entries` при `notifier=None` пытается реально зайти в сеть (даже за RSS-фидом), тест может стать красным после Task 3 без апдейта здесь. Это НЕ зона ответственности Task 4 — это намёк на gap в Task 3 (тестируемость). Если поймали такую регрессию: НЕ расширять scope Task 4 на добавление monkeypatch'а; вместо этого зафиксировать в decisions.md и эскалировать к лидеру фичи. Наша задача — только три явных set/list-assertion'а.

**Implementation hints:**
- Минимальный диф: заменить тело каждого из трёх методов и (опционально) их имена. Не трогать соседние тесты, doc-strings других классов, импорты.
- Перед апдейтом запустить `pytest tests/test_sources_registry.py -v` чтобы зафиксировать red-stage и убедиться, что красные ровно три теста (keys, values, shape) — больше ничего.
