## Required Skills

## Description

Полный аудит качества тестов фичи orangetrack-source — после того как Wave 1 + Wave 2 (Tasks 1-5) написали и/или обновили все тестовые файлы. Цель — независимая проверка, что тестовое покрытие соответствует Testing Strategy из tech-spec и реально ловит регрессии, а не имитирует покрытие.

Аудитор читает три файла, которые были созданы или обновлены задачами 1, 2, 4:

- `tests/test_orangetrack_source.py` (новый, ~40-50 кейсов, создан Task 1).
- `tests/test_boilerplate_filter.py` (расширен 5-7 кейсами в Task 2 — affiliate-патерны + boundary + ReDoS-safety).
- `tests/test_sources_registry.py` (one-line set-assertion update в Task 4).

Аудит — read-only review. Не правит тесты, не запускает их (кроме одной baseline-проверки, что они зелёные). Производит структурированный отчёт с найденными пробелами, рисками и предложенными доп.кейсами. Отчёт — единственный артефакт задачи.

Эта задача — часть Audit Wave (после Wave 2, до Final Wave / Pre-deploy QA). Параллельна Task 6 (Code Audit) и Task 7 (Security Audit). Выполняется без ревьюеров — аудитор сам и есть конечная инстанция в этой волне; результаты аудитов читает Task 9 (pre-deploy QA) и решает блокировать релиз или нет.

## What to do

2. Прочитать `tests/test_orangetrack_source.py` целиком. Сверить наличие всех тест-классов из Testing Strategy:
   - `TestPrimaryPath` — content:encoded parse (≥15 кейсов из tech-spec).
   - `TestSSRFAllowlist` — Decision 13, ОБЯЗАТЕЛЬНО оба call-site сценария: entry-level guard в `_fetch_orangetrack_entries` и fallback-level guard в `fetch_orangetrack_article`. Subdomain attack, cloud metadata IP, scheme-relative, malformed URL, non-http scheme.
   - `TestFallbackPath` — HTTP scrape (≥10 кейсов: 503, 404, timeout, 302 redirect, 5MB cap, parse-empty, connection refused, UTF-8, exception propagation).
   - `TestWPBlockDriftMitigation` — Decision 3, минимальный HTML без wp-block-* классов.
   - `TestYouTubeEmbedWrapping` — Decision 8, ОБЯЗАТЕЛЬНО негативный кейс с attacker-host + позитивные с youtu.be / youtube.com.
   - `TestOrangetrackPingAggregator` — bounds (50/500/3500), ordering (FEED_* < ENTRY_* < ART_*, alphabetical внутри), `_safe_for_ping` sanitization (контроль-байты не дают spoofing), `emit()` swallow-on-error, `instance_label` prefix on/off, lifecycle (try/finally в `_fetch_orangetrack_entries`).
   - `TestDispatcherIntegration` — apex + www routing, pass-through через `fetch_full_article`, defense-in-depth (subdomain attack отбракован парсером, не диспетчером).
3. Прочитать новые кейсы в `tests/test_boilerplate_filter.py`. Сверить:
   - Positive: `*QUICK LINK!* Buy from <store> now.`, `Buy now from 1 Stop Diecast`.
   - Negative: `I'd buy that for $1`, длинный paragraph >120 chars с словом 'buy'.
   - Boundary: ровно 120 chars (filtered), 121 chars (preserved).
   - ReDoS-safety: `'a' * 60 + 'buy' * 20 + ' shop now'` — `is_boilerplate(s)` возвращает за <100ms.
4. Прочитать обновлённый `tests/test_sources_registry.py`. Сверить, что set-assertion = `{'autoevolution', 'lamley', 'mattel', 'orangetrack'}`.
5. Для каждого тестового метода проверить (быстрый сэмпл + spot-check на подозрительных):
   - Assertion реально проверяет поведение (не `assert True`, не `assert result is not None` без следующих утверждений по содержимому).
   - Нет brittle-связей: реальное время (`time.time()` без freezegun / стабильного фикстура), реальная сеть (нет моков на `requests.get`), реальный random (нет seed). Исключение — там, где Verify-smoke специально использует live-окружение (в этой фиче таких unit-тестов быть не должно — все unit, mock-based).
   - Нет дублирования (одинаковая суть в разных тестах).
6. Test pyramid balance: пересчитать кейсы. Цель — ~40-50 unit-тестов в `test_orangetrack_source.py`. Integration-тесты — "None new" по tech-spec line 438; убедиться, что это решение действительно валидное (т.е. покрытие на уровне `test_distributed_schedule_integration.py` не сломалось от введения 4-го источника). Если сломалось — это отдельный finding.
7. Test naming: классы `TestXxx`, методы — descriptive snake_case (например, `test_subdomain_attack_rejected`, `test_safe_for_ping_strips_newlines`). Это lamley-pattern из `tests/test_lamley_source.py`.
8. Записать отчёт в `work/orangetrack-source/logs/audit/test-audit.md` по структуре в секции Details ниже. Для каждого пробела — severity (critical / high / medium / low), описание, предложенный test case (название + pseudo-Given-When-Then в одну строку).

### Edge cases

- Тестовый файл может быть отсутствующим, если Task 1 завершился частично (без тестов). В этом случае — критический FAIL без необходимости продолжать.
- Кейсы могут быть формально перечислены, но с пустым/no-op assert. Spot-check на наличие осмысленных утверждений обязателен.
- "Один тест-метод проверяет 5 разных вещей" (god-test) — отдельный finding с severity medium.
- Mock'и могут быть слишком широкими (`Mock()` вместо явного `Mock(spec=...)`), что прячет регрессии. Отметить как low/medium.
- Проверить, что моки `requests.get` правильно эмулируют `iter_content` для streaming-кейсов в `TestFallbackPath` — иначе тесты на 5 MB cap не реалистичны.

- Severity rubric:
  - **critical**: отсутствует тест на security-критичный сценарий (SSRF allowlist, ReDoS-safety, scheme filter, размер cap). Блокирует релиз.
  - **high**: отсутствует тест на behaviour из user-spec AC. Блокирует релиз без явного operator-override.
  - **medium**: brittle-тест, god-test, дублирование, слишком широкий mock. Можно фиксить пост-релизом.
  - **low**: косметика — naming, missing docstring, незначительный пробел в edge case.
- Аудитор НЕ правит упавшие тесты — это работа Task 1/2/4 в случае возврата. Если pytest baseline-прогон красный — фиксируем в отчёте как automatic FAIL и останавливаемся.
- Не дублируй работу Task 6 (code audit) и Task 7 (security audit). Test audit смотрит на качество тестов, не на качество тестируемого кода. Если тест есть и проходит, но проверяет неправильное поведение — это test-audit finding. Если код кривой, но тест корректно ловит правильное поведение — это code-audit finding, не сюда.
