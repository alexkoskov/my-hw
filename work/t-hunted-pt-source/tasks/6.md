# Task 6: Deploy plumbing (3 FILES lists) + pytest invariant test

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Wire новый модуль `t_hunted_source.py` (созданный в Task 1) в три синхронных deploy FILES-массива: `deploy.sh`, `.github/workflows/deploy.yml`, `.github/workflows/deploy_test.yml`. Эти три списка обязаны меняться в одном коммите — иначе сервер словит `ImportError` на следующем cron tick (см. INVARIANT-комментарии в `deploy.sh:22-24` и `deploy.yml:109-113`). Это известный Risk R7 в tech-spec.

Дополнительно создаём `tests/test_deploy_files_invariant.py` — pytest-инвариантный тест, который читает все три deploy-файла и проверяет, что `"t_hunted_source.py"` присутствует в их FILES-массивах. Так Risk R7 ловится при обычном `pytest tests/` в CI, а не на стадии деплоя (где fallback — `grep`-проверка вручную).

Position в массиве: после `"orangetrack_source.py"` — следуем существующей конвенции группировки source-файлов (autoevolution / mattel / lamley / orangetrack — по "addition order", не alphabetical, см. code-research §A.6).

## What to do

1. **TDD: написать сначала `tests/test_deploy_files_invariant.py`** с тремя тестами (см. TDD Anchor). Запустить — все три должны падать (модуля ещё нет в FILES). Это явно фиксирует Risk R7 как regression-точку.
2. **Добавить `"t_hunted_source.py"` в `deploy.sh`** — новая строка между `"orangetrack_source.py"` и `"telegraph_publisher.py"` в массиве FILES (текущая позиция: после строки 42 в `deploy.sh`).
3. **Добавить `"t_hunted_source.py"` в `.github/workflows/deploy.yml`** — новая строка в массиве FILES шага "Copy files to server" (после `"orangetrack_source.py"`, текущая позиция: после строки 128).
4. **Добавить `"t_hunted_source.py"` в `.github/workflows/deploy_test.yml`** — то же самое в массиве FILES шага "Copy files to server" (после `"orangetrack_source.py"`, текущая позиция: после строки 99).
5. **Запустить TDD-тесты повторно** — все три ассерта должны стать зелёными.
6. **Запустить smoke grep** — `grep -l "t_hunted_source.py" deploy.sh .github/workflows/deploy.yml .github/workflows/deploy_test.yml` должен вывести все три имени файла.

## TDD Anchor

Тесты, которые нужно написать ДО изменений в deploy-файлах. Пишем → запускаем → убеждаемся что падают (модуля ещё нет в FILES) → правим три deploy-файла → убеждаемся что проходят.

- `tests/test_deploy_files_invariant.py::test_t_hunted_source_in_deploy_sh` — читает `deploy.sh`, ассертит что строка `"t_hunted_source.py"` присутствует в FILES-массиве (минимальная регулярка по тексту файла; не парсим bash AST).
- `tests/test_deploy_files_invariant.py::test_t_hunted_source_in_deploy_yml` — читает `.github/workflows/deploy.yml`, та же ассерция в его FILES-массиве (внутри блока шага "Copy files to server").
- `tests/test_deploy_files_invariant.py::test_t_hunted_source_in_deploy_test_yml` — читает `.github/workflows/deploy_test.yml`, та же ассерция.

Все три ассерта работают через простое чтение файла + `in`-проверку или `re.search` — никакого bash/YAML-парсинга не требуется (это намеренно — тест отражает то, что shell-grep делает на стадии деплоя).

## Details

**Files:**
- `deploy.sh` — массив FILES, lines 37-59. Текущая структура: news_bot.py → 4 source-модуля (autoevolution / mattel / lamley / orangetrack) → telegraph_publisher → pending_articles_repo → llm-modules → admin_alerts → boilerplate_filter → config-files (feeds.json / requirements.txt / .env.example) → ux-guidelines.md. Вставка: одна новая строка `"t_hunted_source.py"` между текущей строкой 42 (`"orangetrack_source.py"`) и строкой 43 (`"telegraph_publisher.py"`).
- `.github/workflows/deploy.yml` — массив FILES внутри шага "Copy files to server" (`run: |` блок), lines 123-145. Структура зеркалит `deploy.sh` byte-for-byte. Вставка: одна новая строка с теми же отступами (4 пробела внутри `run`-блока, как остальные элементы массива) между `"orangetrack_source.py"` и `"telegraph_publisher.py"`.
- `.github/workflows/deploy_test.yml` — массив FILES в шаге "Copy files to server", lines 94-116. Структура идентична deploy.yml (комментарий на line 91-92 явно говорит "FILES list mirrors deploy.yml byte-for-byte"). Та же одна новая строка в той же позиции.
- `tests/test_deploy_files_invariant.py` — НОВЫЙ файл. ~30-50 LOC. Импорты: `pathlib.Path` для чтения. Один класс `TestDeployFilesInvariant` или три отдельных функции. Каждый тест: open() файла → читает содержимое → `assert '"t_hunted_source.py"' in content`. Пути в тесте — через `pathlib.Path(__file__).resolve().parent.parent` (repo root), чтобы не зависеть от CWD.

**Dependencies:**
- Task 1 (Wave 1) — создаёт `t_hunted_source.py` на диске. Без него pytest-инвариант пройдёт (так как только грепает строку в deploy-файлах), но реальный `deploy.sh` упадёт на проверке существования файла (`if [[ ! -f "$file" ]]; then exit 1`). Поэтому depends_on: [1].
- Никаких новых Python-пакетов. `pathlib` — stdlib.

**Edge cases:**
- Trailing newlines, разный whitespace в bash vs YAML — тест должен быть устойчив (ищем подстроку `"t_hunted_source.py"` с двойными кавычками; эта форма одинаковая в bash-массиве и в YAML-`run`-блоке).
- Файл `t_hunted_source.py` на диске НЕ обязателен в момент TDD-фазы для теста — pytest-инвариант грепает только deploy-файлы, не fs (намеренное разделение: deploy.sh уже имеет fs-проверку, дублирование не нужно).
- Если кто-то в будущем поменяет имя файла или удалит модуль, инвариант-тест поймает это в CI до деплоя — это и есть value этого теста (R7 mitigation).

**Implementation hints:**
- Не парсить bash или YAML AST — это overkill и хрупко. Простая подстрока `'"t_hunted_source.py"'` в тексте файла достаточна (та же логика, что у shell-grep, но интегрирована в pytest).
- Сохранять byte-for-byte идентичность трёх FILES-массивов — это явный invariant из комментариев в самих файлах ("FILES list mirrors deploy.yml byte-for-byte"). Одна новая строка в той же позиции в каждом из трёх.
- Не трогать ничего вне FILES-массивов — никаких изменений в env-блоках, restart-секциях, концурренси-группах, comments. Diff должен быть минимальным: +1 line в каждом из трёх deploy-файлов + 1 новый test-файл.
- Position rationale (из code-research §A.6): четыре source-модуля сгруппированы в lines 39-42 (`deploy.sh`), порядок отражает время добавления (addition order). `t_hunted_source.py` идёт next-in-order, то есть после orangetrack.
