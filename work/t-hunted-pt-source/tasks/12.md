## Description

Финальный pre-deploy acceptance-gate для фичи `t-hunted-pt-source` перед merge'ем в `dev`. Задача — прогнать полный pytest-сьют (unit + integration), проверить каждый AC из user-spec (AC1-AC10) и каждый технический критерий из tech-spec «Acceptance Criteria», проверить деплой-инвариант (т.е. что `t_hunted_source.py` присутствует в трёх FILES-массивах: `deploy.sh`, `.github/workflows/deploy.yml`, `.github/workflows/deploy_test.yml`), проверить доступность RSS-эндпоинта `t-hunted.blogspot.com`, проверить smoke `news_bot._source_hashtag()` → `#thunted`, и собрать traceability-матрицу AC → тесты/smoke-чек в QA-отчёт.

Это финальная волна (Wave 5). Депенды: Task 9 (Code Audit), Task 10 (Security Audit), Task 11 (Test Audit) должны быть завершены до старта — их находки (если были) должны быть применены лидером до того, как qa-runner соберёт зелёный suite. QA не делает ревью — только запускает тесты, проверяет ACs, фиксирует пасс/фейл.

Если хотя бы один critical найден — `status: failed` в JSON-отчёте, фичу не катим. Если все critical = 0 и majors не блокирующие — `status: passed`, лидер может мержить `feature/t-hunted-pt-source` → `dev`. ACs, которые объективно не проверяются без live-канала (визуальный рендеринг preview-card, RU-качество перевода, отсутствие алертов в журнале сервиса), маркируются `not_verifiable` и переносятся в `deferredToPostDeploy` для Task 14 (Post-deploy verification).

Это non-code task: qa-runner ничего не имплементит, только запускает чеки и пишет JSON-отчёт. Никаких ревью на этой задаче — выход qa-runner'а это и есть единственный гейт.

### Implementation hints

- **QA — не ревью.** Не делай code review (это уже сделали Tasks 9-11). Только запускай чеки, сверяй ACs, фиксируй пасс/фейл. Если что-то в коде смущает по стилю/качеству, но AC выполнен — это не finding QA, упоминай это в decisions.md как замечание для будущего.
- **Traceability — главный артефакт.** Каждый AC1-AC10 user-spec и каждый AC из tech-spec должен иметь `evidence`. Конкретный test-name предпочтительнее, чем «вижу в коде». Если AC проверяется shell-командой — вписывай команду и её stdout.
- **`not_verifiable` ≠ fail.** Если AC объективно не проверяется без live-канала (визуальный рендер, RU-качество, journalctl за N дней) — это `not_verifiable`, перенос в `deferredToPostDeploy` с конкретными steps. НЕ маркируй `failed`.
- **Severity escalation:** major можно поднять до critical, если найденное затрагивает data integrity или core user workflow (например, hashtag рендерится не как `#thunted` — critical, не major).
- **Решение `passed`/`failed`** — детерминистичное: `criticals == 0` → passed, `criticals ≥ 1` → failed. Не «mostly passed».
- **decisions.md entry** — компактный (1-3 предложения summary). НЕ дублируй JSON-отчёт целиком в decisions.md, только ссылку и итог.
- **JSON-схема** — точно по pre-deploy-qa SKILL.md (см. секцию «JSON report → `logs/working/qa-report.json`», только путь у нас другой: `logs/qa/pre-deploy-qa.json` per task input).
- **Аудит-отчёты:** прочти JSON-отчёты `logs/audits/code-audit.json`, `logs/audits/security-audit.json`, `logs/audits/test-audit.json` ДО старта pytest — критичные находки из аудитов должны быть применены лидером, иначе QA увидит регрессии. Аудит-задачи (9, 10, 11) сами являются reviewers — у них нет отдельных раундов ревью; их JSON-отчёт и есть единственный артефакт. Если видишь, что critical findings из аудитов НЕ применены (например, security audit нашёл SSRF leak, а в коде он остался) — это сразу `failed`, перечисляй такие в findings.
- **AC1-AC10 mapping (быстрый референс):**
  - AC1 (RSS-фид) → smoke `python -c feedparser…` + `pytest -k integration_t_hunted`.

  - AC6 (хештег `#thunted #news`) → `pytest tests/test_telegram.py -k thunted` + smoke `_source_hashtag`.
  - AC7 (LLM prompt + glossary) → `pytest tests/test_ux_guidelines_structure.py`.
  - AC8 (PT boilerplate) → `pytest tests/test_boilerplate_filter.py -k portuguese`.
