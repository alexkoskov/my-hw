# Task 14: Post-deploy verification

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Финальная верификация фичи `t-hunted-pt-source` на живом окружении после успешного деплоя (Task 13). Задача охватывает оба окружения по последовательности из tech-spec Decision 6:

1. **Test-инстанс (сразу после dev-merge):** `news_bot_test.service` на `/home/hwbot/bot_test/` публикует в `@myhwchannel123`. Здесь проверяем что первая t-hunted публикация успешно проходит весь pipeline (RSS → parser → boilerplate → LLM транскреация → Telegraph → Telegram preview), хештег рендерится как `#thunted` без обрезания, hero-картинка отрисована, RU-перевод без PT-протечек, нет `[E031-E033]` алертов в журнале.
2. **7-дневное наблюдение:** оператор спот-чекает 5-10 первых t-hunted переводов против оригиналов на t-hunted.blogspot.com и оценивает RU-качество не хуже autoevolution baseline. Существующие источники (autoevolution / lamley / orangetrack) продолжают публиковаться в обычной каденции.
3. **Prod-инстанс (только после положительной верификации test):** оператор инициирует `dev → main` промоушн (отдельная активность вне этой задачи); после промоушна аналогичные проверки повторяются на `news_bot.service` (prod-канал) с урезанным окном (24h, не 7d, т.к. поведение уже верифицировано на test).

Задача чисто верификационная: нового кода нет, единственный артефакт — QA-отчёт `work/t-hunted-pt-source/logs/qa/post-deploy-qa.json` со статусами каждой проверки, ссылками на проверенные посты в канале, дампами grep-команд. Если любой блокирующий критерий проваливается (PT-протечка в RU, `[E031-E033]` всплески, регрессия в существующих источниках, RU-качество ниже baseline), отчёт фиксирует факт и оператор не катит `dev → main` — итерируется следующим PR (промпт/глоссарий/парсер).

Инструменты: bash + ssh (admin alerts grep), Telegram-клиент (визуальная проверка preview, hashtag, hero-image), браузер (Instant View / Telegra.ph страница). Telegram MCP и Playwright не используются — операторская визуальная проверка по user-spec verification_strategy (см. user-spec "Как проверить → Пользователь проверяет").

## What to do

1. **Дождаться первой t-hunted публикации в `@myhwchannel123`** (24-48 ч от merge dev). Открыть Telegram-клиент, найти пост, зафиксировать URL поста (для отчёта).
2. **Визуально проверить preview card** — hero-картинка отрисована, `#thunted #news` хештег виден, без обрезания, кликабельный, эмодзи 🟤 на title (safety net из Decision 7).
3. **Открыть Instant View / Telegraph-страницу из preview** — прочитать RU body целиком, убедиться: нет PT-фраз (compartilhar, marcadores, postado, и т.п.), нет EN-фраз (leak guard работает), текст связный, эмодзи/форматирование на месте.
4. **Проверить отсутствие `[E031-E033]` алертов** в журнале test-сервиса за первые 24 ч после деплоя: `ssh hwbot 'journalctl -u news_bot_test.service --since "24 hours ago" | grep -E "\[E03[1-3]\]"'` — вывод пустой (или только подтверждённые transient errors). Захватить вывод команды (даже пустой) в отчёт.
5. **Запустить 7-дневный watch** — раз в сутки повторять grep команду из шага 4 с расширенным окном (`--since "7 days ago"`), фиксировать количество найденных алертов в отчёте (накопительно).
6. **Спот-чек RU-качества** — после того как накопилось ≥5 t-hunted публикаций в канале: оператор сравнивает каждый RU-пост с оригиналом на t-hunted.blogspot.com (открывается по `source link` в footer Telegraph-страницы). Критерий: RU-качество субъективно «не хуже autoevolution baseline» по тону, связности, точности терминологии. Если выявлены систематические проблемы — записать наблюдения (какие термины глоссария нуждаются в правке, какие конструкции LLM передаёт слабо) для последующего follow-up PR.
7. **Проверить отсутствие регрессии в существующих источниках** — пролистать `@myhwchannel123` за 7 дней, убедиться что autoevolution / lamley / orangetrack продолжают публиковаться в обычной каденции (по ~1-3 поста/день для основных, как в baseline). Если какой-то источник «замолчал» — это регрессия, не катим в prod.
8. **Сформировать итоговый QA-отчёт** — записать в `work/t-hunted-pt-source/logs/qa/post-deploy-qa.json` структурированный JSON со списком проверок, статусом каждой (pass/fail/deferred), артефактами (URL постов, дампы grep, заметки оператора), решением по `dev → main` промоушну (go/no-go).
9. **При положительном решении** — оператор сам инициирует `dev → main` PR (вне этой задачи). После promote — повторить grep-проверку из шага 4 уже на `news_bot.service` (prod) с окном 24 ч; добавить prod-секцию в тот же отчёт.

## Verification Steps

### Automated

Автоматических тестов в этой задаче нет — это пост-деплой верификация на живом окружении. Pre-deploy gate (полный pytest suite) пройден в Task 12.

### Smoke

Команды, которые оператор/агент выполняет на сервере и локально:

- `ssh hwbot 'journalctl -u news_bot_test.service --since "24 hours ago" | grep -E "\[E03[1-3]\]"'` → пустой stdout (либо только подтверждённые transient ошибки)
- `ssh hwbot 'systemctl status news_bot_test.service'` → `active (running)`, no recent crash loops
- (Опционально, для подтверждения что парсер действительно вызывался) `ssh hwbot 'journalctl -u news_bot_test.service --since "24 hours ago" | grep -i "t-hunted\|t_hunted_source"'` → должны быть INFO-строки fetch/publish
- (После prod-промоушна) тот же набор команд на `news_bot.service` вместо `news_bot_test.service`

### User

Операторская визуальная проверка через Telegram-клиент и браузер. Эти шаги не автоматизируются (Telegram-side рендеринг + субъективная оценка качества перевода — см. user-spec обоснования):

- Открыть `@myhwchannel123` в Telegram, найти первую t-hunted публикацию, проверить: hero-картинка отрисована, `#thunted` хештег без обрезания и кликабельный, эмодзи 🟤 в title.
- Открыть Instant View / Telegraph-страницу из поста — прочитать RU body, убедиться что нет PT-фраз (compartilhar, marcadores, postado, decalque и т.п. при их наличии в оригинале), нет EN-фраз, текст связный.
- На горизонте 7 дней — спот-чек ≥5 t-hunted постов против оригиналов с `t-hunted.blogspot.com` (источник доступен по footer-ссылке Telegraph): субъективная оценка RU-качества vs autoevolution baseline.
- Пролистать канал за 7 дней — убедиться что autoevolution / lamley / orangetrack публикуются в обычной каденции.

## Details

**Files:**
- `work/t-hunted-pt-source/logs/qa/post-deploy-qa.json` (new) — итоговый QA-отчёт; структура: верхний уровень `{feature, date, environment_test: {...}, environment_prod: {...|null}, decision: "go"|"no-go"|"pending"}`; каждый environment-блок содержит список проверок с полями `name`, `status` (pass/fail/deferred), `evidence` (URL поста / дамп grep / заметка оператора), `timestamp`. Минимум 6 проверок на test (соответствуют Acceptance Criteria), prod-секция заполняется только после prod-промоушна.

**Dependencies:**
- Task 13 (Deploy) должен быть завершён — `feature/t-hunted-pt-source` смержена в `dev`, `news_bot_test.service` рестартован на новом коде, ImportError отсутствует.
- Доступ к серверу `hwbot` через ssh (см. deployment.md sudoers — `journalctl -u news_bot_test.service` доступен через NOPASSWD).
- Доступ к Telegram-клиенту с подпиской на `@myhwchannel123` (test-канал) — у оператора.
- Доступ к админ-чату бота, куда сыпятся алерты (опционально — основной канал верификации это journalctl, но дублирующий канал также полезен).

**Edge cases:**
- **Нет t-hunted публикаций за 24-48 ч.** Возможно: RSS пуст (источник не публиковал новое), либо `MAX_DAILY_POSTS=4` cap съел слот (4 других источника опубликовали раньше). Действие: подождать ещё 24 ч; если за 72 ч пусто — проверить `feedparser.parse(...)` руками, проверить feeds.json deployment, проверить journalctl на ошибки парсера.
- **`[E031]` host-rejected всплеск.** Признак: SSRF allowlist отвергает что-то, что не должен. Действие: захватить URL из алерта, проверить против `_is_allowed_t_hunted_url` логики из Task 1, инициировать hotfix-PR.
- **`[E033]` no-body всплеск.** Признак: Blogger меняет HTML-разметку (`.post-body`/`.entry-content` селектор устарел). Действие: захватить URL из алерта, проверить страницу руками в браузере, обновить селектор в `t_hunted_source.py` follow-up PR.
- **PT-протечка в RU.** Признак: оператор видит португальские слова/фразы в опубликованном Telegraph body. Действие: записать конкретные примеры в отчёт, отметить decision=no-go для prod, инициировать follow-up PR с правкой глоссария / промпта (на чьём этапе протёкло — `_is_mostly_russian` гарантирует только Cyrillic-долю, не отсутствие PT слов; vocabulary-leak могут требовать дополнительной защиты).
- **Регрессия в существующих источниках.** Признак: канал «замолчал» по autoevolution / lamley / orangetrack. Действие: проверить journalctl на ImportError / RuntimeError, проверить dispatcher на ordering (Task 3) — возможна нарушенная if/return цепочка.
- **RU-качество ниже baseline.** Признак: оператор оценивает 5+ постов как «хуже autoevolution». Действие: decision=no-go для prod, follow-up PR с уточнением глоссария (особенно `[VERIFY operator]` маркированных терминов — decalque, carrinho) и/или per-source style block в ux-guidelines.md.

**Implementation hints:**
- Структура `post-deploy-qa.json` — следовать конвенциям из других `logs/qa/*.json` отчётов в репозитории (если есть в `work/completed/`); если нет — спроектировать минималистично, чтобы lead-агент мог принять go/no-go решение по одному файлу.
- При записи URL постов канала использовать формат `https://t.me/myhwchannel123/<message_id>` — стабильные ссылки для последующего аудита.
- 7-day watch — реалистично выполнять не как непрерывный мониторинг, а как ежедневный spot-check (1 раз в сутки). Если архитектура агентов поддерживает scheduled-runs — отчёт можно дописывать инкрементально (статусы deferred → pass по мере прохождения дней). Если нет — оператор завершает задачу одним проходом после накопления данных.
- Skip Telegram MCP / Playwright — user-spec verification_strategy явно указывает что pошел операторская визуальная проверка (Telegram-side рендеринг + субъективная оценка качества не автоматизируются).
- Prod-промоушн (`dev → main`) — оператор инициирует **сам, вне этой задачи**, по результатам go-decision. Не запускать `git push main` или PR-creation скриптами в рамках Task 14.
