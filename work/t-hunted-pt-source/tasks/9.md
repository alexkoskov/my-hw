Перед выполнением задачи загрузи:

## Description

Holistic code-quality audit of the entire t-hunted feature after Waves 1-3 complete. The per-task code reviewers (rounds 1-3) judge each task in isolation; this audit looks across all components together and catches cross-task issues no single per-task reviewer can see: duplicated logic between `t_hunted_source.py` and `lamley_source.py`/`orangetrack_source.py`, architectural drift from the established source-parser pattern, hidden coupling between the new dispatcher branch and the SOURCE_HASHTAG_OVERRIDE map, regressions to shared resources (HTTP session pool, SQLite per-call pattern, LLM client instances) the tech-spec promised would stay untouched, prompt-file invariant breakage in `ux-guidelines.md`, and ImportError-risk wiring gaps between `news_bot.py`, the deploy FILES lists, and the new parser module.

This is an **analysis-only** task: no code, no tests, no source-file edits. The single deliverable is a structured JSON audit report written to `work/t-hunted-pt-source/logs/audits/code-audit.json`. The orchestrating lead (in `/do-feature`) reads the report after Wave 3 closes; if findings exist, the lead spawns a fixer agent to address them before Wave 5 (Pre-deploy QA). The audit task itself has no reviewers — auditors are themselves reviewers; their output is the source of truth.

## What to do

1. Read tech-spec sections **Architecture / Decisions / Shared resources / Risks / Acceptance Criteria** to ground the audit in feature intent.
2. Read `decisions.md` to learn what was decided during execution (deviations, scope changes, review-round outcomes from Waves 1-3) so the audit can flag undocumented drift.
3. Read all source files created or modified by Tasks 1-8 (full enumerated list in **Details → Files to audit**). Don't skim — read the actual current state of each file as it sits after Wave 3 commits.
4. Read the established parser modules `lamley_source.py` and `orangetrack_source.py` end-to-end as comparison baselines. The new `t_hunted_source.py` is supposed to mirror lamley's contract (minus the WAF apparatus per Decision 1) and intentionally *not* adopt orangetrack's aggregator-alert pattern (per Decision 3) — verify both.
5. Run the audit across these review dimensions, scoped to what cross-task review can see:
   - **Cross-component duplicate logic**: helpers copy-pasted from `lamley_source.py` or `orangetrack_source.py` into `t_hunted_source.py` that should be extracted to a shared module; near-duplicate boilerplate-filter rules; near-duplicate admin-alert builder shapes.
   - **Architectural consistency**: signature of `fetch_t_hunted_article` matches the existing source-parser contract (`(link, session, notifier) -> dict|None`); dispatcher branch in `fetch_full_article` follows the same if/return idiom as existing branches (not if/elif — see code-research §F); `NETLOC_TO_SOURCE` / `SOURCE_HASHTAG_OVERRIDE` / `SOURCE_EMOJI` / `SOURCE_LABEL` entries are positioned consistently with siblings.
   - **Shared-resource regression**: tech-spec promised no new singletons, no HTTP-session pool changes, no SQLite-connection lifecycle changes, no LLM-client instantiation. Verify each promise against actual code.
   - **Wiring invariants**: `t_hunted_source.py` appears in all three deploy FILES arrays (deploy.sh, deploy.yml, deploy_test.yml); import in `news_bot.py` resolves; `feeds.json` entry well-formed; no circular import risk.
   - **Prompt-file invariant**: `ux-guidelines.md` system-prompt blockquote markers preserved verbatim (the file is loaded as system prompt at LLM-engine startup; structural damage breaks every transcreation, not just t-hunted); the three required edits are content-anchored, not line-number-anchored.
   - **Boilerplate-filter safety**: the 10 PT patterns are `^`-anchored, length-bounded by `_MAX_BOILERPLATE_LEN = 120`, and have low false-positive risk against EN/RU prose (cross-check against existing tests).
   - **Error-path coverage holes**: cross-task gaps where a failure mode in `t_hunted_source.py` has no corresponding admin-alert builder, or vice versa.
   - **Dead code / unreferenced symbols**: `SOURCE_EMOJI['t-hunted']` and `SOURCE_LABEL['t-hunted']` entries (Decision 7 marks them archived-consumer-only) — verify they're not accidentally relied upon by non-archived code paths.
   - **Doc/code drift**: tech-spec Decisions reference specific behaviours (e.g. Decision 8: existing `_is_mostly_russian` fallback reused) — verify the code matches the decision text.
6. Classify every finding by severity:
   - **critical** — blocks merge: ImportError risk, security regression, broken invariant (e.g. system-prompt blockquote damaged), wrong hashtag emission.
   - **major** — should fix before merge but won't break runtime: notable architectural drift, duplicate logic that should be extracted, missing error-path alert.
   - **minor** — nice-to-fix: cosmetic inconsistency, missing comment, formatting drift.
7. Write the structured audit report to `work/t-hunted-pt-source/logs/audits/code-audit.json`. Create the `logs/audits/` directory first (`mkdir -p`). See **Details → Report format** for the JSON schema.

## Acceptance Criteria

- [ ] Audit report file exists at `work/t-hunted-pt-source/logs/audits/code-audit.json` and is valid JSON.
- [ ] Report is structured **by component** with one section per area: `parser` (`t_hunted_source.py`), `alerts` (`admin_alerts.py`), `wiring` (`news_bot.py` + `feeds.json` + deploy FILES lists), `prompt` (`ux-guidelines.md`), `tests` (all new/extended test files).

- [ ] **Cross-component review** is explicitly addressed in the report with named sections covering: (a) duplicate logic vs `lamley_source.py` / `orangetrack_source.py`, (b) architectural drift from the established source-parser pattern, (c) shared-resource compliance per tech-spec promise.
- [ ] Top-level report fields present: `feature`, `audit_type: "code"`, `auditor` (skill name), `timestamp`, `tasks_audited: [1..8]`, `summary` (1-2 sentence overall verdict), `total_findings` (count by severity), `findings_by_component` (the structured sections), `cross_component_review` (the three named sections above).
- [ ] If zero findings: report still written with `total_findings: {critical: 0, major: 0, minor: 0}` and `summary` explicitly stating "no findings — feature ready for QA".
- [ ] No source code modified by this task (the deliverable is the report alone).

**Audit focus checklist (cross-component issues the audit must explicitly evaluate):**
- Decision 1 compliance: `t_hunted_source.py` mirrors lamley's contract `(link, session, notifier) -> dict|None` and drops the WAF/cooldown/retry/blacklist/curl_cffi blocks. Mirror without copy-paste-with-rename — extract shared helpers if both parsers diverged on the same logic.
- Decision 2 compliance: `SOURCE_HASHTAG_OVERRIDE` is a module-level constant in `news_bot.py`, consulted by `_source_hashtag` *first*, with legacy netloc parts[-2] logic as the fallback path. Wrong ordering = `#blogspot` emitted = silent quality bug.
- Decision 3 compliance: three direct admin-alert builders (E031/E032/E033) — NOT an orangetrack-style aggregator. Confirm `admin_alerts.py` does not introduce per-tick aggregation for t-hunted.
- Decision 4 compliance: PT patterns appended to the same flat `_BOILERPLATE_PATTERNS` list (no per-language tagging), `^`-anchored, length-bounded by `_MAX_BOILERPLATE_LEN = 120`.
- Decision 7 compliance: `SOURCE_EMOJI['t-hunted'] = '🟤'` and `SOURCE_LABEL['t-hunted'] = 'T-Hunted'` — and *only* read by archived `hw_review.py`, not by admin alerts or channel posts (no leak into production paths).
- Decision 8 compliance: no new code under "PT input fallback" — verify nothing in `t_hunted_source.py` or `news_bot.py` reimplements the `_is_mostly_russian` check or adds a PT-input-specific guard.
- Risk R3 compliance: Blogger image dedup strips `=s\d+(-c)?` size suffix before comparison; lamley's `?`-split logic is replaced (not extended).
- Risk R7 compliance: `t_hunted_source.py` literally appears in all three FILES arrays at the same relative position as other source files; the new `tests/test_deploy_files_invariant.py` actually asserts all three.
- Prompt-file invariant: `ux-guidelines.md` system-prompt blockquote markers (`>` lines defining the LLM role) preserved verbatim — structural damage breaks every transcreation (every source), not just t-hunted. This is the most dangerous regression in the feature.
- Shared resources: tech-spec promises "None. No singleton resources are introduced." Verify no new module-level state, no new connection pool, no new LLM-client instance.

**Edge cases (auditor mindset):**
- A finding labeled "minor" by per-task reviewer may become "major" when seen in cross-component context (e.g. duplicate logic that appears trivial in isolation but is duplicated across 3 source modules).
- A passing per-task test does not mean the cross-task contract is intact (e.g. dispatcher unit test passes but the if/return ordering surfaces an unreachable branch for an existing source).
- Absence of findings in a component is itself a finding-worthy claim — say so explicitly per component rather than omitting the section.

**Implementation hints:**
- Use Read tool per file; do not cat. Note line numbers from the Read output for `line` / `lines` fields.
- Reference `code-reviewing` skill's 11 review dimensions when scoping severity — the audit applies the same standards but at feature-scope, not file-scope.
- If a finding crosses multiple components (e.g. parser + wiring), list it under the most natural component and cross-reference in `cross_component_review`.
- Be concrete: "extract `_strip_blogger_size_suffix` to a shared `image_dedup_helpers.py`" is a recommendation; "consider deduplication" is not.
