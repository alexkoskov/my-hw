## Description

Расширить существующий интеграционный набор `tests/test_distributed_schedule_integration.py` одним новым smoke-тестом — `test_integration_t_hunted_smoke_en_pt_mixed_tick` — который прогоняет полный цикл `news_bot.job()` с двумя замоканными RSS-фидами: один autoevolution-style EN-entry и один t-hunted-style PT-entry. Цель — на интеграционном уровне зафиксировать, что после изменений Wave 1 (новый парсер `t_hunted_source.py`) и Wave 2 (wiring в `news_bot.py`: `NETLOC_TO_SOURCE`, dispatcher branch, `SOURCE_HASHTAG_OVERRIDE`) обе статьи проходят пайплайн без кросс-языковой интерференции: каждая запись попадает в `pending_articles` с правильным `source_name`, обе публикуются через `_fallback_publish` (мокирующий `transcreate_via_claude`), dedup не отбрасывает PT-запись как «дубль» EN, и порядок слотов сохраняется (т. е. дистрибутивный планировщик `compute_publish_slots` работает идентично для смешанного по языкам входа).

Тест — единственное smoke-доказательство перед PR-merge, что EN- и PT-источники сосуществуют в одном тике без регрессий, поэтому формулировки assertов должны быть максимально явными (`source_name` каждой строки, количество вызовов `transcreate_via_claude`, отсутствие admin-pings `[E031-E033]`, оба `published_articles` row'а присутствуют). Заявленные риски R1/R2 (hashtag) и R7 (deploy FILES) покрываются другими задачами — здесь только cross-language pipeline coverage.

## Details

**Files:**
- `tests/test_distributed_schedule_integration.py` — ДОБАВИТЬ один новый метод `test_integration_t_hunted_smoke_en_pt_mixed_tick` в класс `TestDistributedSchedule`. Сейчас файл содержит base class `TestDistributedSchedule` (setUp на ~150-230 строках с патчами DB / Telegram / Telegraph / Google / Claude / RSS), helpers `_create_mock_rss_entry`, `_create_mock_full_article`, `_make_claude_result`, и несколько test-методов под существующие сценарии (happy path 3-article, outage, restart, manual-review preemption и т. д.). Новый тест следует структуре `test_full_happy_path_*` (см. строки 282-348 в файле): через `freeze_time('2026-05-26 09:00:00')` → `_set_rss_entries([...])` → `patch('news_bot.transcreate_via_claude', side_effect=[...])` → `news_bot.job()` → DB + mock assertions.

**Dependencies:**
- Task 1 — `t_hunted_source.py` модуль импортируется в `news_bot.py` (косвенно, через wiring Task 3). Если Task 1 не смержена — `import t_hunted_source` упадёт при загрузке тестового файла.
- Task 3 — wiring в `news_bot.py` (`NETLOC_TO_SOURCE['t-hunted.blogspot.com']`, dispatcher branch на `blogspot.com`). Без этого `_resolve_source_name('https://t-hunted.blogspot.com/...')` вернёт `'other'`, и тест свалится на assert `source_name == 't-hunted'`.
- pytest plugins: `freezegun`, `pytz` уже в requirements (используются другими интеграционными тестами в этом же файле).

**Edge cases:**
- **Dedup false-positive.** `processed_news` PRIMARY KEY на `link` — два разных URL не должны конфликтовать. Тест явно использует два разных link'а (`autoevolution.com/news/...` vs `t-hunted.blogspot.com/2026/05/...`), но assert на `len(_published_links()) == 2` зафиксирует регрессию, если кто-то добавит сравнение по title/source-name.
- **Slot ordering.** `compute_publish_slots(2, now=12:00, window_start=10:00, window_end=20:00, min_interval_min=90)` для двух entries вернёт два slot'а в окне 13:00-20:00 с разносом ≥90 минут. Тест НЕ проверяет точное время slot'ов (это покрыто `test_compute_publish_slots.py`), но проверяет что обе entry публикуются (т. е. оба slot'а попали в окно — не было window-end-cutoff). Если N=2 не помещаются в окно — это сигнал к багу в slot-computation, не к моку.
- **`source_name` flow до LLM.** Тест мокает `transcreate_via_claude` целиком, поэтому `source_name` через `_build_user_message` не проверяется на этом уровне (это unit-test territory `tests/test_claude_transcreation.py`). Проверка `source_name` здесь — на уровне SQLite-строки в `published_articles`.
- **Admin-pings с кодами E031-E033 в `_admin_messages()`.** В happy-path путь к `notifier(admin_alerts.alert_t_hunted_*(...))` не вызывается (mocked `fetch_full_article` не достигает реального парсера). Assert на отсутствие этих кодов — защита от регрессии, при которой кто-то добавит admin-ping в success-path.
- **Cross-test contamination.** Базовый `setUp` создаёт `tempfile` DB и `tearDown` его удаляет. Не запускать `pytest --xdist` для этого теста без флага per-test-DB (но базовый класс уже изолирует через `tempfile.mkstemp`, так что contamination маловероятен).

**Implementation hints:**
- Переиспользовать `_create_mock_rss_entry` и `_create_mock_full_article` без изменений — они уже параметризованы `source_name`. Не создавать новые helpers.
- Для assert'а `source_name` использовать `pending_articles_repo.get_published(link)` (возвращает dict с ключом `'source_name'`) либо прямой SQL-запрос через `sqlite3.connect(self.db_path).execute('SELECT source_name FROM published_articles WHERE link=?', (link,))`.
- Для assert'а на отсутствие admin-pings с кодом `[E031-E033]` — проверять подстрокой через `self.assertFalse(any('[E031]' in m or '[E032]' in m or '[E033]' in m for m in self._admin_messages()))`.
- Имя теста ровно как указано в tech-spec: `test_integration_t_hunted_smoke_en_pt_mixed_tick` — locked для `-k integration_t_hunted` фильтра в `Verify-smoke`.
- НЕ патчить `t_hunted_source.fetch_t_hunted_article` напрямую — `fetch_full_article` уже замокан в setUp (`self.fetch_full_patcher`), что эффективно обходит реальные парсеры. Дополнительные патчи на источник-уровневом коде только запутают тест.
- В `_make_claude_result` указать разные `title_prefix` для двух статей чтобы при отладке было видно, какая была какой — например `'EN article'` и `'PT article'`.
- Если используется `with patch(...) as mock_claude:` — `side_effect` принимает список (по элементу на каждый `.call()`); это уже use'ed в `test_full_happy_path_*` (строки 304-310), копировать паттерн.
