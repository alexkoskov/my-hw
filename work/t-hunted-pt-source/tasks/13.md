## Description

Стандартный деплой фичи `t-hunted-pt-source` через последовательность мержей PR в two-instance топологию (test → prod). Pre-deploy QA (Task 12) уже зелёная — теперь поднимаем код на test-инстансе через CI/CD пайплайн и фиксируем результат для последующего Post-deploy verification (Task 14).

Деплой работает в две ступени:

1. **Сейчас (этот таск):** Squash-merge `feature/t-hunted-pt-source` → `dev`. Это триггерит цепочку `CI → deploy_test.yml`, которая SCP-ит FILES-массив (включая новый `t_hunted_source.py`) в `/home/hwbot/bot_test/` на VPS `148.135.207.54` и рестартит `news_bot_test.service`. Тестовый инстанс начинает работать на новом коде и публиковать t-hunted статьи в `@myhwchannel123`.

2. **Отложено (после успешного Task 14):** Merge `dev` → `main` запускает `deploy.yml`, который SCP-ит те же файлы в `/home/hwbot/bot/` и рестартит `news_bot.service` (прод-инстанс, канал `-1004027529994`). Эта вторая ступень — НЕ в скоупе данного таска, она выполняется отдельно после подтверждения Post-deploy verification.

Цель таска — успешный мерж в `dev`, зелёный `deploy_test.yml`, активный `news_bot_test.service` на новом коде, файл `t_hunted_source.py` физически присутствует в `/home/hwbot/bot_test/`, и никаких import-ошибок в первых 5 минутах работы.

## Verification Steps

### Smoke

Эти проверки агент запускает в процессе деплоя — они и есть «как мы знаем, что задеплоилось».

- `gh pr view <pr-number> --json statusCheckRollup` → CI на feature-ветке зелёный до мержа.
- `gh run list --branch dev --workflow deploy_test.yml --limit 1` → последний run после мержа имеет `conclusion = success`.
- `gh run view <run-id>` → шаги `Copy files to server`, `Write runtime env vars to server .env`, `Install Python dependencies on server`, `Restart news_bot_test service on server` все зелёные; в логах есть `::notice::news_bot_test.service restarted on dev branch code.`.
- `ssh hwbot 'systemctl status news_bot_test.service'` → `Active: active (running)`, uptime < 5 минут от метки деплоя.
- `ssh hwbot 'ls -la /home/hwbot/bot_test/t_hunted_source.py'` → файл существует, mtime соответствует деплою.
- `ssh hwbot 'journalctl -u news_bot_test.service --since "5 minutes ago" --no-pager | grep -E "ImportError|Traceback|t_hunted|t-hunted"'` → пустой вывод (никаких новых ошибок, связанных с фичей).
- `ssh hwbot 'journalctl -u news_bot_test.service --since "5 minutes ago" --no-pager | grep -E "\[E03[1-3]\]"'` → пустой вывод (нет alert-ов от парсера за окно проверки).

**Edge cases:**
- CI на `dev` упал после мержа → не блокируем; смотрим логи `gh run view`, чиним отдельным коммитом в `dev`, ждём зелёный CI → `deploy_test.yml` перезапустится автоматически. Не делаем revert мержа без явной необходимости.
- `deploy_test.yml` упал на шаге `Copy files to server` с `::error::t_hunted_source.py not found in repo root` → значит FILES-массив в `.github/workflows/deploy_test.yml` не содержит запись (Task 6 пропустил/откатился). Чиним отдельным коммитом в `dev`, push, ждём перезапуск воркфлоу.
- `deploy_test.yml` упал на `Restart news_bot_test service on server` с упоминанием `terminal is required` → sudoers сломаны или потеряли права (mode != 0440). SSH на VPS под root, проверить `/etc/sudoers.d/news_bot`, починить, перезапустить шаг через `gh run rerun <run-id>`.
- `systemctl status` показывает `failed` → читать `journalctl -u news_bot_test.service -n 100`. Самый вероятный сценарий — ImportError (пропущенный модуль в FILES, см. выше) или syntax-ошибка, проскочившая CI (крайне редко). Откат: `git revert <merge-sha> && git push origin dev` — `deploy_test.yml` автоматически вернёт предыдущий коммит за ~2-3 минуты.
- В журнале появились `[E031]`/`[E032]`/`[E033]` alert-ы в первые 5 минут → парсер сразу ловит host-rejected/fetch-error/no-body на первой же RSS-итерации. Не блокируем merge — фиксируем в deploy-test.log и эскалируем в Task 14 (Post-deploy verification), там 24h/7d watch покажет, разовый ли это сбой.
- Сетевая проблема между runner-ом и VPS (`Add host to known_hosts` упал) → ретраим через `gh run rerun <run-id>`. Если повторяется — проверить файрвол VPS и доступность по SSH вручную.

**Implementation hints:**
- Merge только squash — это договорённость репо для feature → dev (см. tech-spec Decision 6). Linear history в `dev` упрощает последующий revert одной командой.
- Перед мержем глянуть, что rebase на свежий `dev` не порождает конфликтов (`git fetch origin dev && git rebase origin/dev` локально на feature-ветке) — иначе будет конфликт-merge вместо squash.
- Логи `deploy_test.yml` сохранять текстом через `gh run view <run-id> --log > /tmp/run.log` — потом нужный фрагмент в `deploy-test.log` копируется как обычный текст. Полный лог в репо не коммитить.
- На сервере у юзера `hwbot` есть NOPASSWD правила для `systemctl restart/status news_bot_test.service` и `journalctl -u news_bot_test.service` — все верификационные SSH-команды отрабатывают без TTY.
- В журнале сразу после рестарта легитимно появляется одна строка про инициализацию `init_db`, схему миграций и стартовый tick — это НЕ ошибка. Грепаем именно `ImportError` / `Traceback` / `t_hunted` / `t-hunted`.
- `news_bot_test.service` запускает `news_bot.main()` в режиме демона со `schedule.every().day.at("10:00", tz=Europe/Moscow)`, плюс immediate `job()` на старте. На свежем старте после деплоя — один прогон `job()` сразу, дальше ждём 10:00 МСК. То есть проверка «работает на новом коде» = успешный старт + чистый журнал, не публикация t-hunted статьи (это уже Task 14 в 24h окне).
- При записи `deploy-test.log` использовать UTF-8 и markdown-формат — структурно так же легко парсится для Task 14.
