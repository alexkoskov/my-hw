4. **`journalctl -u news_bot.service | tail -50`:** the bot ticks daily at

   sends `[E009]` each day. Every day it logs `Filtered out 17 off-topic
   entries (sibling brands)` then `Found 1 new entries` → that 1 is an
   orangetrack checklist → skipped → nothing to publish.

**Root cause:** the broad-diecast filter `_is_hot_wheels_relevant` rejects any
t-hunted post whose title lacks the literal words "hot wheels". t-hunted is
Brazilian-Portuguese and names the **series**, not the brand — so genuine HW
posts (Silver Series, Pop Culture, Moving Parts, Neon Speeder, Red Line Club…)
were all dropped. Combined with autoevolution being quiet for several days and
orangetrack yielding only checklists, **nothing passed** → channel silent. The
daily `[E009]` admin pings WERE the signal.

## Fix (dev) — recognise HW series/line names as a HW signal

`news_bot.py`:
- New `_HW_SERIES_SIGNALS = (silver series, pop culture, moving parts, neon
  speeder, car culture, team transport, boulevard, red line club)`.
- `_is_hot_wheels_relevant`: after the explicit `hot wheels` check and the
  sibling-brand (`matchbox`) reject, a title containing any HW series name now
  returns relevant — BEFORE the broad-diecast default-reject. Order matters:
  sibling-brand reject runs first, so a shared name like "Moving Parts … da
  Matchbox" still drops out.
- Conservative list (HW-specific lines only) to avoid false includes; titles
  shared across brands (e.g. generic "linha básica", "Fast & Furious") are NOT
  signals.

`tests/test_relevance_filter.py`: +`test_t_hunted_hw_series_name_keeps_entry`
(5 real dropped titles now pass) and +`test_sibling_brand_beats_hw_series_name`
(Matchbox Moving Parts still rejected). Existing rejects (Johnny Lightning,
Mundo Premium, M2 Machines) still drop. Suite: 1135 → **1137 passed**.

Review: self-review (12-line whitelist); false-positive risk mitigated by
sibling-first ordering + HW-specific list.

## Update (same day) — deploy NOT broken; resilience check; dry-spell alert

**Deploy pipeline self-heals (earlier "broken" note was wrong).** `deploy.yml`
uses `ssh-keyscan` each run (no pinned key), so a changed host key is picked up
automatically. The 06-17 failure was `ssh-keyscan produced no host keys` — the
server was simply UNREACHABLE then. With it back up: dev push → `Deploy test`
✅ (06-23 09:59), and the `dev→main` promotion → prod `Deploy` ✅ (06-23 10:12).
**Filter fix + the in-slot-retry are now LIVE on prod** (`97e0d70`).

**Resilience facts (checked on prod, answering "does it self-recover?"):**
- `systemctl show`: `Restart=on-failure`, `RestartUSec=10s` — crashes/reboots
  auto-restart in 10s; service is `enabled` (starts on boot). ✅
- Temporary network loss is survived: hold-and-wait (LLM), in-slot retry
  (Telegra.ph/Telegram), RSS-skip-on-error, and `socket.setdefaulttimeout(20)`
  (no infinite hangs). Resumes on its own; nothing lost.
- **Gap found: the heartbeat watchdog is NOT installed on prod.** hwbot crontab
  has only `backup_db.sh` (02:00) — no watchdog. The code writes the heartbeat
  (`~/.cache/news_bot/last_tick.ts`) but nothing reads it, so a silent
  stop/hang would NOT auto-alert. (Mitigated by Restart=on-failure + the 20s
  timeout, but the alert net isn't there.)

**Shipped: [E017] channel-silence alert.** A heartbeat watchdog would NOT have
caught today's incident (the bot was ticking and sending daily [E009]). So
added a direct dry-spell guard: at the end of `job()`, if nothing has been
published for `DRY_SPELL_ALERT_DAYS` (3)+ days, send a louder `[E017] ⚠️ Канал
молчит N+ дней` admin ping (vs the easy-to-ignore daily [E009]). Reads
`get_max_published_at` (same source as the crash-loop guard); skips on a
fresh/never-published DB; wrapped so it never breaks the tick. Tests:
`test_e017_channel_silent` + `TestDrySpellAlert` (silent→ping, recent→no ping,
never-published→no ping). Suite: 1137 → **1141 passed**.
