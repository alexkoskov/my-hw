# Task 11: Code Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Полнофичевый аудит качества кода для `manual-review-workflow` после завершения всех десяти реализационных задач (Waves 1–7). Каждая задача проходила свой per-task code-review, но ни один из них не видел фичу целиком. Этот аудит — единственный срез кросс-компонентной картины: как модули стыкуются друг с другом, не расползлась ли архитектура, одинаково ли ведут себя одни и те же концепции в разных местах.

Цель — не перепроверять уже отревьюенные строки, а найти **кросс-компонентные** дефекты, которые невозможно было увидеть внутри одной задачи:

- **Shared-resource compliance** — `news.db`, `TELEGRAPH_ACCESS_TOKEN`, Telegram `Bot` instances используются ровно так, как описано в таблице Shared Resources техспека (один владелец, остальные — consumers; per-call connections, без пулов; ephemeral Bot per `asyncio.run`).
- **Архитектурная консистентность** — `hw_review.py`, `pending_articles_repo.py`, `preview_renderer.py`, `news_bot.py` следуют стилю существующих `*_source.py` (модульные функции, не классы-overkill, dict-based API, плоская структура, единый логгер).
- **Единообразие error handling** — все пути ошибок вызывают `send_admin_notification` через один и тот же хелпер; все записи в `last_error` проходят через `sanitize_error_message` (Decision 11); везде используется `logging.getLogger(__name__)` из того же логгера, что в `news_bot`; exit codes CLI-команд единообразны (0 = успех, 1 = ошибка с сообщением в stderr, без Python-traceback).
- **Dead-code check** — функция `process_new_articles` удалена полностью (нет определения, нет вызовов, нет упоминаний в тестах кроме tests-to-delete); `limit=3` нигде не осталось как параметр; не осталось legacy fallback-путей «старого» `job()`.
- **Cross-cutting корректность** — параметризованные SQL запросы (`?` placeholders) во всех местах, где строится SQL (AC техспека); `json.dumps(..., ensure_ascii=False)` используется везде, где сериализуется кириллица; `attempt_count` инкрементируется через единственный мутатор `increment_attempt` из обоих путей (idle-fallback + overflow).

Результат аудита — единый Markdown-отчёт по пути из Files-to-modify. Аудитор и есть ревью этой задачи — никаких отдельных code/security/test-reviewer раундов сверху не нужно (см. раздел Reviewers). Критические находки должны быть подняты обратно как bugfix-задачи в техспеке до перехода к Final Wave.

## Verification Steps

### Automated

- `pytest tests/ -q` — перед началом аудита весь тест-сьют должен быть зелёным; если нет — остановиться и вернуть задачу в team lead, аудит на красных тестах не имеет смысла.

### Smoke

Быстрые grep/AST-проверки, которые аудитор прогоняет во время работы:

- `grep -RIn "process_new_articles" --include="*.py" .` → нет попаданий. Единственное допустимое место — упоминание в файлах техспека/юзер-спека/decisions, их исключить через `--exclude-dir=work`.
- `grep -RIn "limit=3" --include="*.py" .` → нет попаданий в `news_bot.py`/`hw_review.py`/`pending_articles_repo.py`; допустимо только в legacy helper-модулях (`post_latest_news.py`, `get_latest_article.py`, `debug_feed.py`), если они ещё используются.
- `grep -RIn "executescript\|execute.*%\|execute.*format\|execute.*f\"\|execute.*f'" --include="*.py" .` на `pending_articles_repo.py` и `news_bot.py` → нет попаданий (все SQL через `?` placeholders).
- `grep -RIn "ensure_ascii" --include="*.py" .` — у всех `json.dumps`, затрагивающих кириллические данные, должен быть `ensure_ascii=False`; найти любые голые `json.dumps(` в новом коде и вручную сверить их.
- `grep -RIn "last_error" --include="*.py" .` + визуальный трейс: каждая запись проходит через `sanitize_error_message`.
- `grep -RIn "attempt_count\s*+=\|attempt_count\s*=\s*attempt_count" --include="*.py" .` → нет попаданий вне `pending_articles_repo.increment_attempt` (единственный мутатор).
- `python -c "import ast, pathlib; [print(p) for p in pathlib.Path('.').rglob('*.py') if 'process_new_articles' in p.read_text()]"` → пустой вывод (кросс-проверка grep'а через AST-source).
- `python -c "import news_bot; assert not hasattr(news_bot, 'process_new_articles'), 'ghost symbol'"` → exit 0.

### User

Не требуется. Аудит — внутренняя техническая проверка; отчёт остаётся в `logs/working/audit/` для ревью team lead.

## Details

**Files:**

- `work/manual-review-workflow/logs/working/audit/code-audit.md` — новый отчёт, результат работы аудитора. Должен содержать: Summary, Verdict, Findings table (с колонками severity/area/file:line/issue/fix), Cross-component observations, Out of scope, и — если verdict = `needs-fixes` — готовые черновики bugfix-задач.

**Области аудита (детализация пяти направлений):**

1. **Shared-resource compliance** — сверить каждую строку таблицы Shared resources техспека:
   - `news.db` — `news_bot.init_db()` остаётся единственным создателем; `hw_review.py` и `pending_articles_repo.py` только открывают соединения; нет соединений-долгожителей (проверить, что connection = `sqlite3.connect(...)` всегда в scope функции, а не на уровне модуля).
   - `TELEGRAPH_ACCESS_TOKEN` — создаётся только `telegraph_publisher.ensure_access_token()`; `hw_review publish` не кэширует токен локально, а вызывает `publish_article`.
   - Telegram `Bot` instances — ephemeral, per `asyncio.run`; нет глобальных `Bot(...)` на уровне модуля.

2. **Архитектурная консистентность** — сравнить новые модули с существующими `*_source.py`:
   - Плоские функции, а не классы (исключение — если классы действительно нужны; обосновать).
   - Dict-based API (не dataclasses) — по техспеку параметр «все функции принимают и возвращают plain dicts».
   - Один логгер `logging.getLogger(__name__)` на модуль; формат логов — INFO для критических шагов, ERROR для исключений.
   - Docstrings в стиле существующих модулей (короткие, по-английски).

3. **Error handling uniformity:**
   - Все пути, приводящие к admin-ping, идут через `send_admin_notification` (не через прямые `Bot.send_message` мимо хелпера).
   - Все записи в `last_error` (pending и failed) проходят через `sanitize_error_message` — trace вручную каждый call site, так как это безопасность (Decision 11).
   - Все CLI-команды возвращают `0` на успех и `1` на ошибку, пишут сообщение в stderr через `print(..., file=sys.stderr)` или `logger.error`, НЕ выбрасывают traceback наружу пользователю.
   - Exceptions внутри `job()` изолированы per-source / per-row — один сбой не рушит весь тик.

4. **Dead-code:**
   - `process_new_articles` — определения нет, вызовов нет, в тестах нет (кроме flipped-тестов, где явно проверяется, что функция не вызывается — а этого тоже быть не должно: тесты должны проверять новое поведение, а не отсутствие старого).
   - `limit=3` — в новом коде не осталось; `QUEUE_CAP=10` его заменил.
   - Комментарии вида `# TODO: old pipeline` / `# legacy` / `# deprecated` — либо убрать, либо явно поднять наверх как отдельную находку.

5. **Cross-cutting корректность:**
   - Параметризованные SQL — все `cursor.execute(...)` принимают `(sql, params)`, никаких `execute(f"...")` или `execute(sql % ...)`.
   - `json.dumps(..., ensure_ascii=False)` везде, где поле может содержать кириллицу.
   - `attempt_count` инкрементируется только через `pending_articles_repo.increment_attempt` — один мутатор, оба пути вызывают его.
   - `_fallback_publish(row, via_review=False)` — один helper, используется обоими путями (idle-fallback и overflow), не дублируется.
   - `NETLOC_TO_SOURCE` + `SOURCE_EMOJI` + `SOURCE_LABEL` синхронизированы по ключам (все три используют `'autoevolution'`/`'mattel'`/`'lamley'`; нет `'rss'` как ключа).

**Dependencies:** задачи 1–10 (все реализационные волны) должны быть в статусе `done` до старта этой задачи. Если какая-то задача застряла в in_progress — аудит не начинаем, это сигнал вернуться к той задаче.

**Edge cases при чтении кода:**

- Legacy-модули в корне (`post_latest_news.py`, `get_latest_article.py`, `debug_feed.py`) — они вне scope фичи; если в них что-то зацепляется с новой логикой (например, они тоже лезут в `news.db`), это отдельная находка в секции Cross-component observations, но не блокер.
- `news_bot.py` — самый большой файл с наибольшей хирургией (Tasks 3, 5, 6, 9, 10); особое внимание — что все пять правок мирно сосуществуют.
- Тесты — проверить не только на «проходят», но и на качество assertions (не `mock.called` само по себе, а assertions с конкретными аргументами); однако глубокий test-audit — это Task 13, здесь трогать только тесты, имеющие отношение к кросс-модульным связкам (integration-тесты, `test_job_prep_phase.py`, `test_overflow.py`, `test_idle_fallback.py`).

**Implementation hints (для аудитора, НЕ псевдокод):**

- Работать файл за файлом, а не направлением за направлением — так тратится меньше контекста.
- Вести rolling findings: каждую замеченную нестыковку сразу записывать в черновик отчёта с `File:Line` и severity; в конце сгруппировать по Area.
- Severity критерий: **critical** = нарушение контракта из техспека / потеря данных / секрет в логах; **major** = нарушение Architecture table / дупликация логики между модулями / dead code; **minor** = стилистика, именование, форматирование.
- Если что-то выглядит подозрительно, но требует глубокого security-анализа (например, путь к preview HTML, валидация JSON на stage) — отметить в отчёте ссылкой и отложить к Task 12 (Security Audit), не лезть в security-слой здесь.
- Если что-то выглядит подозрительно в тестах (покрытие, пирамида) — отметить в Out of scope с пометкой «for Task 13 (Test Audit)».
- Отчёт — рабочий документ для team lead, а не публикация. Плотный и конкретный, без воды.
