# Task 10: Overflow fast-track pass + hw_review retry + failed-footer

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Закрываем overflow-путь и retry-путь манульного review-флоу. Три вещи:

1. **Overflow fast-track в `job()`** — когда `count_pending() + len(new) > QUEUE_CAP` (10), самые старые записи с пустым русским текстом прогоняются через `_fallback_publish` (helper из Task 9, `transcreate_text` → `publish_article` → `send_telegraph_teaser` → `move_to_published(via_review=False)`) чтобы освободить слоты. Записи со staged русским НЕ трогаются (Decision 7): это тот самый CLI-cron race, от которого фича и защищает. Счётчик `attempt_count` общий с idle-fallback (Decision 13): три провала в любой комбинации → `move_to_failed`. Новые entries, которым не хватило слотов после пасса, дропаются до следующего cron-tick. Admin-ping: `"Queue pressure: auto-published {evicted}, {deferred} new deferred, {staged_protected} staged rows protected"` с опциональным суффиксом `", fast-track failed for {count}"`.

2. **`hw_review retry N`** — N это 1-based индекс в `list_failed()` (ORDER BY `failed_at DESC`, как в failed-футере). Вызывает `pending_articles_repo.retry_from_failed(link)` который перемещает строку из `failed_articles` обратно в `pending_articles` со свежим `fetched_at=CURRENT_TIMESTAMP` и `attempt_count=0`. Exit 0 на успех, 1 если N вне диапазона.

3. **Failed-footer в `hw_review list`** — всегда (Decision 8) когда `list_failed()` непустой, независимо от состояния основной очереди. Формат: `"⚠️ {K} неопубликованных в failed: [title1, title2, ...]. hw_review retry N чтобы переподнять."` (AC L71 user-spec).

Wave 7, после Task 9 (idle-fallback создал `_fallback_publish` helper и добавил `hw_review take`). Task 10 потребляет тот же helper и тот же общий `attempt_count`. Тесты `tests/test_hw_review_retry.py` отделены от `test_hw_review_take.py` (Task 9) чтобы каждая таска владела своим тест-файлом.

## Acceptance Criteria

- [ ] `_overflow_fast_track` не запускает eviction если `len(new_entries) <= slots_free` (AC L64 user-spec).
- [ ] Eviction трогает только строки с `ru_paragraphs IS NULL` (Decision 7, AC L69 user-spec) — `list_pending_for_eviction` гарантирует это на уровне repo, задача — использовать ТОЛЬКО этот repo-метод для отбора кандидатов.
- [ ] Провал `_fallback_publish` в overflow-пути инкрементирует тот же `pending_articles.attempt_count`, что и idle-fallback (Decision 13, AC L70); три провала в любой комбинации → `move_to_failed`.
- [ ] `send_admin_notification` вызывается только когда есть deferred, staged_protected > 0, или fast-track errors — на happy-path (всё эвикнуто, всё вставлено) ping не уходит.
- [ ] Формат admin-ping: `"Queue pressure: auto-published {E}, {D} new deferred, {S} staged rows protected"`; опциональный суффикс `", fast-track failed for {F}"` — строго когда `fast_track_errors` непуст.
- [ ] `_overflow_fast_track` встроен в `job()` после фильтрации и до INSERT: именно `accepted` идёт в `fetch_full_article` + `insert_pending`, а не исходный `new_entries`.
- [ ] `hw_review retry N` резолвит индекс через `list_failed()` (тот же порядок, что показывает failed-футер); вызывает `retry_from_failed(link)`; exit 0 на успех.
- [ ] `hw_review retry N` на out-of-range (N < 1 или N > len(failed)) → exit 1, stderr содержит `"out of range"` и не вызывает `retry_from_failed`.
- [ ] После `retry_from_failed(link)`: строка в `pending_articles` с `attempt_count=0` и свежим `fetched_at`; из `failed_articles` удалена.
- [ ] `hw_review list` всегда показывает failed-футер когда `list_failed()` непуст (Decision 8, AC L71 user-spec), независимо от состояния основной очереди — включая случай «queue is empty» + failed не пуст.
- [ ] Футер не появляется, если `list_failed()` пуст.
- [ ] Все санитизации `last_error` в overflow-пути идут через `sanitize_error_message(exc)` из Task 3 (Decision 11) — сырой `str(exc)` не пишется в БД и не уходит в админ-пинг.
- [ ] Новые тесты `tests/test_overflow.py` и `tests/test_hw_review_retry.py` зелёные; существующие тесты продолжают проходить.

**Edge cases:**
- Queue ровно на `QUEUE_CAP` + 0 новых → `_overflow_fast_track` даже не вызывается (фильтрация вернула пустой `new_entries`, `job()` пропускает overflow). Если всё-таки вызывается с пустым списком — ранний return с `([], [])`.
- Очередь на `QUEUE_CAP`, все staged, пришло N новых → `to_evict = []`, `staged_protected = needed`, все N deferred, ping с `auto-published=0`.
- `_fallback_publish` падает на первой эвикции-кандидате, но проходит на второй → первая остаётся в pending с `attempt_count+=1`; слот не освобождён, но второй слот есть. `slots_free_after` корректно считается.
- Тот же row накопил 2 провала в idle-fallback (Task 9) и получает третий в overflow → сразу `move_to_failed`, не дожидаясь четвёртого (Decision 13: 3 в любой комбинации).
- `retry_from_failed` на link, которого нет в `failed_articles` → `retry_from_failed` возвращает `False` (репо-контракт, Task 1). CLI должен перед вызовом уже свалидировать индекс через `list_failed()`; дополнительный race-guard не требуется (single-session convention).
- Failed-футер: пустая очередь + failed непустой → `"queue is empty"` на одной строке, потом футер. Обе строки в stdout.
- `list_failed()` возвращает rows ORDER BY `failed_at DESC` — 1-based индекс `retry N` ссылается на ту же позицию, что и в футере. Не переупорядочивай.
- Русские titles и эмодзи в футере — stdout должен быть utf-8 (стандарт для Python 3); не нужна спец-обработка.
- Secrets в `last_error`: на трёх-страйк провале строка уезжает в `failed_articles` — её `last_error` уже санитизирован через `sanitize_error_message` до вставки в failed. Футер показывает только `title`, не `last_error` — секрет туда не утечёт.

**Implementation hints:**
- Для счёта `staged_protected`: это `needed - len(to_evict)`, ГДЕ `needed` это изначальная нехватка слотов. Не путай со «сколько строк осталось staged после пасса» — seeding уже staged, мы их и не собирались эвикнуть.
- Админ-ping отправляй ОДНИМ вызовом — мы в cron-тике, не хотим шторма нотификаций. Формат строки собирай через f-string с опциональным суффиксом.
- В `hw_review retry` после удачного `retry_from_failed` можно вызвать `list_failed()` заново и напечатать обновлённое число в failed — not required, но полезно оператору.
- Для футера используй `", ".join(titles)` — если title с запятой в нём, оператор всё равно видит; это информативный вывод, не машиночек.
- При встраивании в `job()` сохрани логи уровня INFO (например, `logger.info(f"Overflow: evicted={evicted_count}, deferred={len(deferred)}, protected={staged_protected}")`) — полезно для пост-деплой диагностики.
- Не пиши новый `retry_from_failed` в repo — он уже существует (Task 1). Только вызывай.
