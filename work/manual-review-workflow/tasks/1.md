# Task 1: `pending_articles_repo` module

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Создать новый DAO-модуль `pending_articles_repo.py` в корне репо — первый выделенный data-access слой проекта (до сих пор всё SQLite-взаимодействие жило прямо в `news_bot.py`). Модуль владеет DDL + CRUD + транзакционными «перемещениями» между тремя новыми таблицами: `pending_articles` (WIP-очередь, cap 10 строк), `published_articles` (аудит реальных публикаций с флагом `via_review`), `failed_articles` (dead-letter после 3 провалов GT-фоллбэка). JSON-сериализация (`paragraphs`, `images`, `blocks`, `ru_paragraphs`, `ru_blocks`) полностью инкапсулирована внутри репо — вызывающий код (будущие `news_bot.init_db`, `news_bot.job`, `hw_review.py`) передаёт и получает Python-списки.

Это фундамент Wave 1: без работающего репо не стартует ни prep-фаза, ни CLI. Функциональные границы пришли из tech-spec §Data Models и §Repo module interface; транзакционные контракты из Decisions 2, 9, 11, 13; форма API — из code-research §9.1–§9.2. Таблицы создаются через `CREATE TABLE IF NOT EXISTS` — это держит `init_db()` идемпотентным (AC tech-spec: «`init_db()` is idempotent»).

## What to do

1. Создать файл `pending_articles_repo.py` в корне репозитория.

2. Реализовать `init_schema(conn: sqlite3.Connection) -> None` — выполняет три `CREATE TABLE IF NOT EXISTS` (pending_articles / published_articles / failed_articles) с DDL из tech-spec §Data Models. Функция принимает уже открытое `conn` (а не путь) — это позволяет `news_bot.init_db` использовать свой conn и вызывающему тесту передавать `:memory:` DB. В конце — `conn.commit()`.

3. Реализовать все функции API из tech-spec §Repo module interface:
   - Write: `insert_pending`, `update_staged`, `mark_notified`, `clear_notified`, `increment_attempt`, `mark_telegraph_published`.
   - Read: `get_pending`, `list_pending`, `list_pending_stale`, `list_notified_overdue`, `list_pending_for_eviction`, `list_failed`, `count_pending`, `get_published`, `get_failed`.
   - Transactional moves: `move_to_published`, `move_to_failed`, `skip_pending`, `retry_from_failed`.

4. Внутри репо инкапсулировать JSON (де)сериализацию: на запись — `json.dumps(value, ensure_ascii=False)` для JSON-полей; на чтение — `json.loads(...)` с обработкой NULL (для `blocks` / `ru_paragraphs` / `ru_blocks` NULL → остаётся `None`).

5. Для многошаговых мутаций (`move_to_published`, `move_to_failed`, `skip_pending`, `retry_from_failed`) открывать **один** connection, оборачивать все `INSERT` / `DELETE` в try/except с `commit()` на успехе и `rollback()` на исключении. Никаких частичных состояний (AC tech-spec).

6. Все SQL — исключительно с параметризованными плейсхолдерами `?`. Никаких f-strings или конкатенации строк в SQL-теле (AC tech-spec «Code Audit task explicitly grep-verifies this»).

7. `insert_pending` ловит `sqlite3.IntegrityError` (UNIQUE conflict на PK `link`) и возвращает `False`; успешная вставка — `True`. Сценарий race-а описан в tech-spec §Risks.

8. Соединения — по паттерну `news_bot.is_processed` (`news_bot.py:123-130`): `sqlite3.connect(news_bot.DB_FILE)` на вызов, `conn.close()` в finally (или контекст-менеджер). Исключение — функции, принимающие `conn` как параметр (`init_schema`).

9. Написать тесты в `tests/test_pending_articles_repo.py`, покрывающие каждый пункт из tech-spec §Testing Strategy / Unit / первый буллет:
   - insert сериализует JSON; дубликат — `False`; get десериализует;
   - сортировки `list_pending`, `list_pending_stale`, `list_notified_overdue`, `list_pending_for_eviction`, `list_failed`;
   - фильтры stale (`fetched_at` > 48h AND `notified_at IS NULL`), overdue (`notified_at` > grace AND `ru_paragraphs IS NULL`), eviction (`ru_paragraphs IS NULL` per Decision 7);
   - `move_to_published` атомарно: published INSERT + processed_news INSERT OR IGNORE + pending DELETE;
   - `skip_pending` пишет в `processed_news`, не пишет в `published_articles` (AC user-spec L74);
   - `retry_from_failed` ресетит `attempt_count=0` и выставляет свежий `fetched_at` (user-spec L44, AC L72);
   - `update_staged` возвращает `False` если строка уже покинула pending (AC user-spec L63);
   - транзакционный откат: `move_to_published` бросает на втором INSERT (monkeypatch cursor) → pending-строка на месте, `published_articles` и `processed_news` пустые для этой ссылки (tech-spec Integration);
   - `init_schema` идемпотентна — двойной вызов не меняет row counts и не бросает (AC tech-spec).
   - миграционный тест: `init_schema` на пустой tempfile DB + `PRAGMA table_info` для каждой из трёх таблиц сверяет имя / тип / NOT NULL / default / PK для каждой колонки с dict-literal expected (tech-spec AC «dict-literal comparison, no substring matches»).

10. Тесты используют `sqlite3.connect(':memory:')` или `tempfile.mkstemp(suffix='.db')` + `monkeypatch.setattr(news_bot, 'DB_FILE', path)` — паттерн из `tests/test_integration.py:20-26`.

**Files:**

- `tests/test_pending_articles_repo.py` (новый) — unit-тесты по TDD Anchor + миграционный `PRAGMA table_info`-тест.

**Current state (прочитано из кода):**
- `news_bot.py:113-121` — единственный существующий `init_db()`: connection-per-call, `CREATE TABLE IF NOT EXISTS`, `conn.commit()` + `conn.close()`. Никакого ORM, никакой абстракции. Наш репо должен следовать тому же стилю.
- `news_bot.py:123-130` — `is_processed` открывает / закрывает conn сам; повторим этот паттерн для read-функций.
- `news_bot.py:132-140` — `mark_processed` для write-функций — тот же паттерн.
- `tests/test_database.py:15-97` — проверяет точные SQL-литералы `processed_news`-таблицы; мы его НЕ модифицируем (существующая схема неизменна — tech-spec Data Models).
- `tests/test_integration.py:20-26` — pattern для tempfile DB в тестах.

**Dependencies:**
- Only stdlib: `sqlite3`, `json`. Для `list_pending_stale` / `list_notified_overdue` можно использовать SQLite-native `datetime('now', '-? hours')`-выражения через параметры — не таскать Python `datetime` вообще (матчит комментарий tech-spec «`CURRENT_TIMESTAMP` defaults are SQLite-side»).
- Никаких новых пакетов в `requirements.txt` (AC tech-spec).

**Edge cases:**
- `blocks` NULL vs пустой `[]` — разные значения. NULL = источник не даёт blocks (mattel / lamley / autoevolution-RSS); `'[]'` = есть, но пустой. `get_pending` должен различать: NULL → `None`, `'[]'` → `[]`.
- То же для `ru_paragraphs` / `ru_blocks`: NULL = не staged, `'[]'` = staged с пустым списком. Это влияет на `list_pending_stale` (фильтр по `IS NULL`) и `update_staged` (ставит non-NULL). В тестах явно проверить оба случая.
- `list_pending_stale(hours)` / `list_notified_overdue(grace_hours)` — параметризовать hours через `?` (НЕ через f-string в SQL-теле, AC!). Использовать `datetime('now', ? || ' hours')` или `datetime(fetched_at, ? || ' hours') < CURRENT_TIMESTAMP` — обе формы работают, главное — значение hours подано плейсхолдером.
- Rollback на `IntegrityError`: в `insert_pending` нет multi-statement, но всё же закрывать conn в finally.
- `move_to_published` получает `telegraph_url` / `telegraph_path` как аргументы от вызывающего, не читает из pending-строки сам. Причина: вызывающий уже вызвал `mark_telegraph_published` (Decision 9) и имеет значения на руках; передача их явно → меньше скрытых зависимостей.
- `retry_from_failed` должен быть безопасным при коллизии PK — если `link` уже каким-то чудом есть в pending: возвращает `False` и не трогает failed. Защитный стиль — матчит `insert_pending`.
- Типы через type hints: `conn: sqlite3.Connection`, `link: str`, `entry: dict`, `-> dict | None`, `-> bool`, `-> int`, `-> list[dict]`. Python 3.13 (CI) — `dict | None` работает нативно.
- `PRAGMA table_info` возвращает `(cid, name, type, notnull, dflt_value, pk)` — кортежи; в тесте распаковывать.
- `processed_news` — существующая таблица, её схема не меняется; `move_to_published` / `skip_pending` пишут в неё через `INSERT OR IGNORE` с тем же SQL-текстом, что в `news_bot.mark_processed` (литерал асертится в `tests/test_database.py` — не ломать).

**Implementation hints:**
- Держать весь `CREATE TABLE ...` DDL как тройку констант `_PENDING_DDL`, `_PUBLISHED_DDL`, `_FAILED_DDL` в верху модуля — легко грепать и апдейтить.
- Хелперы: `_dumps(value) -> str` (`json.dumps(value, ensure_ascii=False)`; None → None), `_loads_or_none(s) -> list|dict|None` (NULL-safe).
- Для transactional функций — один `try/except/finally` с `conn.commit()` / `conn.rollback()` / `conn.close()`. Явный паттерн надёжнее `with conn:` потому что `with conn:` commit-ит при выходе через исключение только для DDL — поведение контекста зависит от уровня изоляции.
- `_row_to_dict(row, description)` конвертер через `cursor.description` — переиспользуется во всех `get_*` / `list_*`.
- В `move_to_failed`: сначала `SELECT * FROM pending_articles WHERE link=?` чтобы скопировать EN-поля + `original_fetched_at` из `fetched_at`, затем `INSERT INTO failed_articles ...`, затем `DELETE FROM pending_articles WHERE link=?`.
- В `retry_from_failed`: симметрично — SELECT из failed, INSERT в pending (с ресетом `attempt_count=0`, `ru_*=NULL`, `fetched_at=CURRENT_TIMESTAMP`, `notified_at=NULL`, `telegraph_url=NULL`, `telegraph_path=NULL`, `last_error=NULL`), DELETE из failed.
- Кириллический round-trip тест: читать raw через `sqlite3` без декодирования — если в файле сохранилось `Привет` вместо `Привет`, значит забыли `ensure_ascii=False`.
