# Task 6: Refactor `job()` into prep-only + cron bump + delete `process_new_articles`

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Превращаем текущий end-to-end `news_bot.job()` (fetch → translate → publish всё в одном тике) в **prep-only** пайплайн согласно Decision 10 техспека. Prep-фаза больше НЕ публикует в канал напрямую — её работа заканчивается на `insert_pending` в новую очередь `pending_articles`. Реальная публикация уезжает в отдельный оператор-driven CLI `hw_review publish` (Task 8) + в idle-fallback/overflow-helpers (Tasks 9-10). В этой же задаче полностью удаляем `process_new_articles` (файл `news_bot.py:360-420`) — не переименовываем, не флажим, не оставляем deprecated-шим: его fetch-часть мигрирует внутрь `job()`, а publish-часть исчезает до следующих волн.

Параллельно бампаем cron с daily на hourly (Decision 5) — иначе 2-часовое grace-окно user-spec'а становится бессмысленным: при daily-тике следующая проверка через 24 часа. Три таймовые константы (`IDLE_TIMEOUT_HOURS=48`, `GRACE_WINDOW_HOURS=2`, `QUEUE_CAP=10`) становятся env-overridable модульными константами, чтобы dev/prod могли их крутить без правки кода.

Делегируем создание схемы для трёх новых таблиц (`pending_articles`, `published_articles`, `failed_articles`) модулю `pending_articles_repo.init_schema(conn)` (написан в Task 1), который вызывается изнутри `init_db()`. `processed_news` CREATE остаётся как есть (пин-тест в `test_database.py:19-39` продолжает проходить).

Flip восьми существующих auto-publish интеграционных тестов на staging-only семантику: вместо `mock_publish.call_count == 3` ассертим `pending_repo.count_pending() == 3` + `mock_send_teaser.assert_not_called()` — это заставляет тест-сьют честно отражать новую форму pipeline (Decision 10: "форсирует честное выражение новой формы в тестах").

В этой задаче НЕ реализуем idle-fallback (Task 9) и overflow-fast-track (Task 10) — функции-заглушки (вызовы) могут присутствовать как `pass`/стабы, но реальная логика двух шагов приезжает в Wave 6-7. Цель Task 6: прэп-фаза работает end-to-end, очередь наполняется, публикаций нет.

Wave 3 содержит одну задачу, потому что она сериализована: Task 5 (source registry) трогает тот же `news_bot.py`, так что их нельзя ставить параллельно без merge-конфликтов.

4. **Переписать `job()`** согласно §9.10 code-research. Новая структура:
   - `logger.info` + `init_db()` в начале (идемпотентно).
   - **Шаг (1a) idle heads-up** — стаб, возвращающий пустой список (или прямой вызов `pending_repo.list_pending_stale(IDLE_TIMEOUT_HOURS)` с пустой реализацией в Task 9); не отправлять никаких admin-ping в этой задаче.
   - **Шаг (1b) overdue auto-publish** — стаб; пустой цикл.
   - **Шаг (2) fetch всех источников через `SOURCES`** (registry из Task 5): `for fetcher in SOURCES: all_entries.extend(fetcher(notifier=send_admin_notification))` внутри try/except (sanitize через `sanitize_error_message` из Task 3, log + admin ping на hard-fail источника).
   - **Шаг (3) фильтрация против `processed_news` И `pending_articles`.** Решение: **оставить существующую `filter_new_entries` как есть** (она всё ещё нужна юнит-тестам и по контракту отсекает только `processed_news`), а в `job()` применить двухступенчатую фильтрацию: сначала `new_entries = filter_new_entries(all_entries)`, затем `new_entries = [e for e in new_entries if pending_repo.get_pending(e['link']) is None]`. `filter_new_entries_extended` как отдельная функция в этой задаче НЕ вводится — инлайн-фильтр в `job()` достаточен и не плодит API-поверхность.
   - **Шаг (4) overflow fast-track** — стаб, пропускающий все записи (`accepted = new_entries`); реальная логика приезжает в Task 10.
   - **Шаг (5) INSERT в pending**: для каждой принятой записи — `fetch_full_article(entry)` → построить row-dict (со всеми полями `link`, `source_name` из Task 5, `feed_url`, `title`, `subtitle`, `paragraphs`, `images`, `blocks`, `pub_date`) → `pending_repo.insert_pending(row)` (возвращает bool по UNIQUE-конфликту). **Никаких `transcreate_text`/`publish_article`/`send_telegraph_teaser` в prep-фазе.**

- Пустая очередь после prep-фазы → `build_admin_ping` возвращает `None` → `send_admin_notification` не вызывается (guard `if ping:`). Важно: тест `test_admin_ping_suppressed_on_empty_queue` проверяет именно это.
- Шаги (1a), (1b), (4) в этой задаче — стабы/no-op. Реальная реализация — Task 9 (idle), Task 10 (overflow). Структура `job()` должна уже иметь комментарии-placeholders с пометкой "populated in Task 9/10" чтобы следующие волны не переписывали каркас.
- `feedparser.FeedParserDict` vs plain dict: Task 5 уже нормализует entries в plain dict — в prep-фазе полагаемся на это и обращаемся к полям через `entry['link']` / `entry.get(...)` без сюрпризов.
- Cron job-stream: в `main()` сейчас есть строка `job()` выполняющая первый тик немедленно. Сохранить её — иначе dev-запуск бота не покажет работу без часового ожидания. Это в духе существующего кода.

**Implementation hints:**
- Порядок разработки: сначала TDD — пишем `test_migration.py` и `test_job_prep_phase.py`, убеждаемся что они красные → затем расширяем `init_db()` → затем переписываем `job()` → затем flip-им существующие интеграционные тесты → финальный прогон Verify-smoke.
- Flip существующих тестов делать парой passes: сначала read и понимание того, что именно ассертит каждая локация (строки 54/115/146/178/205 в `test_integration.py` — это может быть 5 разных контекстов), потом точечные замены. Не переписывать тесты целиком — менять только конкретные ассерты, чтобы сохранить структуру setup/fixtures.
- Admin-ping в `job()` идёт через `send_admin_notification` — оборачивать в try/except (как это уже делает `load_feeds`), чтобы падение Telegram не клало весь pipeline.
- Константы `IDLE_TIMEOUT_HOURS`/`GRACE_WINDOW_HOURS`/`QUEUE_CAP` должны быть ТОЧНО `int(os.getenv(..., default))` — не `os.getenv(..., default)` в raw-виде, иначе они будут строками и сломают арифметику `list_pending_stale(hours=...)`.
- Удаление `process_new_articles`: убедиться что после удаления не осталось import'ов / вызовов `process_new_articles` нигде в репо (grep перед коммитом).
- Бамп cron: `schedule.every().hour.do(job)` без аргумента `at("...")` — daily.at был заменён именно так.
- Предостережение: шаги (1a), (1b), (4) в `job()` — это не silent no-op, а явные комментарии-placeholders, чтобы auditor в Task 11 видел что Wave 6-7 допишут.
