# Task 12: Security Audit

Перед выполнением задачи загрузи:

## Description

Полный security-аудит всего кода фичи `manual-review-workflow` после завершения Waves 1–7 (задачи 1–10). Читаем все созданные/изменённые исходники и проверяем их против OWASP Top 10 с акцентом на поверхности, специфичные для этой фичи: новый DAO с SQL-трафиком по четырём таблицам, CLI, принимающий JSON на stdin, локальный HTML-preview, открываемый через `webbrowser.open`, санитизация секретов в `last_error`, и Cyrillic-encoding на границах SQLite + HTML.

Смысл задачи — зафиксировать финальный security-отчёт на момент готовности кода, до Pre-deploy QA (Task 14). Задача НЕ пишет и НЕ исправляет код — только аудирует и выдаёт отчёт со списком находок (severity, evidence, recommended fix) и вердиктом pass/fail по каждому инварианту из Acceptance Criteria tech-spec.

Запускается параллельно с Task 11 (Code Audit) и Task 13 (Test Audit) в Audit Wave — три независимых ревьюера смотрят один и тот же срез кода под разными углами.

## What to do

1. Прочитать все исходники, модифицированные задачами 1–10:
   - `pending_articles_repo.py` (Task 1)
   - `preview_renderer.py` (Task 2)
   - `news_bot.py` — секции `SOURCES`/`NETLOC_TO_SOURCE`, `build_admin_ping`, `sanitize_error_message`, `_fallback_publish`, refactored `job()` (Tasks 3, 5, 6, 9, 10)
   - `telegraph_publisher.py` — новая публичная `preview_nodes(...)` (Task 4)
   - `hw_review.py` — весь CLI с 8 субкомандами (Tasks 7, 8, 9, 10)
   - Также прочитать соответствующие тесты, когда нужно подтвердить, что инвариант проверяется автоматически.

2. Пройти OWASP Top 10 2021 по каждому файлу. Для этой фичи особо внимательно:
   - **A01 Broken Access Control** — проверить, что нет способа через CLI-аргумент получить доступ к строке вне `pending_articles` (например, `publish N` на номер из `published_articles`).
   - **A02 Cryptographic Failures** — проверить секреты в логах/admin-ping/`last_error`/stdout `hw_review show`.
   - **A03 Injection** — SQL injection в репо (обязательны `?` placeholders, ни одной f-string/`%`/`.format`/конкатенации в теле SQL), command injection в `webbrowser.open` (путь должен быть строго внутри `CACHE_DIR`, имя — `uuid4`), JSON-injection в `stage` (validator по Decision 6).
   - **A04 Insecure Design** — confirmation-prompt bypass: может ли `hw_review skip N` со staged ru быть обойдён через не-TTY stdin / pipe / пустой ввод / race condition; может ли eviction затронуть staged row.
   - **A05 Security Misconfiguration** — права на `~/.cache/hw-review/` (должно быть `0700`), CSP meta в preview HTML (должна быть `default-src 'none'; img-src https:; frame-src https:; style-src 'unsafe-inline'`), URL-scheme allowlist в preview (`https?://` only для `img src`/`iframe src`/`a href`).
   - **A08 Software & Data Integrity Failures** — JSON parsing в `stage` (обработка `json.JSONDecodeError`, лимит глубины и размера), парсинг `paragraphs`/`blocks` из БД (что если БД повреждена руками).
   - **A09 Security Logging & Monitoring Failures** — все ли write-paths в `last_error` проходят через `sanitize_error_message`; не логируются ли секреты в INFO/ERROR.

3. Проверить каждый инвариант из tech-spec Acceptance Criteria поштучно, с цитатой кода как evidence:
   - (a) Все SQL в `pending_articles_repo.py` используют `?` placeholders — запустить `grep` на `execute`/`executemany` в репо, убедиться, что во втором аргументе всегда кортеж/список, ни одной интерполяции в SQL body.
   - (b) `last_error` всегда пишется через `sanitize_error_message` — найти все write-пути (`increment_attempt`, `move_to_failed`, плюс любые INSERT в `failed_articles`), убедиться, что ни один не принимает сырой `str(exc)`.
   - (c) `preview_renderer` URL-scheme allowlist (`img src`/`iframe src`/`a href` — только `https?://`) + CSP meta — прочитать реализацию + тесты, подтвердить оба инварианта.
   - (d) `webbrowser.open` в `hw_review.py` получает путь строго внутри `CACHE_DIR` — найти call-site, проверить `path.parent == CACHE_DIR.resolve()` assert; проверить, что CLI падает без запуска браузера при нарушении.
   - (e) `stage` validator отклоняет: stdin >256 KiB, depth >3, unknown top-level keys, non-list `ru_paragraphs`, non-dict block entries, unknown block `type`, unknown block keys, string fields >10 KiB — прочитать validator, убедиться, что все восемь векторов покрыты.

4. Дополнительно проверить фичеспецифичные поверхности, упомянутые в описании tech-spec Task 12:
   - **Secret exposure в CLI** — `hw_review show N` печатает `last_error` и поля `pending_articles`; убедиться, что `telegraph_url` никогда не содержит токена и что sanitised `last_error` печатается "как есть" (без повторной десанитизации).
   - **Cyrillic encoding hazards** — `sqlite3` с `text_factory` по умолчанию, `json.dumps(..., ensure_ascii=False)`, `html.escape` в `preview_renderer` — убедиться, что Cyrillic НЕ превращается в `\uXXXX` в `last_error`/admin-ping, и что в HTML ни одна кириллица не попадает в атрибут без `escape(..., quote=True)`.
   - **Symlink/TOCTOU в preview cache** — `tempfile.NamedTemporaryFile(delete=False, dir=..., suffix='.html')` + `0700` dir mode; убедиться, что cache dir создаётся с правами `0700`, а не `0755`; проверить, что startup cleanup hook не следует за симлинками.
   - **Telegraph token в network errors** — `requests`/`telegraph_publisher._api_call` может embed токен в `str(exc)`; подтвердить, что весь трафик `_fallback_publish` и `hw_review publish` перехватывается и `sanitize_error_message` вызывается ДО записи в БД и ДО `send_admin_notification`.
   - **Empty-env-var pathology** — `sanitize_error_message` должен пропускать пустые/None/whitespace-only env vars (иначе `str.replace('', '[REDACTED]')` взрывает каждый символ).
   - **Overflow fast-track race** — может ли eviction выселить строку прямо в момент `hw_review stage N`? Проверить, что фильтр `ru_paragraphs IS NULL` делается в БД-запросе, а не в Python (чтобы не было race window между SELECT и DELETE).

5. Написать финальный отчёт в `work/manual-review-workflow/logs/working/audit/security-audit.md` со структурой:
   - **Summary** — 2–3 предложения: сколько файлов проверено, общий вердикт (pass / pass-with-findings / fail), сколько critical/high/medium/low находок.
   - **Invariants check** — таблица или список, по одной строке на каждый из пяти инвариантов выше: `PASS` / `FAIL` + краткая evidence-цитата (path:line).
   - **OWASP findings** — по каждой находке: `severity` (critical/high/medium/low/info), `category` (OWASP id), `location` (файл:строка), `issue` (что нашли), `evidence` (релевантный фрагмент кода), `recommended fix` (что сделать).
   - **Out-of-scope / accepted risks** — пункты, которые технически security concerns, но сознательно отложены (ссылка на Decision/Risk из tech-spec).
   - **Verdict** — финальный ответ: можно ли переходить к Pre-deploy QA, или нужен fix-wave.

## Verification Steps

### Automated

Прогнать прицельные grep/проверки по инвариантам:
- `grep -nE "execute\(\s*f|execute\(\s*[\"'][^\"']*%|\.format\s*\(" pending_articles_repo.py` → пусто (нет интерполированного SQL).
- `grep -nE "last_error\s*=" pending_articles_repo.py news_bot.py hw_review.py` → каждый hit ссылается на результат `sanitize_error_message(...)`.
- `grep -nE "webbrowser\.open" hw_review.py` → ровно один вызов, и перед ним есть `assert`/`if` на `path.parent == CACHE_DIR.resolve()`.
- `grep -nE "default-src 'none'" preview_renderer.py` → найдено.
- `grep -nE "ensure_ascii=False" pending_articles_repo.py` → JSON dump для paragraphs/blocks.

Прогнать релевантные тесты (должны быть зелёными как evidence, что инварианты закреплены):
- `pytest tests/test_pending_articles_repo.py tests/test_preview_renderer.py tests/test_hw_review_cli.py -q` → all pass.

**Severity rubric:**
- **critical** — прямая эксплуатация: выполнение произвольного кода, утечка секрета, SQL injection.
- **high** — эксплуатация требует специфических условий, но последствия тяжёлые: XSS в preview, bypass confirmation prompt, TOCTOU на preview file.
- **medium** — defense-in-depth miss: отсутствие вторичной проверки, логирование без sanitise в нестандартном пути.
- **low** — hygiene: отсутствующий комментарий об инварианте, неочевидное имя переменной около security-кода.
- **info** — not a finding, но worth noting: архитектурное наблюдение для follow-up.

**OWASP Top 10 2021 categories to walk through:**
- A01 Broken Access Control
- A02 Cryptographic Failures
- A03 Injection
- A04 Insecure Design
- A05 Security Misconfiguration
- A06 Vulnerable and Outdated Components
- A07 Identification and Authentication Failures
- A08 Software and Data Integrity Failures
- A09 Security Logging and Monitoring Failures
- A10 Server-Side Request Forgery

**Edge cases специально проверить:**
- `sanitize_error_message` с пустой/unset env var (не должно быть `str.replace('', '[REDACTED]')`).
- `stage` validator на граничном размере 256 KiB (`sys.stdin.buffer.read(262145)` даёт ровно 262145 байт → reject).
- `webbrowser.open` с путём, содержащим `..` или symlink, указывающим вне `CACHE_DIR`.
- `hw_review skip N` с staged ru через piped stdin (non-interactive) — должен отказать, не публиковать.
- Eviction-query под гонкой с одновременным `stage N` — проверить, что eviction SELECT + DELETE атомарны или что фильтр `ru_paragraphs IS NULL` применяется в DELETE WHERE, а не в Python.
- Cyrillic в `last_error`: например `"Ошибка: токен abc123"` с `TELEGRAM_BOT_TOKEN=abc123` → должно стать `"Ошибка: токен [REDACTED]"`, а не `"Ошибка..."`.

**Dependencies:** задачи 1–10 должны быть помечены `status: done` до запуска этой задачи. Task 11 (Code Audit) и Task 13 (Test Audit) запускаются параллельно в той же волне.

**Implementation hints:**
- Начать с grep-инвариантов (быстро), затем читать код целевых модулей под каждый OWASP-пункт.
- Для цитирования evidence использовать формат `path/to/file.py:NNN` — чтобы reader смог сразу открыть.
- Отчёт — markdown с секциями `## Summary`, `## Invariants check`, `## OWASP findings`, `## Out-of-scope`, `## Verdict`.
- Если в процессе аудита всплывает находка, не закрытая ни одним из существующих инвариантов, — добавить её в OWASP findings и явно поднять вопрос: нужен ли новый инвариант в tech-spec.
