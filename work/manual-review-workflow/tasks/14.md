# Task 14: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Финальная приёмочная проверка фичи `manual-review-workflow` перед деплоем. Задача закрывает весь контур качества: прогоняет полный тест-сьют (`pytest tests/`), проходит по каждому acceptance criterion из `user-spec.md` и из секции Acceptance Criteria в `tech-spec.md`, прогоняет end-to-end смоук всего операторского флоу на tempfile-БД с замоканными Telegraph и Telegram, и сверяется с отчётами аудитов (Task 11 — код, Task 12 — безопасность, Task 13 — тесты), которые лежат в `decisions.md` и `logs/working/`.

Фича — это split pipeline: prep-фаза фетчит и ставит статьи в очередь `pending_articles`, а публикация идёт через новый CLI `hw_review.py`. Все новые модули (`pending_articles_repo.py`, `preview_renderer.py`, `hw_review.py`), рефакторинг `news_bot.job()`, fallback / overflow / retry пути, UNIQUE-constraint по ссылке, shared `attempt_count`, sanitization секретов в `last_error`, URL-scheme allowlist + CSP в превью, strict JSON-валидатор в `stage` — всё это должно быть покрыто тестами и соответствовать AC.

Задача **не** требует живого окружения (VPS, Telegram API, Telegraph API) — это покрывает Task 15 (post-deploy). Здесь проверяем всё, что можно проверить локально: тесты, смоук на tempfile DB, сверка AC против кода/тестов. Критерии, которые без живого окружения недостижимы (визуал канального поста, Instant View card, реальный Telegraph render), помечаются `not_verifiable` и уходят в `deferredToPostDeploy`.

Результат — QA report в JSON + короткая запись в `decisions.md`. Если report `passed` — фича готова к деплою. Если `failed` — QA runner возвращает список critical-блокеров, фича не идёт в деплой до их устранения.

Edge cases из user-spec (overflow со staged, fallback после idle >48h, retry из failed, partial publish с переиспользованием Telegraph-URL, skip с staged ru) — обязательно иметь тест, иначе major.

Последовательность: создать временную БД через `init_db()` → прогнать prep-фазу с замоканными фетчерами (все три источника отдают одну новую запись) → проверить, что `pending_articles` содержит 3 строки с пустыми `ru_*`, `processed_news` не пополнился (статьи ещё не опубликованы), вызвана одна админ-отправка с текстом `"3 ждут review: 🟠 autoevolution ×1, 🟣 mattel ×1, 🟢 lamley ×1"` (формат matches byte-for-byte) → `hw_review stage 1` через stdin с валидным JSON для ru-полей → `hw_review preview --no-open 1` печатает путь к HTML-файлу в `~/.cache/hw-review/` и файл реально создан → `hw_review publish 1` с замоканными `telegraph_publisher._api_call` и `send_telegraph_teaser` (оба возвращают success) → после `publish` строка ушла из `pending_articles`, появилась в `published_articles` с `via_review=1`, HTML-preview-файл удалён, `processed_news` содержит ссылку.
6. Сверить технические AC тех-спека: idempotent `init_db()`, параметризованные SQL (grep `pending_articles_repo.py` на отсутствие f-string/concat в SQL), sanitizer работает на всех четырёх env-секретах, `build_admin_ping([])` возвращает `None`, `preview_renderer` — CSP + URL-allowlist + tag-allowlist, stage-валидатор отвергает восемь векторов из Decision 6.
7. Прочитать аудитные отчёты Task 11 (code audit), Task 12 (security audit), Task 13 (test audit) из `logs/working/` и `decisions.md`. Unresolved critical-findings из любого аудита → critical в QA-отчёте. Это верхнеуровневый контрольный пункт: QA не перепроверяет всё, что уже проверили аудиторы, но блокирует, если их critical-блокеры не закрыты.
8. Собрать финальный JSON-отчёт по шаблону skill:pre-deploy-qa, записать в `work/manual-review-workflow/logs/working/qa/pre-deploy-qa.json`. Статус `passed`, если zero criticals. Любой critical → `failed` + список блокеров в `findings`. Параллельно сложить человекочитаемый markdown-отчёт в `work/manual-review-workflow/logs/working/qa/pre-deploy-qa.md`.

10. Не править код и не менять поведение фичи — QA только читает, прогоняет и репортит. Если что-то сломано — описать в findings; фиксы делает следующая волна правок.

## Verification Steps

### Automated

- `pytest tests/ -v` → все тесты зелёные, 0 failures. Failures = critical в QA-отчёте.
- `pytest --cov=. tests/` (если `pytest-cov` установлен) → coverage не ниже проектного порога для файлов из "Files to modify".
- `grep -nP "f['\"].*(SELECT|INSERT|UPDATE|DELETE)|\+.*(SELECT|INSERT|UPDATE|DELETE)" pending_articles_repo.py hw_review.py` → пусто (параметризованные запросы, tech-spec AC).
- `python -c "import pending_articles_repo, preview_renderer, hw_review, news_bot; print('ok')"` → импорт всех новых/модифицированных модулей без ошибок.

### Smoke

Full operator flow on a tempfile DB:

**Важно:** весь smoke-прогон идёт **в одном Python-процессе** (без `subprocess.run`) — mock-патчи только process-local, subprocess их не наследует и реально сходит в Telegraph/Telegram API. Вызовы CLI-команд выполняем через `hw_review.main()` напрямую, подменяя `sys.argv` и `sys.stdin`. DB-изоляция — через `unittest.mock.patch('news_bot.DB_FILE', db_path)` (паттерн из `tests/test_integration.py:23`); `pending_articles_repo` читает `news_bot.DB_FILE` динамически, так что один патч покрывает и репо, и сам `news_bot`. **НЕ** использовать env-переменную `NEWS_DB_PATH` — она не поддерживается.

```bash
python - <<'PY'
import io, json, tempfile, pathlib, sqlite3, sys
from unittest.mock import patch

db_path = tempfile.mkstemp(suffix='.db')[1]

# All DB-reads in news_bot + pending_articles_repo follow news_bot.DB_FILE
# (pattern established in tests/test_integration.py:23). Patch BEFORE import.
with patch('news_bot.DB_FILE', db_path):
    import news_bot, pending_articles_repo, hw_review
    news_bot.init_db()

    # 1. prep with mocked fetchers + mocked admin-ping
    rss_entries = [
        {'link': 'https://autoevolution.com/a1', 'source_name': 'autoevolution',
         'title': 'AE', 'subtitle': '', 'paragraphs': ['p1'], 'images': [], 'blocks': None},
        {'link': 'https://lamleygroup.com/l1',  'source_name': 'lamley',
         'title': 'L',  'subtitle': '', 'paragraphs': ['p1'], 'images': [], 'blocks': None},
    ]
    mattel_entries = [
        {'link': 'https://corporate.mattel.com/m1', 'source_name': 'mattel',
         'title': 'M',  'subtitle': '', 'paragraphs': ['p1'], 'images': [], 'blocks': None},
    ]
    with patch('news_bot._fetch_rss_entries', return_value=rss_entries), \
         patch('news_bot._fetch_mattel_entries', return_value=mattel_entries), \
         patch('news_bot.fetch_full_article', side_effect=lambda e: {
             'title': e['title'], 'subtitle': '', 'paragraphs': e['paragraphs'],
             'images': [], 'blocks': None,
         }), \
         patch('news_bot.send_admin_notification') as mock_ping:
        news_bot.job()

    assert pending_articles_repo.count_pending() == 3
    ping_text = mock_ping.call_args.args[0]
    assert ping_text == "3 ждут review: 🟠 autoevolution ×1, 🟣 mattel ×1, 🟢 lamley ×1", ping_text

    # 2. stage row 1 via hw_review.main() with argv + stdin patched
    payload = json.dumps({'ru_paragraphs': ['Привет'], 'ru_blocks': None})
    with patch.object(sys, 'argv', ['hw_review', 'stage', '1',
                                    '--ru-title', 'RU', '--ru-subtitle', 'sub']), \
         patch.object(sys, 'stdin', io.StringIO(payload)):
        assert hw_review.main() == 0

    # 3. preview --no-open prints HTML path + file exists
    buf = io.StringIO()
    with patch.object(sys, 'argv', ['hw_review', 'preview', '--no-open', '1']), \
         patch.object(sys, 'stdout', buf):
        assert hw_review.main() == 0
    html_path = buf.getvalue().strip().splitlines()[-1]
    assert pathlib.Path(html_path).is_file()

    # 4. publish with Telegraph API + Telegram teaser mocked (in-process — patches apply)
    with patch('telegraph_publisher._api_call',
               return_value={'url': 'https://telegra.ph/X', 'path': 'X'}), \
         patch('news_bot.send_telegraph_teaser', return_value=True), \
         patch.object(sys, 'argv', ['hw_review', 'publish', '1']):
        assert hw_review.main() == 0

    # 5. row moved to published_articles with via_review=1
    conn = sqlite3.connect(db_path)
    row = conn.execute("SELECT via_review FROM published_articles WHERE link = ?",
                       ('https://autoevolution.com/a1',)).fetchone()
    assert row is not None and row[0] == 1
assert pending_articles_repo.count_pending() == 2  # row 1 gone
assert not pathlib.Path(html_path).exists()  # preview cleaned up
print("SMOKE OK")
PY
```

Output `SMOKE OK` = pass; any `AssertionError` = critical finding.

**Edge cases для QA:**

- AC "`hw_review take N` after auto-publish → `N already auto-published`" — `not_verifiable` без симуляции времени, если нет интеграционного теста; если есть (`test_hw_review_take.py`) — pass с evidence.
- AC про формат канального поста (хэштег, `LinkPreviewOptions(show_above_text=True)`) — partially verifiable через unit test на `send_telegraph_teaser`; real-channel assertion уходит в `deferredToPostDeploy`.
- AC "Dedup-таблица содержит ссылку для любой статьи, которая была опубликована ИЛИ скипнута" — verifiable через integration test для `move_to_published` + `skip_pending`; оба должны писать в `processed_news`.
- AC про idle-fallback heads-up ping — один consolidated message для N stale-rows (Decision 12) — verifiable через integration test, который ассертит единственный `send_admin_notification` call с тремя titles в одной строке.
- `preview_renderer` три security invariants (tag allowlist / URL-scheme allowlist / CSP) — у каждого должен быть отдельный unit test; отсутствие любого → major.
- Stage validator восемь rejection vectors (Decision 6) — каждый отдельный тест; отсутствие любого → major.
- `init_db()` idempotency — integration test вызывает дважды; row counts unchanged.
- `hw_review preview` path guard (cache dir escape) — unit test ассертит отказ + exit 1 + no `webbrowser.open`.
- Shared `attempt_count` (Decision 13) — integration test: одна ошибка в idle-fallback + одна в overflow → `attempt_count=2`, третья → `move_to_failed`.

**Implementation hints:**

- Работай «снаружи внутрь»: сначала запусти `pytest tests/` и собери baseline. Дальше по AC — ищи в test-файлах evidence; если не нашёл теста под AC — finding.
- Для end-to-end смоука используй `tempfile.mkstemp()` для БД и `unittest.mock.patch` для сетевых слоёв. Не трогай реальный `news.db`, не обращайся к живым API.
- Формат `decisions.md`-записи — короткий, по шаблону из skill:pre-deploy-qa. Таблицы findings и dumps в decisions.md **не** попадают; они только в JSON.
- Если из `pytest --cov` приходит coverage ниже порога для одного из файлов фичи — это critical, не major. Feature shipping без тестов — блокер.
- Если текст в админ-пинге отличается хоть на байт от AC-формата — это critical (user-spec требует byte-for-byte match).
- QA не переписывает тесты и не чинит код. Только репорт. Фиксы — следующая волна.
- Секция `deferredToPostDeploy` в JSON — это handoff-контракт с Task 15: каждая запись там должна быть actionable (четкие шаги, каким инструментом, что проверить).
