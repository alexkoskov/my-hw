# Task 5: Source registry + source_name tagging

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Reorganise source fetching in `news_bot.py` into an extensible `SOURCES` registry so the prep phase (Task 6) can iterate a single list instead of hardcoding each source inline. Each entry gets a mandatory `source_name` tag — `'autoevolution'`, `'lamley'`, `'mattel'`, or fallback `'other'` — derived per tech-spec Decision 4 via an explicit `NETLOC_TO_SOURCE` map (bare netloc inference would yield `'lamleygroup'`, not `'lamley'`).

The `source_name` field drives admin-ping counting (keyed by `SOURCE_LABEL` / `SOURCE_EMOJI` from Task 3) and is stored on `pending_articles.source_name` (Task 1 schema). The channel-post hashtag stays on `_source_hashtag(source_url)` per Decision 14 — `source_name` is internal vocabulary only and must not be plumbed into `send_telegraph_teaser`.

This task is isolated into its own wave (Wave 2) to serialize edits against `news_bot.py` with Task 6; both waves must not run in parallel on the same file.

## What to do

1. Add `NETLOC_TO_SOURCE` dict constant in `news_bot.py` mapping the five netlocs from Decision 4 (`www.autoevolution.com`, `autoevolution.com`, `lamleygroup.com`, `www.lamleygroup.com`, `corporate.mattel.com`) to the three `source_name` values (`autoevolution`, `lamley`, `mattel`).
2. Add `_resolve_source_name(link: str) -> str` helper: reads `urlparse(link).netloc.lower()`, returns `NETLOC_TO_SOURCE.get(netloc, 'other')`.
3. Add `_fetch_rss_entries(notifier) -> list[dict]` — iterates `load_feeds()` (fallback to `[RSS_URL]` if empty), calls `fetch_rss(url)` per feed with per-URL try/except error isolation, normalises each `feedparser.FeedParserDict` entry into a plain `dict` (explicit field selection: `link`, `title`, `published`, `summary`), stamps `feed_url` and `source_name` via `_resolve_source_name`, emits a WARNING log when `source_name == 'other'`.
4. Add `_fetch_mattel_entries(notifier) -> list[dict]` — calls `fetch_mattel_news(notifier=notifier) or []`, stamps `source_name='mattel'` on each entry (Mattel already sets `feed_url=NEWS_URL`).
5. Add module-level `SOURCES = [_fetch_rss_entries, _fetch_mattel_entries]` list.
6. Create `tests/test_sources_registry.py` with test cases covering source resolution, dict normalisation, unknown-netloc warning, per-feed error isolation, Mattel tagging, and registry shape (per TDD Anchor below).
7. Do NOT rewrite `job()` or delete `process_new_articles` — those belong to Task 6. This task only adds the registry; `job()` continues to use the old inline fetch loop until Wave 3.

## Details

**Files:**
- `news_bot.py` — currently `job()` (L423-449) iterates `load_feeds()` inline and directly calls `fetch_mattel_news(...)` (L443-445). This task adds the registry without touching `job()`. Suggested placement:
  - `NETLOC_TO_SOURCE` + `_resolve_source_name` near `_source_hashtag` (L291-300) — both are URL→label utilities.
  - `_fetch_rss_entries`, `_fetch_mattel_entries`, `SOURCES` just above `job()` (around L420) — keeps the registry visually adjacent to its (future) consumer.
  - Do NOT modify `job()`, `process_new_articles`, `fetch_full_article`, `_source_hashtag`, `send_telegraph_teaser`.
- `tests/test_sources_registry.py` — new file. Use `pytest` + `monkeypatch` + `caplog` fixtures. Patch module-level `news_bot.load_feeds`, `news_bot.fetch_rss`, `news_bot.fetch_mattel_news` to avoid network calls.

**Dependencies:**
- Depends on Task 3 (admin-ping helper + source vocabulary). Task 3 introduces `SOURCE_EMOJI` / `SOURCE_LABEL` keyed by the same three labels this task produces — but Task 5 does not import or call them; the coupling is vocabulary only. Wave 2 runs strictly after Wave 1 completes, so Task 3 will already be merged.
- No new packages. Uses stdlib `urllib.parse.urlparse` (already imported at `news_bot.py:20`) and existing `load_feeds`, `fetch_rss`, `fetch_mattel_news`, `RSS_URL`, `logger`.

**Edge cases:**
- `load_feeds()` returns `[]` (all feeds invalid) → `_fetch_rss_entries` falls back to `[RSS_URL]` per current `job()` behaviour (L427-429).
- `fetch_rss` raises per-feed → log and continue (matches `news_bot.py:434-438` pattern). Do NOT let one bad feed abort the whole list.
- `fetch_mattel_news` returns `None` (defensive — current contract returns `[]`, but future refactors may return `None`) → `_fetch_mattel_entries` returns `[]` via `... or []`.
- Entry with no `link` → `_resolve_source_name(item.get('link') or url)` falls back to the feed URL's netloc, so the source is still identified (feed netloc = entry netloc for RSS).
- Case sensitivity: `urlparse(...).netloc.lower()` normalises so `WWW.Autoevolution.COM` hits the map.
- `FeedParserDict` gotcha: `dict(entry)` includes `feedparser` internals (`summary_detail`, `title_detail`, `links`, etc.). Build the output dict explicitly from the string fields actually consumed downstream (`link`, `title`, `published`, `summary`) to avoid leaking non-serialisable values into `pending_articles` JSON columns in Task 6.
- Unknown netloc must NOT raise — just log a WARNING and tag `'other'`. The prep phase in Task 6 decides whether to drop `'other'` rows.

**Implementation hints:**
- Reference implementation in `code-research.md §9.5` (lines 469-516) — mirror the structure; it was updated on 2026-04-22 to use `_resolve_source_name` and the explicit `NETLOC_TO_SOURCE` dict (round 3 of skeptic review).
- Keep fetcher helpers named (not lambdas) so tracebacks stay readable — matches `news_bot.py:354` exception-logging pattern.
- `notifier` parameter is accepted by both fetchers for API uniformity even though `_fetch_rss_entries` currently just logs locally. Future sources may need to pipe errors to the admin notifier.
- Do NOT change `_source_hashtag` — per Decision 14 the channel hashtag keeps the TLD-stripped form (`#lamleygroup`, not `#lamley`). `source_name` and hashtag are intentionally different vocabularies.
- Do NOT add a `'rss'` key to `NETLOC_TO_SOURCE` or use `'rss'` as a source_name — earlier drafts used that, but it collapsed lamley + autoevolution into one bucket (see Decision 4 rationale + User-Spec Deviation note).
- Log format: use `logger.warning(f"...")` consistent with the rest of the module (no `%s`-style); the project logger is already configured at L106-110.
- For the `FeedParserDict` normalisation test, you can construct one with `feedparser.util.FeedParserDict({...})` or simply test with a real feed string via `feedparser.parse("<?xml ...?><rss>...</rss>")` — either way, the resulting item must be `type(item) is dict` with a known, bounded key set.
