# Task 13: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [skills/test-master/SKILL.md](~/.claude/skills/test-master/SKILL.md)

## Description

Финальный аудит качества тестов по всей фиче `manual-review-workflow`. Читаем все новые и изменённые тестовые файлы, созданные в Waves 1–7 (Tasks 1–10), и оцениваем их как единый тест-сьют: покрытие всех декларированных в tech-spec Testing Strategy сценариев, осмысленность ассертов, баланс пирамиды (unit-heavy + точечные integration), реальное использование DB/CLI/рендеринга в integration-тестах (а не сплошной мок), корректная симуляция времени в idle-fallback и overflow сценариях.

Задача — не писать код, а выдать развёрнутый отчёт ревьюера, по которому команда сможет либо закрыть ревью, либо точечно залатать пропущенные сценарии до Pre-deploy QA. Отчёт — единственный артефакт задачи.

Отдельно аудит подтверждает, что каждый пункт Testing Strategy checklist из tech-spec реализован хотя бы одним тестом — без этого Pre-deploy QA нельзя считать осмысленным.

## What to do

1. Собрать полный список тестовых файлов, которые нужно прочитать:
   - новые файлы из Tasks 1–10 (см. tech-spec → Implementation Tasks → `Files to modify`);
   - изменённые существующие `tests/test_integration.py`, `tests/test_mattel_integration.py`, `tests/test_feed_iteration.py`, `tests/test_database.py`.
2. Для каждого файла пройтись тест за тестом и зафиксировать:
   - что именно проверяет тест (в одну строку);
   - тип (unit / integration);
   - качество ассертов — есть ли бездумные `assert mock.called` без проверки аргументов/результата, есть ли ассерт на состояние БД/выходного артефакта, а не только на вызовы моков;
   - адекватность моков — что реально исполняется, что замокано (integration-тесты должны гонять реальную SQLite и реальный `argparse`/CLI-диспатч).
3. Сверить покрытие против Testing Strategy checklist из tech-spec (см. список ниже в `Acceptance Criteria`). Для каждого пункта указать файл + имя теста, либо пометить GAP.
4. Оценить баланс пирамиды: сколько unit vs integration по каждому модулю (`pending_articles_repo`, `preview_renderer`, `hw_review`, `news_bot`), нет ли перекоса в сторону integration там, где достаточно unit, и наоборот — нет ли чисто-моковых «псевдо-integration» тестов, которые на самом деле юниты.
5. Проверить симуляцию времени:
   - idle-fallback тесты должны двигать `fetched_at` SQL-апдейтом (`UPDATE pending_articles SET fetched_at = datetime('now', '-50 hours')`), а не патчить `datetime.utcnow` / `time.time` в Python. Причина: `CURRENT_TIMESTAMP` дефолты вычисляются SQLite-side;
   - overflow-тесты с `attempt_count` mixed-path корректно чередуют два пути (idle + overflow) на одной и той же `link`.
6. Проверить «honesty» integration-тестов:
   - `pending_articles_repo` integration прогоняется на реальном tempfile/`:memory:` SQLite (не мок курсора);
   - `hw_review` CLI integration вызывает `argparse`-main, читает реальный stdin / пишет реальный stderr / возвращает реальные exit-коды;
   - `preview_renderer` integration идёт через реальные ноды из `telegraph_publisher.preview_nodes`, а не через фиктивный словарь.
7. Проверить отсутствие bare assertions:
   - запретить `assert mock.X.called` без `assert_called_once_with(...)` или аналога с проверкой аргументов;
   - `assert result is not None` без следующего ассерта на структуру считается слабым, отметить в отчёте;
   - `pytest.raises(Exception)` без `match=` — тоже flag.
8. Написать итоговый отчёт в `work/manual-review-workflow/logs/working/audit/test-audit.md` со структурой:
   - **Summary** (1 абзац): overall verdict — green / yellow / red + главная причина.
   - **Coverage vs Testing Strategy checklist**: таблица «item → файл::тест → status (covered / partial / missing)».
   - **Pyramid balance**: per-module счётчик unit/integration + комментарий.
   - **Time simulation audit**: idle-fallback + overflow findings.
   - **Integration honesty**: список тестов, где мокается слишком много, с конкретным советом.
   - **Weak assertions**: список конкретных `file::test_name` с указанием, что усилить.
   - **GAPs to close before Pre-deploy QA**: нумерованный список с приоритетом P0/P1/P2.
   - **Recommendations**: 3–7 предложений по улучшению тест-сьюта (рефакторинги fixtures, общие хелперы, параметризация).
9. Отчёт пишется строго Markdown, без кодогенерации. Если по ходу аудита обнаружены критические GAP (отсутствие теста из checklist) — это P0, и фича не готова к Pre-deploy QA.

## Verification Steps

### Automated
- `pytest tests/ -q` прогоняется один раз перед стартом аудита, чтобы убедиться: тест-сьют зелёный и отчёт описывает реальное поведение, а не сломанное состояние.
- После написания отчёта выборочно spot-check'нуть, что упомянутые `file::test_name` действительно существуют в соответствующих файлах (для каждого упомянутого теста: `grep -n "def {test_name}" {file}`). Не сравнивай суммарный счёт из `grep -rn "^def test_" tests/ | wc -l` с числом в отчёте — существующие 11 тест-файлов (~100+ тестов) не входят в audit scope Task 13; audit покрывает только новые + модифицированные тест-файлы из Tasks 1–10.

## Details

**Файлы на чтение:** все тестовые файлы из секции Context Files (новые + модифицированные). Дополнительно — исходные модули, чтобы сверять ассерты с реальной сигнатурой: `pending_articles_repo.py`, `preview_renderer.py`, `hw_review.py`, `news_bot.py`, `telegraph_publisher.py`.

**Файл на запись:** `work/manual-review-workflow/logs/working/audit/test-audit.md` (новый; директорию `logs/working/audit/` создать через `mkdir -p` при необходимости).

**Dependencies:** Tasks 1–10 должны быть в статусе `done`. Task 13 идёт параллельно с Task 11 (Code Audit) и Task 12 (Security Audit) — три аудитора читают один и тот же код без конфликтов; пишут каждый в свой отчёт. Зависимости от Task 11/12 нет.

**Edge cases и типичные проблемы, которые стоит искать:**
- Integration-тест, который на самом деле мокает `sqlite3.connect` — тогда это юнит в плаще интеграционного теста.
- `stage` validator-тесты, которые проверяют только один reject-вектор из восьми — checklist требует все восемь как отдельные кейсы.
- Telegraph-retry тест, который симулирует Telegram-fail через `Mock.side_effect=Exception` в одной форме, но пропускает вторую (`returns False`). Должно быть обе ветки.
- `PRAGMA table_info` тест, который проверяет только имена колонок — spec требует сравнение полного кортежа (name, type, notnull, default, pk) как dict-literal.
- Time-simulation через `freezegun` / `monkeypatch.setattr('datetime.datetime', …)` для idle-fallback — это GAP: SQLite-side `CURRENT_TIMESTAMP` не подчиняется Python mock'у, тест должен двигать `fetched_at` SQL-апдейтом.
- Admin-ping тест, который ассертит `send_admin_notification.call_count == 1`, но не проверяет, что именно один вызов содержит все стейл-титулы — должно быть и то и другое.
- Overflow-тест, который создаёт один staged и один unstaged row — недостаточно, должен быть именно mix из `QUEUE_CAP` штук с обоими состояниями.
- Публикация на vanished row — тест должен отдельно покрыть все три стейта (published / failed / not-found), а не только один.

**Implementation hints:**
- Не ходим по тестам последовательно — сначала строим матрицу «Testing Strategy item → файл → тест», потом заполняем ячейки при чтении. Так сразу видно пропуски.
- Для слабых ассертов удобно держать простую таблицу `file::test_name | что сейчас ассертится | что должно` — попадёт в отчёт как есть.
- GAP-список ранжируем: P0 = пункт из tech-spec Acceptance Criteria / Testing Strategy checklist без теста; P1 = тест есть, но неполный (например, проверяет 1 из 8 reject-векторов); P2 = качество ассертов или стиль.
- Не пересказываем содержимое тестов в отчёте целиком — достаточно `file::test_name → вердикт + короткий комментарий`.
- Не пишем ни одного блока с кодом в отчёте (кроме точечных inline-бэктиков для имён функций/файлов). Цель — анализ, а не code dump.
