- `userspec-adequacy-validator` — **changes_required**. 1 critical, 7 major,

## The critical one: the digest quietly disables itself

Round 1 called «silence stops being a free answer» a quality degradation. Round 2
promoted it to critical, and the reason is the interaction with the fix we made
in between:

- Held rows leave `pending_articles` only by operator press — `skip_pending`
  (repo:1281) or publication, which a held row never reaches. Eviction excludes
  them explicitly (repo:975-995).
- The new overflow cap says «показываются **самые старые**» (user-spec.md:134).

Together: articles declined by silence never leave and always sort first. Five of
them permanently occupy the top five rows and push genuinely fresh held articles
into «и ещё M». The feature stops showing exactly what it exists to show, with no
error in any log.

**Resolution, operator's choice:** reminders expire after **7 days**, counted
**from first appearance in the digest** — not from hold time. The from-first-show
detail is the load-bearing one: counted from hold time, the articles stranded
*before* the feature ships would never appear at all, and those are the ones the
11 August incident was about. The article stays held; silence remains a valid
decline; the daily plan's «На утверждении: N» still counts it.

## Ship order reversed

The spec proposed shipping the per-source silence alarm first, «потому что она
проще и не трогает путь с кнопками». The validator disagreed with both halves and
was right:

**A — the `[E017]` restart marker.** A few lines around news_bot.py:4962-4980.
Ships first because the spec's own justification for the alarm — «полный обвал
теперь и так даёт сигнал на второй день» — is *unverified on prod today*,
precisely because the marker does not exist yet and `[E017]` fires once per
restart. Shipping A turns that assumption into a fact, and establishes the
once-per-day marker idiom the other two increments reuse.

**B — the held-article digest** (items 2 and 4). The measured pain: 11 August, an
article reachable only by hand-editing the DB.

**C — the per-source silence alarm.** Last. It is the *largest* piece, not the
smallest: eight counter sites in the b3 loop, cross-tick state with restart
safety, a new alert, and integration tests reproducing a two-day outage. And it
is the only piece whose value is still assumed — the partial outage is recorded
once, 12 August. Shipping A first buys two or three weeks of observation that
will either sharpen C or retire it.

Increment A goes through `/write-code`, not the full planning flow — S-sized, a
few lines, no open design questions.

## Other findings folded into the spec

- A **held article no longer counts as delivered** for the alarm. The nearest
  counter says otherwise today: `funnel['staged'] = inserted` (news_bot.py:4628)
  counts a held row (news_bot.py:4570-4580), so a content-gate regression holding
  everything from one source would read as perfect health — the exact failure
  class the alarm is for.
- **A dead feed is invisible.** `_fetch_rss_entries` swallows a feed failure into
  the log (news_bot.py:3776-3780) without incrementing `sources_failed`, so a
  source whose feed stops parsing offers no «fresh entries» and the alarm's own
  criterion excludes it. Now a separate case with its own wording.
- **«Two days running» must be calendar days.** `job()` re-runs on every startup
  (news_bot.py:5113); four restarts on 13 August would have produced a false
  alarm within an hour. The idiom already exists in `record_fetch_failure`
  (repo:608-620).
- **The digest button and the `[E036]` button are byte-identical** if the token is
  reused (`hd:a:<token>`, grammar at news_bot.py:925-934), and the bot never
  stores a sent message's id (`send_admin_notification` returns bool). They must
  differ by token kind on the same token.
- **Repeat press hangs the spinner.** The edit runs before the callback is
  answered (news_bot.py:1108-1113); an unchanged redraw raises
  `Message is not modified`, so `answer_callback_query` never runs — while the
  «no double action» criterion stays formally green. Answer first, redraw second.
- Kind checking must be strict: a `dedup` and a `hold` token legitimately coexist
  on one link, and a cross-kind press leaves the button dead **forever**, because
  `resolve_hold_callback` does not consume it (news_bot.py:758-764).

# Increment A — [E017] once per calendar day

Shipped through `/write-code` rather than the full planning flow: S-sized, a
few lines, no open design question.

## What it does

`_maybe_ping_dry_spell()` (extracted from `job()`) gates the channel-silence
alarm behind a `bot_state` marker, so one outage produces one ping per calendar
day instead of one per container restart. Details and the four properties worth
knowing are now in `patterns.md`; this log records only what the reviews taught.

## What the reviews caught that I had wrong

Three rounds of code-reviewer / security-auditor / test-reviewer, 25 findings,
23 applied.

**The gate did not fail open on a DB error.** My own docstring claimed "fails
OPEN" and it was true for a missing and a corrupt marker but false for an
unreadable one: `is_dry_spell_ping_rate_limited()` opens its own connection, and
that raise landed in the block's outer handler, dropping the alarm for a tick on
which the outage had already been detected. Confirmed by fault injection, not by
reading. Now decided outside the send's handler, defaulting to not-limited.

**One malformed row could have disabled [E017] indefinitely.** `_parse_dt_
tolerant` caught only `ValueError`, but `bot_state.value` is TEXT and SQLite
TEXT affinity leaves a BLOB a BLOB, so a binary row comes back as `bytes` and
`fromisoformat` answers with `TypeError`. That escaped into the caller's broad
handler and read as a transient check failure. The fix is structural — a blanket
`except` around the gate body — because betting on exception types is how this
class of bug survives review.

**A crafted marker could have written half a megabyte to the log every tick.**
"Parses as ISO-8601" does not bound length: `fromisoformat` accepts unlimited
fractional digits. This was in a line I had *added while fixing something else*,
and I had reasoned it safe by analogy with a finding I had just consciously
deferred. The analogy held on confidentiality and failed on length.

## What I got wrong about my own tests

Twice, and both times the same shape — a test that asserts the right thing
through the wrong door.

1. `test_a_delivered_ping_is_recorded_where_a_restart_will_find_it` asked the
   gate what the gate had recorded. An in-process marker — precisely the bug
   being ruled out — satisfies that. Rewritten to query `bot_state` directly.
2. `test_a_failure_to_record_the_send_...` justified itself by "otherwise the
   heartbeat is skipped". True when written; false ten minutes later, because
   extracting the block into a helper made the outer handler guarantee tick
   completion anyway. Rewritten to pin what the guard actually buys: the
   operator is told the bookkeeping failed, not that the check broke.

Both were caught by running the mutant, not by reading the test. The lesson is
narrow and worth keeping: a test that passes against the mutation it names is
not a weak test, it is not a test.

## The false critical, and the process fix it forces

Round 2 reported three tests failing ~1 in 20 runs with `mark_dry_spell_pinged()`
returning normally and leaving no row — a signature that, if real, meant prod
gets the four-ping storm back while the log claims the marker was written.

It was not real. Two reviewers and I were installing mutants into
`pending_articles_repo.py` and `news_bot.py` **in the shared working tree**
while those runs executed. The reviewer reproduced both failures byte-for-byte
from named mutants in an isolated copy, and corrected my reconstruction along
the way: the restore is a `shutil.move`, so the restored file inherits the
backup's mtime, which means the timestamps record when a mutant went ON and can
never show when it came off. My "the file was clean three seconds earlier"
reading was inverted.

**Rule going forward: a mutation harness runs on a `git worktree` or a tar-copy,
never on the tree another agent is testing against.** This cost a review round
and produced a false critical that would have blocked a correct change.

## Deliberately not fixed

- `job()` tests make live network calls — the reviewer's failure output carried
  a real OpenRouter balance read. Every full suite run spends money and depends
  on a third party. Fixing it means auditing the whole `job()` test surface for
  un-mocked egress; too broad to bolt onto this increment, but it should not sit
  unrecorded.
- `journalctl` advice survives in two other alert bodies. Carried to increment B.
