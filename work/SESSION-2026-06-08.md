## Two fixes shipped (both on `dev`, awaiting next prod promotion)

### 1. fix(prod-hang): `socket.setdefaulttimeout(20)` — commit `2ec59ff`

**Symptom.** `news_bot.service` (prod) was `active (running)` per
systemd, last journal line before the silence was today's `2026-06-08
10:00:12 — Database initialized.` Then **2.5+ hours of nothing**: no
RSS warning, no orangetrack fetch INFO, no admin ping. Process at
`State: S (sleeping)`, `wchan: wait_woken`, 107 MB RSS, fd=4 ESTAB to
`104.20.21.193:443` (Cloudflare) held since 06-06 service start, fd=7
CLOSE-WAIT to `149.154.166.110:443` (Telegram, opened today \~13:19 МСК)
with 25 bytes pending.

**Root cause.** `feedparser.parse(url)` (news_bot.py:615 in `fetch_rss`,
and news_bot.py:1686 in `_fetch_orangetrack_entries`) delegates to
`urllib.request.urlopen` with **no timeout**. feedparser 6.0.12
exposes no `timeout` kwarg (verified via `inspect.signature`); a slow
RSS server (Cloudflare-fronted autoevolution.com) holding the TCP
connection open without sending data will block job() until the kernel
TCP keepalive fires — by default \~2 hours later, well past the next
scheduled tick.

**Fix.** One line in news_bot.py top-of-module:

```python
import socket
socket.setdefaulttimeout(20)
```

Global default for any code path that creates a socket without
explicit timeout. Existing fast paths (autoevolution `curl_cffi
REQUEST_TIMEOUT=20`, orangetrack `requests.get` with own timeout,
Telegraph publisher) all pass explicit timeouts already — this is
defense-in-depth for the urllib hole and any future call that forgets.

**Test.** 1 new in [`tests/test_news_bot_dispatcher.py`](../tests/test_news_bot_dispatcher.py):
`test_socket_default_timeout_set_on_module_load` — `import news_bot`
→ `socket.getdefaulttimeout() == 20.0`. Suite 1086 passed, 0
regressions.

**Operator-side restoration.** Before this fix could land via deploy:
1. `ssh hwbot@148.135.207.54 'kill 729'` — kill the hung process.
   `systemctl Restart=` not set on `news_bot.service` → service goes
   to `inactive (dead)`, doesn't auto-recover.
2. Operator lacks sudo password → can't `sudo systemctl start
   news_bot.service`. Fallback:
   `ssh hwbot@148.135.207.54 'cd /home/hwbot/bot && nohup python3
   news_bot.py > /tmp/news_bot.out 2>&1 &'`.
3. New process PID 127650 started, immediate startup tick fired at
   `14:22:55 МСК`, fetched 50 entries in 9 sec, found 0 new, sent
   `[prod] [E009] 🟢 Бот сработал, новых статей нет.` — admin ping
   confirmed.

**Caveat — fragile state.** Prod is now running **outside** systemd
via nohup. Next VPS reboot leaves it down until manual restart.
Operator action item: when sudo is available, kill the nohup process
and `sudo systemctl start news_bot.service` to restore systemd
management.

### 2. fix(orangetrack): drop inline `[INSTANCE_LABEL]` from aggregator header — commit `3a8bb74`

**Symptom.** Test instance admin ping showed `[test] [test] [E030] 🟡
Orangetrack: 2 проблем за тик` (today, for two orangetrack fallback
HTTP timeouts on fast-furious-premium-Q and pop-culture-R case
reports).

**Root cause.** `OrangetrackPingAggregator.format_summary()` was
prepending `[{self.instance_label}] ` to the header (orangetrack_source.py:1162).
Separately, `send_admin_notification(message)` (news_bot.py:412)
unconditionally prepends `[{INSTANCE_LABEL}] ` to every admin-bound
message. The aggregator-built message went through `send_admin_notification`
via `aggregator.emit(send_admin_notification)` at news_bot.py:1756 →
double prefix.

**Fix.** Remove the prefix-add from the aggregator. The single source
of truth for instance-label prefixing is now `send_admin_notification`
(the convention every other E0XX builder follows). Aggregator's
`__init__(instance_label=None)` arg preserved for back-compat; value
silently dropped.

**Tests.** Collapsed three `test_instance_label_*` tests into one
parametrised `test_no_inline_instance_label_prefix_regardless_of_arg`
pinning the new contract across label values (`"test"`, `"prod"`,
`""`, `None`). Updated `test_three_events_grouping` and
`test_control_char_sanitization` to expect bare `[E030]` headers.
Suite 1084 passed, 0 regressions.

**Where it landed.** Will reach test instance on next `dev` push (auto
via `deploy_test.yml` workflow_run); will reach prod on next dev→main
promotion.

## Diagnostic notes

### How we found the root cause

1. **`systemctl status news_bot.service -n 200 --no-pager`** showed
   the journal cleanly through 06-07 (`[E009]` at 10:00:36 МСК — that
   ping ACTUALLY went, operator missed it in Telegram), then today's
   start at 10:00:12,684 → 10:00:12,692 (`Starting`, `Database
   initialized.`) → **silence**.
2. **`/proc/729/wchan` + `status`** confirmed `S (sleeping)` in
   `wait_woken` (blocking IO).
3. **`ss -tnp | grep pid=729`** showed leaked Cloudflare sockets from
   service start AND a today-opened Telegram socket in CLOSE-WAIT.
4. **Cross-reference with code (news_bot.py:1820-1875)**: between
   `Database initialized.` (line 1821) and the first RSS warning (a
   side effect of `_fetch_rss_entries`) the only paths are
   `crash-loop guard` (sleeps only if gap < 90 min — last publish
   was 06-06 18:23 МСК, gap >>> 90 min, no sleep) and `for fetcher in
   SOURCES`. So the bot was inside `_fetch_rss_entries` or the
   subsequent feedparser.parse() call.
5. **`grep -E "feedparser|timeout" news_bot.py autoevolution_source.py`**
   confirmed `feedparser.parse(url)` is bare — no timeout passed,
   `socket.setdefaulttimeout` never set, no `request_headers` either.

### Why yesterday (06-07) didn't hang

`[E009] Бот сработал, новых статей нет` ping went OK at 10:00:36 МСК.
The same autoevolution RSS that hung today was fast yesterday — this
is intermittent server-side behavior on Cloudflare's edge. Without the
timeout floor we just rolled the dice every morning.

### DeluxHost outage relevance — none

Yesterday's `decisions.md` (cross-source-dedup Task 10 entry)
mentioned a DeluxHost provider outage at 18:23 МСК 2026-06-07 with
simultaneous prod+test restarts. That was a **separate event**;

## Decisions across the session

- **Defense-in-depth via `socket.setdefaulttimeout`** vs targeted
  `requests.get(url, timeout=20).text → feedparser.parse(text)` wrapper.
  Picked the global approach — one line, no UA-matching ceremony, no
  per-call-site change in feed handler. All HTTP libraries we use
  (`requests`, `curl_cffi`, `httpx` via python-telegram-bot,
  anthropic SDK) already set explicit timeouts per call; the global
  default only bites in the urllib gap.
- **Aggregator prefix removed**, not deduplicated. Could have detected
  «already has `[label]`» in `send_admin_notification` and skipped the
  re-add — but that's pattern-matching on the message body, fragile
  to format drift. Single-source-of-truth (only `send_admin_notification`
  prefixes) is the cleaner rule.
- **`instance_label` arg kept for back-compat.** The aggregator's
  external API still accepts the parameter; it is just silently
  ignored. No need to touch the `news_bot._fetch_orangetrack_entries`
  call site, no need to bump any version.
- **No code change for orangetrack `ART_FALLBACK_TIMEOUT`.** Those
  two specific URLs (fast-furious-Q, pop-culture-R) showed
  `ART_FALLBACK_TIMEOUT` once today — single occurrence isn't a
  pattern. If it recurs over multiple days, raise `REQUEST_TIMEOUT`
  in `orangetrack_source.py` then. The `[E030]` ping itself is
  WARNING-tier; the article is just skipped, no publishing block.
